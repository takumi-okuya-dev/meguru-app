# PRD: ThreadsGrower App
*Working title — confirm.*

## 0. Document Purpose

本PRDは、ユーザー（プロダクトオーナー）とダウンストリームのUX/architecture/実装ワークフロー（本リポジトリの`bmad-ux`・`bmad-architecture`・`bmad-ticket`・spec-kit）が参照する仕様の叩き台である。入力は [Product Brief](../brief-threads-grower-app/brief-threads-grower-app.md) と、その由来元である Obsidian vault の `Wiki/仕事/システム開発/アイデア/Threads自動投稿アプリ.md`（2026-09-21〜10-01の継続調査・ユーザー決定の記録）。Glossary（§3）で定義した用語をFR・UJ・SM全体で一貫して使用する。`[ASSUMPTION]`タグは本PRD作成時点でユーザー未確認の推論箇所を示し、§9に索引する。

**重要な前提**：本プロジェクト（`threads-grower-app`）は、同じアイデアから派生した既存リポジトリ `threads-grower`（spec-kit導入済み・Next.js実装が進行中）とは別プロジェクトとして並走させる、という2026-10-01のユーザー確認に基づく。両者の使い分け・将来の統合方針は未確定であり、§8 Open Questionsに記載する。

## 1. Vision

ThreadsGrower Appは、Threadsアカウントを「戦略設計→投稿ストック→承認→自動投稿→パフォーマンス分析→改善」のループで育てるためのダッシュボード型Webアプリである。すでにGoogle Apps Script（GAS）による自己利用版の自動投稿で効果を確認済みであり、本プロダクトはその検証済みの価値を、同じ課題（人格・トーンを保ったまま継続的にThreadsを運用したいコミュニティ運営者・SNS運用代行）を持つ他者にも届けられる形に仕立て直す。Threads本体がネイティブの予約投稿機能をすでに持つ以上、単なる予約投稿ツールとしてではなく、「投稿ストックの型・重複検知・パフォーマンス分析・複数アカウント運用」という運用の質で勝負する。

## 2. Target User

### 2.1 Jobs To Be Done

- 自分の「たくみ」アカウント・AI部アカウントの投稿運用を、投稿ストックから実際の公開まで手離れよく回したい（自分自身がビルダー兼最初のユーザー）
- コミュニティ運営者・SNS運用代行として、複数のThreadsアカウントを一人で、または小さなチームで運用したい
- 投稿のたびに「前と同じような内容になっていないか」「この投稿はうまくいっているか」を確認する手間を減らしたい
- 投稿文の生成そのものは使い慣れた外部LLM（ChatGPT/Claude）に任せたまま、運用部分だけを自動化したい

### 2.2 Non-Users (v1)

- アプリ内でLLMによる投稿文生成そのものを求めるユーザー（本プロダクトは外部LLMへのコピペ運用を前提とする。§5 Non-Goals参照）
- Threads以外のSNS（X、Instagram等）の運用を主目的とするユーザー
- 大規模エンタープライズのソーシャルメディア運用チーム（監査・コンプライアンス要件が重いセグメントは対象外）

### 2.3 Key User Journeys

- **UJ-1. たくみが戦略プロファイルを初めて作り、投稿ストックを埋める。**
  - **Persona + context:** たくみ（プロダクトオーナー自身）、自分のThreadsアカウントの投稿運用を自動化したい。
  - **Entry state:** Googleアカウントでログイン済み、アカウントは未作成。
  - **Path:** 「アカウント追加」→自分のThreadsアカウントを登録→戦略設計画面で課題①②③（ターゲット・悩み・理想像）・宣伝内容・リサーチメモを入力→「プロンプト生成」ボタンでAI用プロンプトをコピー→外部LLM（ChatGPT）に貼り付けて複数件の投稿案を生成→結果を区切り文字付きで投稿ストック画面に貼り戻す。
  - **Climax:** 貼り戻した内容が自動的に複数件の下書きに分割され、投稿ストックに一括登録される瞬間。
  - **Resolution:** 投稿ストックに下書きが並び、承認待ちの状態になる。
  - **Edge case:** 区切り文字（`@@@`）が崩れている、または件数が想定と違う場合、エラーなく部分的に登録しつつ、どこで分割に失敗したかを表示する。`[ASSUMPTION]`

- **UJ-2. たくみが投稿ストックを承認し、自動投稿が走る。**
  - **Persona + context:** たくみ、投稿ストックに下書きが溜まっている状態。
  - **Entry state:** 認証済み、投稿ストック画面。
  - **Path:** 下書き一覧を確認→重複検知の類似度%を見て似た投稿を却下（却下理由を記録）→残りを個別承認、または一括承認→スケジュール投稿の時間枠に従って自動的にThreadsへ公開される。
  - **Climax:** 設定した時間枠で投稿がThreadsに実際に公開される。
  - **Resolution:** 投稿ログに公開済みとして記録され、後でパフォーマンス分析に反映される。
  - **Edge case:** Threads API呼び出しが失敗した場合、通知し、設定済みのリトライポリシーに従って再試行する。

- **UJ-3. たくみが伸びている投稿・伸びていない投稿を把握し、次の戦略に反映する。**
  - **Persona + context:** たくみ、投稿が1〜2週間分公開済み。
  - **Entry state:** 認証済み、パフォーマンス分析画面。
  - **Path:** 投稿ごとのエンゲージメント一覧を開く→アカウント自身の中央値と比較した好調/普通/低調のラベルを確認→低調だった投稿の却下理由・傾向をメモ→次回のプロンプト生成に反映させる。
  - **Climax:** 「このパターンは伸びていない」という判断が次の投稿ストック生成プロンプトに自動的に反映される瞬間。
  - **Resolution:** 戦略プロファイルまたは却下ログが更新され、次のサイクルの投稿品質が上がる。

- **UJ-4. 副業運用代行のユーザーが複数アカウントを一人で運用する。**
  - **Persona + context:** SNS運用代行を副業でやるユーザー。複数のThreadsアカウントを契約している（アカウントごとの料金。FR-12）。
  - **Entry state:** 認証済み、アカウント一覧画面。
  - **Path:** アカウント一覧から運用先アカウントを切り替え→アカウントごとに独立した戦略設計・投稿ストック・分析を管理。
  - **Climax:** 複数の顧客アカウントを1つのダッシュボードから切り替えて運用できる状態。
  - **Resolution:** アカウントごとの承認待ち件数がダッシュボードに表示され、優先順位をつけて処理できる。

## 3. Glossary

- **Account** — Threadsアカウント1件に対応する運用単位。1ユーザーに1〜複数のAccountが紐づく。
- **契約（Subscription）** — 支払うユーザー単位の契約。基本料金（Threadsアカウント1件目を含む）と、2件目以降のアカウントの数で料金が決まる（FR-12、2026-10-08決定）。旧案の`Account.plan`（4値：`auto-only` / `auto-grower` / `multi-account` / `team`）を置き換える。
- **Membership** — User×Accountの中間エンティティ。`role`を持つ。個人運用ではオーナーだけなので画面に出さない。チーム運用では、Accountのオーナー（持ち主）とは別に、チームの人ごとに管理者・メンバー・編集者のロールを持つ（2026-10-13にチームの見直しで改めた。008の「パートナー」は管理者にあたる。旧案は`owner`/`member`の2値）。
- **個人運用・チーム運用** — このアプリの2つの軸。個人運用は、アカウントのオーナーが自分のアカウントを運用し、自分で払う。チーム運用は、管理者が作るチームに、それぞれ自分のアカウントを持つ人が入り、見せてもらったアカウントを参考にしたり、担当のアカウントで投稿の案を作って手伝ったりする（2026-10-13にLINEグループに近い形に改めた）。払うのはいつもアカウントのオーナー（2026-10-08決定）。
- **投稿ストック（Post Stock）** — 承認待ち・承認済み・却下済みの投稿下書きの集合。外部LLM生成結果の貼り付けによって一括登録される。
- **戦略プロファイル（Strategy Profile）** — 課題①（ターゲット）・課題②（悩み）・課題③（理想像）・宣伝内容・リサーチメモで構成される、Account単位の設定。AIプロンプト生成の入力になる。
- **重複検知（Duplicate Detection）** — 投稿ストック内の各下書きについて、既存投稿との類似度%を算出する機能。
- **パフォーマンス分析（Performance Analysis）** — 投稿ごとのエンゲージメントを集計し、そのAccount自身の中央値と比較して「好調／普通／低調」を判定する機能。
- **改善フィードバック（Improvement Feedback）** — パフォーマンス分析で低調と判定された投稿と、ユーザーが付けた傾向メモからなるAccount単位の記録。却下ログとともに次回のAIプロンプト生成の入力になる。
- **5本柱（Five Pillars）** — 初心者向け／専門／あるある共感／コミュニティ人柄／募集・イベントの5カテゴリ。投稿内容の偏りを管理する既存運用の型（`threads-post-writer` skill由来）。
- **grower機能（Grower Features）** — 契約中か無料体験中に使える機能のまとまり。2026-10-02に、戦略プロファイル（課題・宣伝内容・リサーチ）を含めることが決まった。分析・改善フィードバック（FR-9・FR-10）も含む。2026-10-08に料金を「有料ならすべての機能」に変えたため、契約の有無で出し分ける機能という意味になった（名前は、002〜006のspecとコードとの対応のため残す）。
- **無料体験（Free Trial）** — すべてのユーザーが、登録から1か月間、すべての機能を無料で使える期間（2026-10-02決定、2026-10-08に「すべての機能」に読み替え）。

## 4. Features

### 4.1 アカウント管理・認証

**Description:** Googleアカウントでログインし、自分のThreadsアカウントをAccountとして登録・管理する。個人運用では、Membership/roleの概念は表に出さない。realizes UJ-1, UJ-4.

#### FR-1: Googleログイン

ユーザーはGoogleアカウントでログインできる。Realizes UJ-1.

**Consequences (testable):**
- 未ログイン状態でアプリの保護ルートにアクセスするとログイン画面にリダイレクトされる。
- ログイン成功後、最後に使っていたAccountの画面に遷移する。
- ユーザーがAccountを1件も保有していない場合（初回ログイン時など）は、ログイン成功後にアカウント追加画面へ遷移する。

#### FR-2: Threadsアカウントの登録

ユーザーは自分のThreadsアカウントをAccountとして登録できる。Realizes UJ-1.

**Consequences (testable):**
- Threadsアクセストークンが暗号化してサーバ側に保存される。
- 登録できるAccountの数に上限は設けず、2件目以降は1件ごとに料金が加算される（FR-12）。無料体験中は1件までとする（2026-10-09に3件から変更。`[ASSUMPTION]`）。

**Out of Scope:**
- チーム運用（チームの招待、ロールの管理）はFR-13で扱う。

### 4.2 戦略設計

**Description:** Account単位で戦略プロファイルを入力・保存する。realizes UJ-1.

#### FR-3: 戦略プロファイルの入力・保存

ユーザーは課題①②③（ターゲット・悩み・理想像）、宣伝内容、リサーチメモを入力・保存できる。Realizes UJ-1.

**Consequences (testable):**
- 保存後、次回アクセス時に入力内容が復元される。
- 未入力項目があってもプロンプト生成自体は可能（空欄は除外してプロンプトを組み立てる）。`[ASSUMPTION]`

### 4.3 投稿ストック運用

**Description:** 戦略プロファイルを反映したAIプロンプトを生成し、外部LLMの回答を貼り付けて投稿ストックへ一括登録する。承認・却下・重複検知を行う。realizes UJ-1, UJ-2.

#### FR-4: AIプロンプト生成

システムは戦略プロファイルの内容を反映したプロンプトを自動生成し、ユーザーがコピーできる形で表示する。Realizes UJ-1.

**Consequences (testable):**
- 改善フィードバック（FR-10）が1件以上ある場合、生成されるプロンプトにそれが「避けるべきパターン」として含まれる。

#### FR-5: 投稿案の一括登録

ユーザーは外部LLMの回答を貼り付けると、区切り文字（`@@@`）で自動分割された複数件の下書きが投稿ストックに一括登録される。Realizes UJ-1.

**Consequences (testable):**
- 区切り文字で分割された件数だけ、個別の下書きレコードが作成される。
- 分割に失敗した場合（区切り文字が見つからない等）、エラーにせず1件の下書きとして登録し、分割できなかった旨を表示する。`[ASSUMPTION]`

#### FR-6: 重複検知

システムは投稿ストック内の各下書きについて、既存投稿との類似度%を算出し表示する。Realizes UJ-2.

**Consequences (testable):**
- 類似度が閾値（`[ASSUMPTION]`：暫定80%）を超える下書きには警告表示が出る。

#### FR-7: 承認・却下フロー

ユーザーは下書きを個別承認・一括承認・却下できる。却下時は理由を記録できる。Realizes UJ-2.

**Consequences (testable):**
- 却下理由は却下ログとして保存され、次回のプロンプト生成時に「この傾向は繰り返さない」として参照可能な形で表示される。

#### FR-8: スケジュール投稿・自動投稿

承認済みの投稿は、設定した時間枠に従って自動的にThreadsへ公開される。Realizes UJ-2.

**Consequences (testable):**
- Threads API呼び出しが失敗した場合、設定済みリトライポリシーに従って再試行し、最終失敗時はユーザーに通知する。
- 1日の最大投稿数を超える投稿はキューに残り、翌日以降に繰り越される。

**Feature-specific NFRs:**
- Threads APIのレート制限（250投稿/24h、`[ASSUMPTION]`単位未確認）を超えないようレート制御する。

### 4.4 パフォーマンス分析

**Description:** 投稿ごとのエンゲージメントを集計し、好調/普通/低調を判定する。判定結果を改善フィードバックとして保存し、次回のプロンプト生成に反映する。realizes UJ-3.

#### FR-9: エンゲージメント集計・好調判定

システムは投稿ごとの閲覧・いいね・返信・リポスト・引用・シェアを集計し、そのAccount自身の中央値と比較して好調/普通/低調を判定する。Realizes UJ-3.

#### FR-10: 分析結果のプロンプト反映

システムはFR-9で低調と判定された投稿を、Account単位の改善フィードバックとして保存し、次回のAIプロンプト生成（FR-4）の入力に反映する。Realizes UJ-3.

**Consequences (testable):**
- FR-9で低調と判定された投稿は、判定時点で自動的に改善フィードバックへ追加される（投稿本文・判定日時を保持）。
- ユーザーは改善フィードバックの各項目に傾向メモを追記でき、メモはプロンプトに本文とともに含まれる。
- FR-4で生成されるプロンプトには、改善フィードバックのうち直近N件（`[ASSUMPTION]`：暫定5件）と却下ログ（FR-7）が含まれる。
- ユーザーが改善フィードバックから除外した項目は、以降に生成されるプロンプトに含まれない。

### 4.5 複数アカウント管理

**Description:** 1ユーザーが複数のThreadsアカウントを切り替えて運用する。realizes UJ-4.

#### FR-11: マルチアカウント・ダッシュボード

ユーザーは自分が保有する複数のAccountを一覧から選択して個別管理画面に入る。Realizes UJ-4.

### 4.6 課金・プラン管理

**Description:** 無料体験と、有料の契約（基本料金＋アカウントごとの料金）をStripeで管理する。

#### FR-12: 契約・支払い

ユーザーは、無料体験の後に有料の契約をし、運用するThreadsアカウントの数に応じて支払う。Realizes UJ-1, UJ-4.

**Consequences (testable):**
- すべてのユーザーは、登録から1か月間、すべての機能を無料で使える（無料体験）。
- 料金は、基本料金 月1,000円（Threadsアカウント1件目を含む）と、2件目以降のアカウント1件につき月500円（2026-10-08決定。`[ASSUMPTION]` 金額は実需ヒアリングの前の仮の値）。
- 有料の契約中か無料体験中なら、すべての機能を使える。機能ごとの出し分けはしない（旧案の「自動投稿のみ（広告あり）」のプランは廃止）。
- アカウントを追加・削除すると、次の支払いからアカウントの数が反映される。
- 無料体験の終了後に契約がない場合は、データを残して読むだけにし、自動投稿を止める（`[ASSUMPTION]`）。
- チーム運用で、チームの人は、手伝う先・見せてもらう先のアカウントの料金を払わない。自分のThreadsアカウントは、個人運用と同じ料金体系で払う（チームに入るには自分のアカウントが要る）。チームの人数に上限を置く（`[ASSUMPTION]`編集者10人・メンバー50人）。
- 無料体験中に登録できるAccountは1件まで（2026-10-09決定。`[ASSUMPTION]`）。2件目以降を足すには有料の契約が要る。
- オーナーが未払いのAccountでは、チームの人も読むだけになる（FR-13の役割の判定に足す。2026-10-09決定）。
- 料金の詳細と旧案は、addendum「料金」を参照。

**Out of Scope:**
- チーム運用の招待・役割の管理（FR-13）。

### 4.7 チーム運用

**Description:** 管理者がチームを作り、自分のThreadsアカウントを持つ人を招待リンクで招く。チームの人は、オーナーが見せることにしたアカウントの投稿と戦略を参考にでき、担当になったアカウントでは投稿の案を作って手伝える（2026-10-09にMVPへ移し、2026-10-12〜13にLINEグループに近い形に改めた。specs/011-team-revision）。

#### FR-13: チーム運用（チーム・招待・ロール・担当・見せる設定・操作の記録）

管理者はチームを作り、招待リンクで人を招き、ロール（メンバー・編集者）を切り替え、担当のAccountを割り当てる。チームの人は、見せてもらったAccountを読むだけで見て、担当のAccountで投稿の案を作る。Realizes UJ-4.

**Consequences (testable):**
- 管理者は複数のチームを作れる。チームの招待リンクはチームに1本で、期限はなく、作り直すと前のリンクは使えない。招く人がリンクをコピーして自分で相手に送り、受けた人はGoogleログインで参加する（アプリからメールは送らない）。
- チームに入るには、自分のThreadsアカウントを1つ以上チームに入れる（1人1アカウントは必須。管理者を含む）。1つのAccountは1つのチームにだけ入る。入った人は、まずメンバーになる。
- 管理者は、メンバー⇔編集者をいつでも切り替え、チームごとの表で担当（編集者と自分）を割り当て・解除できる。1チームの編集者は`[ASSUMPTION]`10人まで。
- オーナーは、チームに入れたAccountごとに「チームに見せる」を選ぶ（初めはオフ）。見せているAccountは、同じチームの人が投稿ストックと戦略だけを読める。担当の人は、見せていなくても担当のAccountを開ける。
- 承認・却下と、自動投稿・NGワード・投稿ルールの設定は、いつもAccountのオーナーだけができる（任せる仕組みは持たない）。
- メンバー・編集者はいつでも抜けられ、管理者は人を外せる。管理者は1チームに1人で、抜ける前にほかのチームの人へ引き継ぐ。抜けても、Accountとそのデータはオーナーのものとして残る。
- 誰が作成・編集・承認・却下・設定の変更・チームの操作をしたかを操作の記録に残し、オーナーと管理者が見られる。
- サイドバーの「チーム」の見出しの下に、入っているチームの名前を出し、押すとメンバー一覧を開ける。
- どのロールの操作でも、NGワードのチェック（Constitution原則I）と人の承認（原則II）は外せない。
- 個人運用（チームに入っていないAccount）では、チーム・招待・ロール・見せる設定の画面や操作を出さない（Constitution原則IV・V）。
- Threadsとの接続と契約・支払いは、Accountのオーナーだけができる。

**Out of Scope:**
- アカウントをまたいだ匿名のベンチマーク、アカウント単位の簡易PIN（§6.2）。
- 顧客への月次レポート。

## 5. Non-Goals (Explicit)

- アプリ内部からのLLM API直接呼び出しによる投稿文生成の内製化は行わない。投稿文生成は外部LLMへのコピペ運用に委ねる。
- Threads以外のSNS（X、Instagram等）への投稿機能。
- 画像生成機能。
- 大規模エンタープライズ向けの監査・コンプライアンス機能。

- AIプロンプト生成・投稿案の一括登録（FR-4, FR-5）

- 承認・却下フロー（FR-7）

- 無料体験と契約・課金（基本料金＋アカウントごとの料金。FR-12）
- チーム運用（チーム、招待リンク、ロール、担当の割り当て、見せる設定、管理者の引き継ぎ、操作の記録。FR-13）。2026-10-09にOut of Scopeから移した。実装の順番はFR-13（feature 008）→FR-12（feature 013、最後）。2026-10-10に009（このアカウントのチーム）と010（自分のMetaアプリのトークンでのアカウント追加）を、2026-10-13に011（チームの見直し）と012（アカウントを先に作る）を、決済の前に入れた。

### 6.2 Out of Scope for MVP

- チーム運用のうち、アカウントをまたいだ匿名のベンチマークと、アカウント単位の簡易PIN。チーム運用のほかの部分は、2026-10-09にMVPへ移した（§6.1、FR-13）。
- Meta App Reviewを前提とした「他者が使える本番公開」：MVPはローカル／ステージング環境での自分・限定テスターでの検証を優先する。

### 6.3 今後の追加機能の候補（参考プロダクトの変更から）

2026-10-08、006（FR-9・FR-10）の検討のために参考プロダクト（Threads Growth OS）を見直したところ、次の機能が増えていた。いずれもMVPの範囲外とし、MVPの後に追加機能として検討する（優先順位は未定）。画面は参考プロダクトに寄せず、[UI全体設計](../../../docs/ui-design.md)に従う。

- **プロフィール・固定投稿の改善**：Threadsのプロフィール文（150文字以内）と固定投稿（最大3本）の下書きを保管し、AI用のプロンプト（下書きが空なら案を作る、あれば診断して改善する）をコピー＆ペーストで回す。保管した内容は投稿生成のプロンプトにも入れ、投稿の立場・トーンをそろえる。Threadsへは自動で反映しない。
- **ナレッジベース**：投稿生成のAIが参照する事実情報（Account専用のメモと、全Accountで共通の資料）を登録し、プロンプトの「参照してよい事実情報」に入れる。ここにない日付・数字・固有名詞はAIに作らせない。
- **勝ちパターン**：投稿の実績（反応数）から、そのAccount自身の傾向（同じテーマ・書き出しの投稿が3件以上たまったもの）を見つけ、次のプロンプトに入れる。投稿にテーマ・目的などの分類が要る（参考プロダクトでは、投稿にカテゴリ・ターゲット・目的・CTAを持たせている）。
- **ホームの手順表示**：ホームに「発信の土台 → プロフィール → 投稿ストック → 自動投稿」の手順と、いまどこまで進んだかを出す。
- **パフォーマンスの傾向分析**（006では見送り）：反応が良い曜日・時間帯、反応が良かった投稿の上位、文字数の傾向の要約。表での表示。AIに改善案を出してもらうためのプロンプト。
- **好調の投稿をプロンプトに入れる**（006では見送り。006は低調の投稿だけを入れる）。
- **追記（投稿チェーン）**：投稿への返信の形で追記を作り、親の投稿が公開された後に返信として公開する。

## 7. Success Metrics

**Primary**
- **SM-1**: 自分以外のアクティブAccount数 — AI部・IT交流会ネットワーク内から実運用に移行したアカウント数。目標`[ASSUMPTION]`3〜5件（MVPローンチ後1〜2ヶ月）。Validates FR-1, FR-2.
- **SM-2**: 投稿運用の手作業時間削減 — 投稿文の最終確認〜公開までの手作業時間。目標は実需ヒアリング後に設定。Validates FR-5, FR-7, FR-8.

**Secondary**
- **SM-3**: 無料体験の後に有料の契約へ移る割合。Validates FR-12.

**Counter-metrics (do not optimize)**
- **SM-C1**: NGワード違反率・ユーザーによる手動差し戻し率 — 自動化を急ぐあまり投稿品質・人格一貫性が損なわれていないかを監視する。Counterbalances SM-1, SM-2.
