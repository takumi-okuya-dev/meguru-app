# Addendum: ThreadsGrower App

技術的詳細・料金プラン表・リスクなど、Product Brief本体には収まらない深掘り情報。PRD・architectureフェーズの入力として使う。

## 料金（2026-10-08に変更）

このアプリには、**個人運用**と**チーム運用**の2つの軸がある。

- **個人運用**：アカウントのオーナー（個人）が、自分のThreadsアカウントを運用し、その分を自分で払う。
- **チーム運用**：個人運用しているアカウントを伸ばすために、パートナー（とその編集者）が手伝いに入る。**払うのは、いつもアカウントのオーナー**。

| 項目 | 月額 | 内容 |
| --- | --- | --- |
| 無料体験 | 0円（登録から1か月） | すべての機能 |
| 基本料金 | 1,000円 | すべての機能。Threadsアカウント1件目を含む |
| 追加アカウント | ＋500円／件 | 2件目以降のThreadsアカウント |
| パートナー | 個人運用と同じ（基本料金＋追加アカウント） | パートナー自身のThreadsアカウントを持つ前提。手伝う先のアカウントの料金は、そのオーナーが払う |
| 編集者 | 無料 | パートナーが招待する。1チームの人数には上限を置く（`[ASSUMPTION]`10人） |

- 例：個人で1アカウント＝1,000円、3アカウント＝2,000円。パートナーが自分の1アカウントを運用しながら、顧客10人を手伝う＝パートナーは1,000円（顧客はそれぞれ自分の分を払う）。
- **機能の出し分けはしない**：有料なら（または無料体験中なら）すべての機能を使える。旧案の「自動投稿のみ（広告あり）」のプランはやめた。Threads本体に無料の予約投稿があり、自動投稿だけでは差別化にならないため。広告の仕組みも作らない。
- **無料体験の後に契約しない場合**（`[ASSUMPTION]`）：データは残して読むだけにし、自動投稿は止める。
- **無料体験中のアカウント数**（`[ASSUMPTION]`）：上限を置く（例：3件）。
- **費用の見込み**：1人増えるごとの原価はほぼ0で、インフラの費用は利用者が増えても月数千円で頭打ちになる（[docs/cost-estimate.md](../../../docs/cost-estimate.md)）。チームはClerk Organizationsを使わずアプリのDB（Neon）で管理するので（「契約と役割の設計」）、チームや編集者が増えても費用はほぼ増えない。
- 金額は実需ヒアリングの前の仮の値。
- **旧案（2026-10-01〜10-07）**：Accountごとの4段階のプラン（1：自動投稿のみ 月500円・広告あり、2：＋grower機能 月500円、3：＋複数アカウント 月1,000円、4：＋チーム管理 月2,000円）。プラン1と2が同じ価格になる矛盾（PRD §8 Open Question 6）と、「複数アカウント」と「チーム」の区別が分かりにくいことから見直した。

## 契約と役割の設計

- **契約**：ユーザー（支払う人）単位。基本料金と、運用するThreadsアカウントの数を持つ。旧案ではAccountごとに`plan`（4値）を持っていた。
- **役割**：Account（Threadsアカウント）ごとに、誰がどの立場で関わるかを持つ（`Membership.role`）。個人運用ではオーナーだけなので、役割は画面に出さない。
- **チームはアプリのDB（Neon）で管理する**（2026-10-08決定）：Clerk Organizationsは使わず、Clerkはログインだけに使う（チームごとにDBを立てるのではなく、アプリが使っている1つのDBにチーム用の表を足す）。Organizationsはチーム1つごとに課金される（月100チームを超えると1チーム月$1）ため、1人が多くのチームを作ると料金を超える費用になる。自前で作るのは、このアプリに必要な部分だけ：チーム（パートナーの会社）、メンバーと役割（オーナー・パートナー・編集者）、招待（招待のリンク・受け入れ）、担当の割り当てと解除、権限の判定。会社のドメインでの自動参加・SSO・組織を切り替える専用の画面は作らない。
- 契約（お金）と役割（権限）は別のものとして扱う（Constitution原則IVの考え方。原則IVの文言は、旧案の`Account.plan`と`owner`／`member`を前提に書かれているので、見直しが要る）。

## チーム運用（2026-10-08検討）

### ターゲットと使い方

- **ターゲット**：Threadsのコンサル・運用代行。
- **使い方**：個人運用しているアカウントのオーナーが、パートナーを招待する。パートナーは、自社の編集者と一緒に、そのアカウントの投稿やプロフィールの案を作り、アカウントを伸ばす手伝いをする。
- **例**：カフェのB店の店長が、自分でこのアプリを契約してThreadsアカウントを運用している。運用代行会社のA社に手伝ってもらう。
  1. B店の店長（オーナー）が、A社の代表（パートナー）を招待する。
  2. A社の代表が、社員（編集者）をB店の担当にする。
  3. 編集者が、B店の投稿を作る。
  4. B店の店長が投稿を確認し、OKを出す（または差し戻す）。オーナーが許可していれば、パートナーが承認してもよい。
  5. OKの出た投稿が、予定の時刻に自動で投稿される。

### 3つの役割

| 役割 | 誰か | 支払い | 一言でいうと |
| --- | --- | --- | --- |
| オーナー | Threadsアカウントのオーナー（個人運用のユーザー） | 自分のアカウント分を払う | 自分のアカウントの主導権を持つ。パートナーを招いたり外したりし、最終的な判断（承認と設定）をする |
| パートナー | Threadsのコンサル・運用代行（の代表） | 手伝う先の分は払わない（自分のアカウント分は個人運用として払う） | 招かれたアカウントの運用を手伝う。編集者を招待し、担当を割り当てる |
| 編集者 | パートナーの社員（スタッフ） | 無料 | 担当になったアカウントで、投稿やプロフィールの案を作る |

### 役割の名前（よく使われるツールに合わせた）

| 役割 | 同じ考え方の名前を使っているツール |
| --- | --- |
| オーナー | Googleドライブ・Notion・Bufferなどの「オーナー」（持ち主で、すべての権限と支払いを持つ） |
| パートナー | MetaのBusiness Suite（ビジネスポートフォリオ）の「パートナー」（代理店など外部の会社に、自分の資産の運用を任せる）。代理店から依頼する・持ち主から招待する、の両方の流れがある点も同じ |
| 編集者 | Googleドキュメントなどの「編集者」（中身を作る・直す）。投稿を公開してよいかは決められない点は、Bufferの「承認が必要（Requires approval）」の権限と同じ |

- パートナーに承認を任せる設定は、Bufferの「投稿の全権限（Full posting access）」と「承認が必要」の切り替えにあたる。
- 画面では、名前の横に一言の説明を付ける（例：「パートナー（運用を手伝うコンサル・代理店）」）。
- 出典（2026-10-08に確認）：[Buffer: Adding users and setting up permissions](https://support.buffer.com/article/670-adding-users-and-setting-up-permissions-in-your-organization)（Owner・Admin、Full posting access・Requires approval）、[Buffer: Changing the owner of your Buffer account](https://support.buffer.com/en-us/articles/changing-the-owner-of-your-buffer-account-aCU4tRKZGW)、[Chakra: Meta Business Manager – Integrations & Partner Access](https://chakrahq.com/help/learning-centre/meta-business-manager/integrations-partner-access)・[Leadsie: How to give access to a Meta Business Portfolio](https://www.leadsie.com/blog/give-meta-business-portfolio-access)（Metaのパートナーの仕組み。第三者の解説）。

### 各役割のできること

| できること | オーナー | パートナー | 編集者 |
| --- | --- | --- | --- |
| 契約・支払い | ○ | ×（手伝う先の分） | × |
| Threadsとの接続（オーナーのログインが必要） | ○ | × | × |
| パートナーを招待する・外す、任せる範囲を決める | ○ | × | × |
| 編集者を招待する・外す、担当を割り当てる | × | ○ | × |
| 触れるアカウント | 自分のアカウント | 招かれたアカウント | 担当になったアカウント |
| 投稿の案を作る・直す（プロンプトのコピー、貼り付けでの登録、編集） | ○ | ○ | ○ |
| プロフィール・固定投稿の案を作る・直す | ○ | ○ | ○ |
| 戦略（課題・宣伝内容・リサーチ）を作る・直す | ○ | ○ | ○ |
| 投稿を承認・却下する | ○ | △（オーナーが許可したとき） | × |
| 自動投稿の時刻・オンオフ、NGワード、投稿ルールの設定 | ○ | △（オーナーが許可したとき） | × |
| パフォーマンスを見る・CSVで書き出す | ○ | ○ | ○ |
| 操作の記録（誰が作成・編集・承認・却下したか）を見る | ○ | ○ | × |

- 承認と設定は、初めはオーナーだけができる。オーナーが許可すると、パートナーもできるようになる（任せる範囲はオーナーが決める）。
- どの役割でも、人の承認を経ない投稿はしない（Constitution原則II）。NGワードのチェックも、どの役割の操作でも外せない（原則I）。
- Threadsとの接続はオーナーが自分で行うので、パートナーが顧客のログイン情報を預かる必要はない。

### 決まっていないこと・前提

- **前提になる機能**：プロフィール・固定投稿の改善（PRD §6.3）を先に作る。
- **前提になる手続き**：Metaのアプリ審査（App Review）。テスターとして招待する今の方式では、顧客のアカウントごとに招待が要り、パートナーの規模では回らない。
- **候補**：
  - パートナー向けの、手伝っているアカウントをまとめて見る画面（承認待ちの件数・伸びの一覧）。
  - 顧客への月次レポート（006のCSVをもとにした、見せられる形の報告）。
  - パスワード不要の招待リンク（期限付き・1回だけ）、アカウントをまたいだ匿名のベンチマーク、アカウント単位の簡易PIN（旧プラン4の候補。参考プロダクトの調査より）。
- **着手の時期**：個人運用で有料の利用が確かめられてから（Constitution原則V、PRD §6.2）。

## 技術スタック（運用コスト最小化方針、2026-10-01調査）

| レイヤー | 選定 | 理由 |
| --- | --- | --- |
| フロントエンド | React + TypeScript（Vite製SPA） | ダッシュボード型でSSR/SEO不要 |
| フロントエンドホスティング | Cloudflare Pages | 無料枠で商用利用可（Vercel Hobbyは商用利用ToS違反） |
| バックエンド | Cloudflare Workers + Hono | 無料枠で商用利用可、Cron Triggers標準搭載 |
| データベース | Neon（Postgres） | 無料枠100 CU-hours/月、アイドル時自動サスペンド |
| ORM | Drizzle ORM | 軽量、edgeランタイムと相性良 |
| 認証・マルチテナント | Clerk（ログインだけに使う。Organizationsは使わない） | チーム運用のチーム・メンバー・役割・招待はアプリのDB（Neon）で管理する（2026-10-08決定。Organizationsはチーム1つごとに課金され、1人が多くのチームを作ると料金を超える費用になるため） |
| 決済 | Stripe（Billing + Checkout） | 変動費（日本国内3.6%+0.7%）、固定費を積まない |
| スケジューラ | Cloudflare Cron Triggers（+ 必要なら Upstash QStash） | Threads APIレート制限を踏まえたポーリング実装 |
| UI | shadcn/ui（Radix UI + Tailwind CSS） | ChatGPT風ニュートラル質感、コンポーネントをソースコピー方式で導入 |

### コスト試算（MVP〜アーリーステージ）

月額固定インフラ費用は$0からスタート可能（Cloudflare Workers Free / Neon Free / Clerk Free想定）。決済手数料は売上発生後の変動費。**[ASSUMPTION] Neonを高頻度ポーリングすると無料枠(100 CU-hours/月)を超えるリスクがあり、実装時にポーリング間隔またはキャッシュ戦略を再検討する必要がある**（詳細は下記リスク参照）。

### 却下した選択肢

- Vercel（Hobby）：Cron Jobsが1日1回まで、商用利用がToS違反。
- Supabase単体：無料枠が7日非アクティブで自動pauseし手動再開が必要。
- Postizのfork：NestJS+Prisma+Docker前提の常時稼働サーバー運用が必要で、コスト最小化方針と衝突。

## 技術的リスク・未検証事項

- **Meta App Review**：一次審査の却下率60〜70%程度との情報あり（一次情報未確認、母集団不明）。1回の差し戻しで約1週間、スコープごとに2〜7営業日。本番公開（他者が使える状態）まで数週間かかる可能性。
- Threads APIレート制限（250投稿/24h等）の単位（ユーザー単位かアプリ単位か）は未確認。
- Neonを1分間隔でポーリングすると、`0.25 CU × 24h × 30日 = 180 CU-hours/月`となり無料枠100 CU-hoursを超える可能性。対策候補：①ポーリング間隔を5〜15分に緩める、②Cloudflare Workers側でキャッシュして問い合わせを間引く、③実装後に実測して判断。
- （2026-10-01検証済み）Clerkの無料枠は100 MRO（Monthly Retained Organization＝その月にメンバー2人以上・うち1人以上がmonthly retained userである組織）まで。課金単位は月間アクティブベースであり、作成済み累計数ではない（clerk.com/pricingで確認）。超過分は従量制：101〜1,000件目$1/月、1,001〜10,000件目$0.90、10,001〜100,000件目$0.75、100,001件目以降$0.60（いずれも1組織あたり）。残る未確認点：100 MRO超過時にFAQ上「B2B Authenticationアドオンへのアップグレードが必要」とある一方、マーケティングコピーは「全プランに含まれる」としており、このアドオン自体に従量課金とは別の固定月額基本料金が発生するかは実装着手時にClerkダッシュボードで要確認。 → 2026-10-08、チームをアプリのDB（Neon）で管理することにしたため、Organizationsは使わない。
- レート制限が予告なく変更された前例あり（Instagram APIで5,000→200件/時間への無予告削減）。プラットフォームリスクとして前提に入れる。
