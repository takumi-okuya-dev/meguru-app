# プロダクトの構造：めぐる（Threadsアプリを起点にした個人開発スイート）

**作成**：2026-11-10 | **更新**：2026-11-13（029でThreadsをパターン①にそろえた。共通とThreadsの分担） | **状態**：方針（決まっていないことは「未定」と書く。7章）

このリポジトリのアプリ（Threadsの投稿づくり・自動投稿）を起点に、複数のアプリを**共通のアカウント・共通の契約・アプリごとの利用権**で束ねる個人開発のスイート「**めぐる**」を育てる。この文書は、その全体の形と、コードをどう分けるかの決まりを残す。

- **構想の正本**：personal-knowledge-base の`Wiki/仕事/システム開発/アイデア/個人開発版Google Workspace構想（スイート型SaaS）.md`（料金・アプリの候補・クラウドの比較などはこちら。この文書には写さない）
- **コードの境界の正本**：[docs/module-map.md](./module-map.md)（表の持ち主・入口・例外の一覧）。2作目からのDBの境界は[docs/app-separation.md](./app-separation.md)
- **今のシステムの構成**：[docs/architecture.md](./architecture.md)

## 1. 何を目指すか

| 段階 | やること | 次へ進む条件 |
|---|---|---|
| 0. 棚卸し | Threadsアプリの表・処理・APIの入口を仕分ける（027） | 共通の候補とThreads固有の境界を説明できる |
| 1. Threadsを育てる | 機能を足しながら、共通・Threads・窓口の境界を守る（027で境界を作る） | 投稿・認証・決済を壊さず、境界がESLintで守られている |
| 2. 2作目で共通化を確かめる | 2作目を1本選び、同じログイン・契約・利用権で動かす | 2つのアプリで共通の部分を使い回せ、ほかの人のデータ・買っていない機能を拒める |
| 3. 必要な部分だけ切り出す | 別に出したい・負荷や障害を分けたいアプリや処理だけを分ける | 入口とデータの持ち主が決まり、ほかのサービスのDBを直接読まない |
| 4. プラットフォームにするかを決める | ほかの開発者のアプリを載せる需要と責任を確かめる | 自分のスイートとしての価値と、第三者向けの安全・運用が成り立つ |

- **今は段階0〜1**。汎用の基盤を先に作り込まない。2作目で本当に共通だった部分だけを取り出す。
- 2作目の候補は**人物管理**か**イベントの集金管理**（2026-11-11の壁打ちで、バドミントンの試合表から変えた。どちらにするかは未定）。

## 2. 全体の形

```text
利用者のブラウザ（Web/PWA。今は1つのSPA）
   │
   ▼
API（Cloudflare Workersの1つのデプロイ。モジュラーモノリス）
   ├─ 組み立て   ：APIの入口の登録・定期処理の振り分け・モジュールのつなぎこみ
   ├─ アプリ     ：apps/threads（今）・apps/<2作目>（将来）── アプリ同士は使わない
   ├─ 共通       ：platform ── 利用者・契約・利用権・機能のON/OFF・上限・テストのグループ・運営・紹介・退会・出来事・利用の数
   ├─ 窓口       ：adapters ── Stripe・ThreadsのAPI・Metaの署名つきリクエスト
   └─ 土台       ：kernel ── 環境の値・エラー・ログ・入力の確かめ・暗号・DBの接続
   │
   ▼
PostgreSQL（Neon。1つのDB。共通は public、アプリは専用のスキーマ（threads など）。表ごとに持ち主のモジュールが決まっている）
```

- 依存は一方向：**組み立て → アプリ → 共通 → 窓口 → 土台**。共通で起きたこと（退会など）は「出来事」（共通が出し、アプリがあとから受け取る）でアプリに伝える。アプリは共通の表を読まず、共通の入口の関数だけを使う（[app-separation.md](./app-separation.md)）。
- ほかのモジュールは**入口**（`index.ts`）からだけ使う。表を読み書きするのは持ち主のモジュールだけ（027で書いていた例外の列は、029でなくなった）。
- これらはESLintの規則（`eslint-rules/module-boundaries.js`）で自動で止める。APIの入口の一覧（`apps/api/test/repo/routes.snapshot.txt`）もテストで見張る。

## 3. 共通（platform）とアプリの分担

| 共通が持つもの（どのアプリでも使う見込み） | Threadsが持つもの（Threads固有） |
|---|---|
| 利用者（`users`）・退会の記録 | 運用するアカウント（`accounts`）とメンバー・権限の判定 |
| 契約と決済（Stripe）・利用の数（料金の数） | チーム・招待・ロール・活動の記録 |
| 利用権（契約・料金なし・運営者・機能・上限をまとめて返す入口の関数） | Threadsとの接続・トークン・Metaからの要求 |
| 機能のON/OFF・テストのグループ | 戦略・宣伝・リサーチ・投稿の案・確かめる・投稿ルール（NGワード） |
| 上限・運営の記録 | 予約と自動投稿・数字の取得・分析・プロンプト |
| 紹介・出来事の届け・アプリの登録（機能と上限の名前） | 時間差のメンション・外部媒体・テスター招待（Metaの審査の前の接続） |

- `accounts`・チーム・活動の記録は、027では共通に置いたが、中身のほとんどがThreadsの列で、料金・権限の判定もThreadsのアカウントを数えていたため、029でThreadsの持ち物にした。2作目でチームが要るときは、そのときに考える。
- 今の料金は「アカウント1件につき月1,000円」。スイートの料金（アプリをまとめて買う形）は**未定**で、今の料金を上書きしない。

## 4. 2作目の足し方

- **同じリポジトリに足す**（2026-11-10に決定）。共通の部分を直したときに、両方のアプリへの影響を1つのPRとテストで確かめられ、CI・テスト版・デプロイも1つで済むため。
- 置き場所は`apps/api/src/apps/<名前>/`。`index.ts`（入口）・`schema.ts`（表）・小分けを作り、共通の入口だけを使う。ESLintの規則は、設定を書き足さなくても当たる。
- 手順の詳細は[docs/module-map.md](./module-map.md)の「アプリのモジュールを足す手順」（6章）。
- リポジトリの名前は、2026-11-11に`threads-grower-app`から`meguru-app`に変えた（共通のパッケージは`@meguru/shared`）。Cloudflare・Neonの名前（`threads-grower-*`）とブラウザに保存する値の名前は、ドメインを移すときまで変えない。

### 別のリポジトリ・別のサービスに分けるとき

アプリが2本になっただけでは分けない。次の理由が実際に出たときに、そのアプリ（または処理）だけを分ける。

- 出す時期を完全に分けたい・負荷を分けて増やしたい・障害を切り離したい・別の人に任せたい
- アプリを単独で売る・渡す

分けるときは、そのモジュールと入口を持ち出し、共通とは入口（API）とイベントでつなぐ。ほかのサービスのDBを直接読まない。

## 5. 画面の全体の形（めぐる）

2026-11-11に決めた。画面イメージは[めぐる 外枠モック](https://claude.ai/artifact/9ZdabDgbgJbVVny89hFasu)（場面ごとに操作できる。非公開のため、開けるのはオーナーだけ）。見た目は[docs/ui-design.md](./ui-design.md)の今の約束（ChatGPT風・ニュートラルなグレー）をそのまま使う。

| 項目 | 決めたこと |
|---|---|
| 名前 | スイートは「**めぐる**」。コンセプトは「**出会いと挑戦が、めぐる。**」（意味と理念は構想ノートの「0. プロダクトの構想」）。中のアプリは「めぐる Threads」「めぐる 人物管理」のように呼ぶ。今の`ThreadsGrower`は「めぐる Threads」になる。作り手の屋号は分けず、理念（AIを、働く人の味方に）は紹介文で伝える。ドメインは未定（取れるかは確かめていない） |
| URL | 1つのドメインで、アプリごとにパスを分ける（`/threads/…`・`/people/…`）。ログインは1つで、認証の追加の費用もいらない |
| 入口 | ログインしたあとは**最後に使ったアプリ**から始まる。アプリが0本の人（登録した直後など）は、アプリ一覧から始まる |
| アプリの切り替え | サイドバーの**いちばん上**。押すと、使っているアプリと「すべてのアプリ」。**アプリが1本の人には出さない**（今のThreadsアプリと同じ見た目のまま） |
| その下 | アプリごとの中身。Threadsなら今のアカウントの切り替えと機能の一覧。人物管理にはアカウントの切り替えがない |
| すべてのアプリ（`/apps`） | アプリの切り替えと**同時に作る**。1カラムの画面で「使っているアプリ」と「足せるアプリ」（料金と「詳しく見る」）を並べる。アプリの切り替えのメニューと、ユーザーメニューから開く。まだ作っていないアプリは出さない |
| 共通の設定 | ログイン・契約・アプリをまたぐ設定は1か所（ユーザーメニューの「設定」）。アプリの中の設定（例：このアカウントの設定）は今のまま |
| 公開ページ | 人物管理のQRで相手が登録する画面や、集金の閲覧リンクなど、ログインのいらない画面はサイドバーの外に置く |
| 統合ホーム | アプリをまたいだ「次のイベント・今日やること」の画面は、今は作らない |

## 6. アプリを並行して作る

Threadsアプリを改善しながら、別のアプリを並行して実装できる形にする。

| 場所 | 今（2026-11-13） | 並行できる形にするには |
|---|---|---|
| API | ◎ 027で`apps/<名前>/`に分けた。アプリ同士は使わない規則がESLintでかかる | そのままでよい |
| Web | ◎ 028で`shell/`（外枠）と`apps/<名前>/`に分けた。外枠とアプリ・アプリ同士の境界をESLintでかける。Threadsの画面は`/threads/…` | そのままでよい（アプリを足す手順は[docs/module-map.md](./module-map.md) 7-6） |
| 共通の表 | ◎ 029で`accounts`・チームをThreadsへ移し、料金の数はアプリが伝える利用の数（`app_usage`）で決めるようにした。Threadsもパターン①で、共通の表を直接読まない | アプリごとの契約（まとめ買い）は、2作目で本当に要る形を見てから決める。2作目も共通の表を直接読まない（[app-separation.md](./app-separation.md)） |
| マイグレーション | △ 番号が1列 | 下の決まりで回す |
| spec-kitの番号 | ◎ 2026-11-12から、アプリごとのフォルダと番号（`specs/<アプリ>/NNN-…`） | 下の決まりのとおり |
| デプロイ | ○ Workerは1つで、全アプリが一緒に出る | 作りかけのアプリは、アプリの一覧の`released: false`か、アプリの利用の決まり（`granted`。030）で本番では隠す |

**並行するときの決まり**

- Threadsの改善は`apps/threads/`（APIとWeb）の中で、新しいアプリは`apps/<名前>/`の中で進める。互いのフォルダには触らない。
- 共通（`platform/`・Webの外枠）を直す変更は、小さなPRに分けて先にdevelopへ入れ、もう一方のブランチはdevelopを取り込む。共通の大きな作り変えを、アプリの機能のPRに混ぜない。
- マイグレーションは、先にdevelopへ入った方がその番号を使う。後の方はdevelopを取り込んでから`pnpm --filter api db:generate`で作り直す（番号を手で直さない）。
- **仕様のフォルダと番号は、アプリごとに分ける**（2026-11-12に決めた）。
  - 新しい仕様は`specs/<アプリ>/NNN-<短い名前>/`に置く。`<アプリ>`はアプリのID（`@meguru/shared`の`APP_CATALOG`の`id`。今は`threads`）。外枠や共通（`platform/`・Webの外枠・`@meguru/shared`の共通の部分・CI・開発の決まりなど、どのアプリにも属さないもの）は`meguru`。共通とアプリの両方を変えるときは、主に変える方に置く。迷ったら`meguru`。
  - 番号はフォルダごとに振る。`threads`と`meguru`は`029`から（`specs/028`までの続き）、新しいアプリは`001`から。
  - 番号は、ブランチを切る前に、developと作業中のブランチの`specs/<アプリ>/`の最大の番号を確かめ、その次を使う。アプリをまたいで並行するときは、ぶつからない。同じアプリで2つを同時に進めるときだけ気をつける。
  - ブランチは`feature/<アプリ>-NNN-<短い名前>`、コミットの頭は`feat(<アプリ>-NNN)`のように、アプリの名前と番号で呼ぶ（例：`feature/threads-029-…`、`feat(people-001)`）。
  - `specs/001`〜`specs/028`は動かさない（コードのコメントや文書から参照しているため）。`specs/`の直下には新しい仕様を作らない。
  - `/speckit-specify`では、出し先（`SPECIFY_FEATURE_DIRECTORY=specs/<アプリ>/NNN-<短い名前>`）を毎回はっきり指定する。spec-kitの自動の番号は`specs/`の直下しか見ないため。スキルの本文（`.claude/skills/speckit-specify/SKILL.md`）にも、この決まりを書いてある。
- **すべてのアプリを、モジュラーモノリスのパターン①で作る**（2026-11-12に決めた）。今後マイクロサービスにしていく可能性があるため、ほかのアプリのDBも共通の表も直接さわらず、利用者のIDを値として持つだけにし、共通の入口の関数と出来事でやりとりする。Threadsも029でパターン①にそろえた（2026-11-13）ので、2作目以降はThreadsを実例にしてなぞる。決まりと図は[docs/app-separation.md](./app-separation.md)。
- 作りかけのアプリは、機能のON/OFFで本番には出さない。Threadsの改善はいつでもリリースできるようにしておく。
- **アプリの利用の決まり**（2026-11-13、specs/meguru/030-app-access）：アプリは、組み立てのときに「だれでも使える（`open`。登録しなければこれ）」か「運営者が開いた人だけ（`granted`）」かを登録する。`granted`のアプリは、運営者・人ごとの許可がある人・閉じていないテストのグループの許可がある人だけが使える。運営者は、設定 > 運営の「使える機能」（人）と「グループ」で開く・閉じる。許可のない人には、`/api/me`の`available`・すべてのアプリの画面・アプリの切り替えにそのアプリが出ず、APIは403 `APP_NOT_AVAILABLE`。機能のON/OFF（019）はThreadsだけが持つ仕組みのままで、アプリを人ごとに出す・出さないはこちらを使う。Threadsは`open`。
- 手元で同時に進めるときは、`git worktree`で作業場所を分け、それぞれでClaude Codeを動かす。`pnpm worktree:new <名前> [ブランチ]`で作ると、作業場所ごとにローカルのDBとポートが分かれ、`pnpm dev`を同時に動かせる。結合テストとE2Eは、作業場所をまたいで1つずつ流れる。始めから終わりまでの手順は[docs/parallel-development.md](./parallel-development.md)。
- 2作目以降のアプリは、**将来モバイルアプリにすることを視野に入れて技術を選ぶ**（2026-11-12に決めた）。業務の判断とデータのやりとりはAPIと共通のパッケージに置き、Webの画面やブラウザだけで動く仕組みに閉じこめない。モバイルの画面からも同じAPIと判断を使えるようにしておく。Threadsアプリは今のままでよい（モバイル化のための作り直しはしない）。
