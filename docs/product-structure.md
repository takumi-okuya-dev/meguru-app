# プロダクトの構造：Threadsアプリを起点にした個人開発スイート

**作成**：2026-11-10 | **状態**：方針（027で整理を始めたところ。決まっていないことは「未定」と書く）

このリポジトリのアプリ（Threadsの投稿づくり・自動投稿）を起点に、複数のアプリを**共通のアカウント・共通の契約・アプリごとの利用権**で束ねる個人開発のスイートを育てる。この文書は、その全体の形と、コードをどう分けるかの決まりを残す。

- **構想の正本**：personal-knowledge-base の`Wiki/仕事/システム開発/アイデア/個人開発版Google Workspace構想（スイート型SaaS）.md`（料金・アプリの候補・クラウドの比較などはこちら。この文書には写さない）
- **コードの境界の正本**：[docs/module-map.md](./module-map.md)（027で作る。表の持ち主・入口・例外の一覧）
- **今のシステムの構成**：[docs/architecture.md](./architecture.md)

## 1. 何を目指すか

| 段階 | やること | 次へ進む条件 |
|---|---|---|
| 0. 棚卸し | Threadsアプリの表・処理・APIの入口を仕分ける（027） | 共通の候補とThreads固有の境界を説明できる |
| 1. Threadsを育てる | 機能を足しながら、共通・Threads・窓口の境界を守る（027で境界を作る） | 投稿・認証・決済を壊さず、境界がESLintで守られている |
| 2. 2作目で共通化を確かめる | 2作目を1本選び、同じログイン・契約・利用権で動かす | 2つのアプリで共通の部分を使い回せ、ほかの人のデータ・買っていない機能を拒める |
| 3. 必要な部分だけ切り出す | 別に出したい・負荷や障害を分けたいアプリや処理だけを分ける | 入口とデータの持ち主が決まり、ほかのサービスのDBを直接読まない |
| 4. プラットフォームにするかを決める | ほかの開発者のアプリを載せる需要と責任を確かめる | 自分のスイートとしての価値と、第三者向けの安全・運用が成り立つ |

- **今は段階0〜1**。汎用の基盤を先に作り込まない。2作目で本当に共通だった部分だけを取り出す。
- 2作目の候補（バドミントンの試合表・人物メモ・献立・イベントの集金記録など）は**未定**。

## 2. 全体の形

```text
利用者のブラウザ（Web/PWA。今は1つのSPA）
   │
   ▼
API（Cloudflare Workersの1つのデプロイ。モジュラーモノリス）
   ├─ 組み立て   ：APIの入口の登録・定期処理の振り分け・モジュールのつなぎこみ
   ├─ アプリ     ：apps/threads（今）・apps/<2作目>（将来）── アプリ同士は使わない
   ├─ 共通       ：platform ── 利用者・アカウントとメンバー・権限・契約・機能のON/OFF・上限・チーム・運営・活動の記録・退会
   ├─ 窓口       ：adapters ── Stripe・ThreadsのAPI・Metaの署名つきリクエスト
   └─ 土台       ：kernel ── 環境の値・エラー・ログ・入力の確かめ・暗号・DBの接続
   │
   ▼
PostgreSQL（Neon。1つのDB。表ごとに持ち主のモジュールが決まっている）
```

- 依存は一方向：**組み立て → アプリ → 共通 → 窓口 → 土台**。共通からアプリを呼ぶときは「知らせ」（共通が出し、アプリが受け取る）を使う。
- ほかのモジュールは**入口**（`index.ts`）からだけ使う。表を書き換えてよいのは持ち主のモジュールだけ（例外は module-map に列ごとに書く）。
- これらはESLintの規則（`eslint-rules/module-boundaries.js`）で自動で止める。APIの入口の一覧（`apps/api/test/repo/routes.snapshot.txt`）もテストで見張る。

## 3. 共通（platform）とアプリの分担

| 共通が持つもの（どのアプリでも使う見込み） | Threadsが持つもの（Threads固有） |
|---|---|
| 利用者（`users`）・退会の記録 | Threadsとの接続・トークン・Metaからの要求 |
| 運用するアカウント（`accounts`の番号・名前・持ち主）とメンバー | 戦略・宣伝・リサーチ |
| チーム・招待・ロール | 投稿の案・確かめる・投稿ルール（NGワード） |
| 契約と決済（Stripe） | 予約と自動投稿 |
| 機能のON/OFF・テストのグループ | 数字の取得・分析・プロンプト |
| 上限・運営の設定・運営の記録 | 時間差のメンション・外部媒体 |
| 活動の記録 | テスター招待（Metaの審査の前の接続） |

- `accounts`は共通が持つが、Threads固有の列（@ユーザー名・接続・投稿の長さ・CORE RULESなど）が大半ある。これらは「Threadsが書き換えてよい例外」とし、将来Threads専用の表へ移す候補にする（027 Clarifications）。
- 今の料金は「アカウント1件につき月1,000円」。スイートの料金（アプリをまとめて買う形）は**未定**で、今の料金を上書きしない。

## 4. 2作目の足し方

- **同じリポジトリに足す**（2026-11-10に決定）。共通の部分を直したときに、両方のアプリへの影響を1つのPRとテストで確かめられ、CI・テスト版・デプロイも1つで済むため。
- 置き場所は`apps/api/src/apps/<名前>/`。`index.ts`（入口）・`schema.ts`（表）・小分けを作り、共通の入口だけを使う。ESLintの規則は、設定を書き足さなくても当たる。
- 手順の詳細は[docs/module-map.md](./module-map.md)の「アプリのモジュールを足す手順」（027で書く）。
- 2作目を足す時点で、リポジトリの名前をスイート全体の名前に変えることを考える（今は`threads-grower-app`のまま）。

### 別のリポジトリ・別のサービスに分けるとき

アプリが2本になっただけでは分けない。次の理由が実際に出たときに、そのアプリ（または処理）だけを分ける。

- 出す時期を完全に分けたい・負荷を分けて増やしたい・障害を切り離したい・別の人に任せたい
- アプリを単独で売る・渡す

分けるときは、そのモジュールと入口を持ち出し、共通とは入口（API）とイベントでつなぐ。ほかのサービスのDBを直接読まない。

| Postgresのスキーマをモジュールごとに分けるか | 2作目のあとで必要なら |
| モバイル（PWAで足りるか、ネイティブにするか） | 必要が見えてから |
| 将来のクラウド・認証の移行 | 構想ノートの比較をもとに、切り出すとき |
