# コードの書き方の決まり

**対象**：コードを書くすべての人とAI。入口は[CLAUDE.md](../../CLAUDE.md)。モジュールの境界（どこが何を持ち、どこから読んでよいか）は[モジュール地図](../module-map.md)と[アプリを分けて作る決まり](../app-separation.md)が正本で、ESLintの規則（`eslint-rules/`）が自動で守る。

## 1. 書き方

- 外部に公開している関数・クラス・型・定数には、JSDoc形式のドキュメントコメント（`/** … */`）を付ける。説明に加えて、引数は`@param`、戻り値は`@returns`、投げる例外は`@throws`で書く。
- TypeScriptなので、JSDocには型（`{string}`など）を書かない（[TypeScriptのハンドブック](https://www.typescriptlang.org/ja/docs/handbook/jsdoc-supported-types.html)）。
- `pnpm lint`（`eslint-plugin-jsdoc`）が付け忘れや`@param`の名前のずれを検出し、CIでも止まる。shadcn/uiから取り込んだ部品（`apps/web/src/components/ui/`）とテストは対象外。
- コメント・画面の文言・エラーの文言は日本語で書く。
- 直すときは、変える行だけを直す。ファイル全体を整形しなおさない（差分が大きくなり、ほかのセッションの変更とぶつかる）。

## 2. 設定と環境

- 環境ごとの違いを、コードの分岐（`if (APP_ENV === "production")`など）にしない。設定の値（`APP_ENV`・`VITE_APP_ENV`と、`apps/api/wrangler.toml`の環境ごとの`vars`）で分ける。スイッチを足す・値を変えるときは、同じPRで[環境ごとのスイッチ](../environment-switches.md)の表も直す。
- **大きな機能は、設定で止められるように作る**。`BILLING_ENABLED`・`THREADS_CONNECT_METHODS`と同じ形で、`apps/api/wrangler.toml`の環境ごとの`vars`で切り替える。
  1. 本番は「切」のまま出す。
  2. ステージングで「入」にして確かめる。
  3. 問題がなければ、本番も「入」にする（`[env.production.vars]`の1行を変えるPR）。

  こうしておくと、出したあとに困っても**コードを戻さず、設定の1行で止められる**。作りかけのアプリは、アプリの一覧の`released: false`か、アプリの利用の決まり（`granted`。specs/meguru/030-app-access）で本番では隠す。
- 秘密の値・本物の利用者や参加者のデータ・個人の情報は、コミットしない（手元の`.dev.vars`・`.env.local`に置く）。リポジトリは2026-11-13からしばらく公開にしている。

## 3. マイグレーション

デプロイは**マイグレーション → API → Web**の順に動きます。マイグレーションが当たってから新しいAPIに切り替わるまでの間は、**前の版のAPIが新しいDBで動いています**。途中で止まったときや、APIを前の版に戻したとき（[リリースの手順書](../release-runbook.md) 6-1）も同じです。だから、**マイグレーションは、そのとき本番で動いている前の版のAPIでも壊れない形だけ**にします（[research.md R4](../../specs/015-deploy-environments/research.md)）。

| 変更 | 出し方 |
|---|---|
| 表を足す | 1回でよい |
| 列を足す（空を許す、または既定値つき） | 1回でよい |
| 索引を足す | 1回でよい |
| 列を足す（`NOT NULL`で既定値なし） | **だめ**。前の版のAPIの`INSERT`が失敗する。既定値を付けるか、空を許す |
| 列や表を消す | **2回に分ける**。1回目：アプリがその列を読みも書きもしない版を出す（`NOT NULL`なら、ここで外す）。2回目：消す |
| 列の名前を変える | まず、**DBの列の名前は変えずに、コードの中の名前だけ変える**（Drizzleなら`headline: text("title")`）。それで済まないときだけ、下の例の4回に分ける |
| 列の型を変える | 新しい列を足して写す。下の例と同じ4回 |
| 既存の行が通らないかもしれない制約（`UNIQUE`・`CHECK`・`NOT NULL`）を付ける | **2回に分ける**。1回目：違反する値を書かない版を出す。2回目：残っている行を直してから、制約を付ける |

**列の名前を変える例**：`title`を`headline`に変える

どのリリースでも「マイグレーションが当たるときに動いている版」と「戻す先の版」が、新しいDBで正しく動くように並べます。

| リリース | マイグレーション | アプリ | 戻す先（1つ前の版）が困らない理由 |
|---|---|---|---|
| 1回目 | `headline`を足す（空を許す） | `title`と`headline`の**両方に書き**、`title`を読む | 前の版は`headline`を知らないだけ |
| 2回目 | すべての行で`title`を`headline`に写す | 両方に書き、**`headline`を読む** | 写すときに動いている1回目の版は両方に書くので、取りこぼさない。1回目に戻しても、`title`は書かれ続けている |
| 3回目 | `title`の`NOT NULL`を外す（付いていれば） | **`headline`だけに**書いて読む | 2回目の版は`headline`を読むので、`title`が古くなっても困らない |
| 4回目 | `title`を消す | 変えない | 3回目の版は`title`を使わない |

- 次のリリースは、前のリリースが本番で落ち着いてから出します。
- 前の版に安全に戻せるのは**1つ前まで**です。2つ前の版に戻すと、DBと合わないことがあります。

**そのほかの決まり**

- マイグレーションは`pnpm --filter api db:generate`で作り、**できたSQLを読んでからコミットする**。Drizzleは、名前の変更を「消して足す」として書くことがある。
- **一度`develop`に入ったマイグレーションのファイルは、書き換えない・消さない**。ステージングではもう当たっているので、書き換えてもステージングには当たり直さず、ステージングと本番のDBがずれる。直すときは、新しいマイグレーションを足す。

## 4. テスト

- 機能を足したら、テストも足す（APIの結合テスト・Webのテスト・関わるE2E）。
- テストにアプリの数や並びを書かない（[並行開発の決まり](./parallel-development.md) 11-2）。
