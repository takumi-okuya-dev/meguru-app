## G. プランで機能を分けて売る（2026-11-04）

2026-11-04に、ユーザーが料金のプランの分け方を挙げた。**まだ合意が取れていないので後回し**にした（仕様は作っていない）。決まったら仕様にする。

**ねらい**：戦略（課題・宣伝内容・リサーチ）にはThreadsのノウハウが詰まっていて、まねされやすい。真似されたら困る部分で切り分け、渡す相手を選ぶ。

**今のところの案（ユーザー）**：
- **プランA**：サブスク。自動投稿とチーム運用だけ。気軽に試してもらう入り口。
- **プランB**：形（払い方）は検討中。すべての機能が使える想定。信頼できる人だけに売る。

**最初の話（プランを「戦略なし」「戦略あり」の2つにする案）で決めかけたこと**：
- 対象はサイドバーの「戦略」の3つすべて（課題の考えるヒント・AIと深掘り・AIと壁打ち・全体をAIと整理する、宣伝内容、リサーチと参考投稿のAI解説を含む）。
- 料金はまだ決めていない。あとから変えやすくする（コードを直さずに、決済の側と環境の設定で変える）。
- 無料体験（登録から1か月）では、戦略は使えない。
- 上のプランから下げたとき、書いた内容は残すが、画面は開けず、プロンプトにも入れない。戻すとそのまま使える。

**決めること（2026-11-04に挙げた）**：
1. 「投稿をつくる」（AIのプロンプトのコピー）をプランAでも使えるか。プロンプトの文にもノウハウ（投稿の型・長さの配分など）が入っている。Bだけにすると、Aの人は投稿の案を自分で用意して貼ることになる。
2. パフォーマンス（反応数と判定）をプランAでも使えるか。Threads本体にも予約投稿があるので、Aの価値をどこに置くか。
3. プランBの渡し方。案：利用者が自分で契約するのではなく、運営者が運営者の画面で付ける（016の料金なしの印に近い形）。払い方は決まってから足し、それまではアプリの外で受け取る。
4. 今ある契約（プランが1つのころ）を、どちらのプランとして扱うか。
5. チームの人が手伝う・見せてもらうアカウントでは、見る人ではなく、そのアカウントのオーナーのプランに従う（013の「オーナーが未払いなら、チームの人も読むだけ」と同じ考え方）でよいか。

2026-11-04、プランを決める前の仕組みとして、019（機能のまとまりごとのON/OFF、[specs/019-feature-switches](../specs/019-feature-switches/spec.md)）を作った。運営者が、人ごと・組織（グループ）ごとに「自動投稿」「戦略」「チーム」をON/OFFできる（どちらかでOFFなら使えない）。プランは、ONにするまとまりの組み合わせと料金として、あとで決める（上の「決めること」の1・2は「投稿をつくる」「パフォーマンス」を自動投稿のまとまりに入れることにした。5は019で「オーナーに従う」にした。3は、組織のグループで機能を付ける形で試せる）。

**守れないこと**：プランBの人がプロンプトをコピーして人に渡すことは、仕組みでは止められない。渡す相手を選ぶことと、利用規約（配布の禁止）で守る。

**Constitutionとの関係**：原則IVの「有料の契約中か無料体験中なら、すべての機能を使える」と食い違う。仕様にする前に、原則IVの改定が要る。

## J. 参考投稿の「フォロワーに比べた反応」を出す（2026-11-05）

2026-11-05に、ユーザーが友人から「伸びやすいのは、フォロワー数が少ないのに、いいねが多い投稿」と聞き、リサーチの「良い参考アカウントを見極める3つの指標」を自動にできないかと考えた。同じ日に、022（自分の投稿の解析）とは分けて、小さい機能にすると決めた。中身・時期はまだ決めていない。

**できること・できないこと**：
- 3つの指標（フォロワー数・閲覧2,000回以上の投稿がいくつもあるか・投稿頻度）は、どれも他人のアカウントの値。審査の前（トークンを貼る方法）のThreads APIでは、他人のフォロワー数・投稿は取れない。Instagramのフォロワー数は、Threads APIでは取れない。
- 参考投稿には、フォロワー数・閲覧・いいねなどを手で入れられる（014）。この値から、次は今でも計算できる。
  - **いいね ÷ フォロワー**（友人の言う「フォロワーが少ないのに、いいねが多い」）
  - **閲覧 ÷ フォロワー**（1を超えると、フォロワーの外まで届いた目安。022の「広がり」と同じ考え方）
  - 同じ投稿者の参考投稿で、閲覧2,000回以上が何件あるか（指標②）
- 審査が通れば、他人の公開プロフィール・投稿を取れる権限を申し込める（§I）。そのときは3つの指標をほぼ自動にできる。

**決めること**：
1. 参考投稿の一覧・詳細に、2つの割合をどう出すか（数字だけか、目安の印も付けるか）。
2. リサーチのガイドの指標①を「フォロワーが少なくても、フォロワーに比べていいね・閲覧が多ければ良い参考」と書き直すか。
3. 審査が通ったあと、自動で取る形に広げるか。

## K. 拡散してほしい投稿に、ほかのユーザーをメンションする（2026-11-05）

2026-11-05に、ユーザーが「拡散してほしい投稿に、メンション（@ほかのユーザー）できる機能がほしい」と挙げた。中身・時期・作るかどうかはまだ決めていない。

**分かっていること（2026-11-05に調べた範囲。仕様にする前にMetaの公式の説明で確かめる）**：
- Threads APIで投稿するとき、本文に `@ユーザー名` を書けばメンションになり、相手に通知が届く（外部の投稿サービスの説明）。
- 相手のプライバシーの設定でメンションを受けない人だと、投稿はされるが「@」が付かない（同上）。
- 本文は500文字までで、メンションの文字も数える。1つの投稿でメンションできる人数の上限は、公式の数を確かめていない。
- 今の流れ（外のAIが作った文を貼る → 承認 → 自動で投稿）でも、本文に `@ユーザー名` を書けば、そのまま投稿される。

- 2026-11-05に、023として仕様にした（[specs/023-delayed-mention](../specs/023-delayed-mention/spec.md)）。一覧から選ぶ・承認のときに付ける・時間差はアカウントで1つ・ひとこと＋メンション。
- 023で作ったもの：投稿ストックのカードの「メンションを付ける」（ワンクリック・カードの中で直す・まとめて付ける）、投稿済みの投稿へのあとからのメンション、このアカウントの設定の「時間差のメンション」、5分ごとの処理での返信、返信の権限の見分け。

**近い今の機能**：003（投稿をつくる・プロンプト）、004（承認）、005（自動で投稿）、002の「宣伝内容」（宣伝の投稿）、008・011（チームのメンバー）。

**時間差でメンションしたい（2026-11-05 追記）**：
- 投稿してから時間をおいて、自分の投稿への返信（スレッドの2つ目）で `@ユーザー名` を付ける形を想定する（本文を直すのではない）。
- Threads APIでは、返信も投稿と同じ手順で、返信先の投稿を指定して出せる。仕様にする前に、要る権限（返信の権限など）と、トークンを貼る方法（今の形）でも使えるかを確かめる。
- 今の自動投稿（005）の時刻の仕組み・取り込みの仕組み（006）に、「投稿の〇分後・〇時間後に返信を出す」を足す形になりそう。返信の文も、承認してから出す（原則II）。

**決めること**：
1. 誰をメンションするか（チームのメンバー・協力してくれる人の一覧をAccountごとに持つか、投稿ごとに手で入れるか）。
2. 時間差の決め方（投稿の何分後・何時間後か。決まった値か、投稿ごとに決めるか）。返信の文（メンションだけか、ひとこと添えるか）。
3. どの投稿に付けるか（宣伝の投稿だけか、選んだ投稿か）。
4. 相手の同意：自動投稿で、同意していない人を何度もメンションしないようにする（迷惑・スパムと見られないため。人数と回数の上限）。
5. 投稿の前に、ユーザー名が正しいか（そのユーザーがいるか）を確かめるか。
