## Clarifications

### Session 2026-10-12

- Q:チームはいくつ持てるか？ → A:管理者は複数のチームを持てる（例：チーム1・チーム2）。各チームに、編集者が複数人、メンバーが複数人いる。
- Q:オーナーどうしが投稿・戦略を見られるかは、誰が決めるか？ → A:各オーナーが、自分のアカウントごとに決める。初めは見せない。チーム全体のオン・オフは作らない。
- Q:オーナーはどうチームに入るか？ → A:管理者が送るチームの招待リンクから入る。入るときに、チームに入れる自分のアカウントを選ぶ（LINEグループの招待と同じ）。
- Q:編集者が触れる範囲は？ → A: 008と同じく、管理者が割り当てたアカウントだけ（担当の表）。
- Q:サイドバーには何を出すか？ → A:入っているチームの名前を並べ、押すとそのチームのメンバー一覧が見える。

### Session 2026-10-13

- Q:チームに入る人は、自分のアカウントを持つ必要があるか？ → A:はい。1人1Threadsアカウントは必須（管理者を含む）。チームに入るときは、自分のアカウントを必ず1つ以上入れる。008の「アカウントを持たない編集者」はいなくなる。
- Q:ロールは何を決めるか？ → A:自分のアカウントでは、誰でもそのアカウントのオーナー（承認・設定・接続・支払い）。チームでのロールは「ほかの人のアカウントに何ができるか」を決める。
- Q:ロールの呼び方は？ → A:管理者（チームを作り、招待とロールの切り替えをする。008の「パートナー」）・メンバー（見せてもらったアカウントを読むだけで見る）・編集者（担当のアカウントで投稿の案を作る）。「オーナー」は、アカウントの持ち主だけを指す。
- Q:ロールは入った後に変えられるか？ → A:管理者が、メンバー⇔編集者をいつでも切り替えられる。切り替えても、その人のアカウントの持ち主は変わらない。
- Q: 1つのアカウントを、複数のチームに入れられるか？ → A: 1つのチームだけ（データの持ち方は、複数に広げられる形のまま）。
- Q: 008の「オーナーがアカウントの設定からパートナーを招く」流れはどうするか？ → A:やめて、チームのリンクに一本化する。今の手伝いの関係は消す（下の「008で作った今のチームのデータ」を参照）。
- Q:招待リンクは、ロールごとに分けるか？ → A:チームに1本。入った人は、まずメンバーになり、管理者が後から編集者に切り替える。
- Q:担当にした編集者は、「チームに見せる」がオフのアカウントも開けるか？ → A:開ける（チームに入れたときに、手伝ってもらうことに同意した扱い）。
- Q:見せてもらったアカウントで、何が見られるか？ → A:投稿ストックと戦略だけ。パフォーマンスと設定は見せない。
- Q:抜けるときは？ → A:メンバー・編集者は、いつでも自分で抜けられる。管理者が抜けるとロールの切り替えや招待ができなくなるので、管理者は、管理者を他の人に引き継いでから抜ける（抜けるときの画面でそう案内する）。
- Q:管理者は、チームに入っているほかの人のアカウントで何ができるか？ → A:担当にしたところだけ作れる。管理者も、見せているアカウントは読むだけで、投稿の案を作るには担当の表で自分を担当にする。管理は招待・ロール・担当だけで、ほかの人の事業の情報に勝手に触れない（008のパートナーとの違い）。
- Q: 008の「オーナーが投稿の承認・設定をパートナーに任せる」機能はどうするか？ → A:なくす。承認・設定は、いつもそのアカウントのオーナーだけが行う。今の任せる範囲は、008のチームのデータと一緒に消す。
- Q: 008で作った今のチームのデータは、新しいチームに移すか？ → A:移さずに消す。公開前で、開発・確認用のデータだけのはずなので。アカウントとそのデータ、操作の記録は残す。確認用のチームは`pnpm team:demo`で作り直す。
- Q:サイドバーの構造は？ → A:今の構造（投稿をつくる・ホーム・投稿ストック・戦略・分析・チーム（操作の記録）・このアカウントの設定）のまま、「チーム」の見出しの下にチーム名を並べる。

## 用語

- **アカウント**：Threadsアカウント1件に対応する運用単位（001のAccount）。
- **オーナー**：アカウントの持ち主。そのアカウントの承認・設定・Threadsとの接続・支払いを持つ。チームでのロールに関わらず変わらない。
- **チーム**：管理者が作る人の集まり。チームの名前、招待リンク1本、メンバーの一覧、チームに入っているアカウントを持つ。
- **管理者**：チームを作った人（または引き継いだ人）。1チームに1人。招待、ロールの切り替え、担当の割り当て、メンバーを外すことができる。
- **メンバー**：チームの人のうち、ほかの人が見せているアカウントを読むだけで見る人。招待リンクから入った人は、まずメンバーになる。
- **編集者**：メンバーと同じく見られるうえに、担当になったアカウントで投稿の案・戦略を作る・直す人。承認と設定はできない。
- **チームの人**：管理者・メンバー・編集者のすべて。全員が、自分のアカウントを1つ以上チームに入れている。
- **チームに見せる**：オーナーが、チームに入れた自分のアカウントごとに決める設定。オンのとき、チームの人がそのアカウントの投稿ストックと戦略を読める。
- **担当**：管理者が、編集者ごとに割り当てる、チームの中のアカウント。
- **関わりの名前**：判定と契約では、オーナー＝`owner`、担当の人＝`assigned`、見せてもらっている人＝`shared_viewer`と書く。関わりなしは、どれにも当てはまらないときで、`ACCOUNT_NOT_FOUND`を返す（[contracts/permissions.md](./contracts/permissions.md)）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 -管理者がチームを作り、リンクで人を招く(Priority: P1)

運用代行のA社の田中さんが、「飲食チーム」を作り、招待リンクをカフェB店の鈴木さん、ベーカリーEの山口さん、A社のスタッフの佐藤さんに送る。リンクを開いた人は、チーム名と管理者を確かめ、チームに入れる自分のThreadsアカウントを1つ以上選んで参加する。参加した人はメンバーになる。

**Why this priority**:チームの見直しの中心。これがなければ、ほかの機能（ロール・見せる・担当）が使えない。

**Independent Test**:管理者がチームを作り、リンクを開いた別の人が、自分のアカウントを選んで参加し、管理者のメンバー一覧にメンバーとして出ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 自分のアカウントを1つ以上持つ利用者、**When** サイドバーの「チーム」の下の「チームを作る」で名前を入れて作る、**Then** その人が管理者のチームができ、自分のアカウントを1つ以上チームに入れるよう求められる。入れると、サイドバーの「チーム」の下にチーム名が出る。
2. **Given** 管理者、**When** チームの画面の「メンバーを招待」を開く、**Then** チームに1本の招待リンク、「コピー」、QRコード、「リンクを作り直す」と、「入った人はまずメンバーになる」「入るときに自分のThreadsアカウントを1つ以上入れてもらう」の説明が出る。
3. **Given** 招待リンク、**When** 自分のアカウントを持つ人が開いてログインする、**Then** チーム名・管理者・人数・「メンバーとして入ります」と、できること、チームに入れる自分のアカウントの一覧（選ぶ欄と、アカウントごとの「チームに見せる」。初めはオフ）が出る。1つも選んでいなければ参加できない。
4. **Given** 参加の画面でアカウントを選んだ、**When** 「参加する」を押す、**Then** その人はチームのメンバーになり、選んだアカウントがチームに入る。管理者のメンバー一覧に出る。
5. **Given** 自分のアカウントを1つも持たない人、**When** 招待リンクを開く、**Then** 「先に、自分のThreadsアカウントをつないでください」とアカウントの追加への案内が出て、参加できない。つないだ後にリンクに戻ると、続きから参加できる。
6. **Given** 管理者、**When** 「リンクを作り直す」を押す、**Then** 前のリンクはすぐ使えなくなる。

### User Story 2 -管理者がロールを切り替え、編集者に担当を割り当てる(Priority: P1)

田中さんが、A社の佐藤さんを編集者に切り替え、カフェB店の担当にする。佐藤さんは、カフェB店で投稿の案を作れるようになる。承認は、カフェB店のオーナーの鈴木さんが行う。

**Why this priority**:運用代行の仕事（スタッフが案を作り、お店が承認する）の中心。008の編集者と担当を、新しいチームの形で続ける。

**Independent Test**:管理者がメンバーを編集者に切り替えて担当を付け、その人がそのアカウントで投稿の案を登録でき、承認はできないことを確かめる。

**Acceptance Scenarios**:

1. **Given** 管理者のメンバー一覧、**When** 佐藤さんのロールを「編集者」に切り替える、**Then** すぐ反映され、「担当を決める」の表に佐藤さんが出る。もう一度「メンバー」に戻すと、表から消え、担当もなくなる。
2. **Given** 「担当を決める」の表（チームごと）、**When** 佐藤さんにカフェB店をチェックする、**Then** 佐藤さんはカフェB店で、投稿の案の登録・編集、要確認の案の削除、戦略・改善メモの編集、パフォーマンスとCSVの書き出しができる（008の編集者と同じ）。承認・却下と設定はできない。
3. **Given** 表、**When** 列を見る、**Then** そのチームに入っているアカウントが並び、編集者自身のアカウントの列は「自分」と出てチェックできない。
4. **Given** 鈴木さんがカフェB店を「チームに見せる」をオフにしている、**When** 担当の佐藤さんがカフェB店を開く、**Then** 開ける（担当なので）。
5. **Given** 管理者でない人、**When** ロールの切り替え・担当の表を開こうとする、**Then** 操作は出ず、要求も拒まれる。

### User Story 3 -オーナーがアカウントを見せ、チームの人が読むだけで見る(Priority: P1)

鈴木さんが、カフェB店を「チームに見せる」にする。同じチームの山口さん（メンバー）は、カフェB店の投稿ストックと戦略を読めるので、自分のお店の投稿の参考にできる。山口さんはベーカリーEを見せていないので、ほかの人には名前だけが出る。

**Why this priority**: LINEグループのように、お互いの取り組みを見て学べることが、今回の見直しの目的。オーナーの事業の情報なので、見せるかどうかはオーナー本人が決める。

**Independent Test**:オーナーがアカウントを見せる・見せないを切り替え、同じチームのメンバーが、見せているときだけ投稿ストックと戦略を読め、直す操作が出ないことを確かめる。

**Acceptance Scenarios**:

1. **Given** チームに入れたアカウント、**When** オーナーが、チームの画面（または、このアカウントの設定）で「チームに見せる」をオンにする、**Then** 同じチームの人の一覧で、そのアカウントに「見る」が付く。
2. **Given** 見せているアカウント、**When** 同じチームのメンバーが「見る」で開く、**Then** 上部に「（名前）さんのアカウントを見ています（読むだけ）」と出て、投稿ストックと戦略だけを読める。承認・編集・削除・貼り付けの操作は出ない。パフォーマンス・設定・操作の記録は見られない。
3. **Given** 見せていないアカウント、**When** 同じチームの人が一覧を見る、**Then** アカウント名と「見せていません」だけが出て、開けない（担当の編集者を除く）。
4. **Given** 見せていたアカウント、**When** オーナーがオフにする、**Then** 次の要求から、チームの人（担当の編集者を除く）は開けなくなる。
5. **Given** 別のチームの人、**When** そのアカウントを開こうとする、**Then** 見せていても開けない。

### User Story 4 -サイドバーでチームを見る(Priority: P2)

チームに入っている人は、サイドバーの「チーム」の見出しの下でチーム名を見て、押すとそのチームのメンバー一覧を開ける。管理者は複数のチームを切り替えられる。

**Why this priority**:誰がどのチームにいるかがいつでも分かると、チームの使い方（見せる・頼む）が分かりやすい。

**Independent Test**: 2つのチームの管理者と、1つのチームのメンバーで、サイドバーのチーム名と、押したときのメンバー一覧を確かめる。個人運用の人には出ないことを確かめる。

**Acceptance Scenarios**:

1. **Given** チームに入っている人、**When** サイドバーを見る、**Then** 今の構造のまま、「チーム」の見出しの下に、入っているチームの名前（人数つき）が並び、その下に今までどおり「操作の記録」がある（008の条件のまま）。管理者には「チームを作る」も出る。
2. **Given** チーム名、**When** 押す、**Then** そのチームのメンバー一覧が出る：管理者・メンバー・編集者ごとの名前とロール、チームに入れているアカウント（見せている／見せていない）。見ている人には「あなた」の印が付く。管理者には、ロールの切り替え・招待・担当・外す操作も出る。
3. **Given** チームに入っていない人（個人運用のオーナー）、**When** サイドバーを見る、**Then** チーム名は出ない（今と同じ）。
4. **Given** スマートフォン、**When** 引き出しを開く、**Then** 同じ並びで、チーム名が出る。

### User Story 5 -抜ける・外す・管理者を引き継ぐ(Priority: P2)

山口さんはチームを抜けられる。田中さんはメンバーを外せる。田中さんがチームを抜けたいときは、先に管理者を鈴木さんに引き継ぐ。

**Why this priority**:人の出入りは必ず起きる。管理者がいないチームは、招待もロールの切り替えもできなくなるので、引き継ぎを必ず挟む。

**Independent Test**:メンバーが抜ける、管理者がメンバーを外す、管理者が引き継いでから抜ける、の3つで、アカウントと記録が残ることを確かめる。

**Acceptance Scenarios**:

1. **Given** メンバー・編集者、**When** 「チームを抜ける」を押して確かめる、**Then** その人と、その人のアカウントがチームから外れる。その人の担当はなくなる。その人が担当していたアカウントの記録は残る。
2. **Given** 管理者、**When** メンバー一覧の「⋯」から「チームから外す」を確かめる、**Then** 1と同じく外れる。
3. **Given** 管理者、**When** 「チームを抜ける」を押す、**Then** 「管理者がいなくなると、ロールの切り替えや招待ができなくなるので、抜ける前に管理者を引き継ぐ人を選んでください」と出て、新しい管理者を選ぶまで「引き継いで抜ける」を押せない。押すと、選んだ人が管理者になり、自分は抜ける。
4. **Given** 管理者のほかに誰もいないチーム、**When** 管理者が抜けようとする、**Then** 「チームを削除する」を案内する（チームの人がいなくなるので）。
5. **Given** チームから外れたアカウント、**When** オーナーが開く、**Then** 自分のアカウントとして、データ（戦略・投稿ストック・設定・記録）はそのまま残っている。

---

### Edge Cases

- **同じ人が複数のチームに入る**：アカウントごとに1つのチームなので、別のアカウントなら別のチームに入れる。同じアカウントを2つ目のチームに入れようとしたら、「このアカウントは、すでに（チーム名）に入っています」と止める。
- **入れたアカウントを全部外そうとする**：チームの人は自分のアカウントを1つ以上入れている必要がある。最後の1つは外せず、「チームを抜ける」を案内する。
- **入れたアカウントを削除・要再接続になる**：削除されたらチームからも外れる。最後の1つが削除されたら、その人もチームを抜ける。要再接続はチームに残る。
- **管理者が自分を編集者・メンバーに切り替える**：できない（管理者は引き継ぎでだけ替わる）。
- **管理者の引き継ぎ先**：チームの人（メンバー・編集者）の中から選ぶ。引き継がれた人・前の管理者の担当は、そのまま残る。
- **同時の操作**：同じ人のロールの切り替えと外す操作が同時に来ても、結果は一つに決まる。同じリンクで同時に参加しても、同じ人は1回だけ入る。
- **見せている間に、ほかの人が抜ける・外れる**：次の要求から見られなくなる。
- **担当のアカウントが見せるをオフにした**：担当の編集者は引き続き開ける（Clarifications）。
- **メンバーが編集者になったときに見られる範囲**：見せているアカウント（読むだけ）に加えて、担当のアカウント（作る・直す）。
- **招待リンクの人数**：1チームの編集者は10人まで（008のまま）。メンバーの上限は50人（`[ASSUMPTION]`）。上限に達したら参加の画面で止める。
- **ログイン後の最初の画面**：自分のアカウントを必ず持つので、008 FR-045の「手伝い先しかない人」はいなくなる。最後に開いた自分のアカウントか、担当のアカウントを開く。
- **見せてもらったアカウントをメンバーが開いているときに、オーナーが投稿を承認する**：読むだけの画面は、開き直すと新しい内容になる（自動で更新しなくてよい）。

## Requirements *(mandatory)*

### Functional Requirements

#### ロールと判定

- **FR-001**: System MUST アカウントごとに、利用者の関わりを決める：そのアカウントのオーナー、そのアカウントが入っているチームの管理者・編集者（担当あり・なし）・メンバー、関わりなし。
- **FR-002**: System MUST 関わりごとにできる操作を、次の表のとおりにする。

  | 操作 | オーナー | 担当の人（編集者・自分を担当にした管理者） | チームの人（見せている） | 見せていない・関わりなし |
  |---|---|---|---|---|
  | 投稿ストック・戦略を見る | ○ | ○ | ○（読むだけ） | ✕ |
  | パフォーマンス・CSV | ○ | ○ | ✕ | ✕ |
  | 投稿の案・戦略・改善メモを作る・直す、要確認の案を消す | ○ | ○ | ✕ | ✕ |
  | 承認・却下 | ○ | ✕ | ✕ | ✕ |
  | 自動投稿・NGワード・投稿のルールの設定 | ○ | ✕ | ✕ | ✕ |
  | 設定を見る（読むだけ） | ○ | ○ | ✕ | ✕ |
  | 操作の記録 | ○ | 管理者だけ○ | ✕ | ✕ |
  | Threadsとの接続、アカウントの削除、チームに見せる | ○ | ✕ | ✕ | ✕ |

  管理者は、自分のアカウント以外では、ほかのチームの人と同じ扱いにする。担当の表で自分を担当にしたアカウントでだけ、担当の人の操作ができる。承認・設定は、いつもそのアカウントのオーナーだけが行う（008の任せる範囲はなくす。FR-060）。

- **FR-003**: System MUST FR-002の判定を、008と同じく1か所で行い、すべての読み取り・書き込みの要求で通す。画面で操作を隠すだけで済ませない（Constitution原則V）。
- **FR-004**: System MUST 関わりの変化（ロールの切り替え・担当・見せる設定・抜ける・外す・引き継ぐ・リンクの作り直し）を、次の要求から反映する。
- **FR-005**: System MUST どの関わりでも、NGワードのチェック（原則I）と人による承認（原則II）を省かない。
- **FR-006**: System MUST チームに入っていないアカウント（個人運用）では、オーナーの画面と操作を、008の前と同じにする（原則V）。例外は「このアカウントの設定」のチームの区分の1行（「チームに入っていません」と「チームを作る」）だけ（Constitution 4.0.1原則V）。008の「運用を手伝ってもらう」の区分は、チームに入っていなければ出さない。

#### チームと招待

- **FR-010**: Users MUST be able to 自分のアカウントを1つ以上持つ利用者として、「チームを作る」でチーム（名前は50文字まで）を作る。作った人がそのチームの管理者になり、自分のアカウントを1つ以上チームに入れる。1人が作れるチームの数は20まで（`[ASSUMPTION]`）。
- **FR-011**: System MUST チームごとに、招待リンクを1本持つ。管理者はいつでも表示・コピーし、QRコードを出し、「リンクを作り直す」で前のリンクを使えなくできる。期限は設けない。
- **FR-012**: System MUST 招待リンクを開いた人に、チーム名・管理者の名前・人数・「メンバーとして入ります」と、できること（ほかの人が見せているアカウントの投稿ストックと戦略を読める、管理者が編集者にすることがある、自分のアカウントの承認・設定・支払いは自分だけ）を示す確認の画面を出す。ログインしていなければログインを求める。
- **FR-013**: System MUST 確認の画面で、チームに入れる自分のアカウントを選ばせる（1つ以上。ほかのチームに入っているアカウントは選べない）。アカウントごとに「チームに見せる」を選べ、初めはオフにする。1つも選んでいなければ参加させない。
- **FR-014**: System MUST 自分のアカウントを1つも持たない人には、参加させず、アカウントの追加へ案内する。つないだ後にリンクを開き直すと、続きから参加できるようにする。（012で改めた：「自分のアカウントを1つも持たない人」は「Threadsにつないだアカウントを1つも持たない人」と読み替える。未接続のアカウントはチームに入れない。[012 FR-050〜FR-052](../012-accounts-before-connect/spec.md)）
- **FR-015**: System MUST 参加した人をメンバーにし、選んだアカウントをチームに入れる。同じ人の同時の参加でも、1回だけ入る。
- **FR-016**: System MUST 使えないリンク（作り直された・チームが削除された・上限に達した）を開いた人に、理由と、管理者に新しいリンクを頼む案内を出し、参加させない。
- **FR-017**: System MUST 管理者に、チーム名を直す・チームを削除する操作を許す。チームを削除すると、チームの人とアカウントはすべてチームから外れ、アカウントのデータと記録は残る。

#### ロールの切り替えと担当

- **FR-020**: Users MUST be able to 管理者として、チームの人（自分以外）のロールを、メンバー⇔編集者にいつでも切り替える。
- **FR-021**: System MUST 編集者からメンバーに戻したときは、その人の担当をすべてなくす。
- **FR-022**: Users MUST be able to 管理者として、チームごとの「担当を決める」の表で、編集者と自分（管理者）ごとに担当をチェックで付け外しする。表の列は、そのチームに入っているアカウント。その人自身のアカウントの列は「自分」と出してチェックさせない。1チームの編集者は10人まで（008のまま）。
- **FR-023**: System MUST 担当のアカウントでは、「チームに見せる」に関わらず、その人（編集者・自分を担当にした管理者）にFR-002の担当の人の操作を許す。
- **FR-024**: System MUST ロールの切り替え・担当・招待・外す・チーム名の変更・チームの削除を、管理者だけに許す。

#### チームに見せる

- **FR-030**: Users MUST be able to オーナーとして、チームに入れた自分のアカウントごとに「チームに見せる」をオン・オフする。チームの画面と「このアカウントの設定」の両方から変えられる。初めはオフ。
- **FR-031**: System MUST 「チームに見せる」がオンのアカウントを、同じチームの人に、投稿ストックと戦略だけ読むだけで見せる。上部に「（名前）さんのアカウントを見ています（読むだけ）・（チーム名）」と「チームに戻る」を出す。承認・編集・削除・貼り付けの操作は出さない。パフォーマンス・設定・操作の記録は見せない。
- **FR-032**: System MUST 「チームに見せる」がオフのアカウントは、同じチームの人（そのアカウントの担当の人を除く）にはアカウント名と「見せていません」だけを示し、開けないようにする。
- **FR-033**: System MUST 別のチームの人・関わりのない人には、見せる設定に関わらず、アカウントを見せない。

#### 抜ける・外す・引き継ぐ

- **FR-040**: Users MUST be able to メンバー・編集者として、チームの画面の「チームを抜ける」から、確認の後にチームを抜ける。
- **FR-041**: Users MUST be able to 管理者として、チームの人（自分以外）を、確認の後にチームから外す。
- **FR-042**: System MUST 抜けた・外れた人のアカウントをチームから外し、その人の担当と、その人のアカウントでのほかの人の担当をなくす。アカウントのデータ（戦略・投稿ストック・設定・記録）はオーナーのものとして残す。
- **FR-043**: System MUST 管理者が抜けるときは、抜ける前に、チームの人の中から新しい管理者を選ばせる。確認の画面で「管理者がいなくなると、ロールの切り替えや招待ができなくなるので、抜ける前に管理者を引き継ぐ人を選んでください」と出し、選ぶまで「引き継いで抜ける」を押せないようにする。管理者のほかに誰もいなければ、チームの削除を案内する。
- **FR-044**: Users MUST be able to 管理者として、抜けずに管理者だけを引き継ぐ（チームに残り、担当が1件以上あれば編集者、なければメンバーになる。担当はそのまま）。
- **FR-045**: System MUST 管理者は1チームに1人にする。引き継いでも、担当はそのまま残す。同時の引き継ぎでも、管理者は1人に決まる。
- **FR-046**: System MUST チームの人が、入れているアカウントの最後の1つをチームから外すことを止め、「チームを抜ける」を案内する。最後の1つのアカウントが削除されたら、その人はチームを抜けたものとする（管理者なら、ほかの人がいれば、いちばん長くいる人を管理者にし、いなければチームを削除する）。

#### 画面

- **FR-050**: System MUST サイドバーの構造を今のまま保ち、チームに入っている人には、見出し「チーム」の下に、入っているチームの名前と人数を並べる。その下の「操作の記録」は008の条件のまま出す。管理者には「チームを作る」も出す。チームに入っていない人には、チーム名も「チームを作る」も出さない（原則V）。スマートフォンの引き出しも同じ並びにする。
- **FR-051**: System MUST チーム名を押すと、そのチームの画面（メンバー一覧）を出す：管理者・メンバー・編集者ごとの名前とロール、チームに入れているアカウントと見せる状態、見ている人の「あなた」の印。見せているアカウントには「見る」を付ける。
- **FR-052**: System MUST 管理者のチームの画面に、ロールの切り替え（メンバー⇔編集者）、「メンバーを招待」、「担当を決める」、「⋯」の「チームから外す」、「チームを抜ける」を出す。ロールの説明（メンバー・編集者ができること）を添える。
- **FR-053**: System MUST メンバー・編集者のチームの画面に、自分がチームに入れているアカウントと「チームに見せる」のスイッチ、メンバー一覧、「チームを抜ける」を出す。
- **FR-054**: System MUST 切り替えメニューは、自分のアカウントの一覧に加えて、担当のアカウント（オーナー名つき）を「担当しているアカウント」として分けて出す。見せてもらっているアカウントは切り替えメニューには出さず、チームの画面から開く。
- **FR-055**: System MUST 009の「このアカウントのチーム」のカードを、そのアカウントが入っているチームの名前、管理者、そのアカウントの担当の編集者に改める。チームに入っていなければ出さない。
- **FR-056**: System MUST 008の役割の図（FR-048）とdocs/team-roles.mdを、管理者・メンバー・編集者とオーナー（アカウントの持ち主）の関係に改める。

#### 承認・記録・知らせ

- **FR-060**: System MUST 008の「承認・設定を任せる」機能（008 FR-030〜FR-033）をなくし、承認・却下と設定を、いつもそのアカウントのオーナーだけに許す。任せる範囲のスイッチは「このアカウントの設定」から消す。
- **FR-061**: System MUST 操作の記録（008 FR-050〜FR-054）に、チームの操作（作る・名前を変える・削除する・参加・抜ける・外す・ロールの切り替え・担当の付け外し・引き継ぎ・見せる設定の変更）を加える。チームに入っているアカウントについての操作は、そのアカウントの記録に残す。
- **FR-062**: System MUST アプリ内の知らせを、008 FR-047の考え方のまま必要なものに限る：(1) 管理者に、新しい人が参加したとき、チームの画面に1回、(2) 編集者に、担当が付いたとき、ホームに1回。通知の一覧（ベル）は作らない。

#### 008のデータと文書

- **FR-070**: System MUST 008のチームのデータ（パートナーの手伝いの関係、パートナーのチーム、編集者、担当、任せる範囲、招待リンク、参加の知らせ）を移さずに消す。アカウントとそのデータ（戦略・投稿ストック・設定）と、操作の記録は残す。
- **FR-072**: System MUST 008の「オーナーがアカウントの設定からパートナーを招く」流れ（008 FR-010〜FR-017）と、編集者の招待リンク（008 FR-020〜FR-022・FR-026）をやめ、チームの招待リンクに一本化する。
- **FR-073**: System MUST Constitutionを、原則IV（ロールの付け方：チームの管理者が招待リンクで招き、ロールを切り替える。誰でも自分のアカウントのオーナー）と原則V（チーム運用の範囲：複数のチーム、見せる設定、管理者の引き継ぎ。決済は番号でなく「最後のfeature」）について改め、MAJORの版（4.0.0）を上げる。PRD §4.7 FR-13を、本featureの形に書き直す。どちらも計画（`/speckit-plan`）の前に行う。

### Key Entities *(include if feature involves data)*

- **チーム**：名前、管理者（1人）、招待リンク（1本）、作った日時。1人が複数のチームの管理者になれる。
- **チームの人**：チームと利用者の関係。ロール（管理者・メンバー・編集者）、参加した日時。1人が複数のチームの人になれる。
- **チームに入っているアカウント**：チームとアカウントの関係。「チームに見せる」の設定、入れた日時。1つのアカウントは1つのチームにだけ入る（データの持ち方は、複数に広げられる形のまま）。
- **担当**：編集者とアカウントの関係（008のまま、チームの中だけ）。
- **操作の記録**：008のまま、チームの操作の種類を足す。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**:自分のアカウントを持つ人が、招待リンクを開いてから1分以内に、アカウントを選んでチームに入れる。
- **SC-002**: FR-002の表のすべての組み合わせ（関わり4種×操作8種）で、許されない要求が100%拒まれる（自動テストで確かめる）。
- **SC-003**:「チームに見せる」をオフにしたアカウントは、そのアカウントの担当の人を除くチームの人（管理者を含む）から、次の要求で開けなくなる（自動テスト）。別のチームの人からは、見せる設定に関わらず開けない。
- **SC-004**:管理者がいないチームが、どの操作の順番でも生まれない（引き継ぎ・抜ける・アカウントの削除の組み合わせの自動テスト）。
- **SC-005**:個人運用のオーナーの画面と操作の数が、008の前と同じ（自動テストで確かめる）。
- **SC-006**: 008のチームのデータを消した後も、アカウントのデータ（戦略・投稿ストック・設定）と操作の記録が1件も失われない（自動テストで、消す前後の件数を比べる）。
- **SC-007**: 3人のブラウザでの流れ（管理者がチームを作って招く → 2人が参加 → 1人を編集者にして担当 → オーナーが見せる → メンバーが読む → 管理者が引き継いで抜ける）が、自動のE2Eで通る。

## Assumptions

- 1チームの編集者の上限は10人（008のまま）。メンバーの上限は50人、1人が作れるチームは20まで（`[ASSUMPTION]`。013の決済で見直す）。
- 公開前のため、008のチームのデータは開発・確認用のものだけのはず。移さずに消す（Clarifications）。
- 料金は、本featureでは求めない（008 FR-080と同じ）。013の決済で、オーナーの契約の状態による制限（未払いならチームの人もそのアカウントでは読むだけ）を、FR-003の判定に足せる形にしておく。
- 見せてもらったアカウントの読むだけの画面は、自動で更新しない（開き直すと新しい内容）。
- 012（アカウントを先に作る）で、Threadsにつながっていないアカウントでチームに入れるかを決める。本featureでは、Threadsにつながったアカウントだけを「自分のアカウント」として数える。
