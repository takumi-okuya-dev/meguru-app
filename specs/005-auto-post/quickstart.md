# 動作確認ガイド（Quickstart）：スケジュール投稿・自動投稿

**対象feature**：[spec.md](./spec.md) ／ **契約**：[contracts/api.md](./contracts/api.md)、[contracts/auto-post-job.md](./contracts/auto-post-job.md)、[contracts/ui-routes.md](./contracts/ui-routes.md)、[contracts/prompt-template.md](./contracts/prompt-template.md)

本featureが端から端まで動くことを確かめる手順。実装コードは含めない。

## 前提

- 004までのセットアップ（[004 quickstart.md](../004-review-approval/quickstart.md)）が済んでいる。
- 本featureはThreadsへ実際に投稿する。ふだんの確認は、偽のThreadsサーバー（`pnpm dev:fake`）で行う。本物のThreadsでの確認（下の「6」）は、テスター招待したアカウントで最後に1回だけ行う。
- 定期処理は、`wrangler dev`では自動で動かない。下のURLで1回ずつ呼ぶ（`wrangler dev`がこのURLを用意している。起動のオプションは要らない）。

## セットアップ

```bash
pnpm install
docker compose up -d
pnpm --filter api db:migrate        # 0005_auto_post.sql（列挙型・設定・投稿の試み・下書きの列）
pnpm dev:fake
```

定期処理を1回動かす（5分ごとのCronと同じ処理）：

```bash
curl "http://localhost:8787/cdn-cgi/local/scheduled?cron=*/5+*+*+*+*"
```

- KV（`AUTOPOST_KV`）は、`wrangler dev`のローカルのKVを使う。関所で止まって何もしないときは、ログに`auto-post: gate closed`が出る。
- 予定の時刻を待たずに確かめるには、設定の時刻を「今の数分前」にして保存する。ただし保存した時刻より後の時刻しか投稿しないので（FR-012）、「数分後」に設定し、その時刻を過ぎてから定期処理を呼ぶ。「時刻を少しずらす」はオフにしておく。

## 手動の確認

`pnpm dev:fake`で起動した画面で確かめる。004の手順で、承認済みの下書きを5件ほど用意しておく。

### 1. 設定（US1）

1. 「このアカウントの設定」を開き、「投稿のスケジュール」の「編集」を押す。
2. 時刻を「今から5分後」「今から40分後」「21:00」の3つ足す。「時刻を少しずらす」をオフにし、自動投稿をオンにして保存する。
3. **期待**：区分に「1日3件」と出る。通知に次の投稿の予定が出る。2分以内に終えられる（SC-007）。
4. 「時刻を少しずらす」をオンにすると、5分後と40分後の間が35分なので保存できる。間が29分の時刻を足すと、検証の文言が出る。
5. 「接続を確かめる」を押すと、「投稿できる状態です（直近24時間の投稿 0/250件）」と出る。
6. 偽のThreadsの`/__control/publish-permission`で投稿の権限をなくしてから、オフ → オンにして保存すると、オンにならず「Threadsへの投稿の権限がありません…」と「再接続」が出る。権限を戻して保存し直すと、オンになる。

### 2. 予定の表示（US4）

1. 投稿ストックの承認済みのタブを開く。
2. **期待**：承認した古い順に並び、先頭から「今日 {5分後}」「今日 {40分後}」「今日 21:00」「明日 …」の予定が出る。
3. 4番目の「⋯」から「次に投稿する」を選ぶと、先頭に移り、予定が1つずつずれる。
4. ホームを開くと「次の投稿」のカードに、同じ予定と本文の書き出し、「承認済み 5件・あと1日分」が出る。

### 3. 自動投稿（US1・US2）

1. 予定の時刻を過ぎてから、定期処理を呼ぶ（`curl`）。
2. **期待**：先頭の1件だけが投稿済みのタブに移り、「Threadsで開く」がある（偽のThreadsのURL）。承認済みは1件減る。
3. 直前のチェック：画面からはNGワードを含む承認済みを作れない（NGワードを足すと004の処理で要確認に戻る）。そこで、DBで先頭の承認済みの下書きの本文を、登録済みのNGワードを含むものに書き換えてから、次の時刻に定期処理を呼ぶ。
4. **期待**：その下書きは要確認に戻り、要確認のタブに理由が出る。同じ時刻に次の下書きが投稿される。投稿ストックとホームに知らせが出て、「閉じる」で消える。

### 4. 失敗とやり直し（US3）

1. 偽のThreadsの`/__control/publish-failures`で、公開を「一時的な失敗」10回にする。
2. 時刻を過ぎてから、定期処理を5分ごとに4回呼ぶ（テストでは`now`を進める。手動では`curl`を4回呼び、`publish_attempts.next_retry_at`をDBで今に書き換える）。
3. **期待**：持ち越しになり、承認済みのタブの先頭のカードに「前回の投稿に失敗したため、次の時刻にもう一度試します」と出る。
4. 次の時刻でも失敗させると「投稿に失敗」になり、承認済みのタブの先頭のまとまりと、ホームの知らせに出る。
5. 「もう一度投稿の順に入れる」を押し、失敗の注入を止めて、次の時刻に投稿されることを確かめる。

### 5. 要再接続と上限（US3）

1. 偽のThreadsの`/__control/invalidate`でトークンを無効にし、時刻を過ぎてから定期処理を呼ぶ。
2. **期待**：Accountが要再接続になり、知らせ「Threadsとの接続が切れているため、自動投稿を止めています」が出る。下書きは承認済みのまま。
3. 再接続した後、再接続より前の時刻は投稿されず、次の時刻から投稿される。
4. `/__control/publish-failures`で上限のエラー（コード4）を注入すると、「今日の投稿を止めました」の知らせが出て、翌日の最初の時刻まで投稿されない。

### 6. 本物のThreadsでの確認（1回だけ）

1. `pnpm dev`（本物のThreads。001のCloudflare Tunnelの手順）で、テスター招待したアカウントを接続する。
2. 承認済みの下書きを1件にし、数分後の時刻を1つだけ設定してオンにする。オンにする保存で、投稿の権限の確認（`threads_publishing_limit`）が通ることも確かめる。権限のないアカウント（または権限を外して再接続したアカウント）で、Threadsが返すエラーコードを記録し、research.md R15に書き足す。
3. 時刻を過ぎてから定期処理を呼ぶ。
4. **期待**：Threadsのアプリにその本文の投稿が1件だけ出る。投稿済みのタブの「Threadsで開く」で、その投稿が開く。
5. 確認した後、自動投稿をオフにし、Threads上のテストの投稿は手で消す。

### 7. 費用と制限の確認（デプロイの後。その後は週に1回）

Neonは、計算時間か通信量を使い切ると翌月までDBが止まり、アプリ全体が使えなくなる（research.md R14）。止まる前に気づけるよう、次を見る。

1. Cloudflareのダッシュボードで、5分ごとのCronの呼び出しのCPU時間を見る。**期待**：投稿のない回は1ms前後、投稿のある回も10ms未満（research.md R3）。
2. Neonのダッシュボードで、月の計算時間（CU-hours）と通信量（Network transfer）を見る。**期待**：月末までの見込みが、計算時間100 CU-hours・通信量5GBの8割未満であること。
   - 計算時間：投稿の時刻の前後と、画面を使った時間だけ動いていること（深夜に動き続けていないこと）。
   - 8割を超えそうなら、R14の「一覧の読み直しを減らす」修正か、Neonの有料プランへの切り替えを検討する。
3. KVの1日の書き込みの回数が、1,000回よりかなり少ないこと。
4. Workersのログで、`auto-post: late publish`・`auto-post: slots expired`の`warn`がないこと。続けて出るなら、Workers Paid（月$5）へ移す時期（research.md R3「既知の限界」）。
