# Feature Specification:運営者がすべてのアカウントを接続方法ごとに確かめられる一覧

**Feature Branch**: `feature/026-operator-accounts`

**Created**: 2026-11-09

**Status**: Draft

**Input**: 2026-11-09、024・025をテスト版で確かめたとき、つながっているアカウントが接続方法によって運営者の画面に出たり出なかったりして、わかりにくかった。トークンでつないだアカウントは運営者の画面のどこにも出ない。「テスター招待」には、申し込みの記録があるアカウントしか出ない。そこで、設定の「運営」に新しい区分を足し、すべてのアカウントを、つなぐ前のものも含めて一覧にする。1行に、アカウントの名前・@ユーザー名・接続方法（Threadsで許可する／トークン／つなぐ前）・接続の状態（接続中／要再接続／つなぐ前）・オーナー・テスター招待の状態（あれば）を出す。接続方法で絞り込め、それぞれの件数がわかる。運営者だけが見られ、見るだけで操作はしない（招待の操作は「テスター招待」のまま）。

**Source**: [010のspec](../010-token-account-add/spec.md)（トークンでつなぐ）、[012のspec](../012-accounts-before-connect/spec.md)（つなぐ前のアカウント）、[016のspec](../016-test-groups/spec.md)・[019のspec](../019-feature-switches/spec.md)（設定の「運営」）、[024のspec](../024-tester-invite-connect/spec.md)（テスター招待・上限）、[docs/ui-design.md](../../docs/ui-design.md)、[Constitution](../../.specify/memory/constitution.md) 4.4.0 原則IV・V。

## Clarifications

### Session 2026-11-09

- Q:名前・@ユーザー名・オーナーのメールアドレスの一部で探せる検索欄（US3）も付けるか？ → A:付ける。接続方法の絞り込みと合わせて使える（FR-010・FR-011）。
- Q:設定の「運営」に足す区分の名前は？ → A:「アカウント一覧」。「個人設定」の「アカウント」（自分のGoogleアカウント）と区別する（FR-001）。
- Q:1人が複数のアカウントを持つとき、どう出すか？ → A:アカウント1件を1行のまま、オーナーの名前の横に、その人が持つアカウントの数（「（3件）」）を添える。まとめて見るときは検索でその人に絞る（FR-003・FR-014）。

## 用語

- **アカウント**：このアプリで運用するThreadsアカウントの単位（Account）。つなぐ前のものも含む。
- **接続方法**：アカウントがThreadsとどうつながっているか。「Threadsで許可する」（このアプリのMetaアプリで許可）、「トークン」（自分のMetaアプリのトークンを貼り付け）、「つなぐ前」の3つ。
- **接続の状態**：「接続中」「要再接続」「つなぐ前」の3つ。
- **テスター招待の状態**：そのアカウントの申し込みの記録の状態（申し込み中・招待済み・接続済み・外してよい）。記録がなければ出さない。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - すべてのアカウントを1つの一覧で見る（Priority: P1）

運営者が設定の「運営」の新しい区分を開くと、このアプリのすべてのアカウントが、つなぐ前のものも含めて一覧で出る。1行で、アカウントの名前・@ユーザー名・接続方法・接続の状態・オーナー・テスター招待の状態がわかる。運営者は、どのアカウントがどの方法でつながっているかを、ほかの画面を回らずに確かめられる。

**Why this priority**：今は、トークンでつないだアカウントが運営者の画面に出ず、接続の全体がわからない。一覧があれば、テスターの枠の確認や問い合わせへの対応で迷わない。

**Independent Test**：「Threadsで許可する」・トークン・つなぐ前のアカウントを1件ずつ用意し、運営者が一覧を開くと3件とも出て、それぞれの接続方法・接続の状態・オーナー・テスター招待の状態が正しく出ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 「Threadsで許可する」でつながったアカウント（@taku.it.ai、テスター招待は接続済み）、**When** 運営者が一覧を開く、**Then** その行に、アカウントの名前・@taku.it.ai・「Threadsで許可する」・「接続中」・オーナーの名前とメールアドレス・「接続済み」が出る。
2. **Given** トークンでつながり、要再接続になったアカウント（@cafe_b、申し込みの記録なし）、**When** 運営者が一覧を開く、**Then** その行に「トークン」・「要再接続」が出て、テスター招待の状態は出ない。
3. **Given** つなぐ前のアカウント（申し込み中）、**When** 運営者が一覧を開く、**Then** その行に、@ユーザー名の代わりに「未接続」・「つなぐ前」・「申し込み中」が出る。
4. **Given** 運営者でない人、**When** その区分のURLを直接開く、**Then** 一覧は出ず、「この画面は運営者だけが使えます。」が出る（今の運営の区分と同じ扱い）。
5. **Given** 1人のオーナーがアカウントを2件持つ（「Threadsで許可する」とトークン）、**When** 運営者が一覧を開く、**Then** 2件はそれぞれ別の行に出て、どちらの行にもオーナーの名前の横に「（2件）」が出る。

---

### User Story 2 - 接続方法で絞り込み、件数を知る（Priority: P1）

一覧の上に、接続方法ごとの絞り込み（すべて・Threadsで許可する・トークン・つなぐ前）があり、それぞれの件数が出る。運営者は、たとえば「トークンでつないでいるのは何件、どのアカウントか」をすぐ確かめられる。

**Why this priority**：接続方法ごとの数がわからないことが、今わかりにくい点そのもの。テスターの枠（Threadsで許可する）の数を確かめるのにも使う。

**Independent Test**：接続方法の違うアカウントを数件ずつ用意し、絞り込みのそれぞれの件数が実際の数と合うこと、絞り込むとその方法のアカウントだけが出ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 「Threadsで許可する」3件・トークン2件・つなぐ前1件、**When** 運営者が一覧を開く、**Then** 絞り込みに「すべて 6」「Threadsで許可する 3」「トークン 2」「つなぐ前 1」が出て、初めは「すべて」が選ばれている。
2. **Given** 上の一覧、**When** 運営者が「トークン」を選ぶ、**Then** トークンの2件だけが出る。
3. **Given** 要再接続のアカウント、**When** 件数を数える、**Then** 接続方法（Threadsで許可する・トークン）の側に数える（要再接続は接続の状態で、接続方法ではない）。

---

### User Story 3 - 名前やメールアドレスで探す（Priority: P2）

一覧の上の検索欄に、アカウントの名前・@ユーザー名・オーナーの名前・オーナーのメールアドレスの一部を入れると、合うアカウントだけに絞られる。接続方法の絞り込みと合わせて使える。

**Why this priority**：問い合わせで「@〇〇がつながらない」と言われたときに、その1件をすぐ見つけたい。件数が少ないうちは一覧を見ればわかるので、P2にする。

**Independent Test**：数件のアカウントがある状態で、@ユーザー名の一部・オーナーのメールアドレスの一部で検索し、合うものだけが出ることを確かめる。

**Acceptance Scenarios**:

1. **Given** @taku.it.ai と @cafe_b のアカウント、**When** 運営者が「taku」と入れる、**Then** @taku.it.ai の行だけが出る。
2. **Given** 「トークン」を選んだ状態、**When** 運営者がオーナーのメールアドレスの一部を入れる、**Then** トークンでつながっていて、そのオーナーのアカウントだけが出る。
3. **Given** 合うアカウントがない検索語、**When** 運営者が入れる、**Then** 「ありません」と出る。

---

### Edge Cases

- オーナーが退会した → 退会でそのアカウントは消える（今の扱いのまま）ので、一覧にも出ない。
- 1つのアカウントにチームの人がいる → オーナーだけを出す（チームの人は出さない）。
- 1人が複数のアカウントを持つ → アカウントごとに別の行に出し、どの行にもその人が持つアカウントの数を添える。数はつなぐ前を含め、絞り込み・検索に左右されない。
- 運営者自身のアカウント → ほかの人と同じに一覧に出す。
- テスター招待の記録が複数ある（取り下げ・外してよいが残っている）→ 生きている申し込み（申し込み中・招待済み・接続済み）があればそれを出し、なければ、枠を使ったまま残っている「外してよい」を出す。どちらもなければ出さない。
- テスター招待の管理がOFFの環境（審査の後）→ 一覧は出す。テスター招待の状態の列は、記録があるときだけ出る（新しい記録はできないので、だんだん出なくなる）。
- アカウントが多い（数百件）→ 一覧は新しく作った順に出し、読み込みに時間がかかりすぎないようにする（件数の上限と続きの出し方は計画で決める）。
- スマートフォンの幅 → 1行を2段に分けて、横にはみ出さない。

## Requirements *(mandatory)*

### Functional Requirements

**一覧（US1）**

- **FR-001**：設定の「運営」に、すべてのアカウントの一覧の区分を足さなければならない。区分の名前は「アカウント一覧」とする（「個人設定」の「アカウント」と区別する）。
- **FR-002**：一覧には、このアプリのすべてのアカウントを、つなぐ前のものも含めて出さなければならない。並びは、アカウントを作った日の新しい順とする。
- **FR-003**：各行に、アカウントの名前、@ユーザー名（つなぐ前は「未接続」）、接続方法（Threadsで許可する／トークン／つなぐ前）、接続の状態（接続中／要再接続／つなぐ前）、オーナーの名前とメールアドレスとそのオーナーが持つアカウントの数、テスター招待の状態（あれば）を出さなければならない。
- **FR-004**：テスター招待の状態は、そのアカウントの生きている申し込み（申し込み中・招待済み・接続済み）があればその状態、なければ枠を使ったまま残っている「外してよい」、どちらもなければ出さないものとする。
- **FR-005**：一覧は見るだけとし、アカウント・接続・テスター招待を変える操作は置かない（招待の操作は「テスター招待」のまま）。
- **FR-006**：一覧に、投稿の案・戦略・投稿の結果など、アカウントの中身は出してはならない（運営者が見るのは、つながり方を確かめるための情報だけ）。

**絞り込みと件数（US2）**

- **FR-007**：一覧の上に、接続方法の絞り込み（すべて・Threadsで許可する・トークン・つなぐ前）を置き、それぞれに件数を出さなければならない。初めは「すべて」とする。
- **FR-008**：件数は、接続方法で数える。要再接続のアカウントは、その接続方法の側に数える。
- **FR-009**：絞り込みの件数は、検索（US3）をしていないときの全体の数とする（検索しても絞り込みの件数は変えない）。

**検索（US3）**

- **FR-010**：一覧の上に検索欄を置き、アカウントの名前・@ユーザー名・オーナーの名前・オーナーのメールアドレスの一部（大文字・小文字は区別しない）で絞り込めなければならない。接続方法の絞り込みと合わせて使える。
- **FR-011**：合うアカウントがないときは「ありません」と出す。
- **FR-014**：オーナーが持つアカウントの数は、そのオーナーのすべてのアカウント（つなぐ前を含む）を数え、接続方法の絞り込みや検索では変えない。

**共通**

- **FR-012**：この区分と、その中身を読むことは、運営者だけができる（今の「運営」の区分と同じ扱い）。運営者でない人には、区分を出さず、中身も返さない。
- **FR-013**：見た目は、今の「運営」の区分（「テスター招待」の下線のタブ・行の形）にそろえ、新しい強調の色や形は使わない。スマートフォンの幅でも横にはみ出さない。

### Key Entities *(include if feature involves data)*

- **アカウント**：名前・@ユーザー名・接続方法・接続の状態・作った日・オーナー。今ある情報を読むだけで、新しいデータは持たない。
- **オーナー**：アカウントの持ち主（名前・メールアドレス・持っているアカウントの数）。
- **テスター招待の申し込み**（024）：アカウントごとの申し込みの状態と、枠を使っているか。読むだけ。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：運営者が、すべてのアカウントの接続方法と接続の状態を、1つの画面だけで確かめられる（ほかの画面を開く回数が0回）。
- **SC-002**：接続方法ごとの件数が、実際のアカウントの数と一致する（テストで、方法ごとに用意した数と100%一致）。
- **SC-003**：運営者が、@ユーザー名かオーナーのメールアドレスの一部から、目的のアカウントを10秒以内に見つけられる。
- **SC-004**：運営者でない人は、一覧の中身を1件も読めない。
- **SC-005**：この機能の前と比べて、アカウント・接続・テスター招待の動きが変わらない（見るだけ）。

## Assumptions

- オーナーの名前とメールアドレスは、運営者がすでに「使える機能」「上限」「テスター招待」で見ている情報と同じ範囲とする。
- 件数は、今のテスト版・本番の規模（数十〜数百件）を前提にする。続きの読み込み（ページ分け）の要否は計画で決める。
- 接続の状態は、今アプリが持っている状態（接続中・要再接続・つなぐ前）を出す。Threadsに問い合わせて確かめ直すことはしない。
- 文言は日本語。テスト版・本番で同じ。

## Out of Scope

- 一覧からの操作（接続を外す・アカウントを消す・テスター招待の操作など）。
- 一覧のCSVなどへの書き出し。
- チームの人や担当の一覧。
- アカウントの中身（投稿・戦略・結果）を運営者が見ること。
