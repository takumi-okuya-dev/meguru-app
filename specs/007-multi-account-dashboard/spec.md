## User Scenarios & Testing *(mandatory)*

### User Story 1 - 全アカウントの要確認を見て作業先を選ぶ (Priority: P1)

複数のThreadsアカウントを一人で運用するユーザーは、どのアカウントの画面にいても切り替えメニューを開き、各アカウントの「要確認」の投稿下書きの件数を一度に見る。どのアカウントから対応するかを決め、そのアカウントへ切り替える。

**Why this priority**: PRD UJ-4の到達点。現在は表示中のアカウントの件数しか分からず、ほかのアカウントを一件ずつ開いて確認する必要がある。

**Independent Test**: 自分のアカウントを3件持ち、要確認の下書きがそれぞれ5件・2件・0件あるユーザーでメニューを開く。3件の数を同時に確認し、5件のアカウントへ切り替えて投稿ストックの「要確認」に進める。

**Acceptance Scenarios**:

1. **Given** 自分のアカウントを3件持つユーザー、**When** 切り替えメニューを開く、**Then** 3件それぞれの表示名・@ユーザー名・要確認件数が同じメニュー内に見える。
2. **Given** 要確認が5件・2件・0件のアカウント、**When** メニューを開く、**Then** 対応する件数が各行に表示され、0件も「0件」と分かる。
3. **Given** メニューに別のアカウントがある、**When** その行を選ぶ、**Then** 選んだアカウントの個別ホームに移り、そのアカウントが表示中として記録される。その後、投稿ストックの「要確認」を開ける。
4. **Given** 要確認の下書きを承認・却下した、または新しく登録した、**When** 切り替えメニューを開き直す、**Then** 変更後の件数が表示される。

---

### User Story 2 - 状態を見ながらアカウントを切り替える (Priority: P2)

ユーザーは、接続が切れたと判明しているアカウントと現在表示中のアカウントを、件数とともに見分けられる。メニューからアカウントの追加も始められる。

**Why this priority**: 件数だけで作業先を選ぶと、要再接続のアカウントに入って初めて状態を知ることになる。既存の切り替え機能が示す状態を維持する。

**Independent Test**: 接続済み2件と要再接続1件のユーザーでメニューを開く。要再接続のアカウントと表示中のアカウントを文字で識別でき、任意のアカウントに切り替えられる。

**Acceptance Scenarios**:

1. **Given** 接続が切れたと判明しているアカウント、**When** メニューを開く、**Then** そのアカウントに「要再接続」と表示され、選ぶと既存の再接続案内がある個別画面に進む。
2. **Given** あるアカウントを表示中、**When** メニューを開く、**Then** そのアカウントには「表示中」と分かる印があり、ほかのアカウントと区別できる。
3. **Given** アカウントを追加できるユーザー、**When** メニューの「アカウントを追加」を選ぶ、**Then** 既存の追加手続きへ進む。追加の可否は既存の条件に従う。

---

### Edge Cases

- **アカウントが0件**: 切り替えメニューは表示せず、既存の初回追加画面で「Threadsアカウントを接続」を示す。存在しないアカウントの行は表示しない。
- **アカウントが1件**: その1件にも要確認件数を表示する。複数件の保有を利用条件にしない。
- **メニューに収まらない件数**: スマートフォンを含め、すべてのアカウントにスクロールして到達でき、「アカウントを追加」にも到達できる。
- **アカウントの追加・削除**: メニューを開き直したときに現在保有するアカウントだけを表示し、削除済みのものは出さない。
- **接続状態の変化**: その時点までに判明している状態を表示する。メニューを開いただけで接続を検査したかのように表示しない。
- **読み込みの失敗**: 件数を取得できなかった場合は「0件」と誤表示せず、取得失敗と再試行の方法を示す。既存のアカウント切り替え自体は使える。
- **権限の境界**: 別のユーザーのアカウントや件数は表示しない。保有しなくなったアカウントへの移動も認めない。
- **支援技術**: 件数・接続状態・表示中の印は、色やアイコンだけに頼らず文字で意味が分かる。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST 認証済みユーザーが、既存のアカウント切り替えメニューで、自分が保有するすべてのアカウントを確認できるようにする。
- **FR-002**: System MUST 各アカウントの表示名・@ユーザー名・要確認の投稿下書きの件数を同じ行に表示する。要確認は各アカウントの投稿ストックの「要確認」と同じ対象を数える。
- **FR-003**: System MUST 要確認が0件のアカウントにも「0件」を表示し、件数を取得できない状態とは区別する。
- **FR-004**: Users MUST be able to メニューのアカウントを選んでその個別ホームに移り、そのアカウントの投稿ストックの「要確認」を開ける。
- **FR-005**: System MUST 現在表示中のアカウントと、接続が切れたと判明しているアカウントを、件数とともに区別できるようにする。
- **FR-006**: Users MUST be able to メニューから既存のアカウント追加手続きへ進める。追加の可否と上限は既存のルールに従う。
- **FR-007**: System MUST メニューを開くたびに現在保有するアカウントと要確認件数を反映し、承認・却下・新規登録・追加・削除の後に古い数や削除済みのアカウントを表示し続けない。
- **FR-008**: System MUST 件数の取得に失敗したとき、0件と混同されない表示と再試行の方法を示し、アカウント切り替えは利用可能にする。
- **FR-009**: System MUST アカウントと件数を、そのユーザーが保有するものに限定する。
- **FR-010**: System MUST スマートフォン幅でアカウントが20件ある場合も、すべてのアカウント、件数、追加操作へスクロールして到達できるようにする。

### Key Entities

- **Account**: Threadsアカウント1件に対応する運用単位。所有者、表示名、@ユーザー名、接続状態を持つ。既存の情報を利用する。
- **要確認の投稿下書き**: ユーザーの承認・却下を待つ、そのAccountの投稿。件数は投稿ストックの「要確認」と一致する。
- **切り替えメニューの項目**: Accountの情報と、その時点の要確認件数を一緒に示す表示単位。新たな保存対象ではない。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: アカウントが3件あるユーザーが、メニューを1回開くだけで3件すべての要確認件数を把握し、最も件数の多いアカウントの投稿ストックへ30秒以内に移れる。
- **SC-002**: 承認・却下・新規登録の操作完了後にメニューを開き直し、件数の取得が成功した時点で、メニューと各アカウントの投稿ストックに表示される要確認件数が100%一致する。同時に別の端末・タブで状態が変わった場合は、次にメニューを開き直して確認する。
- **SC-003**: 切り替え後に別のアカウントの投稿や設定が表示される事例が0件である。
- **SC-004**: アカウントが0件なら初回追加画面に「Threadsアカウントを接続」、1件・3件なら切り替えメニューに保有アカウントの行と「アカウントを追加」が文字で示される。要再接続のアカウントを含む場合は、メニューに「要再接続」、そのアカウントへの移動先に「再接続」が文字で示される。追加の可否は既存の条件に従う。
- **SC-005**: アカウントを3件保有する状態で安定した通信のもとメニューを開くと、95%以上の回で2秒以内に全件と要確認件数が見える。

## Assumptions

- FR-11の「ダッシュボード」は、ユーザーの選択に従い、既存のアカウント切り替えメニューを拡張して実現する。専用画面は設けない。
- メニューのアカウント行を選んだ際の行き先と並び順は現状を維持する。要確認件数の多い順への自動並べ替えは行わず、全件の数を見比べてユーザーが優先順位を決める。
- このfeatureで横断表示する情報は要確認件数と既知の接続状態に絞る。自動投稿予定、分析結果、契約情報を横断集計しない。
- 個人運用で自分が保有するアカウントを対象とする。パートナー・編集者の招待や担当割り当てはPRD §6.2に従い対象外とする。
- 料金・無料体験・追加上限の変更はFR-12で扱う。このfeatureは現行のアカウント追加条件を使う。
- 「承認待ち件数」（PRD UJ-4）は、画面上では既存の用語「要確認の件数」と表す。
