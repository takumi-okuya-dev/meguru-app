# Feature Specification：当日の集金（受付・締め・振込の確認）

**Feature Branch**: `feature/collect-001-event-day-collection`

**Created**: 2026-11-12

**Status**: Draft

**Input**: 2026-11-12に、めぐるの新しいアプリ「集金管理」（アプリのID `collect`）の最初のfeatureとして決めた。イベントの申込は外部の媒体（港・こくちーずプロ・つなげーと・ジモティー・Peatix・YOUTRUST）に任せ、**当日来た人の集金**（現金・PayPay・銀行振込）を楽にする。アプリはお金を預からず、払い方を問わない「1イベント1つの表、1人1行」の台帳にする。名簿は基本的に手で入れる。受付は複数人ででき、誰が受け取ったかが会場ですぐ共有される。イベントは、めぐる Threadsの宣伝内容（021のイベントの情報）から選ぶか、一から作るかを選べる。

**Source**: 2026-11-12の市場調査と壁打ち（このセッション。競合はPayPay「送る・受け取る」・TeamHubの集金管理・幹事Pay・Peatix・Stripeなど。どれも自分を通った支払いしか見えず、払い方がばらばらな1つのイベントの「誰が払ったか」を一覧にできない）、[docs/app-separation.md](../../../docs/app-separation.md)（パターン①）、[docs/product-structure.md](../../../docs/product-structure.md)（スイートの形）、[specs/021-external-media](../../021-external-media/spec.md)（宣伝内容のイベントの情報・媒体と掲載の状況）、[specs/meguru/029-threads-pattern1](../../meguru/029-threads-pattern1/spec.md)（出来事の仕組み）、[Constitution](../../../.specify/memory/constitution.md) 4.8.1（原則III・技術スタック制約「モバイル化を見込んだ技術の選び方」「アプリのデータの分け方」）。

## Clarifications

### Session 2026-11-12（仕様を書く前にユーザーと決めたこと）

- Q：何の大変さを解くか？ → A：いろいろな支払い方が混ざり、管理が大変なこと。払い方ごとに確かめる場所（現金のメモ・PayPayの履歴・通帳）が違い、名簿に書き写して照らし合わせる作業が毎回手作業になっている。
- Q：申込もこのアプリで受けるか？ → A：**受けない**。申込は外部の媒体に任せる。このアプリは当日来た人の集金を楽にする。当日の払い方は、現金・PayPay・銀行振込。
- Q：お金をアプリで預かるか？ → A：**預からない**。お金は受付をした人の手元の現金・主催者のPayPay・主催者の口座に直接入る。アプリは、誰がどの払い方でいくら払ったか、誰が受け取ったかの記録・照らし合わせ・催促の手助けだけをする（預かると資金移動業の論点が出るため）。
- Q：名簿はどう作るか？ → A：基本は手で入れる。
- Q：イベントはどう作るか？ → A：Threadsの宣伝内容（021のイベントの情報）から選ぶか、一から作るかを選べる。つなぎ方は**方針A**：Threadsが「イベントの情報を保存した・消した」「掲載の状況を変えた」という出来事を出し、集金管理はそれを受け取って「選べるイベントの候補」として自分で持つ。選んだら集金管理のイベントにコピーし、そのあとは別に持つ（021の掲載内容と同じ考え方）。**Threadsから選ぶ部分（User Story 6）は、Threadsをパターン①にそろえる作業（029）で出来事の仕組みができてから作る**。
- 画面イメージ：[めぐる 集金モック](https://claude.ai/artifact/79kh44mkMhAE8Dg7oi9xsB)（イベント・作る・名簿・受付・手伝い・締め・振込待ち・設定を、場面ごとに操作できる。非公開のため、開けるのはオーナーだけ）。見た目は[めぐる 外枠モック](https://claude.ai/artifact/9ZdabDgbgJbVVny89hFasu)と[docs/ui-design.md](../../../docs/ui-design.md)にそろえた。

### Session 2026-11-12（モックを見たあとに決めたこと）

- Q：名簿をもっと楽に入れられないか？ → A：001では、**貼り付けを賢くする**（媒体の申込者一覧を画面写真に撮り、スマートフォンの文字の読み取りでコピーして貼ると、番号・敬称・メールアドレスなどを除いて1行1人にする）と、**前回の参加者から選ぶ**（名前を入れ始めると、過去のイベントに来た人が候補に出る）を入れる。参加者が自分で受付する形（受付のQRを読んで自分で名前を入れる）は、次のfeatureで考える。
- Q：受付は1人か？ → A：**複数人でする**。手伝う人は、主催者が出す**ログインのいらない受付用リンク**から入る（めぐるの登録はいらない）。手伝う人ができるのは受付だけ。
- Q：現金はどう受け取るか？ → A：現金の箱は用意せず、**受付をした人がその場で受け取る**。そこで、記録ごとに**誰が受け取ったか**を残し、**会場の全員の画面にすぐ共有**する。締めでは、受け取った人ごとの現金の合計を出し、主催者がその人から受け取った（精算した）ことを記録する。

### Session 2026-11-12（/speckit-clarify）

- Q：受付用リンクは、開くだけで受付に入れるか、合言葉も入れてもらうか？ → A：**リンクだけで入れる**。合言葉や主催者の許可は求めない。期限（当日中）・主催者がすぐ止められること・受付をしている人の一覧（名前つき）で守る。
- Q：参加者の名前（名簿と受付の記録）は、いつまで残すか？ → A：**主催者がイベントを消すまで残す**（自動では消さない）。イベントを消すと、名前と1人ずつの記録は消えるが、**来場数・売上などの数字（イベントのまとめ）は残す**。
- Q：001を出したとき、だれが集金管理を使えるか？ → A：**テスト版で、運営者が開いた人（テストのグループ）だけ**が使える。料金はかけない。料金と広く出す時期は、使ってもらいながら別に決める。
- Q：1人が2つの料金（参加費と懇親会費など）を払うときは、どう記録するか？ → A：**想定しない**。料金を分けるのは、通常・早割・紹介割のような**値段の違い**で、1人に料金の区分は1つ、記録は1つの払い方・1つの金額とする。
- Q：手伝う人がリンクを開き直したとき、前と同じ人として扱うか？ → A：**同じ端末なら続きから**（名前の入れ直しなし）。**別の端末で同じ名前を入れたら**「すでに〇〇さんがいます。同じ人ですか？」と聞き、「同じ人」なら1人にまとめ、「別の人」なら区別して扱う。

## 用語

- **主催者**：イベントを開き、当日の集金をまとめる人。このアプリの利用者（めぐるにログインする）。
- **手伝う人**：主催者に頼まれて、当日の受付をする人。受付用リンクから入り、めぐるにはログインしない。
- **受付用リンク**：主催者がイベントごとに出す、手伝う人のためのリンク（とQR）。期限があり、主催者がいつでも止められる。
- **受付をする人**：主催者と手伝う人をまとめた呼び方。
- **参加者**：イベントに来る人。このアプリは使わない（名簿の1行として入れる）。
- **イベント**：集金管理の中のイベント。名前・開催日時・会場・料金の区分などを持つ。Threadsから選んで作っても、作ったあとはThreadsの宣伝内容とは別に持つ。
- **名簿**：イベントの参加者の一覧。1人1行。
- **前回の参加者**：主催者の過去のイベントの名簿にいた人。名簿を入れるときの候補になる。
- **媒体**：参加者が申し込んだ場所。港・こくちーずプロ・つなげーと・ジモティー・Peatix・YOUTRUST・当日（飛び入り）・その他。
- **料金の区分**：通常・早割・紹介割・招待など、同じ参加費の値段の違い。名前と金額の組で、イベントごとに1つ以上。1人に1つだけ付ける。
- **払い方**：現金・PayPay・振込（当日）・振込（後日）。振込（当日）は受付のその場で送ってもらうもの、振込（後日）はあとで送ってもらうもの。
- **受付番号**：イベントの中で参加者ごとに振る短い番号。振込の名義の前に付けてもらい（例：`12ヤマダ`）、後日の照らし合わせに使う。
- **受付**：当日、来た人を記録し、払い方と金額と受け取った人を記録すること。
- **受け取った人**：その記録をした、受付をする人。現金なら、その人の手元にお金がある。
- **精算**：受付のあと、手伝う人が受け取った現金を主催者に渡すこと。
- **締め**：受付が終わったあと、現金の精算・PayPay・振込の合計を確かめ、イベントのまとめを出すこと。
- **振込待ち**：振込（当日・後日）を選んだが、主催者がまだ入金を確かめていない状態。
- **イベントの候補**：Threadsから届いた、宣伝内容のイベントの情報のコピー。集金管理のイベントを作るときに選べる。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - イベントを作り、名簿を手で速く入れる（Priority: P1）

主催者が、イベントの名前・開催日時・会場・料金の区分を入れてイベントを作る。名簿の画面で、名前を入れてEnterを押すと次の行に移り、続けて入れられる。名前を入れ始めると、前回の参加者が候補に出て、選ぶだけで名前とふりがなが入る。媒体はボタンで選び、前の行の媒体を引き継ぐ。媒体の申込者一覧を画面写真に撮って文字をコピーし、まとめて貼ると、番号や敬称などが取り除かれて1行が1人になる。

**Why this priority**: 名簿がなければ受付ができない。名簿は基本的に手で入れるので、入れる速さがそのまま使いやすさになる。

**Independent Test**: 料金の区分が3つ（通常3,000円・早割2,500円・紹介割2,000円）のイベントを作る。Peatixの5人を続けて入れ、そのうち1人は前回の参加者の候補から選ぶ。こくちーずプロの3人を「1. 松本 れい 様 matsumoto@example.com」の形の3行の文として貼る。名簿に8人が並び、貼った3人の名前から番号・「様」・メールアドレスが除かれ、媒体がPeatix 5人・こくちーずプロ 3人、受付番号が1〜8で振られることを確かめる。

**Acceptance Scenarios**:

1. **Given** イベントがない、**When** 「一から作る」で名前・開催日時・会場・料金の区分（1つ以上）を入れて保存する、**Then** イベントができ、名簿の画面が開く。
2. **Given** 名簿の画面、**When** 名前を入れてEnterを押す、**Then** その人が名簿に足され、入力の欄が空になって次の人を入れられる。媒体と料金の区分は、前の人の値を引き継ぐ。
3. **Given** 過去のイベントに「森 はるか」がいた、**When** 名前の欄に「もり」と入れる、**Then** 「森 はるか（11/8 朝活もくもく会）」が候補に出て、選ぶと名前とふりがなが入る。このイベントの名簿にすでにいる人は候補に出さない。
4. **Given** 名簿の画面、**When** 複数行の文を貼る、**Then** 空の行を除いた1行が1人になる。行の頭の番号・敬称（様・さん）・メールアドレス・電話番号は除く。足す前に、人数と取り除いたあとの名前の一覧を見せ、直してから足せる。媒体と料金の区分は、そのとき選んでいる値になる。
5. **Given** 同じ名前の人がすでに名簿にいる、**When** 同じ名前を足す、**Then** 「同じ名前の人がいます（Peatix）」と知らせる。足すことは止めない（同じ名前の別の人もいるため）。
6. **Given** 名簿の1行、**When** 名前・ふりがな・媒体・料金の区分・メモを直す、または消す、**Then** 保存される。受付番号は変わらない（消した人の番号は使い回さない）。

### User Story 2 - 受付で、来た人と払い方と受け取った人を1タップで記録する（Priority: P1）

当日、受付をする人がスマートフォンで受付の画面を開く。来た人の名前の一部を入れると名簿が絞られ、その人の行で「現金」「PayPay」「振込」のどれかを押すと、来場・払い方・金額・受け取った人（押した人）が同時に記録される。記録は、会場で受付をしているほかの人の画面にもすぐ出る。PayPayのときは、主催者が登録しておいた受け取り用のQRを大きく出せる。名簿にいない人は、その場で足せる。

**Why this priority**: 機能の中心。受付で名前を探し、チェックを付け、払い方と誰が受け取ったかをメモする手間を、1回の操作にまとめる。複数人で受付しても、同じ人を二重に受け付けない。

**Independent Test**: 8人の名簿で、主催者が2つの端末（スマートフォンとPC）で受付の画面を開く。スマートフォンで「やま」で絞って山田さんの「現金」を押す。スマートフォンで山田さんが「受付済み・現金・3,000円・受け取り：主催者」になり、PCの画面にも5秒以内に同じ記録が出て、上の数が「来場 1 / 8」「現金 3,000円」になることを確かめる。手伝う人が受付したときの確かめは、User Story 3で行う。

**Acceptance Scenarios**:

1. **Given** 受付の画面、**When** 名前かふりがなの一部か受付番号を入れる、**Then** 合う人だけが並ぶ（部分一致・ひらがなとカタカナを区別しない）。
2. **Given** まだ受付していない人の行、**When** 「現金」「PayPay」「振込」のどれかを押す、**Then** その人は来場になり、払い方・金額（その人の料金の区分の金額）・受け取った人（押した人）・時刻が記録される。振込を押したときは「当日」か「後日」を選び、振込待ちになる。
3. **Given** 払い方を押す前、**When** 金額を変えたい（早割・紹介割・無料の招待など）、**Then** その記録の料金の区分を変えるか、金額を直接入れてから記録できる。変えた区分と金額は受付の記録に残り、名簿の料金の区分（申込のときの予定）は変わらない。手伝う人もできる。
4. **Given** 「PayPay」を押すとき、**When** 主催者がQRの画像を登録している、**Then** 主催者の画面でも手伝う人の画面でも、QRを画面いっぱいに出せる。参加者が支払いの完了の画面を見せたら、受付をする人が「受け取った」を押して記録する。
5. **Given** 名簿にいない人が来た、**When** 「飛び入りを足す」で名前を入れる、**Then** 媒体「当日」でその人が足され、そのまま払い方を記録できる。
6. **Given** 受付をしている人が2人以上いる、**When** だれかが記録する・取り消す・飛び入りを足す、**Then** ほかの人の画面にも数秒で反映される。受付済みの行には「受け取り：主催者」のように受け取った人が出る（手伝う人が記録したときは、その人の名前）。
7. **Given** すでに受付した人の行、**When** もう一度払い方を押そうとする、または2人がほぼ同時にその人を押す、**Then** 記録は1件だけ残り、後から押した人には「受付済み（現金・3,000円・19:02・受け取り：主催者）」のように、先に記録した人の名前とともに出る。
8. **Given** 受付の画面、**When** 見る、**Then** 上に、来場の数と名簿の人数・現金の合計・PayPayの合計・振込待ちの数と、**自分が受け取った現金の合計**がいつも出る。

### User Story 3 - 受付を手伝ってもらう（Priority: P1）

主催者が、イベントの「受付を手伝ってもらう」を押すと、受付用リンクとQRが出る。手伝う人はスマートフォンでQRを読み、自分の名前を入れると、そのイベントの受付の画面が開く。主催者は、今だれが受付をしているかと、それぞれが受け取った現金の額を見られる。受付が終わったら、リンクを止められる。

**Why this priority**: 受付は複数人ですることが多く、現金は受付をした人が受け取る。手伝う人がめぐるに登録しなくても、すぐ受付に入れることが必要。

**Independent Test**: 主催者が受付用リンクを出し、別のスマートフォンで開いて名前に「佐藤」と入れる。受付の画面だけが開き、名簿の編集・締め・振込待ち・設定には入れないことを確かめる。主催者の「受付をしている人」に佐藤が出ること、主催者がリンクを止めると、佐藤の画面が「このリンクは止められました」になることを確かめる。

**Acceptance Scenarios**:

1. **Given** イベント、**When** 主催者が「受付を手伝ってもらう」を押す、**Then** そのイベント専用の受付用リンクとQRが出る。期限（初めは、開催日の日本時間23:59と、終わりの時刻の1時間後の遅い方）を出し、リンクをコピーできる。
2. **Given** 受付用リンク、**When** 手伝う人が開き、名前を入れる、**Then** そのイベントの受付の画面が開く。手伝う人は、名簿を探す・記録する・自分の記録を取り消す・飛び入りを足す・PayPayのQRを出すことだけができる。名簿の編集・締め・振込の確認・書き出し・設定・ほかのイベントは見えない。
3. **Given** 手伝う人が受付をしている、**When** 主催者が「受付をしている人」を見る、**Then** 受付をしている人ごとに、名前・最後に記録した時刻・記録した件数・受け取った現金の額が出る。
4. **Given** 受付用リンク、**When** 主催者が止める、または期限が過ぎる、**Then** そのリンクではもう受付の画面を開けず、開いていた画面も「このリンクは止められました」になる。止める前の記録は残る。主催者は新しいリンクを出し直せる。
5. **Given** 手伝う人が、ほかの人の記録を取り消そうとする、**When** 押す、**Then** 取り消せない。取り消しは、自分の記録と、主催者がするものだけにする。

### User Story 4 - 締めで、現金の精算・PayPay・振込が合っているかをすぐ確かめる（Priority: P1）

受付が終わったら、主催者が締めの画面を開く。現金は、受け取った人ごとの合計が出ていて、手伝う人から現金を受け取ったら「精算した」を押す。渡された額を入れれば差が出る。PayPayは件数と合計が出ていて、PayPayのアプリの履歴と見比べて「合った」を押す。振込は、受け取った分と振込待ちの人が分かれて出る。媒体ごとの申込の数・来場の数・売上と、来なかった人の一覧も出る。

**Why this priority**: 今いちばん時間がかかる、払い方ごと・受け取った人ごとの照らし合わせを、数字を見比べるだけにする。媒体ごとの数字は、どの媒体に力を入れるかの判断に使える。

**Independent Test**: 来場6人（佐藤が現金2人、主催者が現金1人とPayPay2人、佐藤が振込（後日）1人）、来なかった人2人のイベントで締めの画面を開く。現金が「佐藤 6,000円・主催者 3,000円」と分かれて出ること、佐藤に5,000円と入れると「1,000円足りません」と出ること、PayPayの件数と合計・振込待ち1人・来なかった2人が出ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 受付の記録があるイベント、**When** 締めの画面を開く、**Then** 払い方ごとに、件数と合計が出る。現金は、受け取った人ごとに件数と合計を出す。
2. **Given** 締めの画面の現金、**When** 主催者が、ある人から渡された額を入れる、**Then** その人が受け取った合計との差（多い・足りない・合っている）が出る。「精算した」を押すと、精算した印と時刻が残る。主催者が自分で受け取った分は、数えた額を入れて差を見る。
3. **Given** 締めの画面、**When** PayPayの「履歴と合った」を押す、**Then** 確かめた印と時刻が残る。合わないときは、PayPayで記録した人の一覧（名前・金額・時刻・受け取った人）を見ながら直せる。
4. **Given** 締めの画面、**When** 見る、**Then** 媒体ごとに、名簿の人数・来場の数・売上が出る。来なかった人（名簿にいて受付していない人）の一覧も出る。
5. **Given** 締めの画面、**When** 「締める」を押す、**Then** 締めた時刻と、精算の結果が残る。まだ精算していない人がいれば、締める前に知らせる（締めることは止めない）。締めたあとも記録は直せ、直したら締めのあとで変わったことを示す。
6. **Given** 締めた、または締める前のイベント、**When** 「書き出す」を押す、**Then** 名簿と受付の記録（名前・媒体・料金の区分・来場・払い方・金額・受け取った人・時刻）を表の形のファイル（CSV）で受け取れる。

### User Story 5 - 後日、振込を確かめ、未入金の人に連絡する（Priority: P2）

イベントのあと、主催者が振込待ちの一覧を開く。通帳を見て、入金があった人の「入金を確かめた」を押す。まだの人には、受付番号・金額・振込先の入った連絡文をコピーして、LINEやメールで送る。

**Why this priority**: 振込は当日に終わらないことがある。誰がまだなのかを覚えておく手間と、名義から人を探す手間をなくす。受付と締め（P1）があれば、ここがなくても当日は回る。

**Independent Test**: 振込（後日）の人が2人いるイベントで振込待ちの一覧を開き、1人の「入金を確かめた」を押す。振込待ちが1人になり、締めの画面の振込の受け取った額が増えることを確かめる。残りの1人の「連絡文をコピー」で、名前・受付番号・金額・振込先の文がコピーされることを確かめる。

**Acceptance Scenarios**:

1. **Given** 振込待ちの人がいるイベント、**When** 振込待ちの一覧を開く、**Then** 名前・受付番号・金額・払い方（当日・後日）・受付した日が並ぶ。受付番号で探せる。
2. **Given** 振込待ちの人、**When** 「入金を確かめた」を押す、**Then** その人は支払い済みになり、確かめた日が残る。間違えたら戻せる。
3. **Given** 振込待ちの人、**When** 「連絡文をコピー」を押す、**Then** 名前・イベント名・金額・受付番号を名義の前に付けてほしいこと・振込先（主催者が登録した案内）の入った文がコピーされる。アプリからは送らない。
4. **Given** 主催者のすべてのイベント、**When** 振込待ちの一覧を開く、**Then** イベントをまたいで、振込待ちの人をまとめて見られる。

### User Story 6 - Threadsの宣伝内容から、イベントを選んで作る（Priority: P3）

めぐる Threadsで宣伝内容にイベントの情報を入れている主催者が、集金管理で「Threadsのイベントから選ぶ」を押す。候補の一覧からイベントを選ぶと、名前・開催日時・会場・定員・参加費が入った状態でイベントの作成画面が開く。名簿の媒体の選択肢は、そのイベントを掲載済みの媒体（と当日・その他）が先に並ぶ。

**Why this priority**: 同じイベントの情報を、Threadsと集金管理で二度入れずに済む。ただし、Threadsのパターン①（029）で出来事の仕組みができてからでないと作れない。一から作る（User Story 1）で代わりがきく。

**Independent Test**: Threadsで、開催日時・会場・参加費3,000円のある宣伝内容を保存し、Peatixを掲載済みにする。集金管理で「Threadsのイベントから選ぶ」を開くと、そのイベントが候補に出ること、選ぶと名前・日時・会場が入り、料金の区分の下書きに3,000円が入ること、名簿の媒体でPeatixが先に並ぶことを確かめる。

**Acceptance Scenarios**:

1. **Given** Threadsで、開催日時のあるイベントの情報を保存した、**When** 少し待って「Threadsのイベントから選ぶ」を開く、**Then** そのイベントが候補に出る（イベント名・開催日時・会場・掲載済みの媒体）。開催日が過ぎたものは、後ろに回すか隠せる。
2. **Given** 候補、**When** 選ぶ、**Then** 名前・開催日時・会場・定員が入り、参加費の金額が料金の区分の下書きに入った作成画面が開く。保存するまでイベントはできない。
3. **Given** Threadsから作ったイベント、**When** Threadsで宣伝内容を直す、または消す、**Then** 集金管理のイベントは変わらない。元が変わったこと・消えたことだけを示す。
4. **Given** Threadsから作ったイベント、**When** 名簿で媒体を選ぶ、**Then** 掲載済みの媒体が先に並ぶ。ほかの媒体も選べる。
5. **Given** Threadsを使っていない、または見られるイベントの情報がない主催者、**When** イベントを作る、**Then** 「Threadsのイベントから選ぶ」は出さないか、使えない理由を1行で出し、一から作れる。

### Edge Cases

- 料金の区分が1つだけ：受付で区分を選ばせず、その金額で記録する。
- 無料のイベント（金額0円）：払い方を押さずに「来場」だけを記録できる。締めでは売上0円として扱う。
- 区分にない値段で払う人（例：その場の特別な割引）：料金の区分を変えずに、金額を直接入れて記録する（FR-032）。メモに理由を書ける。
- 受付したあと、その人が帰った・返金した：記録を取り消すか、金額を0円に直し、メモに理由を書く。返金の記録は001では持たない。
- 名簿の人を消したが、その人に受付の記録がある：消す前に「受付の記録も消えます」と確かめる。
- 貼った文が名前に見えない行（日付・チケットの種類だけの行など）：足す前の一覧で外せるようにする。取り除いたあとに空になった行は足さない。
- 前回の参加者の候補で、同じ名前の人が過去に2人いた：候補に、最後に来たイベント名と日付を出して見分けられるようにする。
- 通信が途切れた：記録できなかったことをはっきり示し、押した内容を失わずにもう一度送れるようにする。記録できたように見せない。ほかの人の記録も、つながり直したら反映する。
- 2人がほぼ同時に同じ人を記録した：先に届いた記録だけを残し、後の人には「受付済み（受け取り：〇〇）」と出す。
- 手伝う人が同じ名前で2人入った：後から入った人に「すでに〇〇さんがいます。同じ人ですか？」と聞く（FR-075）。「別の人」と答えたら、主催者の「受付をしている人」と記録に、入った時刻か印を添えて区別する。
- 受付用リンクが外に漏れた・止めたい：主催者が止めれば、そのリンクはすぐ使えなくなる。出し直したリンクは別のものにする。
- 手伝う人が途中で帰った：その人の記録と受け取った現金の額は残り、締めで精算できる。
- 締めたあとに受付の記録を直した：締めの数字を出し直し、締めのあとで変わったことを示す。
- PayPayのQRを登録していない：「PayPay」を押せば、QRなしでそのまま記録できる。主催者には、QRの登録への案内を出す。
- 開催日時が過ぎたイベント：主催者の受付も締めも、そのまま使える（後日の振込の確認があるため）。受付用リンクは期限で止まる。
- イベントを消した：名簿・受付の記録・精算の記録・受付用リンクは消え、イベントのまとめ（数字だけ）が残る。消す前に確かめる。消したイベントの人は、前回の参加者の候補に出ない。
- 主催者が退会した：その人のイベント・イベントのまとめ・名簿・受付の記録・精算の記録・受付用リンク・既定値をすべて消す（共通の退会の出来事を受け取る）。
- スマートフォン：受付の画面は片手で使え、横にスクロールしない。押すところは指で押しやすい大きさにする。

## Requirements *(mandatory)*

### Functional Requirements

#### 全体の決まり

- **FR-001**: System MUST 支払いを受け取らない。送金・決済・立て替えの機能を持たず、お金の流れに入らない。払い方・金額・受け取った人は、受付をする人が記録したものだけを持つ。
- **FR-002**: System MUST イベント・名簿・受付の記録を、そのイベントを作った主催者だけに見せ、直させる。例外として、手伝う人には、受付用リンクのイベントの受付に要るもの（名簿の名前・ふりがな・受付番号・媒体・料金の区分・受付の記録）だけを見せる（FR-071）。参加者はこのアプリを使わない。
- **FR-003**: System MUST 集金管理を使えるかを、めぐるの共通の利用権で確かめる。001では、運営者が開いた人（テストのグループ）だけが使え、料金はかけない。使えない人には、集金管理の画面とデータを出さず、すべてのアプリの一覧にも出さない。手伝う人には利用権を求めない（受付用リンクで確かめる）。

#### イベント

- **FR-010**: Users MUST be able to イベントを一から作る：名前（必須）・開催日時（必須）・会場（任意）・定員（任意）・料金の区分（名前と金額の組。1つ以上）・使う払い方（現金・PayPay・振込。初めは3つとも）。
- **FR-011**: Users MUST be able to イベントを直す・消す。消すときは、名簿・受付の記録・受付用リンクが消え、イベントのまとめ（FR-014）だけが残ることを確かめてから消す。名前は、主催者がイベントを消すまで自動では消さない。
- **FR-012**: System MUST 主催者のイベントを、開催日時の近い順に一覧で出す。一覧には、名簿の人数・来場の数・振込待ちの数・締めたかどうかを出す。
- **FR-013**: Users MUST be able to 主催者ごとの既定値として、PayPayの受け取り用QRの画像と、振込先の案内（銀行名・支店・口座の種類・番号・名義を書いた文）を登録する。どのイベントでも使う。
- **FR-014**: System MUST イベントを消すときに、イベントのまとめ（イベント名・開催日・名簿の人数・来場の数・払い方ごとの件数と合計・媒体ごとの名簿の人数と来場の数と売上・振込待ちの件数と合計）を残し、主催者が過去のまとめとして一覧で見られるようにする。まとめには参加者の名前を入れない。主催者は、まとめも消せる。

#### 名簿

- **FR-020**: Users MUST be able to 名簿に人を足す：名前（必須）・ふりがな（任意）・媒体（必須。港・こくちーずプロ・つなげーと・ジモティー・Peatix・YOUTRUST・当日・その他）・料金の区分（必須。区分が1つならそれ）・メモ（任意）。
- **FR-021**: System MUST 名前を入れてEnterを押すと、その人を足し、入力の欄を空にして次の人を入れられるようにする。媒体と料金の区分は、前に足した人の値を引き継ぐ。媒体はボタンで選べる。
- **FR-022**: Users MUST be able to 複数行の文を貼り、1行を1人としてまとめて足す。足す前に、人数と名前の一覧を見せ、行ごとに直す・外すことができる。
- **FR-023**: System MUST 足した人に、イベントの中で重ならない受付番号を、足した順に振る。番号は直しても変わらず、消した人の番号は使い回さない。
- **FR-024**: System MUST 同じイベントに同じ名前（表記ゆれを除いて同じ）の人を足すとき、すでにいる人の媒体とともに知らせる。足すことは止めない。
- **FR-025**: Users MUST be able to 名簿の人を直す・消す。受付の記録がある人を消すときは、記録も消えることを確かめる。
- **FR-026**: System MUST 貼った文の各行から、行の頭の番号や記号・敬称（様・さん・さま）・メールアドレス・電話番号・前後の空白を取り除いて名前にする。取り除いたあとに空になった行は足さない。画面写真からスマートフォンの文字の読み取りでコピーした文を貼ることを、画面で案内する（アプリの中では画像を読まない）。
- **FR-027**: System MUST 名前（またはふりがな）を入れ始めると、主催者の過去のイベントの名簿にいた人を候補に出す（ひらがなとカタカナを区別しない部分一致）。候補には、最後に来たイベント名と日付を出す。選ぶと名前とふりがなが入る。このイベントの名簿にすでにいる人は出さない。

#### 受付

- **FR-030**: System MUST 受付の画面で、名前・ふりがな・受付番号の一部から名簿を絞れるようにする。全角と半角・ひらがなとカタカナ・空白の有無を区別しない。
- **FR-031**: System MUST まだ受付していない人の行で、イベントで使う払い方のボタン（現金・PayPay・振込）を出し、1回押すだけで、来場・払い方・金額・受け取った人（押した受付をする人）・記録した時刻を記録する。振込のときは「当日」か「後日」を選ばせ、振込待ちにする。金額は、その人の料金の区分の金額とする。
- **FR-032**: Users MUST be able to 記録の前に、その記録の料金の区分を変えるか、金額を直接入れる（割引・無料の招待など）。変えた区分と金額は受付の記録に持ち、名簿の料金の区分は変えない（手伝う人に名簿を直す権限を渡さないため）。締め・書き出し・媒体ごとの売上は、受付の記録の区分と金額で数える。金額0円のイベント・区分では、払い方なしで来場だけを記録できる。
- **FR-033**: System MUST 「PayPay」のとき、主催者がQRの画像を登録していれば、受付をするだれの画面でも、画面いっぱいに出せるようにする。受付をする人が「受け取った」を押したときに記録する。QRがなければ、そのまま記録できるようにする。
- **FR-034**: Users MUST be able to 受付の画面から、名簿にいない人（飛び入り）を、名前だけで足してそのまま記録する。媒体は「当日」とし、主催者があとで直せる。
- **FR-035**: System MUST 同じ人を二重に記録しない。受付済みの人には、払い方・金額・時刻・受け取った人を出す。2人以上がほぼ同時に同じ人を記録しようとしたときは、先に届いた記録だけを残し、後の人にはそのことを示す。
- **FR-036**: System MUST 受付の画面の上に、来場の数と名簿の人数・現金の合計・PayPayの合計・振込待ちの数・その画面の受付をする人が受け取った現金の合計を、いつも出す。
- **FR-037**: System MUST 記録が保存できなかったとき（通信が途切れたなど）、保存できなかったことをはっきり示し、押した内容を失わずにもう一度送れるようにする。保存できていない記録を、保存できたように見せない。
- **FR-038**: System MUST 受付をするだれかが記録・取り消し・飛び入りの追加をしたら、同じイベントの受付を開いているほかの画面に、数秒のうちに反映する。上の数（FR-036）も合わせて変える。
- **FR-039**: Users MUST be able to 記録を取り消す・直す。主催者はすべての記録を、手伝う人は自分が受け取った記録だけを取り消せる。

#### 受付の手伝い

- **FR-070**: Users MUST be able to 主催者が、イベントごとに受付用リンクを出す。リンクとQRを出し、コピーできるようにする。期限は初めは、開催日の日本時間23:59と、終わりの時刻の1時間後の遅い方とし（日付をまたぐイベントでも途中で切れないように）、主催者が変えられる。
- **FR-071**: System MUST 受付用リンクを開いた人に名前を入れてもらい、そのイベントの受付の画面だけを出す。手伝う人ができるのは、名簿を探す・記録する（FR-031〜034）・自分の記録を取り消す・PayPayのQRを出すことだけとし、名簿の編集・締め・振込の確認・書き出し・設定・ほかのイベントは出さない。
- **FR-072**: System MUST 主催者に、受付をしている人の一覧を出す：名前・入った時刻・最後に記録した時刻・記録した件数・受け取った現金の額・使っている端末の数（「同じ人」でまとめた端末があれば2以上になり、主催者が見覚えのない端末に気づけるようにする）。
- **FR-073**: Users MUST be able to 主催者が受付用リンクを止める・出し直す。止めたリンクと期限の過ぎたリンクでは受付の画面を開けず、開いていた画面も使えなくする。止める前の記録は残す。出し直したリンクは、前のリンクと別のものにする。
- **FR-074**: System MUST 受付用リンクを、推し量れない長い値にし、リンクを開いて名前を入れるだけで受付に入れるようにする（合言葉・主催者の許可は求めない）。リンクが外に漏れたときは、期限（FR-070）・止める（FR-073）・受付をしている人の一覧（FR-072）で守る。手伝う人は、めぐるの利用者として登録されず、主催者の料金にも数えない。
- **FR-075**: System MUST 手伝う人が同じ端末でリンクを開き直したら、名前を入れ直さずに前の続きから受付できるようにする。別の端末で、同じリンクにすでにいる名前を入れたら、「すでに〇〇さんがいます。同じ人ですか？」と聞き、「同じ人」なら同じ手伝う人として扱い（記録と受け取った現金を1人にまとめる）、「別の人」なら別の手伝う人として区別する。

#### 締め

- **FR-040**: System MUST 締めの画面で、払い方ごとの件数と合計を出す。現金は、受け取った人ごとに件数と合計を出す。
- **FR-041**: Users MUST be able to 現金の受け取った人ごとに、渡された額（主催者自身の分は数えた額）を入れ、その人の合計との差（多い・足りない・合っている）を見る。「精算した」を押して、印と時刻を残す。
- **FR-042**: Users MUST be able to PayPayの「履歴と合った」を押し、確かめた印と時刻を残す。PayPayで記録した人の一覧（名前・金額・時刻・受け取った人）を見られる。
- **FR-043**: System MUST 振込を、受け取った分（入金を確かめた分）と振込待ちに分けて、件数と合計を出す。
- **FR-044**: System MUST 媒体ごとに、名簿の人数・来場の数・売上（支払い済みと振込待ちを分けて）を出す。名簿にいて受付していない人（来なかった人）の一覧を出す。
- **FR-045**: Users MUST be able to 「締める」を押し、締めた時刻と精算の結果を残す。まだ精算していない人がいれば、締める前に知らせる（止めない）。締めたあとも記録は直せ、直したら締めのあとで変わったことを示す。
- **FR-046**: Users MUST be able to 名簿と受付の記録（受付番号・名前・ふりがな・媒体・料金の区分・来場・払い方・金額・受け取った人・記録した時刻・入金を確かめた日・メモ）を、表の形のファイル（CSV）で書き出す。

#### 後日の振込の確認

- **FR-050**: System MUST 振込待ちの人の一覧を、イベントごとと、主催者のすべてのイベントをまとめた形で出す。名前・受付番号・金額・当日か後日か・受付した日を出し、受付番号と名前で探せるようにする。
- **FR-051**: Users MUST be able to 振込待ちの人の「入金を確かめた」を押して支払い済みにし、確かめた日を残す。間違えたら振込待ちに戻せる。
- **FR-052**: Users MUST be able to 振込待ちの人の連絡文をコピーする。連絡文には、名前・イベント名・金額・受付番号を名義の前に付けてほしいこと・振込先の案内（FR-013）を入れる。アプリからは送らない。

#### Threadsのイベントから選ぶ（029の出来事の仕組みのあと）

- **FR-060**: System MUST めぐる Threadsから届く出来事（宣伝内容のイベントの情報を保存した・消した、媒体の掲載の状況を変えた）を受け取り、イベントの候補として持つ。同じ出来事が2回届いても、結果を変えない。届くのが少し遅れてもよい。
- **FR-061**: System MUST 主催者が見てよいThreadsのイベントだけを候補に出す（誰に見せるかはplanで決める。少なくとも、そのThreadsのアカウントの持ち主には出す）。
- **FR-062**: Users MUST be able to 候補を選び、名前・開催日時・会場・定員と、参加費の金額を料金の区分の下書きに入れた状態でイベントを作る。保存したら、Threadsの宣伝内容とは別に持ち、元のIDは値として持つ（元を開くための案内に使う）。
- **FR-063**: System MUST Threadsから作ったイベントで、元の宣伝内容が直された・消されたことを示す。集金管理のイベントは自動で変えない。
- **FR-064**: System MUST Threadsから作ったイベントの名簿では、掲載済みの媒体を、媒体のボタンの先に並べる。

### Key Entities *(include if feature involves data)*

- **イベント**：主催者のもの。名前・開催日時・会場・定員・使う払い方・元のThreadsの宣伝内容のID（任意。値として持つだけ）・元が変わった印・締めた時刻・PayPayを確かめた時刻を持つ。料金の区分・名簿・受付用リンクを持つ。
- **料金の区分**：イベントごと。名前と金額。並びの順を持つ。
- **名簿の人**：イベントごと。受付番号・名前・ふりがな・媒体・料金の区分・メモを持つ。受付の記録を0か1つ持つ。前回の参加者の候補は、主催者の過去のイベントの名簿の人から出す。
- **受付の記録**：名簿の人ごとに1つまで。来場した時刻・払い方（現金・PayPay・振込（当日）・振込（後日）・なし）・料金の区分（受付で変えたら変えたもの）・金額・受け取った人（主催者か、手伝う人）・支払いの状態（支払い済み・振込待ち）・入金を確かめた日を持つ。
- **受付用リンク**：イベントごと。推し量れない値・期限・止めた時刻を持つ。止めて出し直すと、新しいものになる。
- **手伝う人**：受付用リンクごと。入れた名前・入った時刻・端末の印（同じ端末で開き直したときに続きから始めるため）を持つ。同じ名前の別の人を区別できる。めぐるの利用者ではない。
- **精算**：イベントと受け取った人ごと。渡された（数えた）額・精算した時刻を持つ。
- **イベントのまとめ**：主催者ごと。消したイベントの数字だけを持つ（イベント名・開催日・名簿の人数・来場の数・払い方ごとの件数と合計・媒体ごとの人数と売上・振込待ち）。参加者の名前は持たない。
- **主催者の既定値**：主催者ごと。PayPayの受け取り用QRの画像・振込先の案内を持つ。
- **イベントの候補**：Threadsから届いたコピー。元の宣伝内容のID・ThreadsのアカウントのID・イベント名・開催日時・会場・定員・参加費・掲載済みの媒体・消された印・最後に届いた時刻を持つ。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 受付をする人が、来た人1人の受付（探す→来場と払い方を記録する）を、3回の操作・10秒以内で終えられる（名簿50人のイベントで）。
- **SC-002**: 主催者が、30人の名簿を手で5分以内に入れられる（名前だけを続けて入れる場合）。画面写真から貼るなら1分以内。前回の参加者が半分いるなら3分以内。
- **SC-003**: 主催者が、受付のあとの締め（受け取った人ごとの現金の精算・PayPayの合計・振込待ちを確かめる）を、受付をした人が3人でも5分以内に終えられる。紙・メモ・電卓への書き写しが0回になる。
- **SC-004**: 媒体ごとの名簿の人数・来場の数・売上と、受け取った人ごとの現金の額が、主催者が手で数えずに出る。
- **SC-005**: 同じ人を二重に記録してしまうことが0件（受付をする人が3人でも）。保存できていない記録を、保存できたと受付をする人が思い込むことが0件。
- **SC-006**: だれかの記録が、会場で受付をしているほかの人の画面に5秒以内に出る。
- **SC-007**: 手伝う人が、受付用リンクを開いてから受付を始めるまで30秒以内（めぐるへの登録なし）。
- **SC-008**: 試しに使った主催者（港の主催者を含む3人以上）が、次のイベントでも使いたいと答える。

## Assumptions

- **受付をする人**：主催者と、受付用リンクで入る手伝う人（複数）。手伝う人はめぐるに登録せず、受付だけをする。主催者のほかにイベントを管理する人（共同の主催者）は001では持たない。チームはThreadsの機能なので、集金管理で要るときは、そのときに考える（029 Clarifications）。
- **手伝う人のなりすまし**：受付用リンクは合言葉なしで、別の端末から同じ名前を入れて「同じ人」と答えれば、その手伝う人として受付し、その人の記録を取り消せる（Clarifications の方針の結果）。リンクは会場で直接渡し、期限は当日中とし、主催者は受付をしている人の一覧（端末の数を含む。FR-072）で気づいてリンクを止められる（FR-073）ことで守る。これで足りなくなったら、合言葉や主催者の許可を足す。
- **現金**：現金の箱（釣り銭）は用意せず、受付をした人がその場で受け取る。締めで、受け取った人ごとに主催者へ渡す（精算）。手伝う人が持ってきた釣り銭は、アプリでは扱わない。
- **料金と公開の範囲**：001では、テスト版で運営者が開いた人（テストのグループ）だけが使い、料金はかけない（Clarifications）。スイートの料金は未定（[product-structure.md](../../../docs/product-structure.md) 3）で、料金と広く出す時期は、使ってもらいながら別のfeatureで決める。手伝う人には料金をかけない。
- **申込と決済**：申込ページ・事前決済（Stripeなど）・参加者向けの画面は作らない。参加者が自分で受付する形（受付のQRを読んで自分で名前を入れる）は、次のfeatureで考える。外部の媒体の名簿の取り込み（CSV）・申込の通知メールの転送・通帳の取り込みによる自動の照らし合わせ・催促の自動送信も001の外とし、使ってみて手間が残れば次のfeatureで考える。
- **画面写真の文字**：画面写真の文字は、スマートフォンの文字の読み取り（iPhoneの「テキスト認識表示」・Androidの「Googleレンズ」など）でコピーしてもらう。アプリの中で画像を読む・AIを呼ぶことはしない（原則III）。
- **1人1つの区分と払い方**：参加費と懇親会費のように、1人が2つの料金を払う形は想定しない（Clarifications）。1人に料金の区分は1つ、記録は1つの払い方・1つの金額にする。紹介割でだれの紹介かは、001ではメモに書く（紹介者を数える仕組みは、港への送客の数え方と合わせて次のfeature以降で考える）。返金の記録は持たない（取り消しか金額の直しとメモ）。
- **通信**：会場では、通信がつながる前提とする。途切れたときに押した内容を失わないこと（FR-037）と、つながり直したらほかの人の記録を反映することまでを001の範囲とし（押した内容を残すのは、その画面を開いている間だけ。画面を閉じたり開き直したりしたら、残っていない記録はもう一度押す）、電波がまったくない場所で受付を続けられる仕組みは、必要が見えてから考える。
- **PayPay**：主催者のPayPay（個人用かお店用か）は問わない。PayPayの支払いは、だれが受付をしても主催者のPayPayに入る。アプリはQRの画像を出し、記録するだけ。PayPayの履歴をアプリが読むことはしない。収益イベントの受け取りに個人用のPayPayを使ってよいかは、主催者がPayPayの規約で確かめる。
- **媒体の一覧**：港・こくちーずプロ・つなげーと・ジモティー・Peatix・YOUTRUST・当日・その他で始める。021の媒体（港以外の5つ）と名前をそろえる。
- **データの消し方**：参加者の名前は、主催者がイベントを消すまで自動では消さない。イベントを消すと、名簿と1人ずつの記録は消え、数字だけのイベントのまとめが残る（FR-014）。主催者が退会したら、共通の退会の出来事を受け取って、その人のデータ（まとめを含む）をすべて消す。参加者の名前は、主催者が自分のイベントのために入れたものとして扱い、主催者と、そのイベントの受付をする手伝う人だけに見せる。前回の参加者の候補は、主催者が消していない過去のイベントの名簿から出す。
- **作り方**：パターン①（集金管理専用の置き場所。共通は入口の関数と出来事だけ。[app-separation.md](../../../docs/app-separation.md)）で作る。業務の判断はAPIと共通のパッケージに置き、将来のモバイルの画面からも同じものを使えるようにする（Constitution「モバイル化を見込んだ技術の選び方」）。会場での共有（FR-038）の仕組みは、planで決める（Constitutionの運用コスト制約を守る）。
- **依存**：実装は、Threadsをパターン①にそろえる作業（[029](../../meguru/029-threads-pattern1/spec.md)。リンク先は029のブランチにあり、029が`develop`に入るまでこのブランチでは開けない）が終わってから始める。**それまでは、このfeatureのコード・マイグレーション・設定は一切作らない**（文書だけ）。User Story 6は、029の出来事の仕組みに、Threadsが出す出来事（イベントの情報・掲載の状況）を足してから作る。User Story 1〜5は、User Story 6がなくても使える。
