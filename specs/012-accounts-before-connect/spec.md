# Feature Specification:アカウントを先に作る

**Feature Branch**: `feature/012-accounts-before-connect`

**Created**: 2026-10-14

**Status**: Draft

**Input**: 2026-10-12のユーザーとの相談（[docs/next-features.md](../../docs/next-features.md)の「B.アカウントを先に作る」）と、2026-10-14の「Bを次に作る」の決定。今は「Threadsアカウントをつなぐこと＝アカウントを作ること」で、ログイン後にアカウントが0件だと、最初に「Threadsアカウントを追加」が出る（001 FR-005）。これを、先にアカウント（名前だけ）を作り、Threadsへの接続は後から「このアカウントの設定」の「Threadsとの接続」（このアプリで許可・トークンの貼り付けの2つ）で行う形に変える。010のトークンでの接続は、Metaアプリを作るところから30分ほどかかる。戦略・宣伝内容・リサーチ・プロンプト・投稿ストック・承認は、つながっていなくても使えるので、先に中身を触ってもらい、無料体験の価値を早く感じてもらう。

## Clarifications

### Session 2026-10-14

- Q:未接続のアカウントをつなごうとしたThreadsアカウントが、すでに自分の別のアカウントとしてつながっていたら？ → A:止めて、そのアカウントへのリンクを出す。未接続のアカウントとデータは残し、要らなければオーナーが自分で削除する。中身を移す操作は作らない（US3-1・FR-022）。
- Q:つないだ後、切り替えメニューやホームでいちばん目立つ名前は？ → A:アカウントの名前を主にし、@ユーザー名を小さく添える。つなぐ前後で見え方を変えない。今あるアカウントの名前はThreadsの表示名で埋めるので、見た目はほぼ今のまま（US5-2・FR-042・FR-044）。
- Q:つなぐ前に自動投稿をオンにしておき、つないだらすぐ投稿を始められるようにするか？ → A:しない。つなぐ前はオンにできず、つないだ後もオフのまま。オーナーが自動投稿の画面でオンにしてから投稿を始める。つないだ直後に「自動投稿を始める」への入口を出す（US2-2・FR-014）。
- Q:未接続のアカウントのホームで、「Threadsにつなぐ」をどう勧めるか？ → A:一番上に控えめな帯（「未接続」と「Threadsにつなぐ」）をいつも出し、承認済みの案が1件以上になったら「次にやること」を「Threadsにつないで自動投稿を始めましょう」にする（US4-1・FR-034）。

## 用語

- **アカウント**：このアプリの運用の単位（001のAccount）。本featureから、Threadsにつながっていなくても作れる。
- **アカウントの名前**：アカウントを作るときに利用者が付ける名前（例：「カフェの公式」）。Threadsのユーザー名とは別。
- **接続の状態**：アカウントごとに「未接続」（一度もThreadsにつないでいない）・「接続中」・「要再接続」（001 FR-018）の3つ。
- **つなぐ**：未接続のアカウントを、はじめてThreadsアカウントにつなぐこと。方法は、001・010と同じく「Threadsで許可する」（このアプリの接続）と「トークンを貼り付ける」（トークンでの接続）の2つ。
- **Threadsが要る機能**：自動投稿（005）、パフォーマンスの取得と分析（006）、投稿の権限・反応数を読む権限の確認、Threadsのプロフィールの表示。

## User Scenarios & Testing *(mandatory)*

### User Story 1 -名前だけでアカウントを作り、すぐに中身を使う(Priority: P1)

はじめてログインした人が、最初の画面「アカウントを作る」で名前（例：「カフェの公式」）だけを入れて作る。そのアカウントのホームに移り、Threadsにつながっていなくても、戦略（課題・宣伝内容・リサーチ）を入れ、プロンプトを作り、外のLLMで作った案を投稿ストックに貼り付け、承認まで進められる。

**Why this priority**:本featureの中心。010のトークンでの接続は30分ほどかかるため、つなぐ前に中身を触ってもらい、無料体験の価値を早く感じてもらう。

**Independent Test**:アカウントを1つも持たない利用者でログインし、名前だけでアカウントを作り、戦略の保存・プロンプトの生成・投稿の案の一括登録・承認ができることを確かめる。

**Acceptance Scenarios**:

1. **Given** アカウントを1つも持たない利用者、**When** ログインする、**Then** 「アカウントを作る」の画面が出る。名前の入力欄（50文字まで）と「作る」だけがあり、Threadsへの接続の操作は出ない。「Threadsには、あとでこのアカウントの設定からつなげます」と添える。
2. **Given** 「アカウントを作る」の画面、**When** 名前を入れて「作る」を押す、**Then** 未接続のアカウントが作られ、利用者がそのオーナーになり、そのアカウントのホームに移る。
3. **Given** 名前が空・空白だけ・50文字を超える、**When** 「作る」を押す、**Then** アカウントは作られず、入力欄の下に理由が出る。
4. **Given** 未接続のアカウント、**When** 戦略・宣伝内容・リサーチ・投稿のルール・NGワードを保存し、プロンプトを作り、案を一括で登録し、承認・却下する、**Then** 接続中のアカウントと同じようにできる（002〜004）。
5. **Given** 未接続のアカウント、**When** 承認する、**Then** 承認済みの案は投稿ストックにたまり、Threadsには投稿されない（Constitution原則IIのまま。投稿はつないで自動投稿を始めてから）。

### User Story 2 -作ったアカウントを、後からThreadsにつなぐ(Priority: P1)

オーナーが、未接続のアカウントの「このアカウントの設定」の「Threadsとの接続」から、「Threadsで許可する」か「トークンを貼り付ける」を選んでつなぐ。つなぐと、Threadsのプロフィールが表示され、自動投稿とパフォーマンスが使えるようになる。つなぐ前に作った戦略・投稿ストック・設定はそのまま残る。

**Why this priority**:つなげなければ、自動投稿という製品の中心（PRD §1）に進めない。US1と2つで最小の形になる。

**Independent Test**:未接続のアカウントで戦略と承認済みの案を作ってから、トークンを貼り付けてつなぎ、データがそのまま残り、接続中になり、自動投稿を始められることを確かめる。「Threadsで許可する」でも同じ。

**Acceptance Scenarios**:

1. **Given** 未接続のアカウントのオーナー、**When** 「このアカウントの設定」を開く、**Then** 「Threadsとの接続」の区分に「未接続」と、「Threadsで許可する」「トークンを貼り付ける」の2つの方法が出る。トークンの方法は、010と同じく開くまで手順と入力欄を出さない。
2. **Given** 未接続のアカウント、**When** 「Threadsで許可する」で許可を終える、**Then** そのアカウントが接続中になり、Threadsのユーザー名・表示名・画像が入る（001 FR-009）。設定の画面に戻り、「つながりました」と、「自動投稿を始める」（自動投稿の画面へ）が出る。新しいアカウントは作らない。
3. **Given** 未接続のアカウント、**When** 有効な長期トークンを貼り付けてつなぐ、**Then** 同じく接続中になる。権限の確認・短期トークンの確かめ直し・失敗の回数の待ちは010と同じ（010 FR-011・FR-012・FR-015）。
4. **Given** 戦略・投稿ストック・設定・操作の記録がある未接続のアカウント、**When** つなぐ、**Then** それらはすべて残る（件数が同じ）。
5. **Given** つないだばかりのアカウント、**When** 自動投稿の画面を開く、**Then** 自動投稿はオフのままで、オーナーがオンにすると、承認済みの案が005と同じ順で投稿される。
6. **Given** アカウントの登録の上限に達している利用者、**When** 未接続のアカウントをつなぐ、**Then** つなげる（つなぐことでアカウントは増えないため。001 FR-020と同じ考え方）。

### User Story 3 -同じThreadsアカウントの二重の登録を防ぐ(Priority: P1)

つなごうとしたThreadsアカウントが、すでに別のアカウントとしてつながっているとき、同じThreadsアカウントに2つのアカウントがつながって自動投稿が2重になるのを防ぐ。010と同じく、ThreadsのユーザーIDとユーザー名の両方で照合する。

**Why this priority**:二重の自動投稿は、運用者が最も恐れる事故に近い（010 US2と同じ理由）。つなぐ入口が設定に移っても、守りは同じでなければならない。

**Independent Test**:接続中のアカウント@cafe_bを持つ利用者が、別の未接続のアカウントを@cafe_bにつなごうとして止められることを確かめる。他の利用者の@cafe_bでも止められることを確かめる。

**Acceptance Scenarios**:

1. **Given** 自分の接続中のアカウント「カフェ」（@cafe_b）と、自分の未接続のアカウント「カフェ2」、**When** 「カフェ2」を@cafe_bにつなごうとする、**Then** つながらず、「@cafe_bは、あなたのアカウント『カフェ』につながっています」と、「カフェ」へのリンクが出る。「カフェ2」とそのデータはそのまま残り、要らなければオーナーが自分で削除する。中身を「カフェ」へ移す操作は作らない。
2. **Given** 他の利用者がつないでいる@cafe_b、**When** 自分の未接続のアカウントを@cafe_bにつなごうとする、**Then** 001 FR-012と同じく「このThreadsアカウントは、すでに別のユーザーが登録しています」と出て、つながらない。登録している人の名前は出さない。未接続のアカウントとそのデータは残る。
3. **Given** ユーザー名だけが一致した、**When** つなごうとする、**Then** 010 FR-023と同じく、登録済みのアカウントのプロフィールを取り直し、もう同じユーザー名でなければ続けてつなぐ。
4. **Given** 同じ未接続のアカウントを、2つのブラウザで同時に別々の方法でつなごうとする、**When** 両方が終わる、**Then** つながるのは1つのThreadsアカウントだけで、後から終わった方は「このアカウントは、すでにThreadsにつながっています」と出る。

### User Story 4 -未接続のあいだの案内(Priority: P2)

未接続のアカウントで、Threadsが要る機能（自動投稿・パフォーマンス）を開くと、「Threadsにつなぐと使えます」と、つなぐ操作への入口が出る。ホームにも、つなぐ案内が出る。

**Why this priority**:案内がないと、使えない機能が壊れているように見える。ただし、つなげばUS1・US2だけで価値は届くのでP2。

**Independent Test**:未接続のアカウントで、ホーム・自動投稿・パフォーマンスの画面を開き、案内と「Threadsとの接続」への入口が出ることを確かめる。つないだ後は消えることを確かめる。

**Acceptance Scenarios**:

1. **Given** 未接続のアカウントのオーナー、**When** ホームを開く、**Then** 一番上に控えめな帯で「未接続：Threadsにつなぐと、承認した案を自動で投稿し、反応を分析できます」と「Threadsにつなぐ」（設定の「Threadsとの接続」へ）が出る。ほかのホームの項目（次にやること・入力の状況など）はいつもどおり出る。
2. **Given** 承認済みの案が1件以上ある未接続のアカウント、**When** ホームを開く、**Then** 「次にやること」が、戦略の入力の進み具合より先に「Threadsにつないで自動投稿を始めましょう」（「Threadsとの接続」へ）になる。承認済みの案が0件なら、今までどおり課題→宣伝内容→リサーチ→投稿をつくるの順で案内する。
3. **Given** 未接続のアカウント、**When** 自動投稿の画面を開く、**Then** 「Threadsにつなぐと使えます」と入口が出て、自動投稿をオンにする操作は使えない。投稿の時刻の設定は、つなぐ前でも保存できる。
4. **Given** 未接続のアカウント、**When** パフォーマンスの画面を開く、**Then** 「Threadsにつなぐと使えます」と入口が出て、数字・グラフ・書き出しは出さない。
5. **Given** 未接続のアカウントの編集者（担当）・チームの人、**When** そのアカウントを開く、**Then** この案内は出るが「Threadsにつなぐ」の操作は出ない（つなぐのはオーナーだけ。Constitution原則IV）。ただし、011により未接続のアカウントはチームに入らないため、ふつうは起きない（Edge Cases）。
6. **Given** つないだアカウント、**When** ホーム・自動投稿・パフォーマンスを開く、**Then** 未接続の案内は出ない。

### User Story 5 -ユーザー名がないアカウントの表示(Priority: P2)

未接続のアカウントにはThreadsのユーザー名・画像がない。切り替えメニュー・アカウントの一覧・ホーム・削除の確認など、今ユーザー名を使っている画面で、アカウントの名前と「未接続」を示し、迷わず見分けられるようにする。

**Why this priority**:複数のアカウントを持つ人が、未接続のアカウントを見分けられないと、別のアカウントで作業してしまう。ただし1つ目のアカウントだけなら困らないのでP2。

**Independent Test**:未接続のアカウントと接続中のアカウントを1つずつ持ち、切り替えメニュー・アカウントの一覧・ホーム・設定・削除の確認で、それぞれの見え方を確かめる。

**Acceptance Scenarios**:

1. **Given** 未接続のアカウント「カフェの公式」、**When** 切り替えメニュー・アカウントの一覧を開く、**Then** 名前の頭文字の仮の画像、「カフェの公式」、「未接続」の印が出る。
2. **Given** 接続中のアカウント、**When** 同じ画面を開く、**Then** Threadsのプロフィール画像、アカウントの名前（主）、@ユーザー名（小さく添える）が出る。つなぐ前後で、主の名前は変わらない。
3. **Given** 未接続のアカウント、**When** 削除する、**Then** 確認でアカウントの名前の入力を求める（001 FR-022のAccount名＝アカウントの名前）。トークンについての注意（010 FR-050）は、未接続なら出さない。
4. **Given** オーナー、**When** 「このアカウントの設定」でアカウントの名前を直す、**Then** 切り替えメニュー・ホームなどの表示がその名前に変わる。直せるのはオーナーだけ。

### User Story 6 -2つ目以降のアカウントも名前だけで作る(Priority: P2)

すでにアカウントを持つ人が、切り替えメニューの「アカウントを作る」から、2つ目以降のアカウントを名前だけで作る。今の「Threadsアカウントを追加」の画面（001・010）は、「アカウントを作る」に置き換わる。

**Why this priority**:入口が2つ（名前だけで作る・つないで作る）あると、つなぐ方法の案内も照合も2か所に分かれる。入口を1つにすれば、つなぐのはいつも設定から、で覚えやすい。

**Independent Test**:アカウントを1つ持つ利用者が、切り替えメニューから2つ目のアカウントを名前だけで作り、そのアカウントのホームに移ることを確かめる。登録の上限に達しているときは作れないことを確かめる。

**Acceptance Scenarios**:

1. **Given** アカウントを持つ利用者、**When** 切り替えメニューを開く、**Then** 「Threadsアカウントを追加」に替わって「アカウントを作る」が出る。
2. **Given** 「アカウントを作る」、**When** 名前を入れて作る、**Then** US1-2と同じく未接続のアカウントができ、そのホームに移る。
3. **Given** 登録の上限に達した利用者、**When** 「アカウントを作る」を開く、**Then** 001 FR-017と同じく、上限の案内と次に取れる操作が出て、アカウントは作られない。同時の操作でも上限を超えない。
4. **Given** 古いURL（今の「Threadsアカウントを追加」の画面）、**When** 開く、**Then** 「アカウントを作る」の画面に移る。

### User Story 7 -未接続のアカウントとチーム(Priority: P3)

011では、チームに入るには自分のThreadsアカウントが要ると決めた。未接続のアカウントは、チームを作るとき・チームに入るときに選べず、「Threadsにつなぐと入れられます」と出る。未接続のアカウントしか持たない人には、先につなぐよう案内する。

**Why this priority**:チームはふだん個人運用の後に使う機能で、011の守り（1人1Threadsアカウント）を崩さないための確認。

**Independent Test**:未接続のアカウントだけを持つ利用者が招待リンクを開き、参加できず、つなぐ案内が出ることを確かめる。つないだ後にリンクを開き直すと参加できることを確かめる。

**Acceptance Scenarios**:

1. **Given** 未接続のアカウントだけを持つ利用者、**When** 招待リンクを開く、**Then** 「先に、自分のアカウントをThreadsにつないでください」と、未接続のアカウントの「Threadsとの接続」への入口が出て、参加できない（011 FR-014）。つないだ後にリンクを開き直すと、続きから参加できる。
2. **Given** 接続中と未接続のアカウントを持つ利用者、**When** 参加の確認の画面を開く、**Then** 接続中のアカウントだけが選べ、未接続のアカウントは「Threadsにつなぐと入れられます」と選べない形で出る。
3. **Given** 未接続のアカウントだけを持つ利用者、**When** 「チームを作る」を押す、**Then** 同じくつなぐ案内が出て、チームは作れない（011 FR-010）。
4. **Given** 個人運用（チームに入っていない）の利用者、**When** 未接続のアカウントの設定を開く、**Then** チームの区分は011のまま1行だけ（Constitution原則V）。

### Edge Cases

- **今あるアカウント**：本featureより前に作ったアカウントは、すべて接続中か要再接続で、アカウントの名前を持たない。名前は、今の表示（Threadsの表示名、なければ@ユーザー名）で埋める。接続の状態とデータは変えない。
- **未接続のアカウントの自動投稿の時刻**：時刻の設定は保存できるが、未接続の間は投稿しない。つないでも自動投稿はオフのままで、オーナーがオンにしてはじめて投稿が始まる（承認済みの案が、つないだ瞬間に一度に出ていくのを防ぐ）。
- **毎日の処理**：期限の延長・プロフィールの取り直し・反応数の取得・トークンの確かめ直しは、未接続のアカウントを飛ばす。失敗として記録しない。
- **未接続のアカウントと「要再接続」**：未接続は一度もつないでいない状態で、要再接続（つないだ後に使えなくなった）とは別に見せる。未接続のアカウントに、要再接続のバナーや「接続し直す」は出さない。
- **つないだ後に、未接続へ戻す**：本featureでは作らない（Threadsとの接続を外すには、アカウントを消すか、Meta側で取り消して要再接続にする）。
- **未接続のアカウントと別のThreadsアカウント**：未接続のアカウントは、最初につないだThreadsアカウントに決まる。その後に別のThreadsアカウントでつなぎ直すことは、001 FR-020のまま拒否する。
- **つなぐ途中でやめた**：「Threadsで許可する」で許可の画面から戻った・拒否した、トークンが確かめられなかった、のときは、未接続のまま残り、データは変わらない。
- **未接続のアカウントの削除**：001 FR-022と同じく、アカウントとデータを消す。消すトークンはない。
- **未接続のアカウントのチームへの関わり**：未接続のアカウントはチームに入れない（US7）。つないだ後に、011の流れでチームに入れられる。つないだ後に要再接続になっても、チームからは外さない（011のまま）。
- **Metaのデータ削除・アンインストールの通知**：ThreadsのユーザーIDに結び付くため、未接続のアカウントには届かない。
- **プロンプトに入るアカウントの情報**：プロンプト（003）にThreadsのユーザー名を入れている所があれば、未接続のときはアカウントの名前を使う。パフォーマンスの改善メモ（006）は、未接続の間はないので、プロンプトの該当の部分は空になる（006の「データがまだない」と同じ扱い）。
- **同じ名前のアカウント**：名前の重なりは止めない（自分のアカウントどうしでも）。見分けは、未接続の印・Threadsのユーザー名で行う。

## Requirements *(mandatory)*

### Functional Requirements

#### アカウントを作る

- **FR-001**: System MUST ログインした利用者がアカウントを1つも持たないとき、「アカウントを作る」の画面を出す（001 FR-005の「アカウント追加画面」を、この画面に改める）。
- **FR-002**: Users MUST be able to アカウントの名前（前後の空白を除いて1〜50文字）だけを入れて、未接続のアカウントを作る。作った利用者がそのアカウントのオーナーになる。
- **FR-003**: System MUST 未接続のアカウントの作成で、オーナーのMembership・初期の設定（宣伝投稿の割合・プロンプトで作る件数・投稿のルールなど）・プランを、001・010でアカウントを作るときと同じにする（001 FR-011・FR-014、010 FR-013）。
- **FR-004**: System MUST 未接続のアカウントも、登録の上限（001 FR-015〜FR-017）に数える。上限に達していれば作らず、001 FR-017と同じ案内を出す。同じ利用者の同時の作成でも上限を超えない。
- **FR-005**: System MUST 切り替えメニューの「Threadsアカウントを追加」を「アカウントを作る」に置き換え、今の「Threadsアカウントを追加」の画面のURLを「アカウントを作る」に移す。アカウントを作る入口は「アカウントを作る」だけにし、Threadsにつなぐことで新しいアカウントを作る流れはなくす。
- **FR-006**: System MUST アカウントを作った後、そのアカウントのホームに移す。

#### Threadsにつなぐ

- **FR-010**: System MUST 「このアカウントの設定」の「Threadsとの接続」に、接続の状態（未接続・接続中・要再接続）を出す。未接続なら「Threadsで許可する」と「トークンを貼り付ける」の2つの方法を出す（010 FR-001・FR-002と同じ見せ方。トークンの方法は開くまで手順と入力欄を出さない）。
- **FR-011**: Users MUST be able to オーナーとして、未接続のアカウントを、どちらかの方法でThreadsアカウントにつなぐ。つなぐと、Threadsのユーザー名・表示名・画像を取り込み（001 FR-009）、接続中にし、つないだ方法を記録する（010の接続の方法）。
- **FR-012**: System MUST つなぐときのトークンの扱い・権限の確認・短期トークンの確かめ直し・確認の失敗の回数の待ちを、010と同じにする（010 FR-003・FR-011・FR-012・FR-015・FR-043）。
- **FR-013**: System MUST つないでも、アカウントのデータ（戦略・宣伝内容・リサーチ・投稿ストック・却下の記録・投稿のルール・NGワード・自動投稿の時刻・操作の記録）をそのまま残す。
- **FR-014**: System MUST つないだ後も、自動投稿はオフのままにする。オーナーがオンにしてから、005と同じく投稿を始める。つないだ直後の「つながりました」の案内に、「自動投稿を始める」（自動投稿の画面へ）を添える。
- **FR-015**: System MUST つなぐ操作を、オーナーだけに許す（Constitution原則IV、010 FR-034）。オーナー以外には、つなぐ操作とトークンの貼り付けを出さず、APIでも拒む。
- **FR-016**: System MUST つなぐ操作は、アカウントの数を増やさないので、登録の上限に達していても使えるようにする（001 FR-020と同じ）。
- **FR-017**: System MUST 一度つないだアカウントの接続し直しは、001 FR-020・010 FR-031〜FR-033のままにする（同じThreadsアカウントでだけ、どちらの方法でも）。
- **FR-018**: System MUST 同じ未接続のアカウントへの同時のつなぐ操作で、つながるThreadsアカウントを1つにする。後から終わった操作は「このアカウントは、すでにThreadsにつながっています」と出し、つないだ結果を変えない。
- **FR-019**: System MUST チームがあるアカウントでは、つないだことを方法とともに操作の記録に残す（010 FR-035と同じ。トークンの中身は書かない）。

#### 二重の登録の防止

- **FR-020**: System MUST つなぐ前に、ThreadsのユーザーIDとユーザー名（大文字・小文字を区別しない）で、登録済みのアカウントと照合する（010 FR-020・FR-023と同じ照合）。どちらかが一致したら、つながない。
- **FR-021**: System MUST 一致したアカウントが他の利用者のものなら、001 FR-012と同じ文言で拒み、登録している人を明かさない。未接続のアカウントとそのデータは変えない。
- **FR-022**: System MUST 一致したアカウントが自分の別のアカウントなら、つながず、「@ユーザー名は、あなたのアカウント『（名前）』につながっています」と、そのアカウントへのリンクを出す（US3-1）。未接続のアカウントとそのデータは変えない。未接続のアカウントの中身を、登録済みのアカウントへ移す操作は作らない。

#### 未接続の間の扱い

- **FR-030**: System MUST アカウントごとに、接続の状態を「未接続」「接続中」「要再接続」の3つで持つ（001 FR-018の2つに「未接続」を足す）。未接続は、一度もThreadsにつないでいない状態とする。
- **FR-031**: System MUST 未接続のアカウントでも、戦略（課題・宣伝内容・リサーチ）・プロンプトの生成・投稿の案の一括登録・重複の確認・承認と却下・投稿のルールとNGワード・操作の記録を、接続中と同じに使えるようにする（002〜004・008）。
- **FR-032**: System MUST 未接続のアカウントで、Threadsに投稿しない。自動投稿をオンにする操作を使えなくし、APIでも拒む。自動投稿の時刻の設定は保存できる。
- **FR-033**: System MUST 未接続のアカウントの自動投稿とパフォーマンスの画面に、「Threadsにつなぐと使えます」と、オーナーには「Threadsとの接続」への入口を出す。パフォーマンスの数字・グラフ・書き出しは出さない。
- **FR-034**: System MUST 未接続のアカウントのホームの一番上に、控えめな帯で「未接続」と、つなぐとできること（自動で投稿・反応の分析）と、オーナーには「Threadsにつなぐ」を出す。承認済みの案が1件以上あるときは、ホームの「次にやること」を、ほかの案内より先に「Threadsにつないで自動投稿を始めましょう」にする。つないだら、どちらも出さない。
- **FR-035**: System MUST 毎日の処理（期限の延長・プロフィールの取り直し・反応数の取得・トークンの確かめ直し）と、画面を開いたときの接続の確認（001 FR-018）で、未接続のアカウントを飛ばす。失敗や要再接続として扱わない。
- **FR-036**: System MUST 未接続のアカウントに、要再接続のバナー・「接続し直す」・投稿の権限や反応数の権限の案内を出さない。
- **FR-037**: System MUST プロンプト（003）でアカウントを示す所に、未接続のときはアカウントの名前を使う。

#### 表示

- **FR-040**: System MUST アカウントごとに、アカウントの名前（1〜50文字）を持つ。オーナーは「このアカウントの設定」で直せる。
- **FR-041**: System MUST 切り替えメニュー・アカウントの一覧・ホーム・設定・削除の確認・チームの画面など、アカウントを示すすべての所で、未接続のアカウントを、名前の頭文字の仮の画像・アカウントの名前・「未接続」の印で示す。
- **FR-042**: System MUST 接続中・要再接続のアカウントを、Threadsのプロフィール画像（なければ名前の頭文字の仮の画像）・アカウントの名前（主）・@ユーザー名（添える）で示す。つないでも、主の名前はアカウントの名前のままにする。
- **FR-043**: System MUST アカウントの削除の確認（001 FR-022）で入力を求める名前を、アカウントの名前にする。未接続のアカウントの削除では、トークンについての注意（010 FR-050）を出さない。
- **FR-044**: System MUST 本featureより前のアカウントの名前を、Threadsの表示名（なければ@ユーザー名）で埋める。

#### チーム

- **FR-050**: System MUST チームを作るとき（011 FR-010）とチームに入るとき（011 FR-013）に、未接続のアカウントを選べなくする。選べない形で並べ、「Threadsにつなぐと入れられます」と添える。
- **FR-051**: System MUST 接続中・要再接続のアカウントを1つも持たない利用者には、チームの作成と参加をさせず、つなぐ案内（未接続のアカウントがあれば、その「Threadsとの接続」への入口）を出す（011 FR-014の「自分のアカウントを1つも持たない人」を、「Threadsにつないだアカウントを1つも持たない人」に読み替える）。つないだ後に招待リンクを開き直すと、続きから参加できる。
- **FR-052**: System MUST 未接続のアカウントがチームに入っている状態を作らない（チームのアカウントは、どれも一度はThreadsにつないだもの）。

#### 文書

- **FR-060**: System MUST 001のspecのFR-005（最初の画面）・FR-018（接続の状態）と、010のspecのFR-001（追加の画面）・011のspecのFR-014に、本featureで改めたことを書き足す。PRDの該当の要件（アカウントの追加・オンボーディング）も直す（Constitution「開発ワークフロー」）。

### Key Entities *(include if feature involves data)*

- **Account**：001のAccount。アカウントの名前を足し、接続の状態に「未接続」を足す。未接続の間は、ThreadsのユーザーID・ユーザー名・表示名・画像・接続の方法を持たない。つないだときに入り、その後はThreadsのユーザーIDは変わらない（010 FR-033のIDの更新を除く）。
- **Threadsの接続**：001・010のまま。未接続のアカウントには、ない。
- **自動投稿の設定**：005のまま。未接続の間も時刻は保存でき、オンにはできない。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: はじめてログインした人が、ログインから1分以内に、名前だけでアカウントを作り、そのアカウントの戦略の画面を開ける。
- **SC-002**: はじめてログインした人が、Threadsにつながずに、戦略の入力→プロンプトの生成→案の一括登録→承認までを、1回のログインの中で終えられる（手で確かめる）。
- **SC-003**: 未接続のアカウントをつないだ前後で、戦略・投稿ストック・設定・操作の記録の件数が同じ（自動テスト）。
- **SC-004**: 同じThreadsアカウントに、2つのアカウントがつながることがない（自動テストで、自分の別のアカウント・他の利用者のアカウントそれぞれについて、2つの方法の組み合わせで確かめる）。
- **SC-005**: 未接続のアカウントから、Threadsへの投稿・Threadsへの問い合わせが1回も起きない（自動テスト。毎日の処理と自動投稿を含む）。
- **SC-006**: アカウントを示すすべての画面で、未接続のアカウントが「未接続」と分かり、ユーザー名の代わりにアカウントの名前が出る（空の表示・「@undefined」のような表示が0件）。
- **SC-007**: 接続中のアカウントだけを使う今の利用者の操作の手数は、アカウントの追加の入口を除いて変わらない。

## Assumptions

- 未接続のアカウントを登録の上限・無料体験の上限・料金にどう数えるかは、決済（013）で決める。本featureでは、001の上限に未接続のアカウントも数える（数えないと、上限を超えて作れてしまうため）。
- 「Threadsで許可する」の流れ（001）は、今は検証期間中で招待されたテスターだけが使える。この案内（002 FR-028）は、つなぐ画面の「Threadsで許可する」の下に今までどおり出す。
- アカウントの名前は、利用者の画面のためだけに使い、Threadsには送らない。
- Threadsにつないだアカウントを未接続に戻す操作、Threadsアカウントを付け替える操作は作らない（Edge Cases）。
- 未接続のアカウントに、002〜004のどの機能もThreadsからの情報を要しない（2026-10-12に確認した前提。planで画面ごとに確かめる）。
- 利用者の退会（docs/next-features.md「D.退会」）は、本featureの後に作る。
