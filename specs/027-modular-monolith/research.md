# 調べたことと決めたこと（Research）：Threadsアプリをモジュラーモノリスに整理する

**日付**：2026-11-10 | **計画**：[plan.md](./plan.md)

2026-11-10時点の`apps/api/src`（約2万行、処理48・APIの入口のファイル32・表42）の読みこみ関係と、表を使っている場所を機械的に洗い出して決めた。

## R1. モジュールの種類と並び

- **決定**：コードを次の5つに分ける。spec.mdの3種類（共通・アプリ・窓口）に、どこからでも使う「土台」と、全部をつなぐ「組み立て」を足す。

  | 種類 | 置き場所 | 中身 | 使ってよい相手 |
  |---|---|---|---|
  | 土台（kernel） | `src/kernel/` | 環境の値と設定・エラー・ログ・入力の確かめ・暗号と識別子のハッシュ・DBの接続とロック | なし（外部のライブラリだけ） |
  | 窓口（adapters） | `src/adapters/<名前>/` | Stripe・ThreadsのAPI・Metaの署名つきリクエスト | 土台 |
  | 共通（platform） | `src/platform/` | 利用者・アカウントとメンバー・権限・契約と決済・機能のON/OFF・テストのグループ・上限・チーム・紹介・活動の記録・運営・退会 | 土台・窓口 |
  | アプリ（apps） | `src/apps/<名前>/`（今は`threads`だけ） | アプリ固有の処理・表・APIの入口 | 土台・窓口・共通（の入口） |
  | 組み立て（composition） | `src/app.ts`・`src/index.ts`・`src/jobs/` | APIの入口の登録、定期処理の振り分け、モジュールのつなぎこみ | すべて（の入口） |

- **理由**：
  - エラー・ログ・環境の値は窓口も共通もアプリも使う。これを共通に入れると、窓口から共通への依存（禁止）が生まれる。
  - 毎日の処理（`daily-jobs`）や`app.ts`は、共通とThreadsの両方を呼ぶ。つなぐ役の場所を決めておかないと、どちらかのモジュールに逆向きの依存が残る。
- **ほかの案**：土台を共通の中に入れる：窓口が共通に依存する形になる。不採用。

## R2. 入口の単位

- **決定**：
  - 入口（`index.ts`）は、**共通全体（`platform/index.ts`）・アプリごと（`apps/threads/index.ts`）・窓口ごと（`adapters/<名前>/index.ts`）**に1つ置く。土台は`kernel/index.ts`ではなく、ファイルごとに直接使ってよい（中身が小さく、どこからでも使うため）。
  - 共通の中の小分け（`platform/billing/`など）同士、Threadsの中の小分け同士は、入口を通さずに使ってよい。
- **理由**：
  - 2作目から見た約束は「共通の入口」だけでよい。共通の中を細かく区切ると、今ある相互の呼び出し（権限 ↔ 契約 ↔ テストのグループ ↔ 招待）に入口を通す直しが増え、動きを変えないという前提に対して危険が大きい。
  - 共通の中の区切りは、2作目で本当に共通だった部分を取り出すときに見直す。

## R3. 境界の止め方

- **決定**：ESLintの**このリポジトリの中だけの規則**（`eslint-rules/module-boundaries.js`）を作り、`apps/api/src`にだけかける。
  - 読みこみ先のパスを、読みこむファイルからの相対で解き、両者の種類とモジュールを求めて判定する。
  - 4つの違反を止める：①ほかのモジュールの入口でないところ、②共通 → アプリ、③アプリ同士、④窓口 → 共通・アプリ、土台 → 土台以外。
  - モジュールの判定はパスの形（`src/apps/<名前>/…`）で行うので、アプリを足しても設定は要らない（FR-016）。
  - 規則のテストは、ESLintの`RuleTester`で書く（4つの違反と、通る例）。
  - テスト（`apps/api/test`）と`scripts/`には、かけない。
- **理由**：
  - 新しい依存を足さない（Constitutionの運用コストの制約）。日本語のわかりやすいメッセージを出せる。
  - 標準の`no-restricted-imports`では「自分のアプリ以外のアプリ」をパスの形で書き分けにくい。
- **ほかの案**：
  - `eslint-plugin-boundaries`：よく使われているが、依存（解決のためのパッケージを含む）が増え、設定も大きい。不採用。
  - `dependency-cruiser`：CIに別の道具が増える。不採用。

## R4. 共通からThreadsを呼んでいるところ（逆向きの依存）

洗い出した結果、共通にすべき処理がThreads固有の処理を呼んでいるところは次の5つ。

| # | 場所 | 今の呼び出し | 決定 |
|---|---|---|---|
| 1 | `account-service`の`completeConnection`・`verifyConnection` | Threadsの接続・テスター招待・接続の表 | 接続の処理はThreadsのものなので、**Threadsへ移す**。共通の`account-service`には、作る・名前を変える・消す・数える・上限・最後に開いたアカウントの記録（`openAccount`）を残す |
| 2 | `account-service`の`deleteAccount` | テスター招待の取り下げ（`withdrawForAccountDeletion`） | 共通に「アカウントを消す前の知らせ」を作り、Threadsが受け取る（同じトランザクションの中で呼ぶ） |
| 3 | `withdrawal-service`（退会） | テスター招待の片づけ（`purgeForWithdrawal`）、Threadsのデータ削除の要求の表の更新 | 共通に「退会する前の知らせ」を作り、Threadsが受け取る（同じトランザクション） |
| 4 | `limit-service`（上限） | 自動投稿を起こす（`notifyWake`）、運営の設定を読む（`readOperatorSettings`、テスター招待のサービスにある） | 起こすのは「上限が変わった知らせ」に替え、Threadsが受け取る。`readOperatorSettings`は運営の設定の表の持ち主である共通へ移す |
| 5 | `/api/me/needs-review-counts`（`routes/me.ts`の中） | 確かめ待ちの件数（`account-review-counts`、投稿の案の表） | Threads専用の入口なので、知らせにせず**入口ごとThreadsへ移す**（URLと応答は変えない。セルフレビューの指摘） |

- **知らせの作り**：共通の中に、知らせの名前ごとに受け取る関数を並べる小さな登録の仕組みを置く。登録は組み立て（`app.ts`の初めと`index.ts`の定期処理の初め）で、Threadsの入口の`registerThreads()`を1回呼んで行う。
- **動きを変えないこと**：知らせは、今の呼び出しと同じ場所・同じ順番・同じトランザクション（`tx`を渡す）で、`await`して呼ぶ。登録されていなければ何もしない（テストで共通だけを使うとき）。
- **確かめ方**：今ある結合テスト（テスター招待の取り下げ・退会の片づけ・上限を変えたら起こす・確かめ待ちの件数）がそのまま通ること。
- **ほかの案**：
  - 共通からThreadsの入口を直接呼ぶ：依存の向きの違反が残る。不採用。
  - 非同期のイベント（キューやoutbox）にする：トランザクションの範囲が変わり、動きが変わる。今回は不採用（構想ノートの「必要時に`EventPublisher`とoutbox」は、その時に）。

## R5. 運用するアカウントの表と、運営の設定の表

- **決定**（Clarifications 2026-11-10）：
  - `accounts`の持ち主は共通。共通が書き換える列は、`id`・`name`・`created_at`・`updated_at`・`last_used_at`。
  - それ以外の列（`threads_user_id`・`username`・`display_name`・`profile_picture_url`・`connection_status`・`connection_method`・`connection_generation`・`reconnect_hint`・投稿の長さ・CORE RULES・宣伝の割合・プロンプトの件数・`insights_denied_at`・`replies_denied_at`・各`*_changed_at`・`*_version`・`*_updated_by_user_id`など）は、**Threadsが書き換えてよい例外**として、列の一覧を地図に書く。将来Threads専用の表（例：`threads_account_settings`）へ移す候補。
  - `operator_settings`の持ち主も共通（上限の既定値）。`tester_slot_capacity`はThreadsが書き換えてよい例外。
- **理由**：表を分ける（新しいマイグレーション）は今回の範囲外（FR-012）。持ち主と書き換えてよい列を決めておけば、2作目は共通の列だけを使える。
- **書き換えの約束**：ESLintでは列までは止められないので、地図に書き、レビューで確かめる（例外として件数を見える形にする）。

## R6. 表の定義の分け方

- **決定**：
  - `src/platform/schema.ts`（共通の17表と、列挙型・共通の時刻の列の定義）と、`src/apps/threads/schema.ts`（Threadsの25表）に分ける。
  - `src/db/schema.ts`は、両方を読み直して出すだけのファイルにする（drizzle-kitの`schema`の指定と、テストの読みこみ先を変えないため）。モジュールの中のコードは、`db/schema`ではなく自分の`schema.ts`（ほかのモジュールの表は、その入口）から読む。
  - Threadsの表が共通の表（`users`・`accounts`）を参照するのはよい（アプリ → 共通）。共通の表からThreadsの表への参照は、今はない。
- **確かめ方**：`pnpm --filter api db:generate`を流して「変更なし」（新しいマイグレーションができない）こと（FR-012・SC-004）。

## R7. APIの入口が変わらないことの確かめ方

- **決定**：Honoの`app.routes`から、①「メソッド パス ×処理の数」を並べたもの（入口ごとの関所（認証・運営者だけ・契約の確かめ）の数も見る）と、②すべての入口にかかる関所（メソッドが`ALL`）の登録した順番、を書き出して`apps/api/test/repo/routes.snapshot.txt`に残し、比べるテストを足す（`test/repo/routes-snapshot.test.ts`）。テストは027のあとも残し、入口を足す・変えたら`pnpm --filter api routes:snapshot`で書き直す（セルフレビューの指摘で、件数と順番を見るようにし、置き場所をテストの横にした）。
- **理由**：APIのURLとメソッドを変えないこと（FR-011・SC-004）を、人の目でなく機械で確かめる。

## R8. PRの分け方

- **決定**：
  - **PR1（地図と決まり）**：モジュール地図（`docs/module-map.md`）、docs/architecture.mdとConstitutionの書き足し、ESLintの規則とそのテスト、APIの入口の一覧のテスト。規則はこのPRで有効にするが、モジュールのフォルダーがまだないので、どのファイルにも当たらない。
  - **PR2（並べ替え）**：①土台・窓口 → ②逆向きの依存の解消（接続の処理の切り出し・知らせ）と共通 → ③Threads・表の定義の分割、の3つのコミットに分ける。規則はフォルダーができた順に効き始めるので、②では共通へ移す前に逆向きの依存をなくす。各コミットで、境界の規則を含むすべてのチェックとテストが通る。
- **理由**：地図（設計）を先にレビューでき、並べ替え（機械的な移動が主）とまぜない。並べ替えは途中でdevelopの変更を取りこむと手間が大きいので、1つのPRで短く終える。
