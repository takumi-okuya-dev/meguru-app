# Feature Specification:Threadsアプリをモジュラーモノリスに整理する（動きは変えない）

**Feature Branch**: `feature/027-modular-monolith`

**Created**: 2026-11-10

**Status**: Draft

**Input**: 2026-11-10、このThreadsアプリを起点に、共通アカウント・共通契約・アプリ別の利用権で束ねる個人開発スイートを育てると決めた（構想の正本：personal-knowledge-base の「個人開発版Google Workspace構想（スイート型SaaS）」）。構想ノートの方針は「論理の分離を先に、物理の分離は後に」「Threadsを基準に進め、2作目で共通化を確かめ、必要な部分だけ後で分ける」「直近は現状の棚卸し」。そこで、将来アプリを切り出しやすいように、APIのコードの境界を整える。今回は2段階まで。(1) 棚卸し：表・処理・APIの入口を「共通の候補」「Threads固有」「外部サービスの窓口」に仕分け、データの持ち主とモジュール間で呼んでよい入口を決めた「モジュール地図」を作る。(2) APIの並べ替え：地図のとおりにコードを分け、ほかのモジュールの中身を直接使うことを自動のチェックで止める。表の定義もモジュールごとに分ける。利用者から見える動き（画面・APIの応答・料金・データ）は何も変えない。2作目も同じリポジトリの中に、Threadsと並ぶモジュールとして足せる形にする。

**Source**: 構想ノート（personal-knowledge-base `Wiki/仕事/システム開発/アイデア/個人開発版Google Workspace構想（スイート型SaaS）.md` の4・5・8章）、[docs/architecture.md](../../docs/architecture.md)、[Constitution](../../.specify/memory/constitution.md) 4.4.0（技術スタック制約・開発ワークフロー）。

## Clarifications

### Session 2026-11-10

- Q:運用するアカウントの表（accounts：番号・名前・持ち主に加え、@ユーザー名・接続・投稿の長さ・CORE RULESなどThreads固有の列が大半）の持ち主は、共通とThreadsのどちらか？ → A:共通。番号・名前・持ち主（メンバー・チーム・料金の数の基準）は共通が持ち、2作目でも使う。Threads固有の列は「Threadsが書き換えてよい例外」として地図に書き、将来Threads専用の表へ移す候補にする（FR-004・FR-018）。

## 用語

- **モジュール**：まとまった役割を持つコードの単位。次の3種類に分ける。
  - **共通（platform）**：どのアプリでも使う見込みのもの。利用者・アカウントとメンバー・契約と決済・機能のON/OFFと上限・チーム・運営・活動の記録・退会とデータの削除など。
  - **アプリ（apps）**：アプリ固有のもの。今はThreadsだけ（接続・トークン・投稿の案・予約と自動投稿・数字の取得と分析・戦略・リサーチ・メンション・テスター招待・外部媒体など）。2作目はここに並べて足す。
  - **窓口（adapters）**：外部サービスとのやりとり（決済のStripe・ThreadsのAPI・暗号・識別子のハッシュなど）。業務の判断は持たない。
  - このほかに、どこからでも使う**土台**（エラー・ログ・環境の値・DBの接続など）と、全部をつなぐ**組み立て**（APIの入口の登録・定期処理の振り分け）を置く（plan で決めた。research.md R1）。
- **入口**：モジュールがほかのモジュールに見せる、使ってよい部分。入口にないものは、そのモジュールの中だけで使う。
- **データの持ち主**：その表を書き換えてよいモジュール。ほかのモジュールは、持ち主の入口を通して読む・頼む。
- **モジュール地図**：上の仕分け・持ち主・入口・依存の向きを1つにまとめた文書。

## User Scenarios & Testing *(mandatory)*

このfeatureの利用者は、開発者（このアプリの作り手）と、開発を手伝うAIエージェントである。アプリの利用者から見える変化はない。

### User Story 1 - どのコード・どの表が、どのモジュールのものかがわかる（Priority: P1）

開発者がモジュール地図を開くと、APIのすべての表・処理・入口が、共通・Threads・窓口のどれに属するかと、表ごとのデータの持ち主がわかる。モジュール同士で、どの向きに、どの入口を使ってよいかもわかる。2作目を作るときに、何が共通で使えそうか、どこを触ってはいけないかを、コードを読み回らずに判断できる。

**Why this priority**：構想ノートで「直近の次のアクション」とされた棚卸しそのもの。並べ替え（US2）の設計図になる。

**Independent Test**：地図の一覧と、今のAPIの表・処理・入口の一覧を突き合わせ、漏れも重なりもないことを確かめる。

**Acceptance Scenarios**:

1. **Given** モジュール地図、**When** 開発者が今ある表（42表）のどれかを探す、**Then** その表のデータの持ち主のモジュールが1つだけ書いてある。
2. **Given** モジュール地図、**When** 開発者が今ある処理やAPIの入口のどれかを探す、**Then** それがどのモジュールに属するかが書いてある。
3. **Given** モジュール地図、**When** 開発者がモジュール同士の依存を確かめる、**Then** 依存の向き（アプリ → 共通 → 窓口。共通からアプリへは依存しない）と、例外の扱いが書いてある。
4. **Given** 共通とThreadsの両方の性質を持つもの（例：運用するアカウントの表は、メンバーと契約の数の単位でもあり、Threadsとの接続の情報も持つ）、**When** 開発者が地図を見る、**Then** 今どちらを持ち主にしたか（運用するアカウントの表は共通）と、Threadsが書き換えてよい列、将来分ける候補であることが書いてある。

---

### User Story 2 - コードがモジュールごとに分かれ、境界が自動で守られる（Priority: P1）

APIのコードが、モジュール地図のとおりに共通・Threads・窓口のモジュールに分かれる。各モジュールには入口があり、ほかのモジュールの中身を直接使うコードを書くと、自動のチェックが失敗して知らせる。表の定義もモジュールごとに分かれ、どの表がどのモジュールのものかがコードからもわかる。

**Why this priority**：地図だけでは、日々の変更で境界が崩れていく。自動で止めることで、2作目を足すときもThreadsを切り出すときも、境界をあてにできる。

**Independent Test**：わざとThreadsのモジュールの中身を共通のモジュールから直接使うコードを書くと、自動のチェックが失敗する。入口を通せば通る。

**Acceptance Scenarios**:

1. **Given** 並べ替えたコード、**When** 開発者がほかのモジュールの入口でないところを直接使う、**Then** 自動のチェック（ふだんのチェックとCI）が失敗し、どのモジュールの境界を越えたかがわかる。
2. **Given** 並べ替えたコード、**When** 開発者が共通のモジュールからアプリのモジュールを使う、**Then** 自動のチェックが失敗する（依存の向きの違反）。
3. **Given** 並べ替えたコード、**When** 開発者が表の定義を探す、**Then** 持ち主のモジュールの中にある。
4. **Given** 並べ替えた直後のコード、**When** 自動のチェックを流す、**Then** 境界の違反は0件。

---

### User Story 3 - 利用者から見える動きは何も変わらない（Priority: P1）

並べ替えのあとも、画面・APIの入口と応答・料金・データ・自動投稿などの定期処理は、並べ替えの前とまったく同じに動く。今あるテストは、中身を変えずにすべて通る（テストのファイルの場所と読みこみ先の直しは除く）。テスト版にデプロイしても、これまでどおり動く。

**Why this priority**：本番の公開の前で、利用者に影響を出せない。リファクタリングの前提条件。

**Independent Test**：並べ替えの前後で、すべての自動テストが同じ数だけ通り、マイグレーションのファイルとAPIの入口の一覧に差がないことを確かめる。

**Acceptance Scenarios**:

1. **Given** 並べ替えたコード、**When** すべての自動テスト・型の確認・ESLintを流す、**Then** すべて通り、テストの数は並べ替えの前より減らない。
2. **Given** 並べ替えたコード、**When** マイグレーションのファイルと表の定義から作られるデータベースの形を比べる、**Then** 並べ替えの前と差がない（新しいマイグレーションはできない）。
3. **Given** 並べ替えたコード、**When** APIの入口（URLとメソッド）の一覧を比べる、**Then** 並べ替えの前と同じ。
4. **Given** 並べ替えたコードをテスト版にデプロイする、**When** ログイン・アカウントを開く・投稿の案・自動投稿の予約・設定を確かめる、**Then** これまでどおり動く。

---

### User Story 4 - 2作目をThreadsと並ぶモジュールとして足せる（Priority: P2）

開発者が2作目を作るとき、モジュール地図と手順に沿って、Threadsと並ぶアプリのモジュールを足せる。共通のモジュールの入口（利用者・アカウントとメンバー・契約・機能のON/OFFなど）を使い、Threadsのモジュールには触らない。

**Why this priority**：2作目は未定で、今回は作らない。ただ、受け皿の形と手順を決めておかないと、境界の決め方が2作目で通用しない。

**Independent Test**：手順のとおりに、中身のない仮のアプリのモジュールを足すと、自動のチェックがそのモジュールにも同じ境界を当てる（確かめたあとは消す）。

**Acceptance Scenarios**:

1. **Given** モジュール地図の「アプリを足す手順」、**When** 開発者が仮のアプリのモジュールを足す、**Then** 新しい設定を書き足さなくても、Threadsと同じ境界のチェックがかかる。
2. **Given** 仮のアプリのモジュール、**When** そこからThreadsのモジュールの中身を使う、**Then** 自動のチェックが失敗する（アプリ同士は直接使わない）。

---

### Edge Cases

- 共通の処理が、今はThreads固有の処理を呼んでいる（例：アカウントをつないだときに、Threadsのテスター招待の申し込みを進める・アカウントの削除のときにテスター招待を取り下げる）→ 共通からアプリへは依存しない決まりに合わせる。共通の側は「つないだ・消した」の知らせだけを出し、アプリの側が入口で受け取る形にする。動き（同じトランザクションで進むこと）は変えない。
- 複数のモジュールにまたがる定期処理（自動投稿・数字の取得・毎日の処理など）→ どのモジュールが持つかを地図に書き、ほかのモジュールは入口を通して使う。
- 表同士の参照（外部キー）がモジュールをまたぐ（例：Threadsの表が利用者やアカウントの表を参照する）→ アプリから共通への参照はよい。共通からアプリの表への参照は作らない（今あるものは地図に例外として書く）。
- テストのコードが中身を直接使っている → テストは境界のチェックの対象外にしてよい（ただし場所と読みこみ先は新しい構成に合わせる）。
- 窓口（外部サービス）を共通とアプリの両方が使う → 窓口はどちらからも使ってよい。窓口からは共通・アプリを使わない。
- 境界のチェックに、今すぐは直せない違反が見つかった → 例外として地図に理由とともに書き、件数を増やさない（0件を目標にし、残すものは一覧で見える）。
- 並べ替えの途中で、ほかのfeatureの変更がdevelopに入る → 並べ替えのPRを小さく分け、取りこみ直しの手間を減らす（計画で決める）。

## Requirements *(mandatory)*

### Functional Requirements

**モジュール地図（US1）**

- **FR-001**：APIのすべての表・処理・APIの入口を、共通・アプリ（Threads）・窓口のどれかのモジュールに仕分けたモジュール地図を、リポジトリの文書として作らなければならない。
- **FR-002**：地図には、表ごとのデータの持ち主（1つのモジュール）を書かなければならない。持ち主でないモジュールは、その表を書き換えない。
- **FR-003**：地図には、モジュールごとの入口（ほかのモジュールが使ってよいもの）と、依存の向き（アプリ → 共通 → 窓口、アプリ同士は直接使わない）を書かなければならない。
- **FR-004**：共通とアプリの両方の性質を持つ表・処理は、今の持ち主と、将来分ける候補であることを地図に書かなければならない。
- **FR-005**：今すぐは直せない境界の違反は、例外として理由とともに地図に書かなければならない。
- **FR-018**：運用するアカウントの表（accounts）の持ち主は共通とする。番号・名前・持ち主に関わる列は共通が書き換え、Threads固有の列（@ユーザー名・接続・投稿の長さ・CORE RULESなど）はThreadsが書き換えてよい例外として、列の一覧を地図に書く。Threads固有の列は、将来Threads専用の表へ移す候補とする（今回は移さない）。

**並べ替えと境界のチェック（US2）**

- **FR-006**：APIのコードを、地図のとおりに共通・アプリ（Threads）・窓口のモジュールに分けなければならない。
- **FR-007**：各モジュールに入口を置き、ほかのモジュールからは入口だけを使えるようにしなければならない。
- **FR-008**：入口でないところを直接使うコード、共通からアプリへの依存、アプリ同士の直接の依存、窓口から共通・アプリへの依存、土台から土台のほかへの依存は、自動のチェック（ふだんのチェックとCI）で失敗にしなければならない。
- **FR-009**：表の定義を、持ち主のモジュールごとに分けなければならない。表の名前・列・制約は変えない。
- **FR-010**：共通の処理がアプリの処理を呼んでいるところは、共通の側から知らせを出してアプリの側が受け取る形に直さなければならない。トランザクションの範囲など、動きは変えない。

**動きを変えない（US3）**

- **FR-011**：画面・APIの入口（URLとメソッド）と応答・料金・データ・定期処理の動きを変えてはならない。
- **FR-012**：新しいマイグレーションを作ってはならない（表の定義を分けても、データベースの形は同じ）。
- **FR-013**：今あるテストは、中身を変えずにすべて通らなければならない（ファイルの場所と読みこみ先の直しは除く）。テストの数は減らさない。
- **FR-014**：テスト版へのデプロイと、そこでの基本の操作（ログイン・アカウント・投稿の案・自動投稿の予約・設定）が、並べ替えの前と同じに動かなければならない。

**2作目の受け皿（US4）**

- **FR-015**：地図に「アプリのモジュールを足す手順」を書かなければならない。
- **FR-016**：アプリのモジュールを足したとき、新しい設定を書き足さなくても、Threadsと同じ境界のチェックがかかるようにしなければならない。

**決まりの記録**

- **FR-017**：モジュールの決まり（3種類・入口・依存の向き・データの持ち主）を、[docs/architecture.md](../../docs/architecture.md)とConstitutionの技術スタック制約に書かなければならない。

### Key Entities *(include if feature involves data)*

- **モジュール**：名前・種類（共通・アプリ・窓口）・入口・持っている表・依存してよい相手。
- **表の持ち主**：表ごとに1つのモジュール。今ある42表すべてに割り当てる。
- **境界の例外**：今すぐは直せない違反。場所・理由・解消の予定。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：今あるAPIの表・処理・入口の100%が、モジュール地図でどれか1つのモジュールに割り当てられている（漏れ・重なり0件）。
- **SC-002**：並べ替えの直後、自動のチェックでの境界の違反は0件（地図に書いた例外を除く。例外は5件以下を目標）。
- **SC-003**：わざと境界を越えたコードを書くと、100%自動のチェックで失敗する（入口の外・共通からアプリ・アプリ同士・窓口から外の4つの型それぞれで確かめる）。
- **SC-004**：並べ替えの前後で、自動テストの成功数が同じかそれ以上で、失敗は0件。マイグレーションの差・APIの入口の一覧の差は0件。
- **SC-005**：テスト版での基本の操作（5つ）が、並べ替えの前と同じに動く。
- **SC-006**：開発者（またはAIエージェント）が、ある表やAPIの入口がどのモジュールのものかを、地図を開いてから1分以内に答えられる。

## Assumptions

- 今回の範囲はAPIだけ。Webとsharedの分割は、APIの境界が固まってから別のfeatureで行う。
- データベースはこれまでどおり1つで、表の名前・Postgresのスキーマは変えない。モジュールごとのスキーマ分けは、2作目のあとで必要なら考える。
- 共通のモジュールは「共通の候補」であり、汎用の基盤として作り込まない（構想ノート：「今すぐ汎用Suite Coreを完成させない」）。workspaces・利用権・外部の認証の対応など新しい表や仕組みは足さない。
- デプロイの単位（Workersの1つのAPI）と、定期処理の動かし方は変えない。
- 自動のチェックは、今使っているESLintとCIに足す（新しい有料のサービスは使わない）。
- 並べ替えは、レビューしやすいようにいくつかのPRに分けてよい（計画で決める）。どのPRの時点でも、すべてのテストが通る。
- 構想ノートは外部のリポジトリにあるので、地図からは場所を書いて参照するだけにする（中身は写さない）。

## Out of Scope

- Webとsharedのモジュール分割。
- Postgresのスキーマの分割、表の名前の変更、新しいマイグレーション。
- workspaces・利用権（entitlement）・外部の認証の対応（auth_identities）など、スイート向けの新しい表と仕組み。
- 認証（Clerk）・決済（Stripe）の作り直しや、ほかのクラウドへの移行。
- 2作目のアプリそのもの、リポジトリの名前の変更。
- 利用者から見える機能の追加・変更。
