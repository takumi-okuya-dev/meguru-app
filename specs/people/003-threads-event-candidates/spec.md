# Feature Specification：Threadsの宣伝内容のイベントから、人物メモのイベントを作る

**Feature Branch**: `feature/people-003-threads-event-candidates`

**Created**: 2026-11-15

**Status**: Draft

**Input**: 3つのアプリのイベントを「Threads → 人物メモ」「Threads → 集金」の一方通行でつなぐ（ユーザー、2026-11-15）。Threads → 集金は集金 001（Threadsのイベントの候補）でできている。この機能で Threads → 人物メモを足す。あとでマイクロサービスにすることを考えて作る。

**Source**: [集金 001 contracts/events.md](../../collect/001-event-day-collection/contracts/events.md) 2（Threadsが出す出来事）、人物メモ 001 の [spec.md](../001-people-memo/spec.md)「イベントのつなぎ（将来、出来事でつなぐ）」、[アプリを分けて作る決まり](../../../docs/app-separation.md)。

## Clarifications

### Session 2026-11-15（ユーザーと決めたこと）

- Q：3つのアプリのイベントをどうつなぐか？ → A：**Threads → 人物メモ、Threads → 集金の一方通行で十分**。集金 → 人物メモ（参加者を渡す）・人物メモ → 集金はつながない。
- Q：だれが作るか？ → A：今は並行開発していないので、このセッションだけで作る。
- Q：作り方の前提は？ → A：**あとでマイクロサービスにできるように作る**（パターン①：人物メモは Threads の表を読まず、出来事で受け取って自分の表に写す）。

## 用語

- **Threadsのイベントの候補**：作り手が めぐる Threads の宣伝内容に開催日時を入れて保存したイベント。人物メモは、その名前と開催日時を出来事で受け取って写しておく。
- **Threadsから作ったイベント**：候補を選んで作った人物メモのイベント。元の宣伝内容の番号を持つ。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Threadsのイベントを選んで、人物メモのイベントを作る (Priority: P1)

作り手は めぐる Threads で、宣伝内容（交流会など）に開催日時を入れて保存している。人物メモで「イベントを作る」を開くと、そのイベントが候補に並び、選ぶと名前と開催日が入る。そのまま作れば、あとでアンケートを取り込むときにそのイベントを選べる。

**Independent Test**：Threadsで「12月の交流会」（2026-12-20 19:00）を保存する → 人物メモの「イベントを作る」に候補「12月の交流会」が出る → 選ぶと名前「12月の交流会」・開催日 2026-12-20 が入る → 作る → イベントの一覧に出る。候補には「作った」と出る。

**Acceptance Scenarios**：

1. **Given** Threadsで開催日時のある宣伝内容を保存した作り手、**When** 人物メモの「イベントを作る」を開く、**Then** その宣伝内容の名前と開催日時が候補に出る（開催日時の近い順。過ぎたものは後ろ）。
2. **Given** 候補が出ている、**When** 候補を選ぶ、**Then** 名前と開催日（日本時間の日付）が入力欄に入り、直してから作れる。「自分の会」は初めから付いている。
3. **Given** 候補から作ったイベントがある、**When** もう一度「イベントを作る」を開く、**Then** その候補には「作った」と出て、選べない（同じ宣伝内容から2つ目は作れない）。
4. **Given** アンケートの取り込みで「新しいイベントを作る」を開く、**When** 候補を選んで作る、**Then** そのイベントが選ばれた状態で取り込みを続けられる。
5. **Given** ほかの人の宣伝内容、**When** 作り手の候補を開く、**Then** ほかの人の宣伝内容は出ない。

### User Story 2 - Threadsで直した・消したことが候補に反映される (Priority: P2)

作り手が Threads で宣伝内容の名前や開催日時を直したり、開催日時を消したり、宣伝内容を消したりすると、人物メモの候補もそれに合わせて変わる。

**Independent Test**：候補「12月の交流会」がある → Threadsで開催日を 12-21 に直す → 候補の開催日が 12-21 になる → Threadsで宣伝内容を消す → 候補から消える。

**Acceptance Scenarios**：

1. **Given** 候補がある、**When** Threadsで名前か開催日時を直す、**Then** 候補の名前と開催日時が新しくなる。
2. **Given** 候補がある、**When** Threadsで開催日時を消すか宣伝内容を消す、**Then** 候補に出なくなる。
3. **Given** 候補から作ったイベント、**When** Threadsで元を直す・消す、**Then** 人物メモのイベント（名前・開催日・取り込んだ回答）は変わらない。
4. **Given** 出来事が2回届く・順番が入れ替わって届く、**When** 受け取る、**Then** 結果は1回だけ・新しい順に届いたときと同じになる。

### Edge Cases

- この機能を入れる前に Threads で保存した宣伝内容は、候補に出ない（出来事は、出したときの受け取り先にだけ届くため）。Threadsでもう一度保存すると出る。候補がないときの案内にそう書く。
- 開催日時のない宣伝内容は、Threadsが出来事を出さないので候補にならない。
- 作り手が退会したら、候補もほかの人物メモのデータと一緒に消す。
- 候補から作ったイベントを消したら、その候補はまた選べるようになる。
- 人物メモを使えない人（運営者が開いていない人）にも出来事は届いて候補は写るが、画面と API は使えない（403）。あとで開いたときに候補が出る。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：人物メモは、Threads が出す「宣伝内容のイベントの情報を保存した」「消した」の出来事を受け取り、作り手ごとの候補として自分の表に写す。Threads の表は読まない。
- **FR-002**：候補に写すのは、宣伝内容の番号・作り手（アカウントの持ち主）・名前・開始の時刻だけ。会場・定員・料金・本文は写さない。
- **FR-003**：同じ出来事が2回届いても、結果を変えない。持っている「起きた時刻」より古い出来事は捨てる。
- **FR-004**：作り手には、自分の候補だけを、消されていないものに限って、開催日時の近い順（過ぎたものは後ろ）で見せる。候補から作ったイベントがあれば、その番号を添える。
- **FR-005**：イベントを作るとき、候補の番号を渡せる。人物メモは、それがその作り手の消されていない候補かを確かめ、イベントに元の番号を持たせる。ほかの人の番号・知らない番号は 400 VALIDATION_FAILED。
- **FR-006**：1つの宣伝内容から作れる人物メモのイベントは、作り手ごとに1つ。2つ目は 409 PEOPLE_THREADS_EVENT_USED。
- **FR-007**：イベントの名前・開催日・自分の会かは、候補から作るときも作り手が直せる。作ったあとは Threads の変更に合わせて変えない。
- **FR-008**：「イベントを作る」の画面と、取り込みの「新しいイベントを作る」に、候補を選ぶ欄を出す。選ぶと名前と開催日（開始の時刻の日本時間の日付）が入る。候補がないときは、Threadsで開催日時を入れて保存すると出ることを案内する。
- **FR-009**：作り手が退会したら（user.withdrawn）、候補も消す。
- **FR-010**：ログ・ブラウザの保存に、候補の名前を残さない（001の決めごと）。

### Key Entities

- **Threadsのイベントの候補**：宣伝内容の番号（主キー）・作り手・名前・開始の時刻・消された時刻・起きた時刻。
- **イベント**（001）：元の宣伝内容の番号（候補から作ったときだけ）を足す。

## Success Criteria *(mandatory)*

- **SC-001**：Threadsで開催日時のある宣伝内容を保存してから10秒以内に、人物メモの候補に出る（届かなかったときも、5分ごとのやり直しで10分以内）。
- **SC-002**：候補を選んでイベントを作るまで、名前と開催日を手で入れずに済む（選ぶ・作るの2回の操作）。
- **SC-003**：人物メモのコードは Threads の表・共通の表を読まない（ESLintの境界の規則で止まる）。出来事の中身だけで動くので、人物メモを別のWorker・別のDBに移しても、受け取りの処理は変えずに済む。

## Assumptions

- Threads が出す出来事（`threads.promotion_event.saved`・`.deleted`）の形は、集金 001 で決めたものをそのまま使う。Threads 側は変えない。
- 掲載の状況（`threads.listing_status.changed`）は、人物メモでは使わない。
- 候補から作ったイベントに「元が変わった・消された」の印は付けない（集金と違い、人物メモのイベントは名前と開催日だけで、当日の受付に使わないため）。要るとわかったら次の機能で足す。

## Out of Scope

- 集金 → 人物メモ（参加者の受け渡し）・人物メモ → 集金。
- この機能を入れる前に保存された宣伝内容を、さかのぼって候補にすること。
