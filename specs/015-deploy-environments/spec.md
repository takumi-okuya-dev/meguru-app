# Feature Specification: 公開のためのブランチと環境

**Feature Branch**: `feature/015-deploy-environments`

**Created**: 2026-10-18

**Status**: Draft

**Input**: 2026-10-18、PRDのFR-1〜FR-13の実装が終わり（001〜014）、次は商用公開の準備だとユーザーが判断した。[docs/next-features.md](../../docs/next-features.md)「C. 公開後のブランチと環境」と[specs/013-billing/notes.md](../013-billing/notes.md)「1. 公開後のブランチと環境」で決めていた方針を、実際に動く形にする。`main`＝本番（商用公開）、`develop`＝ステージング（テストユーザー）、`feature/*`＝開発の3段構成にし、(1)ブランチの運用（ふだんのPRは`develop`、リリースは`develop`→`main`、本番の急ぎの修正は`main`から分けて後で`develop`へ戻す）、(2)GitHub Actionsでの自動デプロイ（`develop`へのmergeでステージング、`main`へのmergeで本番。マイグレーションの当て方も決める）、(3)環境ごとに分ける設定（Cloudflareの変数・自動投稿のKV・Cron、NeonのDB、Clerk、Threadsのコールバック、Stripeの鍵）、(4)決済は環境の設定で切り替え、ステージングはStripeのテスト用環境でONにしてテストユーザーには「料金なしの印」を使う、(5)ステージングの自動投稿も実際にThreadsへ投稿し、ステージングだと分かる帯を出す、(6)秘密情報の置き場所と公開前の確認の手順書を、実際に使える形に書き直す、を作る。範囲外：MetaのApp Reviewの申請そのもの、事業者としての手続き（適格請求書・特定商取引法の表記の中身）、監視と通知の整備（別のfeature）。

## Clarifications

### Session 2026-10-18

- Q:ステージングの決済はどうするか？ → A:Stripeのテスト用環境でONにする。テストユーザーに料金を求めないのは、決済を止めるのではなく、利用者ごとの「料金なしの印」（013の`billing_exempt`）で行う。
- Q:ステージングの自動投稿はどうするか？ → A:本番と同じく、テストユーザーの実際のThreadsアカウントへ投稿する。代わりに、ステージングだと分かる帯を画面に出す。
- Q:デプロイのやり方は？ → A:GitHub Actionsで自動にする（`develop`へのmergeでステージング、`main`へのmergeで本番）。
- Q:本番のURLは？ → A:独自ドメインを使う（本番とステージングで別の名前。例：`app.…`と`staging.…`）。Clerkの本番のログインに独自ドメインが要るため。買うドメイン名は、計画のときに決める。
- Q:ステージングに入れる人は？ → A:許可した人だけにする（テストユーザーのメールアドレスの一覧で絞る）。テストユーザーは本物のThreadsアカウントをつなぐため。

## User Scenarios & Testing *(mandatory)*

### User Story 1 -テストユーザーが使える場所に、自動で出る（Priority: P1）

開発者が機能のPRを`develop`にマージすると、ステージングに自動で出る。テストユーザーは、ステージングのURLでログインして、本番と同じ流れ（アカウントを作る・Threadsにつなぐ・投稿を作る・自動投稿される）を試せる。ステージングでは、画面の上に「これはテスト環境です」と分かる帯が出る。

**Why this priority**：本番に出す前に、本番と同じ道を通して確かめられる場所を作ることが、この機能の目的の中心。これだけでも、今の「手元でしか確かめられない」状態から前に進む。

**Independent Test**：`develop`に小さな変更をマージし、数分のうちにステージングのURLでその変更が見え、ステージングの帯が出ていて、テストユーザーがログインから自動投稿まで通せることを確かめる。

**Acceptance Scenarios**:

1. **Given** `develop`に変更をマージした、**When** デプロイが終わる、**Then** ステージングのWebとAPIが新しい版になり、デプロイの記録（いつ・どの変更か）が残る。
2. **Given** ステージングの画面、**When** 利用者が見る、**Then** 「テスト環境」であることが分かる帯が、どの画面にも出る。
3. **Given** ステージングで承認した投稿、**When** 投稿する時刻になる、**Then** テストユーザーのThreadsアカウントに実際に投稿される。
4. **Given** ステージングのDB、**When** 本番のDBを見る、**Then** 互いのデータが混ざらない（別のDB）。

---

### User Story 2 -本番に、決めた手順で出る（Priority: P1）

リリースのとき、開発者は`develop`→`main`のPRを作ってマージする。本番に自動で出て、DBのマイグレーションも当たる。本番のURLで、一般のお客さまが使える。

**Why this priority**：商用公開そのもの。US1と並んで、この機能の目的。

**Independent Test**：`develop`→`main`のPRをマージし、本番のWebとAPIが新しい版になり、マイグレーションが当たっていることを確かめる。

**Acceptance Scenarios**:

1. **Given** `develop`→`main`のPRをマージした、**When** デプロイが終わる、**Then** 本番のWebとAPIが新しい版になる。
2. **Given** 新しいマイグレーションを含むリリース、**When** デプロイが走る、**Then** マイグレーションがアプリの入れ替えの前に当たり、当たった記録が残る。
3. **Given** マイグレーションが失敗した、**When** デプロイが走る、**Then** アプリの入れ替えを行わず、失敗が分かる形で止まる。
4. **Given** `main`への直接のpush、**When** 誰かが行おうとする、**Then** PRを通すよう止められる（リリースはPRで行う）。

---

### User Story 3 -環境ごとに、設定と秘密情報が分かれている（Priority: P1）

ステージングと本番で、DB・ログイン・Threadsの接続・決済・自動投稿の設定が別々になっている。秘密情報はリポジトリに置かず、決められた場所に置く。どの値をどこに入れるかが、手順書を見れば分かる。

**Why this priority**：US1・US2が動くための土台。混ざると、ステージングの操作が本番のデータやお客さまのThreadsに影響する。

**Independent Test**：ステージングと本番それぞれで、使っている設定の出どころを確かめ、リポジトリに秘密情報が入っていないこと、片方の設定を変えても他方が変わらないことを確かめる。

**Acceptance Scenarios**:

1. **Given** ステージングと本番、**When** 設定を見る、**Then** DB・ログイン・Threadsのコールバック・決済の鍵・自動投稿の関所が、それぞれ別の値になっている。
2. **Given** リポジトリ、**When** 中を探す、**Then** 本番・ステージングの秘密情報（鍵・接続文字列）が1つも入っていない。
3. **Given** ステージングの操作、**When** 本番のデータを見る、**Then** 変わっていない。

---

### User Story 4 -ステージングでも決済を試せて、テストユーザーには料金を求めない（Priority: P2）

ステージングでは、Stripeのテスト用環境で決済が動く。テスト用のカードで契約・解約・支払いの失敗まで試せる。テストユーザー本人には、利用者ごとの「料金なしの印」を付けて、料金を求めずに全機能を使ってもらう。

**Why this priority**：決済の変更を本番で初めて動かさないため。ただし、US1〜US3が動いてからでよい。

**Independent Test**：ステージングでテスト用のカードで契約し、「契約中」になること、別のテストユーザーに「料金なしの印」を付けると契約なしで全機能を使えることを確かめる。

**Acceptance Scenarios**:

1. **Given** ステージング、**When** テスト用のカードで契約する、**Then** 契約中になり、Stripeのテスト用環境に記録される（本番には何も起きない）。
2. **Given** 「料金なしの印」を付けたテストユーザー、**When** 使う、**Then** 契約がなくても読むだけにならない。
3. **Given** 本番、**When** 決済の設定を見る、**Then** 本番の鍵で動き、テスト用の鍵が使われていない。

---

### User Story 5 -急ぎの修正を本番に出し、ステージングにも戻せる（Priority: P2）

本番で急ぎの修正が必要なとき、開発者は`main`から修正のブランチを作り、`main`へのPRでマージして本番に出す。その後、同じ修正を`develop`にも戻し、ステージングと本番の差が残らないようにする。

**Why this priority**：公開後に必ず起きる。ただし、ふだんの流れ（US1・US2）が先。

**Independent Test**：`main`から修正のブランチを作って`main`にマージし、本番に出ること、`develop`にも同じ修正が入って差がなくなることを確かめる。

**Acceptance Scenarios**:

1. **Given** `main`から作った修正のブランチ、**When** `main`にマージする、**Then** 本番に出る。
2. **Given** 本番に出した急ぎの修正、**When** `develop`と比べる、**Then** 差が残っていないことを確かめられる。

---

### User Story 6 -ブランチの運用と公開前の手順が、文書で分かる（Priority: P3）

開発者（と将来の自分）が、PRをどこに向けるか、リリースはどうするか、公開の前に何を済ませるかを、文書を見れば分かる。Constitutionの「ブランチ運用」と、設定の手順書が、今の形に合っている。

**Why this priority**：仕組みが動けば作業は進むが、手順が文書にないと、次に触るときに迷う。

**Independent Test**：Constitutionとリポジトリの手順書を読み、PRの行き先・リリースの手順・公開前に必要な作業が、迷わず分かることを確かめる。

**Acceptance Scenarios**:

1. **Given** Constitution、**When** 開発ワークフローを読む、**Then** 3段構成の運用（PRの行き先・リリース・急ぎの修正）が書かれている。
2. **Given** 公開前の手順書、**When** 上から順に進める、**Then** 本番に必要な設定（ログイン・Threads・決済・DB・URL）が、抜けなく済ませられる。

---

### Edge Cases

- **デプロイが途中で失敗する**：マイグレーションだけ当たってアプリの入れ替えが失敗した場合、どちらの版でも動くように、マイグレーションは前の版のアプリでも壊れない形（列の追加など）にする。壊れうる変更（列の削除・名前の変更）は、2回のリリースに分ける。
- **同時に2つのデプロイが走る**：後から始まった方が前の方を待つ（同じ環境へのデプロイは1つずつ）。
- **`develop`と`main`の差が大きくなる**：差が残ったままだと、リリースのたびに危なくなる。差の大きさを見られるようにし、1〜2週間ごとにリリースする運用にする。
- **ステージングのURLが誰でも開ける**：ログインが要るので中は見えないが、テスト環境だと分かる帯と、検索に載せない指定を入れる。
- **本番のデータをステージングに持ってこない**：お客さまのデータ（Threadsのトークンを含む）をステージングに写さない。
- **公開の前に`main`に出す**：公開の判断が出るまでは、本番の環境にお客さまを入れない（URLを配らない）。

## Requirements *(mandatory)*

### Functional Requirements

**ブランチの運用（US1・US2・US5・US6）**

- **FR-001**: System MUST `main`（本番）・`develop`（ステージング）・`feature/*`（開発）の3段構成で運用する。
- **FR-002**: System MUST ふだんの機能・修正のPRを`develop`に向け、リリースは`develop`→`main`のPRで行う。
- **FR-003**: System MUST 本番の急ぎの修正を、`main`から分けたブランチの`main`へのPRで行い、その後`develop`にも同じ修正を戻す。
- **FR-004**: System MUST `main`と`develop`への直接のpushを止め、PRを通すようにする。
- **FR-005**: System MUST PRの検査（lint・型チェック・テスト）を、`develop`向けと`main`向けの両方で行う。

**デプロイ（US1・US2）**

- **FR-010**: System MUST `develop`へのmergeで、ステージングのAPIとWebを自動で新しい版にする。
- **FR-011**: System MUST `main`へのmergeで、本番のAPIとWebを自動で新しい版にする。
- **FR-012**: System MUST デプロイの前にDBのマイグレーションを当て、失敗したらアプリの入れ替えを行わずに止める。
- **FR-013**: System MUST 同じ環境へのデプロイを1つずつ行う（同時に走らせない）。
- **FR-014**: System MUST デプロイの記録（いつ・どの変更・結果）を残し、後から見られるようにする。
- **FR-015**: System MUST デプロイが失敗したとき、前の版が動き続けるようにする。

**環境ごとの設定（US3）**

- **FR-020**: System MUST ステージングと本番で、DBを別にする。
- **FR-021**: System MUST ステージングと本番で、ログイン（Clerk）の環境を別にする。
- **FR-021a**: System MUST 本番のログインを、独自ドメインで使えるようにする（本番とステージングで別の名前）。
- **FR-021b**: System MUST ステージングにログインできる人を、許可した人（テストユーザーのメールアドレスの一覧）だけに限る。許可していない人は、ログインできても中の画面を使えない。
- **FR-022**: System MUST ステージングと本番で、Threadsの接続の戻り先（コールバックのURL）を別にする。
- **FR-023**: System MUST ステージングと本番で、自動投稿の関所（KV）と定期処理を別にする。
- **FR-024**: System MUST 秘密情報（鍵・接続文字列・Webhookの秘密の値）をリポジトリに置かず、環境ごとの決められた場所に置く。
- **FR-025**: System MUST 環境の違いをコードの分岐ではなく設定で表す（どのブランチでもコードは同じ）。
- **FR-026**: System MUST 本番・ステージングのどちらの環境で動いているかを、画面と記録から分かるようにする。

**決済（US4）**

- **FR-030**: System MUST ステージングでStripeのテスト用環境の鍵を使い、本番で本番の鍵を使う。
- **FR-031**: System MUST ステージングのテストユーザーに、利用者ごとの「料金なしの印」で料金を求めずに使ってもらえるようにする（決済そのものは止めない）。
- **FR-032**: System MUST ステージングの決済の操作が、本番のStripeに影響しないようにする。

**ステージングの見分け（US1）**

- **FR-040**: System MUST ステージングの画面に、テスト環境であることが分かる帯を、どの画面にも出す。
- **FR-041**: System MUST 本番の画面に、その帯を出さない。
- **FR-042**: System MUST ステージングのページを、検索に載せない指定にする。

**文書（US6）**

- **FR-050**: System MUST Constitutionの開発ワークフローを、3段構成の運用に書き直す。
- **FR-051**: System MUST リポジトリの手順書に、公開前に必要な作業（ログイン・Threads・決済・DB・URL・秘密情報の置き場所）を、順に進められる形で書く。
- **FR-052**: System MUST 新しい開発者（と将来の自分）が、PRの行き先・リリース・急ぎの修正のやり方を、文書だけで分かるようにする。

### Key Entities

- **環境（Environment）**：本番・ステージング・開発（手元）の3つ。それぞれに、URL・DB・ログイン・Threadsの戻り先・決済の鍵・自動投稿の関所と定期処理を持つ。
- **デプロイ（Deploy）**：ある環境に、ある変更を出した記録。いつ・どの変更・結果（成功／失敗）を持つ。
- **料金なしの印（既存。013の`billing_exempt`）**：利用者ごとに、契約がなくても全機能を使えるようにする印。ステージングのテストユーザーに使う。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `develop`にマージしてから、ステージングで新しい版を確かめられるまで、10分以内に終わる（人の操作なしで）。
- **SC-002**: `develop`→`main`のPRをマージしてから、本番で新しい版を確かめられるまで、10分以内に終わる（人の操作なしで）。
- **SC-003**: ステージングでの操作（投稿の登録・承認・自動投稿・決済）が、本番のデータとStripeの本番に1件も影響しない。
- **SC-004**: 本番とステージングの秘密情報が、リポジトリの中に1つも入っていない。
- **SC-005**: マイグレーションが失敗したとき、アプリは前の版のまま動き続ける。
- **SC-006**: ステージングを開いた利用者が、テスト環境であることを、ひと目で分かる（どの画面でも帯が見える）。
- **SC-006a**: 許可していない人がステージングのURLを開いても、中のデータ（アカウント・投稿）を1件も見られない。
- **SC-007**: 公開前の手順書のとおりに進めると、本番に必要な設定が抜けなく済む（手順の中に「どこで値を作るか」「どこに入れるか」が全部ある）。
- **SC-008**: 本番に出すまでの流れ（PRを作る → レビュー → `develop` → リリースのPR → `main`）が、文書だけで分かる。

## Assumptions

- **ドメイン**：独自ドメインを1つ用意し、本番とステージングで別の名前を使う。ドメイン名と、どこで買うかは計画のときに決める（費用は年に数千円を見込む）。
- **使うサービスは今のまま**：Cloudflare（Workers・Pages・KV）、Neon（Postgres）、Clerk（ログイン）、Stripe（決済）、GitHub（リポジトリとCI）。新しいサービスは増やさない。
- **費用**：ステージングと本番でDBなどを分けるぶん、今より費用がかかる。無料の枠に収まるかは、[docs/cost-estimate.md](../../docs/cost-estimate.md)を見ながら計画のときに確かめる。
- **テストユーザー**：ステージングを使うのは、開発者と少人数のテストユーザー（ユーザーが選ぶ）。一般のお客さまはステージングを使わない。
- **ステージングのデータ**：本番のデータを持ってこない。テストユーザーが自分で作る。
- **公開の判断は別**：この機能は「公開できる状態」を作るところまで。実際に公開するか（URLを配るか）はユーザーが決める。
- **Metaの申請と事業者の手続きは範囲外**：App Reviewの申請、適格請求書・特定商取引法の表記の中身は、この機能の外で進める（手順書には「ここで必要」と書く）。
- **監視と通知は範囲外**：エラーの通知・稼働の監視は、別のfeatureにする。
