# 調べたこと（Phase 0）：公開のためのブランチと環境

**Feature**：[spec.md](./spec.md) | **日付**：2026-10-18

仕様の`[NEEDS CLARIFICATION]`は、specifyのときにユーザーと決めて残っていない。ここでは、実装の形（どのサービスのどの機能を使うか）を決める。外部サービスの仕様は2026-10-18に調べた。

## R1.ブランチの構成と保護

**決定**：`main`（本番）・`develop`（ステージング）・`feature/*`（開発）の3段にする。GitHubの既定のブランチは`develop`にし、`main`と`develop`は直接のpushを禁止してPRだけにする。`main`へのPRは`develop`からのリリースのPRと、`main`から分けた急ぎの修正だけにする。どちらのブランチへのPRでも、今のCI（lint・型チェック・テスト）を必須にする。

- 既定のブランチを`develop`にするのは、新しいPRの行き先が既定で`develop`になり、間違って`main`に向けるのを減らすため。
- ルールは GitHub の **ruleset**（新しい方）で入れる。`main`：直接のpushを禁止・PRを必須・CIを必須。`develop`：同じ（レビューの必須は、1人の開発なので入れない）。
- 急ぎの修正を`develop`へ戻すのは、人がPRを作る手順にする（自動のマージは、競合したときに黙って壊れるので入れない）。差が残っていないかは、`main`と`develop`の差を見るだけで分かる。

**理由**：仕様のFR-001〜FR-005。既定のブランチを変えるだけで、ふだんの事故（`main`への直接のPR）がほぼなくなる。

**ほかの案**：trunk based（`main`だけ）でステージングをタグやフラグで切り替える案は、公開後に「本番に出ていない変更をテストユーザーに触ってもらう」ことができないので採らない。

## R2.デプロイの仕組み（GitHub Actions）

**決定**：GitHub Actionsのワークフロー`deploy.yml`を1本作り、`push`（`develop`・`main`）で起動する。環境はGitHubの**Environment**（`staging`・`production`）で分け、秘密情報はEnvironmentのSecretsに置く。手順は、(1)チェックアウト・依存の用意、(2)共通のビルド、(3)**DBのマイグレーション**、(4)APIのデプロイ（`wrangler deploy --env …`）、(5)Webのデプロイ（`wrangler pages deploy --branch …`）の順。`concurrency`で同じ環境へのデプロイを1つずつにする。

- Workersのデプロイは、Cloudflare公式の`wrangler-action`を使う（`CLOUDFLARE_API_TOKEN`・`CLOUDFLARE_ACCOUNT_ID`はEnvironmentのSecrets）。
- WebもActionsから出す（`wrangler pages deploy`）。**Cloudflare PagesのGit連携は使わない**（使うと、Actionsと二重にデプロイされ、順番（マイグレーション→API→Web）も守れない）。
- 失敗したら後ろの手順を実行しない。マイグレーションが失敗すれば、APIもWebも入れ替わらない（FR-012・FR-015）。
- ワークフローの実行履歴が、そのままデプロイの記録になる（FR-014）。

**理由**：FR-010〜FR-015。今あるCI（`ci.yml`）と同じ仕組みの中で完結し、増やす道具がない。

**ほかの案**：Cloudflareの「Workers Builds」やPagesのGit連携に任せる案は、マイグレーションとの順番を決められず、monorepoのビルドの設定もCloudflare側に分かれてしまうので採らない。

## R3.`wrangler.toml`の環境の分け方

**決定**：`[env.staging]`と`[env.production]`を足し、**それぞれに変数・KV・Cronをすべて書く**。Workerの名前は`threads-grower-api-staging`・`threads-grower-api`にする。秘密情報は`wrangler secret put --env staging|production`で入れる。

- **注意**：wranglerの名前付きの環境は、一番上の設定（`vars`・`triggers`・`kv_namespaces`）を**受け継がない**。書き忘れると、ステージングでCronが動かない・KVが無い、という事故になるので、両方に書き切る。
- 自動投稿の関所のKVは、環境ごとに別のnamespaceを作る（`wrangler kv namespace create AUTOPOST_KV --env …`）。
- 手元（`wrangler dev`）は今までどおり、一番上の設定と`.dev.vars`を使う。

**理由**：FR-023・FR-025。コードはどのブランチでも同じにし、違いは設定だけに置く。

**ほかの案**：環境ごとに`wrangler.*.toml`を分ける案は、共通の設定が二重になって、ずれやすいので採らない。

## R4.マイグレーションの当て方

**決定**：デプロイの中で`pnpm --filter api db:migrate`を、**アプリの入れ替えの前に**走らせる。接続先はEnvironmentのSecretsの`DATABASE_URL`。失敗したらそこで止める。マイグレーションは**前の版のアプリでも壊れない形**（列や表の追加、既定値つき）だけにし、壊れうる変更（列の削除・名前の変更・制約の追加で既存の行が通らないもの）は、2回のリリースに分ける（1回目：足す・両方書く、2回目：外す）。

- 当たった記録は、今のマイグレーションの仕組み（Drizzleの記録の表）とActionsの実行履歴の両方に残る。
- 本番のマイグレーションは、`develop`で同じものがすでに当たっている（ステージングが先に通る）ので、本番で初めて走ることがない。

**理由**：FR-012。デプロイの途中で失敗しても、前の版のアプリが動き続けられる（SC-005）。

**ほかの案**：アプリの起動時に当てる案は、Workersでは起動が何度も起きるため採らない。手で当てる案は、リリースのたびに人の手順が増えるので採らない。

## R5.DBの分け方（Neon）

**決定**：Neonの**プロジェクトを2つ**作る（本番用・ステージング用）。同じプロジェクトのブランチでは分けない。

- Neonの無料プランは、1プロジェクトあたり1GBの保存・100 CU-hours/月で、プロジェクトは100件まで作れる（2026-10-18に確認）。プロジェクトを分けても無料の範囲に収まり、CU-hoursの枠も別々になる。
- ブランチで分けると、保存は節約できるが、同じプロジェクトの枠（CU-hours）を分け合うことになり、ステージングの実験が本番の枠を食う。接続文字列の取り違えも起きやすい。
- 本番のデータをステージングに写さない（仕様のエッジケース）。

**理由**：FR-020・SC-003。本番の枠と安全を、ステージングと混ぜない。

**ほかの案**：1つのプロジェクトのブランチで分ける案（費用は有利）。今回は安全と枠の独立を優先する。

## R6.ログイン（Clerk）と独自ドメイン

**決定**：ドメインを1つ用意し、本番は`app.<ドメイン>`、ステージングは`staging.<ドメイン>`にする。Clerkは**本番インスタンスを新しく作り**（本番用）、ステージングは今の開発用インスタンスを使い続ける。ステージングは、Clerkの「許可したメールアドレスだけ登録できる」設定（allowlist）で、テストユーザーに限る。

- Clerkの本番インスタンスは、自分のドメインに`clerk.`・`accounts.`などのCNAMEを足す必要がある（`*.accounts.dev`のままでは本番にできない。2026-10-18に確認）。GoogleのOAuthも、本番では自分で作った認証情報に差し替える。
- 開発用インスタンスは利用者が100人までという上限があるので、ステージング（テストユーザー数人）では足りる。
- 利用者のデータはインスタンス間で移せないので、本番は新しいインスタンスで始める（今の開発用の利用者は移らない＝本番は空から）。

**理由**：FR-021・FR-021a・FR-021b。商用公開に必要な条件で、ユーザーの決定（独自ドメイン・許可した人だけ）に沿う。

**ほかの案**：ステージングにも本番インスタンスを作る案は、Clerkの本番インスタンスをもう1つ持つ必要があり、ドメインとDNSの手間が増えるので採らない。

## R7.WebのURLとデプロイ（Cloudflare Pages）

**決定**：Pagesのプロジェクトは1つのまま、`main`を本番、`develop`をブランチの別名（プレビュー）にする。独自ドメインは、本番を`app.<ドメイン>`、ステージングを`staging.<ドメイン>`にし、ステージングはCloudflareのDNSで**ブランチの別名**（`develop.<プロジェクト>.pages.dev`）に向ける。

- Cloudflareは、特定のブランチの最新のビルドに独自ドメインを向けられる（proxy（オレンジの雲）が必要。外部のDNSや、proxyなしでは本番の方に行ってしまう。2026-10-18に確認）。
- ビルドはActionsで行い、`wrangler pages deploy --branch main|develop`で上げる（R2）。
- 画面に渡す値（APIのURL・Clerkの公開鍵・環境の名前）は、**ビルドのときの環境変数**（`VITE_…`）で入れる。ActionsのEnvironmentごとに別の値を渡す。

**理由**：FR-010・FR-011・FR-026。1つのPagesプロジェクトで2つのURLを持て、設定が1か所にまとまる。

**ほかの案**：Pagesのプロジェクトを2つに分ける案。URLの扱いは素直だが、設定が二重になる。今回は1つで足りる。

## R8.ステージングの見分け（帯）と検索に載せない

**決定**：ビルドのときの環境変数`VITE_APP_ENV`（`production`・`staging`・`development`）を見て、`production`以外のときだけ、画面の一番上に帯（例：「テスト環境です。本番のデータではありません」）を出す。あわせて、ステージングのときだけ`<meta name="robots" content="noindex, nofollow">`を入れる。

- 帯は、今ある帯（無料体験の終わり・読むだけ・要再接続）の**上**に置き、どの画面でも見えるようにする（`AppShell`の`banner`の並びの先頭）。
- 手元（`development`）でも出す（本番と見分けるため）。
- APIの応答にも環境の名前を入れる案は取らない（画面の表示だけで足り、APIを増やさない）。ただし、APIの記録（ログ）には環境の名前が入るようにする。

**理由**：FR-026・FR-040〜FR-042・SC-006。

**ほかの案**：URLで見分ける（`staging.`が付いているか）案は、手元のURLでは効かないので採らない。

## R9.Threadsの接続（Meta）

**決定**：Metaのアプリは**1つのまま**使い、コールバックのURLに本番とステージングの両方を登録する（`https://api.<ドメイン>/api/threads/callback`と、ステージングのAPIのURL）。APIのURLは、Workersの環境ごとのURL（独自ドメインを当てるか、`*.workers.dev`のまま）にする。

- MetaのアプリにはリダイレクトURIを複数登録できる。アプリを分けると、App Reviewをもう一度受けることになるので分けない。
- ステージングのテストユーザーは、今と同じ「テスターとして招待」（メモ`meta-app-review-strategy`のB案）で使う。本番の一般公開はApp Review（A案）が要る——これは範囲外（別で進める）。

**理由**：FR-022。申請の手間を増やさずに、2つの環境から接続できる。

**ほかの案**：ステージング用にMetaのアプリをもう1つ作る案は、App Reviewが二重になるので採らない。

## R10.決済（Stripe）の環境の分け方

**決定**：ステージングは**テスト用環境**の鍵（`sk_test_`）とWebhookの秘密の値、本番は**本番の鍵**（`sk_live_`）にする。`BILLING_ENABLED`は両方`true`。料金のID（`STRIPE_PRICE_ID`）も環境ごとに別（テスト用環境と本番で別のIDになる）。テストユーザーには、013で入れた「料金なしの印」（`users.billing_exempt`）を運用のスクリプトで付ける。

- WebhookのURLは環境ごとに登録する（ステージングのAPIのURL・本番のAPIのURL）。
- 013で、決済はすべて環境変数で切り替わる形になっているので、コードの変更はいらない（確かめるだけ）。

**理由**：FR-030〜FR-032・US4。

**ほかの案**：ステージングを`BILLING_ENABLED=false`にする案は、決済の変更を本番で初めて動かすことになるので採らない（specifyでユーザーと決定）。

## R11.秘密情報の置き場所

**決定**：3か所に分ける。

| どこ | 何を | 誰が入れるか |
|---|---|---|
| GitHubのEnvironment Secrets（`staging`・`production`） | `CLOUDFLARE_API_TOKEN`・`CLOUDFLARE_ACCOUNT_ID`・`DATABASE_URL`（マイグレーション用）・Webのビルドに渡す公開鍵（`VITE_CLERK_PUBLISHABLE_KEY`など） | 開発者がGitHubの画面で |
| Cloudflareのシークレット（`wrangler secret put --env …`） | APIが動くときに使う秘密（`DATABASE_URL`・`CLERK_SECRET_KEY`・`THREADS_APP_SECRET`・`TOKEN_ENCRYPTION_KEY`・`STRIPE_SECRET_KEY`・`STRIPE_WEBHOOK_SECRET`） | 開発者が手元から1回ずつ |
| 手元の`.dev.vars`・`.env.local` | 開発用の値 | 今までどおり（リポジトリに入れない） |

`DATABASE_URL`は2か所（GitHubのSecretsとCloudflare）に入る。マイグレーションはActionsから、APIはWorkerから、それぞれ接続するため。

**理由**：FR-024・SC-004。

**ほかの案**：すべてをGitHubのSecretsに置き、デプロイのたびにCloudflareへ流し込む案は、秘密がActionsのログの近くを何度も通るので採らない。

## R12.費用の見込み

**決定**：固定の費用は**ドメイン代だけ**（年に数千円）を見込む。ほかは無料の枠に収める。

| サービス | 本番 | ステージング | 枠 |
|---|---|---|---|
| Cloudflare Workers | 1つ | 1つ | 無料プラン（1日10万リクエスト、Cronも使える） |
| Cloudflare Pages | 1プロジェクト（本番とブランチの別名） | 同左 | 無料 |
| Neon | プロジェクト1つ | プロジェクト1つ | 無料（1GB/プロジェクト・100 CU-hours/月・合計20GB） |
| Clerk | 本番インスタンス | 開発用インスタンス（100人まで） | 無料 |
| Stripe | 本番 | テスト用環境 | 売上に応じた手数料のみ |
| ドメイン | 1つ（本番とステージングで名前を分ける） | 同左 | **年に数千円** |

Constitutionの「月額固定のインフラ費用は$0からの運用を目標」に対し、ドメイン代だけが増える。商用公開にはClerkの本番インスタンス＝独自ドメインが要るため、避けられない（ユーザーの決定）。[docs/cost-estimate.md](../../docs/cost-estimate.md)に追記する。

**理由**：Constitutionの運用コスト制約。

## R13.確かめ方（テスト）

**決定**：この機能は設定とワークフローが中心なので、ふだんのユニット・結合テストで確かめられるのは「ステージングの帯」と「設定の読み取り」だけ。残りは、実際に動かして確かめる（quickstart.md）。

- 自動のテスト：帯の表示（`VITE_APP_ENV`ごと）、APIの設定の確認（必要な環境変数がなければ起動時に`CONFIG_ERROR`）、`wrangler.toml`の環境に必要な項目がそろっているかの検査（簡単なスクリプトで、`[env.staging]`と`[env.production]`に`vars`・`kv_namespaces`・`triggers`があるかを見る）。
- 手で確かめる：デプロイの通し（`develop`→ステージング、`main`→本番）、マイグレーションの失敗で止まること、ステージングの決済、ステージングの自動投稿、許可していない人がステージングに入れないこと。

**理由**：仕様のSC-001〜SC-008の多くは、実際の環境でしか確かめられない。

**ほかの案**：ワークフローをローカルで動かす道具（act）を入れる案は、Cloudflareへの接続が必要な部分を再現できないので採らない。
