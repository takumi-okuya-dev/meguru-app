# Feature Specification:機能のまとまりごとのON/OFF

**Feature Branch**: `feature/019-feature-switches`

**Created**: 2026-11-04

**Status**: Draft

**Input**: 2026-11-04に、ユーザーが料金のプランを機能で分ける案を挙げた（[docs/next-features.md](../../docs/next-features.md) §G）。戦略（課題・宣伝内容・リサーチ）にはThreadsのノウハウが詰まっていてまねされやすいので、信頼できる人だけに使ってもらいたい。ただ、プランの中身はまだ関係者と合意できていない。そこで、プランを決める前に、運営者が機能のまとまりごとにON/OFFできる仕組みを先に作る。ON/OFFは人ごとと、組織（グループ）ごとにできる。プランの中身と料金はまだ決めず、あとで「ONにする組み合わせ」として決める。最初は全員すべてON。OFFの機能は、書いた内容を残したまま、画面を開けず、プロンプトにも入れない。

**Source**: [docs/next-features.md](../../docs/next-features.md) §G、[016のspec](../016-test-groups/spec.md)（運営者・運営者の画面・テスト用のグループ）、[013のspec](../013-billing/spec.md)（契約・無料体験・読むだけ）、[011のspec](../011-team-revision/spec.md)（チーム・見せているアカウント・担当）、[Constitution](../../.specify/memory/constitution.md) 4.2.0 原則I・IV・V。

## Clarifications

### Session 2026-11-04

- Q:まとまりがOFFの人には、サイドバーでどう見せるか？ → A:隠す。URLを直接開いたときだけ「この機能は今は使えません」と出す（FR-004・FR-006）。
- Q:チームで手伝う・見せてもらうAccountでは、誰の機能の設定に従うか？ → A:そのAccountのオーナーに従う（013の「オーナーが未払いなら、チームの人も読むだけ」と同じ考え方。FR-012）。
- Q:機能のまとまりをどう分けるか？ → A:「自動投稿」「戦略」「チーム」の3つにする。自動投稿は、投稿をつくる・投稿ストック・パフォーマンス（と自動投稿の設定）のまとまり。サイドバーは「自動投稿」を「戦略」と同じ文字だけの見出しにして、その下に投稿をつくる・投稿ストック・パフォーマンスを並べる（「分析」の見出しはなくす。FR-001・FR-004）。
- Q:人ごとだけでなく、組織ごとにもON/OFFするか？ → A:する。テスト版で使っている「テスト用のグループ」の管理を本番でも使えるようにし、グループごとにまとまりをON/OFFできるようにする（FR-017）。
- Q:組織と個人の設定が違うとき、どちらに従うか？ → A:どちらかがOFFならOFF（FR-018）。
- Q:本番のグループは、テスト版のグループと何が違うか？ → A:本番では機能の設定にだけ使う。誰でも登録でき、グループに入っても料金はかかる。招待制と料金なしは、今までどおりテスト版だけ（FR-019）。
- Q:自動投稿をOFFにした人の、承認した案と予約した自動投稿はどうするか？ → A:自動投稿と反応の取り込みも止める。承認済みの案は消さず、ONに戻すと続きから投稿する（FR-008）。
- Q:チームをOFFにした人はどうなるか？ → A:チームを新しく作れず、招待から入れない。入っているチームは消さず、チームの画面・担当・見せてもらう画面は使えない。その人のアカウントをチームの人が手伝うことも止まる。ONに戻すと元どおり（FR-009）。

## 用語

- **機能のまとまり**：ON/OFFを切り替える単位。自動投稿・戦略・チームの3つ（FR-001）。
- **機能の設定**：人ごと・グループごとに、まとまりのOFFを記録したもの。記録がなければON。
- **使えるまとまり**：その人の設定とグループの設定の両方でONのまとまり（FR-018）。
- **グループ**：016の「テスト用のグループ」。この機能から、本番でも組織の単位として使う。
- **運営者**：アプリを運営する人（016と同じ。今は開発者1人）。誰が運営者かは環境の設定で決める。
- **プラン**：将来、料金と「ONにするまとまりの組み合わせ」を結び付けたもの。この機能では作らない。

## User Scenarios & Testing *(mandatory)*

### User Story 1 -運営者が、ある人の戦略をOFFにする（Priority: P1）

運営者は、関係者に「戦略なし」の使い心地を試してもらいたい。運営者の画面でその人をメールアドレスで探し、「戦略」をOFFにする。その人が次にアプリを開くと、サイドバーから課題・宣伝内容・リサーチが消え、URLを直接開いても使えない。投稿をつくるのプロンプトにも、戦略の内容が入らない。書いてあった戦略は消えず、運営者がONに戻すと、そのまま使える。

**Why this priority**：この機能の中心。プランを決める前に、機能を分けた形を実際に試せる。

**Independent Test**：戦略を書いてある人の「戦略」をOFFにし、サイドバー・URL・プロンプト・APIのどこからも戦略が使えないことを確かめる。ONに戻し、書いた内容がそのまま出ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 運営者、**When** 運営者の画面でメールアドレスを入れて探す、**Then** その人の名前・グループと、まとまりごとのON/OFFが出る。グループでOFFのまとまりには「グループでOFF」と出る。
2. **Given** 上の画面、**When** 「戦略」をOFFにして保存する、**Then** その人の機能の設定が変わり、いつ・誰が・何をしたかが記録に残る。
3. **Given** 戦略がOFFの人、**When** アプリを開く、**Then** サイドバーに「戦略」の区分（課題・宣伝内容・リサーチ）が出ない。
4. **Given** 戦略がOFFの人、**When** 課題の画面のURLを直接開く、**Then** 画面は開かず、FR-006 の案内が出る。
5. **Given** 戦略がOFFの人、**When** 投稿をつくるでプロンプトをコピーする、**Then** プロンプトに課題・宣伝内容・リサーチの内容が入らない。
6. **Given** 戦略がOFFの人、**When** 戦略の読み書きをAPIに直接頼む、**Then** 拒まれる。
7. **Given** 戦略をOFFにしていた人、**When** 運営者がONに戻す、**Then** 書いてあった内容がそのまま出て、プロンプトにも入る。

---

### User Story 2 -何もしなければ、今までどおりすべて使える（Priority: P1）

この機能を入れても、運営者が何も設定していない人は、今までと同じように使える。新しく登録した人も、すべてONから始まる。

**Why this priority**：入れた日に、今の利用者の使い方を変えないため。

**Independent Test**：機能の設定のない人で、すべての画面・プロンプト・自動投稿が、この機能を入れる前と同じに動くことを確かめる（サイドバーの見出しの並びの変更を除く）。

**Acceptance Scenarios**:

1. **Given** 機能の設定のない人、**When** アプリを使う、**Then** すべてのまとまりがONとして扱われ、プロンプトと自動投稿はこれまでと同じ。
2. **Given** 新しく登録した人、**When** アプリを使い始める、**Then** すべてのまとまりがON。
3. **Given** 決済がONの環境で、無料体験が終わって契約していない人、**When** アプリを使う、**Then** これまでどおり読むだけになる（機能の設定は、決済の制限をゆるめない）。

---

### User Story 3 -運営者が、組織（グループ）ごとにON/OFFする（Priority: P1）

運営者は、ある組織に「自動投稿とチームだけ」を渡したい。本番でグループを作り、招待リンクを組織の窓口の人に送る。グループの「使える機能」で「戦略」をOFFにすると、グループに入っている人の全員が戦略を使えない。グループから外れると、その人の設定だけに戻る。

**Why this priority**：組織の単位でプランを試すため（ユーザーの希望）。

**Independent Test**：本番と同じ設定（招待制OFF）でグループを作って2人を入れ、グループの戦略をOFFにすると2人とも使えないこと、1人を外すとその人は使えるようになること、グループに入っても料金なしにならないことを確かめる。

**Acceptance Scenarios**:

1. **Given** 本番（招待制がOFF）の運営者、**When** 設定の「運営 › グループ」でグループを作る、**Then** グループと招待リンクができる（016と同じ）。
2. **Given** 本番のグループの招待リンク、**When** 登録している人が開いて「参加する」を押す、**Then** その人はグループに入る。料金なしの印は付かない。テスト版のための注意（料金はかかりません・テスト版のデータは本番へ引き継がれません）は出さない。
3. **Given** グループ、**When** 運営者がグループの「使える機能」で戦略をOFFにして保存する、**Then** グループに入っている全員が戦略を使えない。記録に残る。
4. **Given** グループで戦略がOFFの人、**When** 運営者がその人をグループから外す（またはグループを閉じる）、**Then** その人は、その人の設定だけで判定される。

---

### User Story 4 -運営者が、誰がOFFになっているかを確かめる（Priority: P2）

運営者は、どの人がどのまとまりをOFFにされているかを、一覧で確かめる。試してもらう期間が終わったら、まとめてONに戻せる。

**Why this priority**：OFFにした人を忘れると、その人が理由もわからず機能を使えないままになるため。

**Independent Test**：2人の戦略をOFFにし、一覧に2人が出ること、1人を「すべてONに戻す」と一覧から消えることを確かめる。

**Acceptance Scenarios**:

1. **Given** 運営者、**When** 「使える機能」の画面を開く、**Then** 人の設定でOFFのまとまりがある人だけが、名前・メールアドレス・OFFのまとまり・最後に変えた日とともに並ぶ。
2. **Given** 一覧の1人、**When** 運営者が「すべてONに戻す」を押す、**Then** その人の設定はすべてONになり、一覧から消える。記録に残る（グループの設定は変わらない）。
3. **Given** 運営者、**When** 「最近の変更」を開く、**Then** 人とグループの変更が、新しい順に並ぶ。

---

### Edge Cases

- OFFの画面を開いたまま、運営者がOFFにした → 次に画面を読み込むか、保存しようとしたときに使えなくなる。保存は拒まれ、「この機能は今は使えません」と出る。
- ホームの「次にやること」・入力状況のカードが、OFFのまとまりの画面を指していた → OFFのまとまりは、どちらにも出さない。
- 自動投稿がOFFの人の、承認済みの投稿 → 自動投稿しない。消さない。ONに戻すと、次の時刻から続きを投稿する。
- 自動投稿がOFFになった時点で公開の途中だった投稿 → 結果を確かめる処理だけは続ける（決済で読むだけになったときと同じ）。
- 運営者が自分自身の機能をOFFにした → 自分にもほかの人と同じように効く。運営者の画面は、まとまりに含めないので使い続けられる。
- 運営者の画面で探したメールアドレスの人がいない → 「見つかりません」と出す。まだ登録していない人には設定できない。
- 同じ人を2人の運営者が続けて変えた → あとから保存したほうが残り、記録には両方が残る。
- チームの管理者がチームをOFFにされた → チームは消えない。管理者はチームの画面を開けず、ほかの人もそのチームの管理の操作（招待・ロール・担当）を頼めない状態になるので、運営者は管理者のチームをOFFにする前に、引き継ぎを案内する（この機能では止めない）。
- 退会した人・閉じたグループ → 機能の設定も、ほかのデータと同じく013の退会・016の閉じるの扱いに従う。閉じたグループの設定は、もう誰にも効かない。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：機能のまとまりは、次の3つとする。ホーム・設定（料金・紹介・このアカウントの設定のうち、まとまりに含めないもの）は、いつも使える。
  - **自動投稿**：投稿をつくる（AIのプロンプトのコピー・文字数と長さの割合・貼り付けて登録）、投稿ストック（承認・却下・編集）、パフォーマンス（反応数と判定・メモ・CSVの書き出し）、自動投稿の設定（投稿のスケジュール・投稿ルールとNGワード）。
  - **戦略**：課題・宣伝内容・リサーチと、その中のAIの手助け（考えるヒント・AIと深掘り・AIと壁打ち・全体をAIと整理する・参考投稿のAI解説）。
  - **チーム**：チームを作る・招待から入る、チームの画面・担当を決める・操作の記録、ほかの人のAccountを手伝う・見せてもらう、自分のAccountをチームに入れて手伝ってもらう。
- **FR-002**：運営者は、運営者の画面で、登録している人をメールアドレスで探し、まとまりごとにON/OFFを変えられなければならない。運営者でない人には入口を出さず、開いても使わせない（APIでも拒む）。この画面は、テスト版でも本番でも使えなければならない。
- **FR-003**：人にもグループにも設定がない人は、すべてのまとまりをONとして扱わなければならない。新しく登録した人も同じ。
- **FR-004**：使えないまとまりの画面は、サイドバー・ホーム（「次にやること」と入力状況のカードを含む）・ほかの画面からのリンクのどこにも出してはならない。サイドバーでは区分（見出し「自動投稿」「戦略」「チーム」と、その下の項目）ごと隠し、鍵の印などで「使えない機能がある」ことも見せない。サイドバーの並びは、ホーム → 自動投稿（投稿をつくる・投稿ストック・パフォーマンス）→ 戦略（課題・宣伝内容・リサーチ）→ チーム とする。
- **FR-005**：使えないまとまりの読み書きは、APIで拒まなければならない。判定は、誰がどのAccountで何をできるかの判定（原則V）と同じ1か所に足す形にする。
- **FR-006**：使えないまとまりの画面をURLで直接開いたときは、その画面の内容を出さず、「この機能は今は使えません」と、ホームへ戻る道だけを出す。理由や料金の案内は出さない（プランが決まってから足す）。
- **FR-007**：戦略が使えない人のプロンプトには、課題・宣伝内容・リサーチの内容を入れてはならない。「プロンプトに入っている情報」と、課題を埋める案内も出さない。
- **FR-008**：自動投稿が使えない人のAccountでは、自動投稿（時刻の処理・公開）と反応の取り込みを行ってはならない。承認済みの案・投稿の記録・反応は消さず、ONに戻したら続きから動かなければならない。公開の結果がわからない途中の投稿だけは、結果を確かめる処理を続ける。
- **FR-009**：チームが使えない人は、チームを作ること・招待から入ること・チームの画面（担当を決める・操作の記録を含む）を開くこと・ほかの人のAccountを手伝う・見せてもらうことができない。その人がオーナーのAccountは、チームの人が手伝う・見せてもらうことができない。チーム・入っている人・担当・見せる設定の記録は消さず、ONに戻したら元どおりにしなければならない。
- **FR-010**：まとまりをOFFにしても、そのまとまりで書いた内容・集めたデータを消してはならない。ONに戻したら、そのまま使えなければならない。
- **FR-011**：機能の設定は、決済の制限（無料体験・契約・読むだけ、013）と別に持ち、どちらの制限も満たしたときだけ使える。機能の設定で、決済の制限をゆるめてはならない。
- **FR-012**：チームで手伝う・見せてもらうAccountでは、そのAccountのオーナーの使えるまとまりに従わなければならない（013の「オーナーが未払いなら、チームの人も読むだけ」と同じ考え方）。ただし、チームのまとまりだけは、オーナーと見る人の両方で使えるときに限る（FR-009）。
- **FR-013**：運営者は、人の設定でOFFのまとまりがある人の一覧（名前・メールアドレス・OFFのまとまり・最後に変えた日。最後に変えた日は、その人の機能の設定を最後に変えた日で、ONに戻した変更も含む）を見て、人ごとに「すべてONに戻す」ができなければならない。
- **FR-014**：人・グループの機能の設定を変えたことは、いつ・誰が・誰の（どのグループの）・どのまとまりを・どう変えたかを記録に残さなければならない。
- **FR-015**：NGワードのチェックと、承認してから自動投稿する流れ（原則I・II）は、まとまりのON/OFFによって飛ばされてはならない。
- **FR-016**：運営者の画面は、スマートフォンの幅でも使えるようにする。画面の文字は短くし、説明は閉じたトグルの箇条書きにする（docs/ui-design.md）。
- **FR-017**：運営者は、グループの画面で、グループごとにまとまりのON/OFFを変えられなければならない。グループの管理（作る・名前と上限・招待リンク・外す・閉じる・記録）は、テスト版でも本番でも使えなければならない（016を変える）。
- **FR-018**：使えるまとまりは、その人の設定とグループの設定の両方でONのまとまりとする（どちらかがOFFならOFF）。閉じたグループの設定は効かない。グループに入っていない人は、その人の設定だけで決まる。
- **FR-019**：本番（招待制がOFFの環境）では、グループは機能の設定にだけ使う。誰でも登録して使え（グループに入っていなくてよい）、グループに入っても料金なしの印は付かない。招待の画面には、テスト版のための注意を出さない。招待制と料金なしは、今までどおりテスト版（招待制がONの環境）だけとする。

### Key Entities

- **人の機能の設定**：誰の（ログインした人1人）・どのまとまりがOFFか・OFFにした日と運営者。記録がないまとまりはON。
- **グループの機能の設定**：どのグループの・どのまとまりがOFFか・OFFにした日と運営者。
- **機能の設定の記録**：いつ・どの運営者が・誰の（またはどのグループの）・どのまとまりを・OFFにしたかONに戻したか。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：運営者が、ある人（またはグループ）の1つのまとまりをOFFにするのに、運営者の画面を開いてから1分以内でできる。
- **SC-002**：使えないまとまりの内容は、画面・プロンプト・APIの3つの経路のどれからも、その人に0件しか出ない。自動投稿が使えないAccountでは、新しい公開が0件。
- **SC-003**：機能の設定がない人では、この機能を入れる前と後で、プロンプトの中身と自動投稿の動きが同じである（今のテストがそのまま通る。サイドバーの並びの変更を除く）。
- **SC-004**：OFFからONに戻した人の、書いてあった内容が100%そのまま残っている。
- **SC-005**：運営者は、OFFのまとまりがある人を、一覧から漏れなく確かめられる。

## Assumptions

- 運営者は016と同じく環境の設定（`OPERATOR_CLERK_USER_IDS`）で決める。機能の設定の画面とグループの管理は、招待制（`TEST_GROUPS_ENABLED`）にかかわらず使う。運営者の料金なし（016）は、招待制がONの環境でだけ。
- 人の機能の設定は人（ログインした人）ごとに持ち、その人がオーナーのすべてのAccountに効く。Accountごとの設定は作らない。
- 1人が入れるグループは1つまで（016と同じ）。
- OFFの人がプロンプトをコピーして人に渡すことは、仕組みでは止められない（§G）。この機能では扱わない。
- 利用者本人が自分の機能の設定を見る画面は作らない。使えないまとまりは、出てこないだけにする。
- 本番のグループの名前は、画面では「グループ」と呼ぶ（テスト版でも同じ名前にそろえる）。

## Dependencies

- Constitution 4.2.0（原則I・IV・Vの例外）。まとまりの名前を「自動投稿・戦略・チーム」に直し、原則VIの例外を外す改定が要る（パフォーマンスは自動投稿のまとまりに入り、自動投稿が使えなければプロンプトも作らないので、原則VIの「必ず反映」は今のまま守れる）。
- 016の運営者の判定（環境の設定）と、テスト用のグループの仕組み・運営者の画面。

## Out of Scope

- プランの中身・料金・Stripeとのつなぎ（プランが決まってから、別のfeatureにする）。
- 利用者が自分でプランを選ぶ・変える画面。
- 使えない機能の案内に、料金や「上のプランにすると使えます」を出すこと。
- 運営者を画面から足す仕組み（016と同じく、環境の設定で決める）。
- 1人が複数のグループに入ること。
