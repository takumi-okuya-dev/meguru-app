# Phase 0 調査：テスター招待での接続、アカウント数・投稿数の上限、無料体験の廃止

**日付**：2026-11-08 | **計画**：[plan.md](./plan.md)

技術コンテキストに「要確認」は残っていない。決めたことを、決定・理由・ほかの案の形で書く。

## R1. 申し込みの持ち方

- **決定**：
  - 表`tester_applications`に、1件の申し込みを1行で持つ。
  - アカウント（`account_id`）と利用者（`user_id`）に結び付ける。
  - 「生きている」申し込み（状態が`pending`・`invited`・`connected`）は、アカウント1件につき1つまでにする（部分一意インデックス）。
  - 取り下げ・見送りの行は残す。申し込み直すと新しい行を作る。
- **理由**：
  - アカウント1件に1つの申し込み（FR-005）を、DBの制約で守れる。
  - 見送りの理由と、テスターから外す必要があるかを、行ごとに追える。
- **ほかの案**：
  - `accounts`に列を足す：見送り・取り下げの履歴を持てない。アカウントを消すと、外す必要があることも消える。不採用。
  - 利用者ごとに1つ：1人が複数のアカウントを申し込めない。不採用。

## R2. テスター枠の数え方と「外してよい」

- **決定**：
  - 行に`holds_slot`（真偽）を持つ。
    - 運営者が「招待した」で真にする。
    - 「申し込み中に戻す」「外した」で偽にする。
  - テスター枠の使用数は`holds_slot = true`の行の数。
  - 「外してよい」は、`holds_slot = true`で、かつ`removal_reason`が入っている行。
  - `removal_reason`が入るとき：
    - `account_deleted`：アカウントを消した
    - `user_withdrawn`：退会した
    - `withdrawn`：「招待済み」の申し込みを利用者が取り下げた
    - `token_connected`：トークンでつながった
    - `username_mismatch`：申し込みと違うユーザー名でつながった
  - 枠の数（Metaの上限の目安）は、運営者が`operator_settings.tester_slot_capacity`で決める（初めは25）。
- **理由**：
  - Metaのテスターは、運営者が手で外すまで枠を使い続ける。
  - 申し込みの状態（利用者の側の進み）と、枠を使っているか（Metaの側の事実）を分けると、SC-005（使用数がいつも一致する）を1つの列で守れる。
- **ほかの案**：
  - 状態から使用数を求める：取り下げのあとも枠を使っている行を表せない。不採用。
  - Metaの上限の数を決め打ちする：Metaの値を確かめられないので、運営者が変えられる値にする。

## R3. ユーザー名の扱い

- **決定**：
  - 入力の前後の空白と先頭の`@`を取り、小文字にそろえる。
  - 使える形は、英小文字・数字・`.`・`_`の1〜30文字。
  - 照合（同じユーザー名の申し込み、つながったアカウントとの一致）も小文字で行う。
- **理由**：Threadsのユーザー名はInstagramと同じ規則で、大文字と小文字を区別しない。
- **ほかの案**：Threadsに問い合わせて、あるかを確かめる。トークンなしでは問い合わせられないため、不採用。

## R4. 招待の管理のON/OFF

- **決定**：
  - 新しいスイッチは作らない。
  - `THREADS_ACCESS_MODE`が`testers`（未設定も`testers`）で、かつ`THREADS_CONNECT_METHODS`に`app`があるとき、招待の管理をONにする（`testerInvitesEnabledOf`）。
  - OFFなら：
    - 利用者の申し込みのAPIは`404`
    - 運営者の一覧は読めるが、`enabled: false`を返す
- **理由**：
  - 審査の前か後かを表すスイッチ（002 FR-028）がすでにあり、意味が同じ（FR-026）。
  - `app`を出していない環境では、招待してもつなげない。
- **ほかの案**：`TESTER_INVITES_ENABLED`を足す。審査の後に2つを同時に変える必要が出て、片方だけ変える間違いが起きやすい。不採用。

## R5. 接続済みにする場所

- **決定**：
  - `completeConnection`（OAuthとトークンで共通。010 research.md R5）のトランザクションの中で、つないだアカウントの生きている申し込みを読む。
  - OAuth（`app`）でつながったとき：
    - ユーザー名が申し込みと同じなら`connected`
    - 違えば`withdrawn`と`removal_reason = username_mismatch`
  - トークン（`token`）でつながったとき：`withdrawn`と`removal_reason = token_connected`
  - 申し込みが「申し込み中」のままOAuthでつながった（すでにテスターだった）ときも、同じ規則で進める（運営者が「招待した」を押していなくても、枠を使っているので`holds_slot = true`にする）。
  - **申し込みがないまま**OAuthでつながったとき（024の前からのアカウントの、つなぐ・接続し直し）と、ユーザー名が違ってつながったときのつながったアカウントは、招待の管理がONなら`connected`・`holds_slot = true`の記録を作る（2026-11-09 の fix。テスト版で、接続し直したアカウントが「接続済み」に出ず、枠の数にも入っていなかった）。
  - 024の前から「Threadsで許可する」でつながっていたアカウントは、マイグレーション`0024_tester_backfill_connected`でまとめて同じ記録を足す。トークンでつながっているアカウントは、Metaのテスターの枠を使わないので足さない。
- **理由**：
  - 接続の確定と同じトランザクションにすれば、「つながったのに接続済みにならない」が起きない（SC-003）。
  - OAuthとトークンの両方がここを通る。
- **ほかの案**：
  - 日次の処理で照合する：遅れが出る。不採用。
  - Web から知らせる：取りこぼす。不採用。

## R6. 上限の持ち方

- **決定**：
  - 既定値は1行だけの表`operator_settings`（`id = 1`）に持つ。
    - `default_account_limit`（初めは3）
    - `default_daily_post_limit`（初めは10）
    - `tester_slot_capacity`（初めは25）
  - 利用者ごとの値は、`users.account_limit`・`users.daily_post_limit`（NULLなら既定値）に持つ。
  - 実際の上限は次のとおり。
    - 運営者なら上限なし（`null`）
    - それ以外は`coalesce(利用者の値, 既定値)`
- **理由**：
  - 運営者が画面から変えられ、デプロイが要らない（US3）。
  - 退会で`users`の行が消えれば、利用者ごとの値も消える。
- **ほかの案**：
  - 環境の設定（`wrangler.toml`）：変えるたびにPRとデプロイが要る。不採用。
  - 汎用のキーと値の表：型と既定値をDBで守れない。不採用。

## R7. アカウントの上限と投稿の上限の効かせ方

- **アカウント**：
  - `accountLimitFor`で、次の小さい方を上限にする。
    - 使える状態の上限（前からの無料体験なら1、それ以外は`null`）
    - 上限（R6）
  - 作るときは、今の`lockUserRow`の中で数え直す（同時に作っても超えない。013と同じ）。
- **投稿**：
  - 投稿のスケジュールの保存で、時刻の数がオーナーの上限を超えたら`POSTING_SLOT_LIMIT`。
  - 共有の`validatePostingSchedule`は、上限を引数で受け取る。
  - 自動投稿の時刻の処理は、オーナーの上限を設定の読み込みに結合で足し、時刻を早い順に並べて上限の数までだけ使う。
  - 時刻の行は消さない（FR-020）。
- **運営者**：上限なし。投稿の時刻の数だけは、Threadsの24時間の上限（250件）を最大にする。
- **理由**：判定を1か所に保ち（原則V）、上限を下げても登録した内容を残す。
- **ほかの案**：上限を下げたときに超えた時刻を消す。利用者の設定を勝手に変えることになる。不採用（FR-020）。

## R8. 無料体験の途中の人の見分け方

- **決定**：
  - `users.legacy_trial`（真偽）を足す。
  - マイグレーションでは、列を既定値`true`で足したあと、既定値を`false`に変える。今いる人には`true`が付き、新しく作る人は`false`になる。
  - 認証のミドルウェアの新しい行の作成でも、`false`を明示する（016の`signed_up_open`と同じ作法）。
  - `entitlementOf`は次のとおりにする。
    - `legacyTrial`で、登録から1か月の間 → `trial`
    - 契約がなく`legacyTrial`でもない → `unsubscribed`
    - 支払いの失敗・解約の扱いは今のまま
- **理由**：
  - 環境ごとにデプロイの日が違っても、マイグレーションを当てた時点で正しく分かれる。
  - 日付の決め打ちが要らない。
- **ほかの案**：
  - 区切りの日時を環境の設定に置く：テスト版と本番で違う値を手で入れる必要がある。不採用。
  - `created_at`で区切る：同じく日付の決め打ちになる。不採用。

## R9. 契約前の人の止め方

- **決定**：
  - 使える状態に`unsubscribed`（`fullAccess: false`、`readOnlyReason: "not_subscribed"`、`accountLimit: 0`）を足す。
  - 認証のミドルウェアで、契約の状態と`legacy_trial`を同じ問い合わせで読む。`unsubscribed`なら、許す経路のほかを`403 SUBSCRIPTION_REQUIRED`で止める。許す経路は次のとおり。
    - `GET /api/me`、退会の2つ
    - `GET /api/billing`、`POST /api/billing/checkout`・`sync`・`portal`
    - `/api/test-invites/*`（グループに入れば料金なしになる）
    - `GET /api/invites/:token`（チームの招待の確認。参加は止める）
  - Webは、`me.billing.state === "unsubscribed"`か`SUBSCRIPTION_REQUIRED`で、契約前の画面に替える。
- **理由**：
  - 016の`TEST_ACCESS_REQUIRED`と同じ作りで、すべてのAPIを1か所で守れる（FR-029）。
  - 読むだけ（013）は「契約していた人のデータを見られる」状態で、契約前とは別にする。
- **ほかの案**：
  - 読むだけを使い回す：アカウントを作る・チームに入るを個別に止める必要があり、漏れやすい。不採用。

## R10. 料金の変更（アカウント1件につき月1,000円）

- **決定**：
  - 共有の定数を`BILLING_UNIT_PRICE_JPY = 1000`の1つにし、次の請求の見込みを「数 × 1,000円」にする。
  - 数は今のとおり`max(件数, 1)`で、0件でも1件分。
  - Stripeには、テスト用環境と本番のそれぞれで、1件1,000円の料金（数による定額）を新しく作り、`STRIPE_PRICE_ID`を替える。
  - すでにある契約は、数の合わせ直し（`syncQuantity`。アカウントを足した・消したときと日次）で、契約の項目の料金が`STRIPE_PRICE_ID`と違えば、新しい料金へ切り替える。日割りはしない（`proration_behavior: none`）。次の請求から新しい料金になる。
  - Checkoutの試用は、前からの無料体験の人（`trial`）だけに付ける（今のまま）。
- **理由**：
  - Stripeの料金は金額を変えられないので、作り直しが要る。
  - 切り替えを今ある数の合わせ直しに入れれば、新しい仕組みが要らない。
  - 本番はまだ公開しておらず、テスト版の契約はテスト用環境のもの。
- **ほかの案**：
  - 段階制の2段目を1,000円に変える：Stripeは料金の金額を変えられない。
  - 切り替えのスクリプトを別に作る：日次の処理で済むので不採用。

## R11. 運営者の料金なし

- **決定**：
  - `billingModeOf`は、招待制にかかわらず`operators`を持つ。
  - `billingExemptSql`は、いつも運営者を「料金なし」に含める。
  - テスト版に入れる判定（`testAccessSql`）は今のまま、招待制がONのときだけ運営者を含める。
- **理由**：FR-023。テスト版に入れる判定は、招待制がOFFなら誰でも入れるので、変える必要がない。
- **影響**：docs/environment-switches.mdの「運営者」の説明と組み合わせの表を直す（FR-025）。

## R12. 環境とMetaアプリ

- **テスト版**：
  - `THREADS_CONNECT_METHODS`を消す（両方）。
  - `THREADS_APP_ID`はThreadsAutomationのID、`THREADS_APP_SECRET`はSecretに入れる。
  - `THREADS_REDIRECT_URI`は今の値（`…workers.dev/api/threads/callback`）。
  - ThreadsAutomationに、リダイレクト・アンインストール・削除の3つのURLを登録する（2026-11-08の時点で空）。
- **本番**：
  - 本番用のMetaアプリを新しく作り、同じ3つの値とURLを入れる。
  - `THREADS_CONNECT_METHODS`は未設定（両方）。
  - `THREADS_ACCESS_MODE = "testers"`のまま。
- **審査に通ったら**：本番だけ`THREADS_ACCESS_MODE = "public"`にすると、招待の管理が切れる。
- **理由**：FR-028。どちらのアプリを使うかを環境の設定だけで決める（015）。

## R13. 招待済みでつなげなかったとき

- **決定**：
  - Metaは、テスターでない人や招待を承認していない人に、許可の画面でエラーを出す。戻ったときは`error`付きになる（`THREADS_AUTH_CANCELLED`・`THREADS_AUTH_FAILED`）。
  - Webは、戻った先のアカウントの申し込みが「招待済み」のとき、エラーの代わりに「招待を承認してから、もう一度お試しください」と承認の手順を出す（FR-007）。
  - Metaの画面で止まって戻らない場合に備え、「招待済み」の画面には、つなげなかったときの案内をいつも小さく出す（モック4枚目）。
- **理由**：Metaの戻し方は、確かめられる範囲でも一定しない。どちらでも利用者が次にすることがわかるようにする。

## R14. 申し込みの回数の制限と記録

- **決定**：
  - 記録の表`operator_events`に、利用者の申し込み・取り消しも記録する。
  - 直近10分の、その利用者の申し込みと取り消しが5回以上なら`429 RATE_LIMITED`。
  - 運営者の操作も同じ表に記録する。種類は次のとおり。
    - 招待した・見送る・戻す・外した
    - 枠の数・既定値・利用者ごとの上限を変えた
- **理由**：記録（FR-014）と制限（FR-006）を同じ行で済ませる。トークンの確認の失敗の制限（010）と同じ考え方。

## R15. 退会したときの個人の情報

- **決定**：
  - 退会では、利用者の行が消える。その前に、同じトランザクションで、枠を使っていない申し込みの行（申し込み中・見送り・取り下げ）を消す。
  - 枠を使っていた行は、Threadsのユーザー名だけを残して「外してよい」（`user_withdrawn`）にする。`user_id`は`ON DELETE SET NULL`で空になる。運営者が「外した」を押したら行を消す。
  - 名前とメールアドレスは申し込みの行に写さない（一覧では`users`を結合して出す）。
  - 記録（`operator_events`）の`detail`には、Threadsのユーザー名・名前・メールアドレスを入れない（`application_id`でたどる）。
- **理由**：
  - 退会でデータをすぐ消す（013・PRD FR-12）のを崩さない。
  - Metaのテスターから外すのに、ユーザー名だけは要る（Metaの側に残っている枠を、運営者が外すまでの間だけ）。
