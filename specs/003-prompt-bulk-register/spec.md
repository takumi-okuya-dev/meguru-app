## Clarifications

### Session 2026-10-03

- Q: プロンプトの生成と一括登録は、どのプランで使えるか？ → A: 今のプラン定義（プラン1は「投稿ストックからの自動投稿のみ」、戦略プロファイルはgrower機能）に沿って、プロンプトの生成はgrower機能（プラン2以上と無料体験中）、貼り付けによる一括登録と下書きの編集・削除は全プランとする。
- Q: プロンプトの文面はどうするか？ → A: 参考プロダクト（Threads Growth OS）の投稿ストック画面のプロンプトを読み取り、構成と言い回しを取り込む。
- Q: 下書きの長さを画面でどう見せるか？（Threadsの上限は公式ドキュメントで確認） → A: 文字数と、Threadsの上限までの使用量をバーで示し、超えたら注意の色と「Threadsの上限を超えています」を出す。上限は公式ドキュメントのとおり500文字（絵文字だけはUTF-8のバイト数で数える）。リンクは5個まで。
- Q: 要確認の一覧の並び順は？ → A: 新しい登録（貼り付けの送信）が上。同じ登録の中は、貼り付けたテキストの順（外部LLMの回答と同じ順）。
- Q: 「作る件数」はどこに覚えておくか？ → A: Accountごとにサーバーで覚える（別の端末でも同じ件数になり、Accountごとに変えられる）。
- Q: 貼り付けを間違えたとき、直前の登録をまとめて取り消せるか？ → A: 登録直後の案内に「取り消す」を付け、押すとその登録の下書きをまとめて削除し、貼り付けた内容を貼り付け欄に戻す。

### Session 2026-10-04

- Q: 下書きの削除に確認を求めるか？（動作確認で、確認のダイアログはクリック数が多いと分かった） → A: 確認のダイアログは出さず、すぐ一覧から消して、トーストの「元に戻す」で取り消せるようにする。削除の確定は約5秒後（または画面を離れたとき）。課題・宣伝内容・リサーチの削除は002のとおり確認を求める。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - プロンプトを作ってコピーする (Priority: P1)

ユーザーは投稿ストックの画面を開き、上部のカードから、そのAccountの戦略プロファイル（課題・宣伝内容・リサーチ）を反映したAI用のプロンプトをコピーする。作りたい投稿の件数を指定でき、コピーする前にプロンプトの中身を確認・書き換えられる。コピーしたプロンプトをChatGPTやClaudeに貼り付けて送ると、区切り文字「@@@」で区切られた投稿案がまとめて返ってくる。

**Why this priority**: 002で入力した戦略プロファイルが、ここではじめて投稿づくりに使われる。プロンプトがなければ、外部LLMに何を頼めばよいかをユーザーが毎回組み立て直すことになり、プロダクトの中心の流れ（UJ-1）が始まらない。

**Independent Test**: 課題・宣伝内容・リサーチを入力済みのAccountで投稿ストックの画面を開き、プロンプトをコピーして、その中に入力した課題・宣伝の対象の宣伝内容・参考投稿の「なぜ良いか」と、出力の形の指示（件数、「@@@」で区切ること）が含まれていることを確認する。このストーリーだけで「戦略に沿った投稿案を外部LLMに作ってもらえる」という価値が成立する。

**Acceptance Scenarios**:

1. **Given** 課題・宣伝内容・リサーチを入力済みのAccount、**When** ユーザーが投稿ストックの画面を開く、**Then** 上部に「プロンプトをコピーして、ChatGPTやClaudeに送る」のカードと、反映した内容の要約（例：「課題 11/16・宣伝の対象 1件・参考投稿 3件を反映」）、作る件数、「コピー」ボタンが出る。
2. **Given** 投稿ストックの画面、**When** ユーザーが「コピー」を押す、**Then** プロンプトがクリップボードにコピーされ、「コピーしました。ChatGPTやClaudeに貼り付けて送ってください」と出る。
3. **Given** 投稿ストックの画面、**When** ユーザーが作る件数を変える、**Then** プロンプトの件数の指示がその件数に変わる。
4. **Given** 投稿ストックの画面、**When** ユーザーが「プロンプトを見る」を開いて中身を書き換えてからコピーする、**Then** 書き換えた内容がコピーされる。書き換えは保存されず、画面を開き直すと元のプロンプトに戻る。
5. **Given** 課題が未入力の項目を含むAccount、**When** プロンプトを作る、**Then** 未入力の項目は見出しごと省かれ、入力済みの項目だけが含まれる。
6. **Given** 課題・宣伝内容・リサーチがすべて未入力のAccount、**When** 投稿ストックの画面を開く、**Then** プロンプトは作れる（出力の形の指示とAccountの表示名だけを含む）うえで、「課題を入力すると、投稿の精度が上がります」と課題の画面への案内が出る。

### User Story 2 - 外部LLMの回答を貼り付けて一括登録する (Priority: P1)

ユーザーは外部LLMの回答を、投稿ストックの画面の下部にある貼り付け欄にそのまま貼り付けて送る。回答は「@@@」で区切られた投稿ごとに分割され、それぞれが投稿ストックに「要確認」の下書きとして登録される。登録された下書きは、画面の一覧にすぐ並ぶ。

**Why this priority**: UJ-1のクライマックス（「貼り戻した内容が自動的に複数件の下書きに分割され、投稿ストックに一括登録される瞬間」）。US1と合わせてはじめて、戦略 → 投稿案 → ストックの流れが完結するためP1とする。

**Independent Test**: 「@@@」で区切られた3件分のテキストを貼り付けて送り、要確認の一覧に3件の下書きが増えることを確認する。

**Acceptance Scenarios**:

1. **Given** 投稿ストックの画面、**When** ユーザーが「@@@」で区切られた3件分のテキストを貼り付けて送る、**Then** 3件の下書きが「要確認」として登録され、「3件を登録しました」と出て、一覧の先頭に、貼り付けたテキストと同じ順で並ぶ。
2. **Given** 区切りの前後に空白・改行がある、または最初の区切りの前・最後の区切りの後が空のテキスト、**When** 送る、**Then** 各下書きの前後の空白・改行は取り除かれ、空の部分は下書きにしない。
3. **Given** 「@@@」を1つも含まないテキスト、**When** 送る、**Then** エラーにせず、全体を1件の下書きとして登録し、「区切り（@@@）が見つからなかったため、1件として登録しました」と出す（PRD FR-5）。
4. **Given** 一部の投稿がThreadsの上限（500文字。絵文字はUTF-8のバイト数で数える）を超える、またはリンクが6個以上あるテキスト、**When** 送る、**Then** すべて登録したうえで、該当する下書きに「Threadsの上限を超えています」と表示し、登録後の案内でもその件数を伝える。
5. **Given** 貼り付け欄が空、または空白だけ、**When** 送ろうとする、**Then** 送る操作はできない。
6. **Given** 送った後、**When** 登録が終わる、**Then** 貼り付け欄は空になる。登録に失敗した場合は、貼り付けた内容を欄に残したまま、原因と再試行の手段を示す。
7. **Given** 登録直後の案内（「30件を登録しました」）が出ている、**When** ユーザーが案内の「取り消す」を押す、**Then** その登録の下書きがまとめて削除され、貼り付けた内容が貼り付け欄に戻る（別のAccount用の回答を貼ってしまったときなどに、1回で戻せる）。

### User Story 3 - 登録した下書きを確認・修正・削除する (Priority: P2)

ユーザーは要確認の一覧で、登録した下書きの本文を確認し、必要なら書き直したり、明らかに不要なもの（区切り損ねた前置きの文章など）を削除したりする。

**Why this priority**: 外部LLMの回答には前置きや崩れた区切りが混じることがあり、承認（004）の前に整えられないと、要確認の一覧が使いにくくなる。ただし登録（P1）ができれば流れは成立するためP2とする。

**Independent Test**: 下書きを1件書き直して保存し、一覧で更新されていること、別の1件を削除して一覧から消えることを確認する。

**Acceptance Scenarios**:

1. **Given** 要確認の下書き、**When** ユーザーが編集を開いて本文を書き直して保存する、**Then** 一覧に書き直した本文が出る。
2. **Given** 要確認の下書き、**When** ユーザーが削除を選ぶ、**Then** 確認なしでその下書きが一覧から消え、トーストの「元に戻す」を押すと一覧に戻る。
3. **Given** 要確認の下書きが複数ある、**When** ユーザーがいくつかを選んで「選んだ下書きを削除」を選ぶ、**Then** 確認なしで選んだ下書きがまとめて消える。
4. **Given** 編集中の下書きが別のタブで書き直されていた、**When** 保存する、**Then** 002と同じく「他の場所で更新されています」のダイアログで、読み込み直すか上書きするかを選べる。

### Edge Cases

- 一度に貼り付けられる量には上限を設ける（1回で最大50件、貼り付け全体で最大50,000文字、分割した1件は最大2,000文字）。超える場合は、登録せずに上限と、分けて貼り付けるよう案内する。1件が長すぎる場合は、何件目かも伝える。
- 投稿ストックの下書き（要確認）の件数にも上限を設け（1つのAccountにつき500件）、上限を超える登録はしない。超える分があるときは、登録せずに、不要な下書きを削除するよう案内する。
- 区切り文字が「@@@」と少し違う形（「＠＠＠」「@@@@」、前後に空白がある、「**@@@**」「`@@@`」のように装飾された、など）で出力された場合も、同じ区切りとして扱う。区切り文字として扱う形はプロンプトの指示と一致させる。
- 外部LLMが投稿の頭に番号（「1.」「【1】」など）を付けて出力しても、そのまま本文として登録する（自動で消さない）。気になる場合はユーザーが編集する。
- 宣伝内容がない・宣伝の対象（有効で期限切れでないもの）がない場合、プロンプトには宣伝についての指示を入れない（宣伝投稿の割合の指示も入れない）。
- 参考投稿が多い場合、プロンプトには新しい順に最大10件を入れる（長くなりすぎないように）。
- プロンプトが外部LLMに貼り付けにくい長さになるのを避けるため、プロンプト全体の長さの目安（30,000文字）を超える場合は、参考投稿・これまでの下書きを古いものから減らして収める。
- クリップボードへのコピーができない環境（ブラウザの許可がない等）では、プロンプトを表示して、手で選択してコピーできるようにする。
- 同じ内容を2回続けて送った（二重送信）場合でも、1回分しか登録されない。
- Threads接続が「要再接続」のAccountでも、プロンプトの作成と下書きの登録・編集・削除はできる（Threadsと通信しないため）。
- Accountが削除された場合は、そのAccountの下書きもすべて一緒に削除される。

## Requirements *(mandatory)*

### Functional Requirements

**AIプロンプトの生成（PRD FR-4）**

- **FR-001**: System MUST Accountごとに、外部LLMに投稿案を作ってもらうためのプロンプトを生成し、ユーザーがコピーできる形で表示する。
- **FR-002**: System MUST プロンプトを、[参考プロダクトのプロンプトの型](./reference-prompt.md)の構成で組み立て、次の節を、材料があるものだけ含める（材料のない節は見出しごと省く）。
  - 導入（作る件数）
  - 話者（Accountの表示名）
  - アカウントの戦略設計：課題の各項目（課題①〜③・人柄・その他）。人柄の「近い人間性」は表示名（例：「丁寧・温かい」）で含める。プロフィール・固定投稿の下書きは含めない（002 FR-003b）
  - 今回組み込む宣伝内容：宣伝の対象（状態が有効で期限切れでないもの）を掲載期限の近い順に、届けたい相手・CTAとともに。宣伝投稿の割合から、今回の件数のうち宣伝に絡める件数の目安を示す。偏らせない・押し売りにしないための指示も含める
  - リサーチで見つけた伸びている投稿：参考投稿の本文と「なぜ良いか」（新しい順に最大10件）と、「型」を抜き出して当てはめる手順（文章はコピーしない）
  - 重複防止：作る投稿どうし、上の材料、投稿ストックの直近の下書き（最大20件）と核が被らないこと
  - 短文・中文・長文の役割と比率、書き出しの変え方
  - 文字数（1投稿150文字以内、絵文字は3個まで。参考プロダクトで効果のあった目安として。Threadsの上限そのものは500文字で、絵文字はUTF-8のバイト数で数える）
  - 出力形式（FR-003）
- **FR-003**: System MUST プロンプトに、出力の形の指示を必ず含める：各投稿を「@@@」だけの行で区切ること（区切りの数は件数−1）、前置き・タイトル・番号・Markdownの装飾を付けないこと、存在しないエピソード・実績を作らないこと、柔らかい語尾で前向きに終えること。最後に、回答をこのアプリの投稿ストックの貼り付け欄にそのまま貼り付ける案内を入れる。
- **FR-004**: Users MUST be able to 作る件数を1〜50件の範囲で選べる。既定は30件とする（参考プロダクトと同じ）。選んだ件数はAccountごとにサーバーに保存し、別の端末・次に開いたときも使う。
- **FR-005**: Users MUST be able to コピーする前にプロンプトの全文を表示し、その場で書き換えられる。書き換えは保存しない（画面を開き直す・「元に戻す」を選ぶと、生成した内容に戻る）。
- **FR-006**: System MUST プロンプトのカードに、反映した内容の要約（課題の入力済み項目数、宣伝の対象の件数、参考投稿の件数）を表示する。課題が0項目のときは、課題の画面への案内を出す。
- **FR-007**: System MUST プロンプトを、表示した時点の最新の戦略プロファイルと下書きから作る。戦略プロファイルを別の画面で保存した後に投稿ストックの画面を開くと、変更が反映されている。
- **FR-008**: System MUST プロンプトの文面を、[参考プロダクトのプロンプトの型](./reference-prompt.md)の言い回しを土台に組み立てる。参考プロダクトにあり、材料がまだないもの（CORE RULES、事実情報、過去の投稿例、却下された投稿）は、本featureでは含めない（004・005で足す）。

**投稿案の一括登録（PRD FR-5）**

- **FR-009**: Users MUST be able to 投稿ストックの画面の下部にある貼り付け欄に外部LLMの回答を貼り付けて送り、下書きとして一括登録できる。
- **FR-010**: System MUST 送られたテキストを「@@@」だけの行（前後の空白、全角の「＠＠＠」、4つ以上の「@」、「**」や「`」で囲まれたものも含む）で分割し、各部分の前後の空白・改行を取り除いて、空でない部分をそれぞれ1件の下書きとして登録する。下書きの並びは、貼り付けたテキストの順を保つ。
- **FR-011**: System MUST 区切りが1つもない場合、全体を1件の下書きとして登録し、区切りが見つからなかったことを表示する。
- **FR-012**: System MUST 登録した下書きの状態を「要確認」とする。要確認の下書きは、004の承認を経ない限り、Threadsへ投稿されない（Constitution原則II）。
- **FR-013**: System MUST 下書きの長さを「Threadsの数え方」で数える：1文字を1として数え、絵文字だけはUTF-8のバイト数（多くは4）で数える。上限は500とし、各下書きに文字数と上限までの使用量のバーを表示する。上限を超える下書き、リンクが6個以上の下書きも登録し、一覧でその下書きに注意の色と「Threadsの上限を超えています（500文字まで／リンクは5個まで）」を表示する（[Threads APIの公式ドキュメント](https://developers.facebook.com/docs/threads/posts/)）。
- **FR-014**: System MUST 1回の登録の上限（50件、50,000文字、1件あたり2,000文字）と、Accountごとの要確認の下書きの上限（500件）を守る。上限を超える送信は、1件も登録せずに案内する。1件あたりの上限は、下書きの編集の上限（FR-019）と同じにする。
- **FR-015**: System MUST 二重送信（同じ送信の再試行やボタンの連打）で、同じ内容が二重に登録されないようにする。
- **FR-016**: System MUST 登録の結果（登録した件数、Threadsの上限を超える下書きの件数、区切りが見つからなかったこと）を、送った直後に表示する。
- **FR-016a**: Users MUST be able to 登録直後の案内の「取り消す」で、その登録（1回の送信）の下書きのうち、まだ残っているものをまとめて削除できる。取り消すと、貼り付けた内容を貼り付け欄に戻す。案内は、次の登録をするか画面を離れるまで表示する。

**投稿ストックの画面と下書きの管理**

- **FR-017**: System MUST 投稿ストックの画面を、docs/ui-design.mdの型C（作業画面型）で作る：上部にプロンプトのカード、中ほどに状態のタブと下書きの一覧、下部に固定の貼り付け欄。
- **FR-018**: System MUST 状態のタブとして「要確認」を表示し、要確認の下書きを、新しい登録（貼り付けの送信）が上、同じ登録の中は貼り付けたテキストの順で一覧表示する（「承認済み」「却下」のタブは004で足す）。各下書きには本文（改行を保つ）、文字数と上限までの使用量のバー（FR-013）、登録日時を表示する。
- **FR-019**: Users MUST be able to 要確認の下書きの本文を編集できる（2,000文字まで）。保存は002と同じく、別のタブ・端末での更新を検知して、読み込み直すか上書きするかを選ばせる。
- **FR-020**: Users MUST be able to 要確認の下書きを、1件ずつ、または複数選んでまとめて削除できる。削除は確認を求めずにすぐ一覧に反映し、直後のしばらくの間（約5秒）は「元に戻す」で取り消せる。
- **FR-021**: System MUST サイドバーに「投稿ストック」を、見出しなしの「ホーム」の下に表示する（docs/ui-design.md「2. 画面の骨格」）。「投稿をつくる」ボタンは、この画面へ移動する。
- **FR-022**: System MUST 未保存の変更（書きかけの貼り付け欄、編集中の下書き）がある状態で画面・Accountの移動やタブを閉じる操作が行われたとき、002と同じく警告する。

**アクセス範囲・プラン・データの扱い**

- **FR-023**: System MUST 投稿ストックの表示・操作を、そのAccountの`owner`であるユーザーだけに許可する（002 FR-023と同じ）。
- **FR-024**: System MUST プロンプトの生成を、そのAccountでgrower機能を使える場合（プラン2以上か無料体験中。002 FR-024と同じ判定）だけ許可する。使えない場合は、プロンプトのカードの代わりに「AIプロンプトの生成はプラン2以上で使えます」という案内と、「@@@」で区切って貼り付ければ自分で用意した投稿もまとめて登録できることを表示する。
- **FR-024a**: System MUST 貼り付けによる一括登録と、下書きの表示・編集・削除は、全プランで許可する（プラン1の自動投稿は投稿ストックが前提のため）。
- **FR-025**: System MUST Threads接続が「要再接続」のAccountでも、プロンプトの生成と下書きの登録・編集・削除を許可する。
- **FR-026**: System MUST Accountの削除時に、そのAccountの下書きをすべて削除する。

**スコープの境界**

- **FR-027**: System MUST NOT 本featureで、重複検知（類似度）、承認・却下、NGワードのチェック、スケジュール投稿・自動投稿、改善フィードバックのプロンプトへの反映を行わない（それぞれPRD FR-6・FR-7・FR-8・FR-10。004〜006で扱う）。ただし、それらが下書きを参照・更新できる形で保持し、プロンプトの生成は後から「却下の傾向」「改善フィードバック」を足せる作りにする（Constitution原則VI）。

### Key Entities *(include if feature involves data)*

- **下書き（Post Draft）**: 投稿ストックの1件の投稿案。Accountに複数紐づく。本文、状態（本featureでは「要確認」のみ。004で「承認済み」「却下」を足す）、登録のまとまり（どの送信で登録されたか）、登録日時・更新日時を持つ。Accountの削除と同時に削除される。
- **登録のまとまり（Draft Batch）**: 1回の貼り付けの送信。登録した件数、区切りが見つかったか、送信日時を持ち、二重送信の判定に使う。
- **プロンプトの設定（Prompt Preference）**: Accountごとの「作る件数」の値（1〜50、既定30件）。サーバーに保存し、端末をまたいで使う。
- **Account・戦略プロファイル**: 001・002で定義済み。プロンプトの材料として読むだけで、本featureでは変えない。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ユーザーが、投稿ストックの画面を開いてから、プロンプトをコピーし、外部LLMの回答を貼り付けて登録するまでのアプリ内の操作を、2分以内に終えられる（外部LLMの応答を待つ時間を除く）。
- **SC-002**: 生成したプロンプトに、入力済みの課題の項目・宣伝の対象の宣伝内容・参考投稿（最大10件）が100%含まれ、未入力の項目の見出しは0件である。
- **SC-003**: 「@@@」で区切られたN件の回答を貼り付けると、N件の下書きが元の順で登録される（区切りの揺れ（全角・4つ以上・前後の空白）を含む確認用のデータで100%）。
- **SC-004**: 二重送信で同じ内容が二重に登録される件数が0件である。
- **SC-005**: 要確認の下書きがThreadsに投稿される件数が0件である（承認の機能ができるまで、投稿されることはない）。
- **SC-006**: 限定テスターのうち90%以上が、説明なしで、プロンプトのコピーから一括登録までを完了できる。
- **SC-007**: プロダクトオーナーが、自分のAccountで1回の操作で30件の投稿案を投稿ストックに登録でき、これまでのスプレッドシートへの貼り付け作業をしなくて済む。

## Assumptions

- 投稿文の生成はアプリの中では行わず、外部LLM（ChatGPT・Claude等）へのコピー＆ペーストで行う（Constitution原則III）。参考プロダクトにある「APIキーを設定してアプリ内で自動生成する」機能は取り込まない。
- Threadsの1投稿の上限は、公式ドキュメント（2026-10-03に確認）のとおり500文字で、絵文字だけはUTF-8のバイト数で数える。リンクは5個まで（6個以上は投稿に失敗する）。参考プロダクトのプロンプトにある「日本語は1文字3バイト」という説明は誤りなので取り込まない。プロンプトの「150文字以内・絵文字3個まで」は、参考プロダクトで効果のあった書き方の目安として残す。下書きの編集では、外部LLMの出力をそのまま直せるよう2,000文字まで受け付ける。
- 画像の添付は本featureでは扱わない（テキストの投稿だけ）。画像は、自動投稿のfeature以降で必要に応じて扱う。
- 作る件数の既定値（30件）、1回の登録の上限（50件・50,000文字）、要確認の下書きの上限（500件）、参考投稿の上限（10件）、直近の下書きの上限（20件）、プロンプトの長さの目安（30,000文字）は暫定値とする。実運用で見直す。
- 下書きの削除は、外部LLMの出力の前置きや崩れた区切りなど「明らかに不要なもの」を取り除くためのもの。内容を見て使わないと判断したものは、004の「却下」（理由を記録し、次のプロンプトに反映する）で扱う。
- 5本柱（投稿ジャンルの偏り管理）の配分の指示は、課題の「投稿ジャンル」の自由記述をそのままプロンプトに含めることで代える。配分の数値管理は本featureでは扱わない。
- 宣伝に絡める件数の目安は「作る件数 × 宣伝投稿の割合」（四捨五入）とする。参考プロダクトの「1日の投稿数のうち何件」という書き方は、投稿時間の設定ができる005で取り入れる。
- 「投稿をつくる」ボタン（docs/ui-design.md）は、本featureで投稿ストックの画面への移動として出す。
- 画面の文言は日本語とする。日時は日本時間で表示する。
