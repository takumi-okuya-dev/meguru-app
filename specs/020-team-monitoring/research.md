# Research：チームの運用状況を見る

**Feature**：[spec.md](./spec.md) | **計画**：[plan.md](./plan.md) | **日付**：2026-11-04

技術コンテキストに「要確認」は残っていない。以下は、今のコードを読んで決めたこと。

## R1. 新しく記録を取らず、今ある表から数える

- **決定**：マイグレーションは足さない。人の動きは `activity_logs`、投稿は `post_drafts`、伸びは `post_metrics` から、開いたときに数える。
  - 人の動き：`activity_logs` のうち、`actor_user_id` がその人で、`account_id` が範囲のAccount（管理者はチームに入っているすべて、編集者は担当のAccount。R5）で、`action` が次の4つの行。`drafts_registered`（案を作る）・`draft_edited`（直す）・`drafts_approved`（承認）・`drafts_rejected`（却下）。
  - 投稿：`post_drafts` の `status = 'published'` と `published_at`。承認済みの残りは `status IN ('approved','publishing')`、要確認は `status = 'needs_review'`。
  - 伸び：`post_metrics` の `state IN ('confirmed','late_confirmed')` の `views` を、`post_drafts.published_at` で30日ずつに分ける（R4）。
- **理由**：操作の記録は、チームに入っているAccountでだけ書かれ（specs/011 research.md R8）、ちょうど「チームに入った後の動き」になる（spec Edge Cases「入る前の動きは数えない」）。索引も足りる（`activity_logs_account_actor_idx`・`post_drafts_published_idx`・`post_metrics` の主キー）。
- **ほかの案**：毎日の集計の表を作る（Cronと表が増える。20件のAccountなら開いたときに数えても十分速い。SC-002）。

## R2. 操作の記録の保存期間（90日）との関係

- **決定**：操作の記録は90日で消える（`ACTIVITY_LOG_RETENTION_DAYS`）。90日より前の動きは数えられないので、最後に動いた日が見つからない人は「90日以内にありません」と出し、「止まっている」の印を付ける。チームに入ってからまだ90日たっていない人で記録がなければ「まだありません」と出す。
- **理由**：「まだありません」と「90日より前に動いた」を正しく分けられないため、嘘にならない言い方にする。どちらも7日より長く止まっているので、印は同じ。
- **ほかの案**：最後に動いた日だけを `team_members` に持つ（列とマイグレーションが増え、操作のたびに書き込みが増える）。

## R3. 「止まっている」の日数の起点

- **決定**：人は `max(最後に動いた日時, チームに入った日時 team_members.joined_at)`、Accountは `max(最後に投稿した日時, チームに入った日時 team_accounts.added_at)` から、今までが7日（168時間）より長いと「止まっている」。並びは、この起点の古い順（FR-012）。
- **理由**：入ったばかりの人・Accountに、すぐ印が付かないようにする（spec Edge Cases）。日付の境目（日本時間の0時）でなく時間で数えると、境目の扱いで迷わない。
- **ほかの案**：日本時間の暦の日で数える（境目の前後で1日ずれ、テストが時刻に左右される）。

## R4. 伸びの比

- **決定**：投稿した日時で、直近30日（`now-30d ≦ published_at < now`）とその前の30日（`now-60d ≦ published_at < now-30d`）に分け、それぞれ確定した閲覧数の中央値（`percentile_cont(0.5)`）をとる。比＝直近÷前。どちらかの30日の確定した投稿が5件に満たないか、前の中央値が0なら「まだ判定できません」。比が0.8以下なら「伸びていない」。
  - 直近30日のうち、投稿から7日たっていない投稿は、まだ確定していないので入らない（006のとおり、確定した値だけで比べる。FR-021）。
- **理由**：006の判定（そのAccountの直近30件と比べる）とは別の物差し。ずっと低いAccountでも、前より下がっていればわかる（2026-11-04 の決定）。しきい値と件数は共有の定数にし、テスト版のデータを見て直せるようにする。
- **ほかの案**：平均（大きく伸びた1件に引っぱられる）、006の低調の割合（ずっと低いAccountが「普通」に見える）。

## R5. 見られる人と範囲の判定

- **決定**：`access.ts` に `authorizeTeamStatus(db, user, teamId)` を足す。`authorizeTeamMember`（チームの人か・チームのまとまりが使えるか）を通したあと：
  - 管理者：範囲は「チームのすべて」。
  - 編集者：同じチーム経由の担当（`memberships` の `role = 'editor'` かつ `team_id` がこのチーム）のAccountのうち、オーナーのチームのまとまりが使えるもの（019：チームがOFFの人は手伝ってもらえない）。1つもなければ `403 ROLE_FORBIDDEN`。
  - メンバー：`403 ROLE_FORBIDDEN`。
  - 結果は `{ team, scope: "all" } | { team, scope: "assigned", accountIds }`。数える関数は、この範囲の外の行を問い合わせの時点で除く（画面で隠すだけにしない。FR-001・SC-003）。
- **理由**：Constitution原則V（判定は1か所）。チームの判定（`authorizeTeamMember`・`authorizeTeamAdmin`）と同じ場所・同じ形に足す。担当の判定は、`getTeamDetail` と同じ `memberships` の行を使う。
- **ほかの案**：`authorizeAccount` をAccountごとに呼ぶ（20件で20回の問い合わせになり、チーム単位の画面に合わない）。

## R6. 管理者に見せる範囲と、チームのまとまりがOFFの人

- **決定**：管理者には、チームの画面（`getTeamDetail`）と同じく、チームに入っているすべての人とAccountを出す。チームのまとまりがOFFの人も、行は出す（チームから外れたわけではないので）。編集者には、R5のとおり、オーナーのチームがOFFのAccountを出さない。
- **理由**：019は、チームがOFFの人を「手伝えない・手伝ってもらえない」とした。運用状況は手伝いではなく、チームの画面に名前が出ている人の数を出すだけ。編集者の範囲は「手伝える先」なので、手伝えない先は外す。

## R7. 自動投稿のまとまりがOFFのオーナー・接続の切れたAccount

- **決定**：オーナーの `autopost` が使えないAccount（`featureOnSql(owner, "autopost")` が偽）は、伸びを「取り込んでいません」にし、「伸びていない」の印を付けない（反応数を取り込まないため。FR-022）。投稿の数と「止まっている」はそのまま数える。`accounts.connection_status` が `needs_reconnect`・`not_connected` なら「接続が切れています」を出す（spec Edge Cases）。
- **理由**：投稿が止まっている理由を、管理者・編集者が取り違えないようにする。

## R8. 1つのAPI、チームの画面の件数の印

- **決定**：`GET /api/teams/:teamId/status` の1本で、人とAccountの一覧を返す。チームの画面の詳細（`GET /api/teams/:teamId`）に `statusVisible`（運用状況を開けるか）を足し、開ける人のチームの画面は、同じ `status` を読んで件数の印（止まっている人とAccountの数）を出す。`status` の結果は、運用状況の画面と同じ問い合わせのキーで共有する。
- **理由**：件数のためだけのAPIを作らない。チームの画面を開いた後に運用状況を開くと、読み込みを待たずに出る。メンバーには `statusVisible` が偽なので、問い合わせ自体をしない。
- **ほかの案**：チームの詳細に件数を足す（チームの画面の問い合わせが重くなり、メンバーにも毎回数える）。

## R9. 招待の確認の画面とチームの画面の説明

- **決定**：招待の確認の画面（`apps/web/src/pages/invite.tsx` の「メンバーとして入ります」）の説明に、1文を足す。チームの画面には、閉じたトグル「チームで見えること」を置き、箇条書きで同じ内容を出す（docs/ui-design.md：説明は閉じたトグルに箇条書き）。
- **理由**：今の参加の流れの「できること」と同じ場所で同意を取る（011 FR-012）。本featureの前から入っている人にも、チームの画面で伝わる（spec US3）。

## R10. 画面

- **決定**：新しい画面 `/teams/:teamId/status`（「担当を決める」`/teams/:teamId/assign` と同じく、チームの下の画面）。スマートフォンは行を縦に積み、パソコンは表にする（モック https://claude.ai/artifact/ESSqiqhGna9qZ56YFBUKg1 ）。印の色は今の色を使う：「止まっている」＝ `bg-warning-bg text-warning`、「伸びていない」＝パフォーマンスの低調（`perf-poor`）の矢印と倍率、それ以外の比は灰色。チームの画面の「運用状況」のボタンに、止まっている数の印を付ける（モックのとおり）。
- **理由**：チームの画面を長くしない。モックで見せた形をそのまま作る。
