# Feature Specification:Threadsで許可するときのアカウントの取り違えを減らす案内

**Feature Branch**: `feature/025-threads-account-guide`

**Created**: 2026-11-08

**Status**: Draft

**Input**: 2026-11-08、024をテスト版で確かめたとき、@taku.it.ai のアカウントを「接続し直す」→「Threadsで許可する」と進めると、許可の画面に前に使った別のThreadsアカウント（marron.taku）が出た。Threadsの許可の画面は、ブラウザでthreads.comにログインしているアカウントをそのまま使い、アプリから切り替える指定はない（Metaの公式の資料に載っていない。`force_reauth=true`・`prompt=login` をURLに足しても効かないことを確かめた）。シークレットウィンドウを使う・threads.comでログインし直す、という回避は手間が大きい。そこで、画面の案内で取り違えと手間を減らす。つなぐ動き（001・010・024）とトークンの貼り付けの方法は変えない。

**Source**: [001のspec](../001-login-account-setup/spec.md)（Threadsで許可する）、[010のspec](../010-token-account-add/spec.md)（接続し直す・トークン）、[012のspec](../012-accounts-before-connect/spec.md)（つなぐ前のアカウント）、[024のspec](../024-tester-invite-connect/spec.md)（テスター招待・FR-011・FR-015）、[docs/ui-design.md](../../docs/ui-design.md)（説明は閉じたトグルの箇条書き）、[Constitution](../../.specify/memory/constitution.md) 4.4.0 原則V。

## Clarifications

### Session 2026-11-08

- Q:「ほかの人が登録済み」「自分の別のアカウントに登録済み」で戻ってきたときにも、threads.comを開くボタンと切り替えの手順を出すか？ → A:出す。今のエラーの文（と、登録済みのアカウントを開くリンク）に加えて、接続し直しの取り違えと同じ手順を出す（FR-006）。
- Q:招待済みで違うアカウントでつながったときの案内は、いつまで出すか？ → A:オーナーが「閉じる」を押すまで「このアカウントの設定」に出し続け、閉じたら二度と出さない（FR-008。閉じた記録を持つ）。

## 用語

- **許可するアカウント**：Threadsの許可の画面で使われるアカウント。ブラウザでthreads.comにログインしているアカウントになる。
- **使うべきアカウント**：その操作で許可してほしいThreadsアカウント。
  - 接続し直すとき：今つながっているアカウントのユーザー名
  - テスター招待が「招待済み」のとき：申し込んだユーザー名
  - それ以外（はじめてつなぐ・審査の後）：決まっていない
- **取り違え**：使うべきアカウントと違うアカウントで許可したこと。

## User Scenarios & Testing *(mandatory)*

### User Story 1 -押す前に、どのアカウントで許可されるかがわかる（Priority: P1）

利用者が「Threadsで許可する」を押す前に、その近くに「threads.comでログインしているアカウントで許可されます。@〇〇でログインしているか確かめてください」と短く出る。くわしい手順（違うときの切り替え方）は、閉じたトグルの中に箇条書きで出る。利用者は、押す前に自分のブラウザの状態を確かめられる。

**Why this priority**：取り違えの多くは、押す前に知っていれば防げる。案内を出すだけで、つなぐ動きを変えずに済む。

**Independent Test**：接続し直す画面と、招待済みのつなぐ画面で、「Threadsで許可する」の近くに使うべき@ユーザー名と短い案内が出ること、トグルを開くと切り替えの手順が出ることを確かめる。

**Acceptance Scenarios**:

1. **Given** つながっているアカウント（@taku.it.ai）、**When** 利用者が「接続し直す」を開く、**Then** 「Threadsで許可する」の近くに「threads.comでログインしているアカウントで許可されます。@taku.it.ai でログインしているか確かめてください」が出る。
2. **Given** テスター招待が「招待済み」（申し込んだユーザー名 @shop_tokyo）のつなぐ前のアカウント、**When** 利用者が「Threadsにつなぐ」を開く、**Then** 「Threadsで許可する」の近くに、@shop_tokyo でログインしているか確かめる案内が出る。
3. **Given** 使うべきアカウントが決まっていない（はじめてつなぐ・審査の後）、**When** 利用者が「Threadsで許可する」の近くを見る、**Then** 「threads.comでログインしているアカウントで許可されます」だけが出る（@ユーザー名は出さない）。
4. **Given** 上の案内、**When** 利用者が「違うアカウントが出たときは」のトグルを開く、**Then** 次の箇条書きが出る。
   - threads.comを開き、今のアカウントからログアウトする
   - @〇〇 でログインし直す（決まっていなければ「つなぎたいアカウント」）
   - このページに戻って、もう一度「Threadsで許可する」を押す
   - threads.comを新しいタブで開くリンク
5. **Given** トークンの貼り付けの方法、**When** 利用者が開く、**Then** この案内は出ない（トークンの方法は変えない）。

---

### User Story 2 -接続し直しで違うアカウントだったとき、すぐ切り替えられる（Priority: P1）

利用者が接続し直しで違うアカウントで許可して戻ってきたとき、今のエラーの文（「再接続には、元の@〇〇で認可してください…」）に加えて、threads.comを新しいタブで開くボタンと、「ログアウト → @〇〇でログイン → このページに戻ってもう一度押す」の短い手順が出る。利用者は、シークレットウィンドウを使わずに、この画面のまま切り替えて、やり直せる。

**Why this priority**：今は、エラーの文だけで何をすればよいかがわからず、利用者が詰まる（2026-11-08のテスト版で実際に起きた）。

**Independent Test**：接続し直しで違うアカウントで許可して戻ると、エラーの文・threads.comを開くボタン・3つの手順・「接続し直す」がそろって出ることを確かめる。

**Acceptance Scenarios**:

1. **Given** @taku.it.ai のアカウント、**When** 利用者が接続し直しで別のアカウント（marron.taku）で許可して戻る、**Then** 「再接続には、元の@taku.it.aiで認可してください。別のアカウントで認可されました。」に加えて、「threads.comを開く」（新しいタブ）と、次の手順が出る。
   1. threads.comで、今のアカウントからログアウトする
   2. @taku.it.ai でログインする
   3. このページに戻って、もう一度「接続し直す」を押す
2. **Given** 上の画面、**When** 利用者がthreads.comで切り替えて、この画面で「接続し直す」→「Threadsで許可する」を押す、**Then** @taku.it.ai の許可の画面になり、つなぎ直せる。
3. **Given** 上の画面、**When** 利用者が「threads.comを開く」を押す、**Then** threads.comが新しいタブで開き、アプリの画面はそのまま残る。

---

### User Story 3 -招待済みで違うアカウントでつながったとき、何が起きたかわかる（Priority: P2）

テスター招待が「招待済み」の申し込みで、申し込んだユーザー名と違うアカウントで許可してつながったとき、つなぐ動きは024のまま（そのままつながる）で、「@〇〇（実際につながったアカウント）でつながりました。申し込んだ @△△ とは違うアカウントです」という案内が、つながったあとの画面に出る。

**Why this priority**：つながること自体は止めないが、利用者が気づかないと、違うアカウントで自動投稿を始めてしまう。US1・US2より起きる頻度は低い。

**Independent Test**：招待済みの申し込み（@shop_tokyo）のアカウントを、別のアカウント（@other_shop）でつなぐと、つながったあとの画面に違うアカウントである旨と、つながったアカウント名が出ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 申し込んだユーザー名が @shop_tokyo の招待済みの申し込み、**When** 利用者が @other_shop で許可してつながる、**Then** アカウントは @other_shop でつながり（024のまま）、「このアカウントの設定」の「Threadsとの接続」に「@other_shop でつながりました。申し込んだ @shop_tokyo とは違うアカウントです」が出る。
2. **Given** 上の案内、**When** 利用者が違うアカウントでつなぎ直したい、**Then** 案内の中に「接続し直す」からつなぎ直せることと、US1の切り替えの手順が出る。
3. **Given** 上の案内、**When** 利用者が「閉じる」を押す、**Then** 案内は消え、その接続については二度と出ない（申し込み直して、また違うアカウントでつながったときは、改めて出す）。
4. **Given** 申し込んだユーザー名と同じアカウントでつながった、**When** つながったあとの画面を見る、**Then** この案内は出ない。

---

### Edge Cases

- 利用者のブラウザがthreads.comにログインしていない → 許可の画面の前にThreadsのログインの画面が出る。案内は同じでよい（「@〇〇でログインしてください」）。
- 違うアカウントで許可して戻ったが、そのアカウントがほかの人の登録済み（`THREADS_ACCOUNT_TAKEN`）・自分の別のアカウントに登録済み（`ACCOUNT_ALREADY_REGISTERED`）→ 今のエラーの文に加えて、US2と同じ切り替えの手順を出す（@ユーザー名がわかるときは使うべきアカウントを出す）。
- 使うべきアカウントのユーザー名が、Threadsの側で変わっていた → 案内はアプリが知っている名前で出す。違うと止められたら、US2の案内のとおりにやり直してもらう（名前が変わったかもしれないことは書かない）。
- スマートフォンでThreadsのアプリが入っている → threads.comを開くリンクがThreadsのアプリを開くことがある。手順の文は「threads.com（またはThreadsのアプリ）で」とし、どちらでもよいことがわかるようにする。
- チームの人（担当・見せてもらっている人）→ 接続はオーナーだけなので、案内もオーナーにだけ出る（今の出し分けのまま）。
- 招待の管理がOFF（審査の後）で、はじめてつなぐ → 使うべきアカウントは決まっていないので、US1-3の短い案内だけを出す。

## Requirements *(mandatory)*

### Functional Requirements

**押す前の案内（US1）**

- **FR-001**：「Threadsで許可する」を出すすべての画面（つなぐ前のアカウントの「Threadsにつなぐ」、テスター招待の「招待済み」、「接続し直す」）で、そのボタンの近くに、threads.comでログインしているアカウントで許可されることを短く出さなければならない。
- **FR-002**：使うべきアカウントが決まっているとき（接続し直す＝今つながっているユーザー名、招待済み＝申し込んだユーザー名）は、FR-001の案内に「@〇〇でログインしているか確かめてください」を入れなければならない。決まっていなければ@ユーザー名は出さない。
- **FR-003**：FR-001の案内の下に、初めは閉じたトグル「違うアカウントが出たときは」を置き、開くと切り替えの手順（threads.com（またはThreadsのアプリ）でログアウト → @〇〇でログイン → このページに戻ってもう一度押す）を箇条書きで出し、threads.comを新しいタブで開くリンクを添えなければならない。
- **FR-004**：トークンの貼り付けの方法の画面と手順は、変えてはならない。

**違うアカウントで戻ったとき（US2）**

- **FR-005**：接続し直しで違うアカウントで許可して戻ったとき（`RECONNECT_ACCOUNT_MISMATCH`）は、今のエラーの文を残したうえで、threads.comを新しいタブで開くボタンと、3つの手順（ログアウト → 元の@〇〇でログイン → このページに戻ってもう一度「接続し直す」を押す）を出さなければならない。手順は閉じずに出す（その画面で次にする操作のため）。
- **FR-006**：接続で、そのThreadsアカウントがほかで登録済みと止められて戻ったとき（`THREADS_ACCOUNT_TAKEN`・`ACCOUNT_ALREADY_REGISTERED`）も、今のエラーの文に加えて、FR-005と同じ切り替えの手順を出さなければならない（`ACCOUNT_ALREADY_REGISTERED` の、そのアカウントを開くリンクは残す）。使うべきアカウントが決まっていなければ「つなぎたいアカウント」と書く。

**招待済みで違うアカウントでつながったとき（US3）**

- **FR-007**：招待済みの申し込みで、申し込んだユーザー名と違うアカウントでつながったときは、つなぐ動き（024 FR-015・FR-011）を変えずに、そのアカウントの「このアカウントの設定」の「Threadsとの接続」に、つながったユーザー名と申し込んだユーザー名を示す案内を出さなければならない。案内には「接続し直す」からつなぎ直せることを添える。
- **FR-008**：FR-007の案内は、オーナーが閉じるまで出し続け、閉じたらその接続については出さない（申し込み直して、また違うアカウントでつながったときは改めて出す）。申し込んだユーザー名と同じアカウントでつながったとき、申し込んだユーザー名でつなぎ直したときは出さない。

**共通**

- **FR-009**：案内の文は短くし、説明は箇条書きにする。新しい強調の色や形は使わず、今の注意の表示（案内の枠）とボタンの形にそろえる。スマートフォンの幅でも読めるようにする。
- **FR-010**：案内は、そのアカウントのオーナーにだけ出す（接続の操作はオーナーだけ。今の出し分けのまま）。
- **FR-011**：つながっているアカウントで、接続し直しから失敗して戻ったときは、どのエラーでも「Threadsとの接続」にエラーの文を出さなければならない。今のトーストの代わりに出し、二重には出さない。接続し直しを始めたら消す。手順の「もう一度押す」ボタンの名前は、画面のボタン（「接続し直す」か「再接続」）に合わせる（research.md R2）。

### Key Entities *(include if feature involves data)*

- **使うべきアカウント**：画面ごとに決まるThreadsのユーザー名（接続し直す＝今つながっている名前、招待済み＝申し込んだ名前）。新しいデータは持たない。
- **違うアカウントでつながった知らせ**：招待済みの申し込みが違うアカウントでつながった事実（申し込んだ名前・つながった名前）と、オーナーが閉じたかどうか。024の申し込みの記録（違うユーザー名でつながった記録）をもとにする。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：「Threadsで許可する」を出すすべての画面で、押す前に、どのアカウントで許可されるか（使うべき@ユーザー名が決まっていればそれも）が見える。
- **SC-002**：接続し直しで違うアカウントで許可して戻った利用者が、シークレットウィンドウを使わずに、その画面の案内だけで正しいアカウントでつなぎ直せる（テスト版で、2分以内にやり直せることを人が測る）。
- **SC-003**：招待済みで違うアカウントでつながった場合、オーナーが閉じるまで、毎回その事実が「Threadsとの接続」に出る（見落としが0件）。
- **SC-004**：トークンの貼り付けの方法と、つなぐ・接続し直すの動き（成功・失敗の判定）が、この機能の前と変わらない。

## Assumptions

- Threadsの許可の画面でアカウントを切り替える指定はない（2026-11-08時点。Metaの公式の資料、`force_reauth`・`prompt=login` の試し）。Metaが将来その指定を出したら、そのときに使うかを決める。
- threads.comのログアウトは、threads.comの画面（プロフィール › 設定 など）から利用者が行う。アプリからthreads.comのログアウトを直接させる手段は使わない（Metaが用意していない）。手順の文は、画面の名前に頼らず「今のアカウントからログアウトする」と書く。
- threads.comを開くリンクは、トップ（https://www.threads.com/）にする。
- 「閉じた」の記録は、024の申し込みの記録に足すか、アカウントごとの印として持つ（どちらにするかは計画で決める）。
- 文言は日本語。テスト版・本番で同じ。

## Out of Scope

- 許可の画面でアカウントを選ばせる・ログインし直させる指定（Metaにないため）。
- つなぐ動きの変更（違うアカウントでつながったときに止める、など）。
- トークンの貼り付けの方法の変更。
- threads.comのログイン状態をアプリから読み取ること（できないため）。
