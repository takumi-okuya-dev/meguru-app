# Research：Threadsのアルゴリズムの解析

**Feature**：[spec.md](./spec.md) | **計画**：[plan.md](./plan.md) | **日付**：2026-11-05

研究の根拠は [docs/threads-algorithm-research.md](../../docs/threads-algorithm-research.md) の 1章（ランキングの仕組み）・5.3（自分のデータで見る案）・5.5（相関と因果）・5.7（上位表示に関わる学術的な研究）。

## R1. 計算する場所：決まった計算を shared に置き、読むたびに計算する

- **Decision**：解析の計算はすべて `packages/shared/src/analysis/` の純粋な関数（`analyzePosts`）にする。APIは確定した投稿を1回の問い合わせで読み、関数に渡して結果を返す。結果は保存しない。プロンプトを作るときも、同じ関数で傾向を求める。
- **Rationale**：
  - 直近90日の確定した投稿は、1日10件でも900件まで。計算は1回で数ミリ秒で終わる。
  - 保存しないので、006の値が変わっても（遅れて確定など）古い結果が残らない。
  - 画面とプロンプトで同じ傾向になる（同じ関数）。テストも関数だけで書ける。
  - アプリの中でAIを呼ばない（原則III）。
- **Alternatives considered**：
  - 毎日の処理で集計して表に保存する：Cronの処理が増え、値がずれる時間ができる。件数が小さいので要らない。
  - Webで計算する：プロンプトを作るAPIでも同じ計算が要るので、APIで持つ。

## R2. 材料：確定した投稿・投稿時点のフォロワー数・24時間時点の値

- **Decision**：
  - 投稿：`post_drafts.status = 'published'` で、`post_metrics.state = 'confirmed'`、`published_at` が直近90日（日本時間の今日から89日前の0時以降）。遅れて確定（`late_confirmed`）と計測できない（`unmeasurable`）は使わない（FR-001）。
  - 投稿時点のフォロワー数：006のCSVと同じく、`follower_snapshots` のうち `captured_at <= published_at` で最も新しい行（FR-002c）。ない投稿は広がりを求めない（FR-023）。
  - 24時間時点の値：`post_metric_snapshots` の `kind = 'h24'`。ない投稿は初速と後からの伸びを求めない。
- **Rationale**：006で取りためた値だけで足りる。新しくThreadsから取る値はない（spec Key Entities）。
- **Alternatives considered**：3日の値（`d3`）も使う：「後からの伸び」は24時間と確定の2点で足りる。画面が増えるので使わない。

## R3. 値の定義

| 値 | 定義 | 求めないとき |
|---|---|---|
| 閲覧（伸び） | 確定した `views` | — |
| 反応率 | (いいね＋返信＋リポスト＋引用) ÷ 閲覧 | 閲覧が0 |
| 返信率 | 返信 ÷ 閲覧 | 閲覧が0 |
| 広がり | 閲覧 ÷ 投稿時点のフォロワー数 | フォロワー数がない・0 |
| 初速 | 24時間時点の閲覧 | 24時間の値がない |
| 後からの伸び | 確定した閲覧 ÷ 24時間時点の閲覧 | 24時間の値がない・0 |

- 集計はいつも中央値（`median`、006と同じ関数）。平均は使わない（FR-010）。数件だけ極端に伸びるため（Szabo 2010・Cheng 2014。調査 5.7）。
- 文字数はコードポイントで数える（プロンプトの文字数と同じ数え方）。
- 広がりは、おすすめに乗った目安の表で並べる。フォロワー数が急に増えても、広がりで比べられる（spec Edge Cases）。区切りの表は、短く保つため閲覧・反応率・返信率だけにする。

## R4. 区切り

- **時間帯**（日本時間の `published_at` の時）：朝5〜10時・昼11〜15時・夕方16〜19時・夜20〜23時・深夜0〜4時（FR-002）。
- **曜日**：平日・休日。土日と祝日・振替休日・国民の休日を休日にする。祝日は `packages/shared/src/analysis/holidays.ts` に、祝日法の決まり（固定の日・ハッピーマンデー・春分と秋分の式・振替休日・国民の休日）で計算する関数を置く（2000〜2099年。解析は直近90日なので、一度だけの特別な休日は扱わない。新しい依存は足さない）。
- **文字数**：Accountの文字数の設定（014の `lengthSettings`）の短文・中文・長文の長さの間で分ける。短い＝(短文＋中文)÷2 以下、長い＝(中文＋長文)÷2 より上、その間が中くらい。初めの値（55・100・135）なら、〜77字・78〜117字・118字〜。利用者が自分で決めた「短文・中文・長文」と同じ言葉で見られる。
- **本文の特徴**（あり・なし）：
  | key | 名前 | 決まり |
  |---|---|---|
  | `question` | 最後に問いかけ | 最後の空でない行が「？」か「?」で終わる |
  | `number` | 数字を入れる | 半角・全角の数字がある |
  | `shortFirstLine` | 1行目が20字以内 | 1行目が20字以内 |
  | `manyLines` | 改行が多い（5行以上） | 空でない行が5行以上 |
  | `emoji` | 絵文字 | 絵文字がある（`\p{Extended_Pictographic}`） |
  | `callout` | 呼びかけ | 「あなた」「みんな」「皆さん」「みなさん」がある |
- **書き出しの型**（R8）・**テーマ**（R8）：分類が付いた投稿だけで区切る。

## R5. 傾向の選び方（FR-030）

- **Decision**：区切りごとに「その区切りの投稿」と「ほかの投稿」（書き出しの型・テーマは分類の付いたほかの投稿、本文の特徴は「なし」）を比べる。次の3つをすべて満たすものだけを傾向にする。
  1. 両側が10件以上（`ANALYSIS_MIN_BUCKET`）。
  2. 閲覧の中央値が、ほかの投稿の1.5倍以上（`ANALYSIS_TREND_RATIO`）。
  3. ほかの投稿の閲覧の中央値が0より大きい。
- 本文の特徴は、「なし」の側が伸びた場合も傾向にする（例：絵文字のない投稿が伸びやすい）。
- 倍率の大きい順に並べ、5つまで（`ANALYSIS_MAX_TRENDS`）。同じ区切りの種類からは1つまで（時間帯の傾向が2つ並ばない）。
- 傾向の文と、件数・両側の中央値を返す（例：「夜（20〜23時）に出した投稿が伸びやすい」「23件・閲覧の中央値 450（ほかの投稿 250）」）。
- 傾向の行に、合う投稿と合わない投稿の両方の中央値を出す。傾向を活かし始めてから4週間たてば、利用者は同じ行で、合う投稿の閲覧が高いままかを確かめられる（SC-006。新しく記録する値はない）。
- **Rationale**：
  - 比べる数が多いと偶然の差が出る（調査 5.5）。件数と差の決まりで絞る。統計の検定（p値）は出さない（spec Assumptions）。
  - 区切りの種類ごとに1つにすると、同じことを言う傾向が並ばない。
- **Alternatives considered**：
  - 平均と標準偏差で比べる：外れ値に弱い。
  - 回帰で複数の要因を同時に見る：件数が少ないうちは安定しない。説明もしにくい。

## R6. おすすめに乗った目安（FR-020〜FR-023）

- **Decision**：
  - 広がりを求められる投稿が10件以上あるときだけ出す。
  - 広がりの上位20%（`ANALYSIS_RECOMMENDED_TOP`。小さいほうから数えて80%の位置の値以上）で、かつ広がりが1を超える投稿を、広がりの大きい順に並べる。
  - 「おすすめに乗った目安」と「ほかの投稿（広がりを求められる投稿のうち残り）」の、初速・後からの伸び・返信率・文字数の中央値と、最後に問いかけがある件数を並べる（FR-021）。
- **Rationale**：Threadsは、フォローしていない人にも表示する（調査 1章）。フォロワー数を超えた閲覧は、おすすめに出た目安になる。初速と後からの伸びは、広がった投稿の早い時期の手がかりとして研究で使われている（Cheng 2014・Lerman 2010・Szabo 2010。調査 5.7）。
- 表示の順位・場所はAPIで取れないので、推し量りであることを「この画面の見方」に書く（FR-022）。

## R7. プロンプトに入れる傾向と、原則Iの守り（FR-040〜FR-042）

- **Decision**：
  - プロンプトに入れるのは、本文で変えられる傾向だけ（文字数・本文の特徴・書き出しの型・テーマ）。時間帯・曜日の傾向は、文章を作るAIには変えられないので入れず、「自動投稿の時刻の見直しの参考に」として画面に出す（FR-040b）。
  - 次の傾向は入れない（FR-041）：
    - CORE RULESの行に、その特徴の言葉が出てくるもの（絵文字→「絵文字」、問いかけ→「問いかけ」「質問」、数字→「数字」、呼びかけ→「呼びかけ」、改行→「改行」、1行目→「1行目」「書き出し」）。向きに関係なく外す（ルールのほうを優先する）。
    - 傾向の文に、NGワードが入るもの（テーマの名前など。NGワードの照合は004の `findNgWords` を使う）。
  - 節は「■反応が低かった投稿」の後に置く：
    ```text
    ■伸びた傾向(取りためた反応数から見た傾向。合わせすぎず、人柄とCORE RULESを優先すること)
    ・最後に問いかけがある投稿が伸びやすい(20件。閲覧の中央値が、ほかの投稿の1.9倍)
    ```
  - 「プロンプトに入れる」がOFF、または入れる傾向がないときは、節を入れない。プロンプトの文は今と1文字も変わらない（FR-042、SC-004）。
  - 長さの調整では減らさない（最大5行で短いため。006の低調の節と同じ扱い）。
- **Rationale**：
  - 解析の特徴は機械的に決まるものだけで、強い対立の言葉などは特徴に入れていない。それでも、利用者が決めたルールと逆の傾向（例：絵文字は使わないと決めているのに、絵文字の投稿が伸びた）が入らないようにする。
  - 原則VIの低調の投稿と却下ログの節は変えない（Dependencies）。
- **Alternatives considered**：時間帯の傾向もプロンプトに入れる：投稿の時刻は投稿の設定で決まり、文章では変えられない。

## R8. 内容の分類（FR-050〜FR-053）

- **Decision**：
  - 書き出しの型は固定の7つ（`OPENING_TYPES`）：`aruaru`（あるある）・`question`（問いかけ）・`assertion`（言い切り）・`story`（体験談）・`number`（数字）・`announce`（告知）・`other`（その他）。
  - テーマはAccountごとに10個まで（`ANALYSIS_THEMES_MAX`）。名前は1〜20文字、同じ名前は不可。1つずつ短いid（`t` で始まる英数字）を持ち、名前を変えても分類はそのまま。テーマを消すと、そのテーマの分類は「テーマなし」になる。
  - 分類のプロンプトは shared の `classifyPrompt(posts, themes)` で作る。投稿には【1】〜【50】の番号を付け、答えの形を決める：
    ```text
    【1】書き出しの型：あるある／テーマ：仕事の悩み
    ```
  - 答えは shared の `parseClassifyAnswer(text, posts, themes)` で読む。番号・型・テーマの名前が一覧と合う行だけを候補にする。合わない行（知らない型・知らないテーマ・知らない番号）は理由つきで返し、保存しない（US4 シナリオ2）。テーマが「なし」なら、テーマなしで型だけ付ける。
  - プロンプトに入れる投稿は、分類が付いていない確定した投稿の新しい順に50件まで（FR-051）。
  - 手で直す：同じ画面の「分類済み」で、型とテーマを選び直す（FR-053）。
- **Rationale**：018の「AIと考える」と同じく、目印のある決まった形で答えてもらい、貼って反映する（原則III）。番号と投稿の対応はWebが持つ（プロンプトを作ったときの一覧）。
- **Alternatives considered**：テーマも固定の一覧にする：Accountごとに話す内容が違うので、利用者が決める。

## R9. 宣伝の投稿を分けて見る（Edge Cases）

- **Decision**：本文に、そのAccountの宣伝内容のタイトルか専用URL（`linked_url`）が入っている投稿を「宣伝の投稿」とみなす。画面の上で「すべて」「ふだんの投稿」を選べる（初めは「すべて」）。プロンプトに入れる傾向は、いつも「ふだんの投稿」で求める。
- **Rationale**：下書きには、どの宣伝内容を使ったかの記録がない（spec「投稿づくりの記録で分かる範囲」）。タイトルとURLの一致なら、決まりで分かる。宣伝の投稿は伸び方が違うので、ふだんの投稿の傾向をゆがめないようにする。
- **Alternatives considered**：下書きに宣伝内容のidを記録する列を足す：外のAIが作った文を貼る流れなので、どの宣伝内容を使ったかは確かには分からない。

## R10. 判定と画面の場所（FR-060〜FR-062）

- **Decision**：
  - 読む：`authorizeAccount(..., "view", { feature: "autopost" })`（パフォーマンスと同じ。見せてもらっている人には出ない）。
  - 書く（「プロンプトに入れる」・テーマ・分類）：`"content"` と `feature: "autopost"`。操作は `recordActivity`（`kind: "content"`）に残す。
  - 画面：`/accounts/:accountId/analysis`。サイドバーの「自動投稿」の「パフォーマンス」の次に「解析」（ChartLineIcon）。
- **Rationale**：011の判定の1か所（原則V）、019の機能のまとまり。新しいロールや区分は作らない。

## R11. 投稿が少ないとき

- **Decision**：確定した投稿（選んだ範囲）が20件（`ANALYSIS_MIN_TOTAL`）より少なければ、表と傾向を出さず、「あと〇件たまると見られます」と出す（US1 シナリオ4）。20件は、2つの側がそれぞれ10件になる最小の数。
- 区切りの件数が10件未満なら「件数が少ない」、0件なら「試していない」の印を付ける（FR-011）。
