# Feature Specification:Threadsのアルゴリズムの解析

**Feature Branch**: `feature/022-algorithm-analysis`

**Created**: 2026-11-05

**Status**: Draft

**Input**: 2026-11-05に、ユーザーが022として「Threadsのアルゴリズムの解析」を作ると決めた（[docs/next-features.md](../../docs/next-features.md) §F-3）。パフォーマンス（006）で取りためた反応数から、伸びやすい内容・時間帯・曜日・長さと、上位表示（おすすめ）に乗りやすい投稿の特徴（フォロワー数に比べた閲覧の広がり・24時間の初速・返信の割合など）を見つけて、投稿づくりに活かす。表示の順位はAPIで取れないので、取りためた値から推し量る。学術的な研究も調べる。

**Source**: [docs/threads-algorithm-research.md](../../docs/threads-algorithm-research.md)（2026-10-08の調査と、2026-11-05に足した 5.7「上位表示（おすすめ）に関わる学術的な研究」）、[006のspec](../006-performance-feedback/spec.md)（反応数・取り込みの履歴・投稿時点のフォロワー数・確定・好調／低調）、[019のspec](../019-feature-switches/spec.md)（機能のまとまり「自動投稿」）、[Constitution](../../.specify/memory/constitution.md) 4.3.0 原則I（人柄・NGワード）・III（アプリの中でAIを呼ばない）・VI（改善の反映）。

## Clarifications

### Session 2026-11-05

- Q: 見つかった傾向を、投稿づくりにどう活かすか？ → A: 投稿のプロンプトに「■伸びた傾向」の節を足す（入れるかは切り替えられる。初めは入れる）。時間帯・曜日の傾向は、自動投稿の時刻の見直しの参考として画面に出す。
- Q: テーマや書き出しの型でも比べるか？付け方は？ → A: 比べる。本文の特徴（機械的に分かるもの）に加えて、外のAIに分類を頼む。分類のプロンプトをコピーし、答えを貼ると、投稿ごとにテーマと書き出しの型が付く（018の「AIと考える」と同じ形。原則III）。分類の一覧は固定する。

## 用語

- **確定した投稿**：006で、投稿から約7日たって値が確定した投稿。計測できない投稿は含めない。
- **伸び**：確定した閲覧数。数件だけ極端に伸びるので、中央値と対数で扱う。
- **広がり**：確定した閲覧数 ÷ 投稿した時点のフォロワー数。1を超えると、フォロワーの数より多くの人に表示された（フォロー外、つまり「おすすめ」に出た目安）。
- **初速**：投稿から24時間時点の閲覧数。
- **後からの伸び**：確定した閲覧数 ÷ 24時間時点の閲覧数。1日目のあとも、おすすめに出続けた目安。
- **返信率**：返信の数 ÷ 閲覧数。Threadsのランキングは返信・会話を予測に使う（調査 1章）。
- **おすすめに乗った目安の投稿**：広がりがそのAccountの中で特に大きい投稿（FR-020）。表示の順位や場所はAPIで取れないので、推し量りであることを画面に示す。
- **傾向**：比べた結果のうち、件数が足りて、差がはっきりしているもの（FR-030）。
- **本文の特徴**：本文から機械的に分かること（文字数・行数・1行目の長さ・問いかけ・数字・絵文字・呼びかけ・一人称など）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 伸びやすい時間帯・曜日・長さが分かる (Priority: P1)

オーナーが「解析」を開くと、そのAccountの確定した投稿から、時間帯・曜日・文字数ごとの伸びの中央値と件数が並ぶ。件数が足りて差がはっきりしているところだけ「傾向」として出る。

**Why this priority**: いちばん求められている「いつ・どれくらいの長さで出すと伸びるか」。006のデータから、そのまま出せる。研究でも、時刻と長さの正解は人ごとに違う（調査 5.7）ので、そのAccountのデータで出す価値がある。

**Independent Test**: 確定した投稿が60件あるAccountで、夜（20〜23時）の投稿の閲覧数を高めにしておく。「解析」を開き、時間帯の表で夜の中央値が高く、件数が出て、「夜に出した投稿が伸びやすい傾向」が出ることを確かめる。件数の少ない区切りには「件数が少ない」と出ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 確定した投稿が十分にあるAccount、**When** 「解析」を開く、**Then** 時間帯（朝・昼・夕方・夜・深夜）・曜日（平日・休日）・文字数（短い・中くらい・長い）ごとに、件数と、閲覧・反応率・返信率の中央値が並ぶ。
2. **Given** 区切りの件数が足りない、**When** 見る、**Then** その区切りは「件数が少ない」と出て、傾向には使わない。
3. **Given** 件数が足りて、ほかの区切りとの差がはっきりしている、**When** 見る、**Then** 「〇〇の投稿が伸びやすい」のような短い傾向が出る。
4. **Given** 確定した投稿がまだ少ない（最初の数週間）、**When** 「解析」を開く、**Then** 「あと何件たまると見られるか」が出る。

---

### User Story 2 - おすすめに乗りやすい投稿の特徴が分かる (Priority: P1)

「解析」に、おすすめに乗った目安の投稿（広がりの大きい投稿）と、その特徴が並ぶ。初速・後からの伸び・返信率が、ほかの投稿とどう違うかが分かる。

**Why this priority**: ユーザーが挙げた「上位表示されやすい」。表示の順位は取れないが、フォロワー数を超えた閲覧と初速から推し量れる（Cheng 2014・Lerman 2010・Huszár 2022。調査 5.7）。

**Independent Test**: フォロワー100人のAccountで、閲覧が300を超える投稿を数件作る。「解析」を開き、それらが「おすすめに乗った目安」に並び、広がり（×3.0など）・初速・返信率が、ほかの投稿の中央値と並べて出ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 確定した投稿と投稿時点のフォロワー数があるAccount、**When** 「解析」を開く、**Then** 「おすすめに乗った目安」の投稿が、広がりの大きい順に並ぶ（本文の書き出し・投稿日時・閲覧・広がり・初速・後からの伸び・返信率）。
2. **Given** おすすめに乗った目安の投稿と、ほかの投稿、**When** 見る、**Then** 2つのまとまりの、初速・後からの伸び・返信率・本文の特徴の違いが並ぶ。
3. **Given** 投稿時点のフォロワー数がない投稿（記録を始める前）、**When** 見る、**Then** 広がりは出さず、ほかの値だけを使う。
4. **Given** 画面、**When** 見る、**Then** 「表示の順位はThreadsから取れないので、フォロワー数と閲覧から推し量っています」と分かる（閉じたトグルの説明）。

---

### User Story 3 - 傾向を次の投稿づくりに活かす (Priority: P2)

見つかった傾向が、次の投稿のプロンプトに入る。または、投稿の時刻の見直しに使える。

**Why this priority**: 分析が表示されるだけで次の生成に活きないと、原則VIの考え方（改善が次に活きる）に届かない。

**Independent Test**: 傾向が2つ出ているAccountで、プロンプトを作り直す。プロンプトに「■伸びた傾向」の節があり、2つの傾向が件数つきで入ることを確かめる。「プロンプトに入れる」を外すと、節がなくなることを確かめる。

**Acceptance Scenarios**:

1. **Given** 傾向があるAccount、**When** プロンプトを作る、**Then** 「■伸びた傾向」の節に、傾向が件数つきで入る（低調の投稿と却下ログの節は今のまま）。
2. **Given** 傾向の中に、人柄・CORE RULES・NGワードと食い違うもの（例：強い対立の言葉で伸びた）、**When** 活かす、**Then** その傾向は入れない（原則I）。
3. **Given** 傾向がない（件数不足・差がない）、**When** プロンプトを作る、**Then** 今と同じ文。
4. **Given** 時間帯・曜日の傾向、**When** 「解析」を見る、**Then** 「自動投稿の時刻の見直しの参考に」として、今の投稿の時刻と並べて出る（時刻は自動では変えない）。

---

### User Story 4 - 内容（テーマ・書き出しの型）でも比べられる (Priority: P3)

本文から機械的に分かる特徴のほかに、テーマや書き出しの型（あるある・問いかけ・体験談など）でも比べられる。

**Why this priority**: 「伸びやすい内容」の中心になる（調査 5.3 案C）。内容の分類はアプリの中ではAIで付けられない（原則III）ので、外のAIに分類を頼み、答えを貼る。

**Independent Test**: 確定した投稿30件に内容の分類が付いた状態で、「解析」の内容の表に、分類ごとの件数と中央値が並ぶことを確かめる。

**Acceptance Scenarios**:

1. **Given** 分類が付いていない確定した投稿、**When** 「内容を分類する」を開く、**Then** 分類のプロンプト（固定の分類の一覧と、投稿の本文と番号）をコピーでき、答えを貼ると、投稿ごとのテーマと書き出しの型の候補が並ぶ。
2. **Given** 候補、**When** 「反映する」を押す、**Then** 投稿に分類が保存される。知らない分類名や、読み取れなかった投稿は、保存せずに知らせる。
3. **Given** 分類が付いた投稿、**When** 「解析」を開く、**Then** 分類ごとの件数と、閲覧・反応率・返信率の中央値が並ぶ。

---

### Edge Cases

- 確定した投稿が少ない：区切りごとに件数を出し、足りないものは傾向にしない。全体で足りなければ「あと何件」を出す。
- 時刻の偏り：いつも同じ時間帯にしか出していないと、ほかの時間帯は分からない。「試していない時間帯」と出す（調査 5.3 案A）。
- フォロワー数が急に増えた：伸びはフォロワー数の影響を受けるので、広がり（フォロワー数で割った値）も並べる。
- 計測できない投稿・遅れて確定した投稿：使わない（006と同じ）。
- 宣伝の投稿：宣伝の投稿とふだんの投稿は伸び方が違うので、分けて見られるようにする（宣伝内容を扱ったかは、投稿づくりの記録で分かる範囲）。
- 自動投稿のまとまりがOFF：反応数を取り込まないので、解析も出さない（019）。
- 多くの比べ方をすると、偶然の差が出る：傾向には、件数と差の大きさの決まりを満たしたものだけを出す（FR-030）。

## Requirements *(mandatory)*

### Functional Requirements

#### 解析の材料

- **FR-001**: System MUST 解析に、そのAccountの確定した投稿だけを使う（遅れて確定・計測できないは使わない）。期間は直近90日（`[ASSUMPTION]`）とし、画面で期間と件数を示す。
- **FR-002**: System MUST 投稿ごとに、時間帯（朝5〜10時・昼11〜15時・夕方16〜19時・夜20〜23時・深夜0〜4時）・曜日（平日・休日。祝日は休日）・文字数の区切り・本文の特徴・閲覧・反応率・返信率・広がり・初速・後からの伸びを求める。時刻は日本時間。
- **FR-003**: System MUST 解析をアプリの中の決まった計算で行い、アプリの中でAIを呼ばない（原則III）。

#### 時間帯・曜日・長さ（US1）

- **FR-010**: System MUST 時間帯・曜日・文字数・本文の特徴ごとに、件数と、閲覧・反応率・返信率の中央値を出す。平均は使わない。
- **FR-011**: System MUST 件数が足りない区切り（10件未満。`[ASSUMPTION]`）には「件数が少ない」と出し、傾向に使わない。投稿していない区切りは「試していない」と出す。

#### おすすめに乗った目安（US2）

- **FR-020**: System MUST 広がりがそのAccountの確定した投稿の中で上位20%（`[ASSUMPTION]`）かつ1を超える投稿を「おすすめに乗った目安」とし、広がりの大きい順に出す。
- **FR-021**: System MUST おすすめに乗った目安の投稿と、ほかの投稿の、初速・後からの伸び・返信率・本文の特徴の中央値を並べて出す。
- **FR-022**: System MUST 表示の順位・場所はThreadsから取れず、フォロワー数と閲覧から推し量っていることを、閉じたトグルの説明に出す。
- **FR-023**: System MUST 投稿時点のフォロワー数がない投稿は、広がりを求めず、おすすめに乗った目安の判定から外す。

#### 傾向

- **FR-030**: System MUST 比べた結果のうち、両側の件数が10件以上（`[ASSUMPTION]`）で、中央値の差が1.5倍以上（`[ASSUMPTION]`）のものだけを「傾向」として、短い文で出す。どの傾向にも件数を添える。
- **FR-031**: System MUST 傾向は相関で原因とは限らず、件数が少ないうちは偶然に振り回されることを、閉じたトグルの説明に出す（調査 5.5）。

#### 投稿づくりに活かす（US3）

- **FR-040**: System MUST 傾向を、投稿のプロンプトの「■伸びた傾向」の節に、件数つきの短い文で入れる（最大5つ。`[ASSUMPTION]`）。節は低調の投稿・却下ログの節のあとに置き、「傾向に合わせすぎず、人柄とCORE RULESを優先する」の一文を添える。
- **FR-040a**: Users MUST be able to 「解析」で、「プロンプトに入れる」を切り替える（初めは入れる）。
- **FR-040b**: System MUST 時間帯・曜日の傾向を、「自動投稿の時刻の見直しの参考に」として、今の投稿の時刻と並べて画面に出す。時刻は自動では変えない（原則II の考え方：投稿の設定はオーナーが決める）。
- **FR-041**: System MUST 人柄・CORE RULES・NGワードと食い違う傾向（NGワードを含む本文の特徴・強い対立の言葉など）を、活かす対象から外す（原則I）。
- **FR-042**: System MUST 傾向がないときは、プロンプトの文を今と同じにする。

#### 内容の分類（US4）

- **FR-050**: System MUST テーマ・書き出しの型の分類を、固定の一覧から選ぶ形で持つ（書き出しの型：あるある・問いかけ・言い切り・体験談・数字・告知・その他。テーマはAccountごとに10個まで、利用者が名前を決める。`[ASSUMPTION]`）。
- **FR-051**: Users MUST be able to 「内容を分類する」で、分類のプロンプト（分類の一覧と、分類が付いていない確定した投稿の本文と番号。1回に50件まで）をコピーし、外のAIの答えを貼って、投稿ごとの分類を反映する（018と同じ形）。アプリの中ではAIを呼ばない（原則III）。
- **FR-052**: System MUST 分類ごとに、FR-010 と同じ表を出す。分類の付いた投稿が少なければ「件数が少ない」と出す。
- **FR-053**: Users MUST be able to 投稿ごとの分類を、手で直す。

#### 画面と範囲

- **FR-060**: System MUST 「解析」を、機能のまとまり「自動投稿」の中（パフォーマンスの近く）に置く。自動投稿が使えない人には出さない（019）。
- **FR-061**: System MUST 解析を見られる人を、パフォーマンスと同じにする（オーナーと担当の人）。判定は今の判定の1か所を通す（原則V）。
- **FR-062**: System MUST そのAccountのデータだけで解析する。ほかのAccountと比べない（Constitution 原則V：アカウントをまたいだ比べはMVPの範囲外）。
- **FR-063**: System MUST スマートフォンの幅でも、横にスクロールせずに、すべての表と傾向に届くようにする。
- **FR-064**: System MUST 説明は閉じたトグルに箇条書きで置き、画面の文は短くする（docs/ui-design.md）。

### Key Entities *(include if feature involves data)*

- **投稿の解析の値**：確定した投稿ごとの、時間帯・曜日・文字数の区切り・本文の特徴・閲覧・反応率・返信率・広がり・初速・後からの伸び。006の記録から求める（新しく取る値はない想定）。
- **区切りの集計**：区切りごとの件数と中央値。
- **傾向**：比べた区切り・差・件数・短い文。
- **内容の分類**：投稿ごとのテーマ・書き出しの型。外のAIの答えを貼って付け、手でも直せる（FR-050〜FR-053）。
- **テーマの一覧**：Accountごとのテーマの名前（10個まで）。
- **傾向をプロンプトに入れるか**：Accountごとの切り替え（初めは入れる）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 確定した投稿が60件あるAccountで、「解析」を開くと、時間帯・曜日・文字数・おすすめに乗った目安が1画面で見られる。
- **SC-002**: 件数が10件未満の区切りから、傾向が1つも出ない。
- **SC-003**: 人柄・CORE RULES・NGワードと食い違う傾向が、投稿づくりに1つも入らない。
- **SC-004**: 傾向がないAccountで、プロンプトの文が本featureの前と1文字も変わらない。
- **SC-005**: 自動投稿が使えない人・関わりのない人に、解析の結果が1つも返らない。
- **SC-006**: 傾向を活かし始めてから4週間で、その傾向に合った投稿の閲覧の中央値が、合わない投稿より高いかを、利用者が画面で確かめられる。

## Assumptions

- 件数のしきい値（区切り10件・差1.5倍・上位20%・90日）は仮の値。テスト版のデータを見て直してよい。
- 投稿時点のフォロワー数・24時間時点の値は、006で記録している（FR-002c・FR-002b）。記録を始める前の投稿は、その値を使わない。
- 解析は、そのAccountの投稿だけ。学術的な研究の結果は、説明と「見る値」を選ぶ根拠に使い、そのまま傾向として出さない。
- 統計の検定（p値など）は出さず、件数と差の大きさの決まりで傾向を選ぶ。利用者に分かりやすくするため。

## Dependencies

- 006（反応数・取り込みの履歴・フォロワー数）、019（自動投稿のまとまり）、018（貼って反映する形）、003・014（投稿のプロンプト）。
- 原則VIは「低調の投稿と却下ログを必ず反映する」。本featureは、それに「伸びた傾向」を足すもので、原則に反しない（低調の投稿と却下ログの扱いは変えない）。
- 調査：[docs/threads-algorithm-research.md](../../docs/threads-algorithm-research.md) 5.7。
