# Feature Specification: このアカウントのチーム

**Feature Branch**: `feature/008-team-roster`（008の追加の修正として始めたため、ブランチ名は008のまま。PR #10）

**Created**: 2026-10-10

**Status**: Implemented

**Input**: 008の手動確認（2026-10-10）でのユーザーの要望。「このアカウントを手伝っている人」の一覧では、誰が誰の下で動いているか、自分がどこにいるかが分からない。オーナー → パートナー（チーム） → 担当の編集者を、実際の名前でつないで見せ、3つの役割とも自分の位置が分かるようにしたい。オーナー・編集者には、そのAccount以外の情報（パートナーが手伝う他の顧客など）は見せない。

**Source**: [008のspec](../008-team-operations/spec.md) FR-042・FR-048、[008 contracts/ui-routes.md](../008-team-operations/contracts/ui-routes.md)「このアカウントの設定」、[docs/team-roles.md](../../docs/team-roles.md)、[Constitution](../../.specify/memory/constitution.md) 3.0.0 原則V（個人運用のオーナーには役割・チームを見せない）。

## Clarifications

### Session 2026-10-10

- Q: カードに何を出すか？ → A: そのAccountのオーナー → パートナー（名前・チーム名） → 担当の編集者の名前を、上から順につなぐ。役割の名前と短い説明を各段に添える。
- Q: 誰が見られるか？ → A: オーナー・パートナー・編集者の全員（008 FR-042のまま）。見ている人の名前に「あなた」の印を付ける。
- Q: どこまで出すか？ → A: そのAccountの人だけ。パートナーが手伝っている他のAccount、そのAccountを担当していない編集者は出さない。
- Q: 008の「3つの役割と、できることを見る」の図との違いは？ → A: 図は役割の一般的な説明、カードはこのAccountの実際の人。両方を置く。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 自分のチームの並びと、自分の位置が分かる (Priority: P1)

パートナーが参加し、編集者が担当になったAccountで、オーナー・パートナー・編集者の誰が「このアカウントの設定」を開いても、カード「このアカウントのチーム」で、オーナー → パートナー → 編集者の並びと、自分がどこにいるかが分かる。

**Why this priority**: 008の役割の仕組みは他のアプリにあまりなく、一覧だけでは関係が分からないため（008 Clarifications 2026-10-10）。

**Independent Test**: 3人のブラウザで同じAccountの設定を開き、カードの3段と「あなた」の位置を確かめる（`pnpm e2e -- team`）。

**Acceptance Scenarios**:

1. **Given** パートナー（チーム名あり）と担当の編集者2人がいるAccount、**When** オーナーが設定を開く、**Then** カードに「オーナー（自分の名前・あなた）」→「パートナー（名前 · チーム名）」→「編集者（2人の名前）」が上から順に出る。
2. **Given** 同じAccount、**When** パートナーが開く、**Then** パートナーの段の名前に「あなた」が付く。任せる範囲のスイッチ・外す・招待は出ない。
3. **Given** 同じAccount、**When** 担当の編集者の1人が開く、**Then** 編集者の段の、その人の名前にだけ「あなた」が付く。
4. **Given** パートナーが同じチームで別のAccountも手伝い、そこに別の編集者が担当している、**When** このAccountのカードを見る、**Then** 別のAccountの編集者は出ない。
5. **Given** パートナー自身のAccount（パートナーがオーナー）を自社の編集者が担当している、**When** 開く、**Then** 「オーナー（あなた）」→「編集者」の2段で出る。
6. **Given** パートナーも編集者もいないAccount、**When** オーナーが開く、**Then** カードは出ない（招待の行だけ。個人運用の画面は変わらない）。

### Edge Cases

- 名前が長いときは1行に収め、はみ出しは省略する。
- 読み込みに失敗したときは、008と同じく区分を消さずに「再読み込み」を出す。
- 同じ名前の人がいても、印は利用者のIDで付ける（名前では判定しない）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST 008 FR-042を、カード「このアカウントのチーム」に置き換える。オーナー → パートナー（チーム名） → 担当の編集者を、名前と役割で上から順につないで示す。
- **FR-002**: System MUST 見ている人の名前に「あなた」の印を付ける。判定は利用者のIDで行う。
- **FR-003**: System MUST そのAccountの人だけを出す。パートナーが手伝う他のAccount・担当していない編集者は出さない。
- **FR-004**: System MUST パートナーがいないときはオーナー → 編集者、手伝う人がいないときはカードを出さない。
- **FR-005**: System MUST 見られる人と権限を008から変えない（`view`。オーナー・パートナー・編集者）。

### Key Entities

- 新しいデータは持たない。008の `memberships`・`account_partners`・`teams` から読む。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 3つの役割それぞれで、「あなた」の印がちょうど1人（自分）に付く（自動テストとE2Eで確認）。
- **SC-002**: 別のAccountだけを担当する編集者が、カードの応答に1件も含まれない（APIのテストで確認）。
- **SC-003**: 個人運用のオーナーの設定画面が変わらない（008 SC-005のテストがそのまま通る）。

## Assumptions

- 名前は008と同じ（表示名、なければメールアドレスの@の前）。
- 008のPRD・Constitutionの範囲内の画面の変更で、新しい役割・権限・データは足さない。
