# 調査と判断（Research）：パフォーマンス分析と改善フィードバック

**対象feature**：[spec.md](./spec.md) ／ **計画**：[plan.md](./plan.md)

specの「計画の段階で決めること」と、実装の方針を決める。各項目は「決定・理由・検討した代替案」で書く。001〜005のresearchの決定（DBの接続、定期処理の関所、Threads APIの呼び出しの作法など）は、そのまま使う。

## R1. 反応数とフォロワー数の読み方

- **決定**：
  - `ThreadsClient`に2つ足す。
    - `getMediaInsights(token, mediaId)`：6つの指標を1回の呼び出しで読む。応答の`data[]`から、`name`ごとに`values[0].value`（ない場合は`total_value.value`）を取る。返らなかった指標は`null`にする（spec エッジケース「一部の数を返さない」）。
    - `getFollowersCount(token, userId)`：`threads_insights?metric=followers_count`の`total_value.value`を取る。
  - トークンは、001・005と同じく`Authorization`ヘッダーで渡す。
  - エラーの分け方は005と同じ（認証・上限・一時的・それ以外）に、2つ足す。
    - **投稿が見つからない**（`ThreadsNotFoundError`）：HTTP 404、またはGraph APIのコード100でサブコード33（「その IDのオブジェクトがない」）。投稿を「計測できません」（理由`not_found`）にする（FR-004）。
    - **反応数を読む権限がない**（`ThreadsPermissionError`）：コード10・200番台（権限のエラー）。そのAccountの取り込みをその回は止め、Accountに「反応数を読む許可がない」の印を付けて画面で知らせる（R11）。
- **理由**：1回の呼び出しで6つ取れるので、1投稿・1時点のThreadsへの問い合わせは1回で済む。権限がないとき・投稿がないときの扱いを分けないと、1つのAccountの問題で毎回同じ呼び出しを繰り返してしまう。
- **要確認（実機）**：投稿を消したときの応答（コード100／サブコード33か、別のコードか）と、`views`の応答の形（`values`か`total_value`か）は、テスターのアカウントで確かめる（quickstart.md 手順6）。偽のThreadsサーバーは、上の形で返す。
- **検討した代替案**：指標ごとに別に読む → 問い合わせが6倍になるので不採用。

## R2. どこで取り込むか（自動投稿の処理への相乗り）

- **決定**：
  - 取り込みは、005の`runAutoPost`の最後に「**反応数の段階**」として足す。日次のCron（`0 18 * * *`）の処理には入れない。
  - 反応数の段階は、次の3つを、この順で、使える回数（R3）の範囲で行う。
    1. **時点の取り込み**（FR-002d）：投稿からの経過が23〜25時間・71〜73時間・167〜169時間で、その時点の値をまだ取っていない投稿（`method: slot`）。
    2. **補い**（FR-002）：その日の補いがまだで、日本時間の3:00を過ぎていれば行う。過ぎた時点（経過がその時点＋1時間を過ぎた）を取りそこねている投稿について、過ぎた時点のうち最も新しい1つだけを取る（`method: daily`）。経過が192時間を過ぎて確定していない投稿は「遅れて確定」として1回取る。投稿IDのない投稿は「計測できません」にする（Threadsには問い合わせない）。
    3. **フォロワー数の記録**（FR-002c）：その日の記録がないAccountのフォロワー数を読む。
  - 3:00の補いを始めるため、関所の次の時刻の候補に「次の日本時間3:00」を足す。補いが終わったら、KVの`metrics:catchup`に日付（日本時間）を書き、その日はもう行わない。
  - 1回で終わらなかったとき（使える回数を使い切った）は、関所を「すぐ」にして、次の回（5分後）に続ける。3:00ごろはDBがすでに起きているので、Neonの計算時間はほぼ増えない。
- **理由**：
  - 時点の取り込みは、自動投稿の時刻に合わせるのがいちばん正確で、追加のDBの起動もない（Clarifications /speckit-clarify）。
  - 補いは件数が読めない（本featureを入れた直後は、それまでの投稿をすべて補う）。1回50件の上限の中で分けて進めるには、関所で続きを起こせる`runAutoPost`の仕組みがそのまま使える。日次のCronは1日1回しか動かないので、続きを起こせない。
- **検討した代替案**：
  - 日次のCronで補う → 1回で終わらない分を翌日に持ち越すことになり、本featureを入れた直後の補いに何日もかかる。不採用。
  - 別の5分ごとのCronを足す → Cron Triggerの数が増え、関所の仕組みを2つ持つことになる。不採用。

## R3. 1回の処理で使える回数（サブリクエストの割り当て）

- **決定**：
  - 反応数の段階で使える外部への呼び出しを、その回の公開の数から決める。
    - `METRICS_MAX_CALLS_PER_TICK = 24`（公開が0件の回）
    - 公開を1件進めるごとに8を引く（公開4件の回は0件になり、反応数の段階を次の回に回す）
  - 反応数の段階のDBの読み書きを、まとめて行う。
    - 対象の読み込みは1回のクエリ（下書き・反応数の記録・Account・トークン・grower機能の判定の材料を結合する）。
    - 書き込みは、段階の最後に`db.batch`で1回にまとめる（取り込みの履歴の追加、反応数の記録の更新、判定、フォロワー数の記録）。
    - したがって、使う回数は「Threadsへの呼び出しの数＋DB 3回程度」になる。
  - トークンの復号は、Accountごとに1回だけ行う（同じAccountの投稿が続くとき）。
- **理由**：005の1回の処理は、公開4件で約32回、ほかのDBの読み書きで約8回を使う。残りの枠で反応数を進め、上限を超えないようにする。
- **確かめ方**：テストで`fetch`の呼び出し回数を数え、1回の処理が50回を超えないことを確かめる（quickstart.md 手順3）。超えそうになったら`METRICS_MAX_CALLS_PER_TICK`を下げる。
- **規模の目安**：1Accountで1日10件投稿すると、時点の取り込みは1日30回（1つの時刻の処理あたり3回）。1つの時刻に同じ時刻のAccountが8つ重なっても24回で収まる。それを超える分は、時点の幅（±1時間）の中で次の回に回し、幅を過ぎた分は3:00の補いで取る（ログ`metrics: deferred`で気づける。Workers Paidに移すと上限が1,000回になる）。

## R4. 時点・状態・確定のルール

- **決定**：
  - 時点は`h24`（24時間）・`d3`（72時間）・`d7`（168時間）の3つ。取り込みの履歴の`kind`には、ほかに`late`（遅れて確定）を持つ。
  - 時点の取り込みの幅は、その時点の±1時間（23〜25時間など）。
  - 補いの対象：経過がその時点＋1時間を過ぎ、その時点もそれより後の時点も取っていない。過ぎた時点のうち最も新しい1つだけを取る（例：24時間と3日を取りそこね、経過が80時間なら、3日の値として取る）。
  - 状態（`post_metrics.state`）：
    - 行がない：確定待ち（まだ一度も取っていない）
    - `updating`：更新中（`h24`か`d3`まで取った）
    - `confirmed`：`d7`を取った（時点の取り込みでも補いでも）で、経過が192時間以内
    - `late_confirmed`：経過が192時間を過ぎてから、はじめて確定の値を取った（`kind: late`）
    - `unmeasurable`：計測できません（理由`no_media_id`か`not_found`）
  - 補いで`d7`を取るとき、経過が192時間を過ぎていれば`late`として扱う（SC-008の「確定は167〜192時間」を守る）。
- **理由**：specのFR-002・FR-002a・FR-002dと、Clarifications（3つの時点）をそのまま形にした。

## R5. 判定と基準値

- **決定**：
  - 基準値：そのAccountの`state = confirmed`で`views`のある投稿のうち、投稿した日時が新しい30件の`views`の中央値（Postgresの`percentile_cont(0.5)`）。
  - 判定は確定したときに1回だけ行い、`judgment`・`judgment_ratio`・`judgment_baseline`・`judged_at`を保存する。以後変えない（FR-010・FR-024）。
  - 反応数の段階の書き込みの最後に、確定した投稿があったAccountごとに、1つのSQLで「判定がまだで、確定していて、`views`がある投稿」をまとめて判定する。基準値に使える投稿が5件未満、または基準値が0なら判定しない（その投稿は、5件たまった後の確定のときに一緒に判定される。FR-010）。
  - 倍率の比べ方：`ratio >= 2.0`で好調、`ratio <= 0.5`で低調。丸める前の値で比べ、表示は小数第1位。
  - 画面に出す基準値は、読むたびに同じSQLで求める（保存しない）。
- **理由**：判定を保存すると、画面とプロンプトが同じ結果を使え、基準値が後から変わっても判定がぶれない。基準値は1つのSQLで求まるので、保存して整合を取る手間をかけない。
- **検討した代替案**：画面を開くたびに全投稿を判定し直す → 判定が日によって変わり、FR-010に反する。不採用。

## R6. 画面のデータと、件数・ページ

- **決定**：
  - `GET /accounts/:accountId/performance`で、まとめて返す：基準値、基準値に使える件数、最終取り込み日時、タブごとの件数、権限の印、選んだタブの投稿の1ページ（50件）、続きのカーソル、次のプロンプトに入る低調の投稿のID（最大5件）。
  - 並びとカーソルは、005の投稿済みの一覧と同じ（`published_at`の新しい順、同じなら`id`。カーソルは`(publishedAt, id)`）。
  - タブの件数は、1つの集計のクエリ（`count(*) FILTER (WHERE …)`）で求める。
  - 「確定待ち」は、行がない投稿と`updating`の投稿。「計測できません」は「すべて」だけに出す。
- **理由**：画面の最初の表示を1回のAPIで済ませる（SC-007の2秒）。Neonの通信量を抑えるため、本文以外の大きな列は返さない。

## R7. CSVの作り方

- **決定**：
  - CSVは**ブラウザで作る**。APIは`GET /accounts/:accountId/performance/export?kind=posts|snapshots&before=…`で、行のデータをJSONで200件ずつ返し、Webが続きを読みながら1つのCSVにまとめて保存させる。
  - 形式：UTF-8で先頭にBOM（Excelで文字化けしないため）、改行はCRLF、値はすべて`"`で囲み、`"`は`""`にする（RFC 4180）。日時は`2026-09-25T19:01:00+09:00`の形。
  - ファイル名：`threads-{username}-posts-{YYYYMMDD}.csv`・`threads-{username}-snapshots-{YYYYMMDD}.csv`（日本時間の書き出した日付）。
- **理由**：数千行の文字列をWorkerで組み立てると、CPU時間の10msを超えるおそれがある。ブラウザなら制限がなく、ページに分けて読めば1回の応答も小さい。
- **検討した代替案**：Workerでストリームで返す → CPU時間の制限と、途中で失敗したときの扱いが難しい。不採用。

## R8. プロンプトへの反映

- **決定**：
  - `buildPrompt`（`packages/shared/src/prompt.ts`）の入力に`poorPosts: { body: string; memo: string | null }[]`を足し、「■過去に却下された投稿」の節の直後に「■反応が低かった投稿」の節を出す。空なら節ごと省く（FR-025〜FR-027）。
  - 材料は`prompt-service`で読む：`judgment = poor`かつ`include_in_prompt = true`かつ`state`が`confirmed`か`late_confirmed`の投稿を、`published_at`の新しい順に5件。
  - grower機能を使えないAccountではプロンプト自体を作らない（003 FR-024）ので、追加の判定は要らない。
- **文面**は[contracts/prompt-template.md](./contracts/prompt-template.md)。

## R9. 分析のための記録（FR-002e〜FR-002g）

- **決定**：
  - **本文の編集**：`post_drafts`に`body_edit_tracked`（boolean）と`body_edited_at`を足す。マイグレーションで既存の行は`false`（不明）、以後の行は既定で`true`。`updateDraft`で本文が変わったときに`body_edited_at`を入れる。
  - **公開の時点の情報**：`post_drafts`に`published_slot_minute`・`published_carryover`・`published_prioritized`を足し、005の公開の成功の記録（`publish-executor`の成功のコミット）で一緒に入れる。`publish_attempts`は保存期間を過ぎると消える（005）ので、下書きに写しておく。承認した日時は既存の`reviewed_at`を使う。
  - **プロンプトの材料の版**：`accounts`に`promotions_changed_at`・`research_changed_at`・`core_rules_changed_at`を足し、宣伝内容・リサーチ（参考の投稿とキーワード）・投稿ルールを追加・変更・削除するサービスで今の時刻を入れる。課題は`strategy_designs.updated_at`を使う。下書きのバッチを登録するとき（`createDraftBatch`）に、4つを`draft_batches`に写す。マイグレーションで、既存のAccountには各表の`max(updated_at)`を入れる。
- **理由**：
  - 削除は`updated_at`に残らないので、各表の`max(updated_at)`では「材料が変わった」を取りこぼす。Accountに変更の日時を持てば、削除も含めて分かる。
  - 公開の時点の情報は、あとから`publish_attempts`を見ても残っていない。
- **検討した代替案**：材料の中身のハッシュを保存する → 「いつ変えたか」が分からず、分析で時期と結びつけにくい。不採用。

## R10. 計測できない投稿

- **決定**：
  - 投稿IDのない投稿済み：補いの段階で見つけたら、Threadsに問い合わせずに`post_metrics`の行を`unmeasurable`（`no_media_id`）で作る。
  - 投稿が見つからない（R1）：`unmeasurable`（`not_found`）にする。それまでの取り込みの履歴は残す（spec エッジケース）。
  - 判定・基準値・プロンプトの対象から外し、以後は取り込まない。

## R11. 取り込めないAccount・権限

- **決定**：
  - 対象のAccount：接続が`connected`で、grower機能を使える（`hasGrowerAccess`。契約の判定は課金のfeatureで置き換える）Account。要再接続・使えないAccountは飛ばす（FR-005）。
  - 認証のエラー（`ThreadsAuthError`）：005と同じく、接続の世代番号を条件にAccountを要再接続にする。
  - 権限のエラー（`ThreadsPermissionError`）：`accounts.insights_denied_at`に今の時刻を入れ、そのAccountをその日は飛ばす。パフォーマンスの画面の上に「反応数を読む許可がありません。再接続して、インサイトの許可をオンにしてください」と出す。再接続（001の`writeConnection`）で消す。
  - 上限のエラー（`ThreadsRateLimitError`）：その回の反応数の段階を止め、次の回に回す。
  - 一時的な失敗：その投稿を飛ばす（時点の幅の中なら次の回、過ぎたら3:00の補い）。
- **理由**：1つのAccountの問題で、ほかのAccountの取り込みを止めない。権限がないときに毎回呼び出し続けない。
- **specへの反映**：権限がない場合の表示を、spec のエッジケースに足した。

## R12. 費用と規模の見積もり

- **Neonの計算時間**：時点の取り込みは、もともとDBが起きている時刻の処理の中で行う。補いは3:00の回（日次の処理でDBが起きる時刻）に行う。増える起動はほぼない。
- **Neonの通信量**：1投稿あたり履歴3行（各100バイト程度）。画面は50件ずつ。増える量はわずか。
- **KV**：`metrics:catchup`の書き込みが1日1回。
- **Threads API**：1投稿あたり最大3回（遅れて確定は1回）と、Accountごとに1日1回のフォロワー数。Threadsの呼び出しの上限に当たったときは、その回を止めて次に回す（R11）。
- **保存の量**：1Accountで1日10件・1年なら、履歴は約1万行。Neonの保存（無料枠0.5GB）に対して小さい。
