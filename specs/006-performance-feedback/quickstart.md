# 動作確認ガイド（Quickstart）：パフォーマンス分析と改善フィードバック

**対象feature**：[spec.md](./spec.md) ／ **契約**：[contracts/api.md](./contracts/api.md)、[contracts/metrics-job.md](./contracts/metrics-job.md)、[contracts/ui-routes.md](./contracts/ui-routes.md)、[contracts/prompt-template.md](./contracts/prompt-template.md)、[contracts/csv.md](./contracts/csv.md)

本featureが端から端まで動くことを確かめる手順。実装コードは含めない。

## 前提

- 005までのセットアップ（[005 quickstart.md](../005-auto-post/quickstart.md)）が済んでいる。
- ふだんの確認は、偽のThreadsサーバー（`pnpm dev:fake`）で行う。偽のサーバーは、投稿ごとの反応数・フォロワー数を返し、投稿の削除・権限のエラー・上限・5xxをテストから設定できる（[contracts/api.md](./contracts/api.md)の最後）。
- 反応数の段階は、005の定期処理（5分ごと）の中で動く。`wrangler dev`では、005と同じURLで1回ずつ呼ぶ。

## セットアップ

```bash
pnpm install
docker compose up -d
pnpm --filter api db:migrate        # 0008_performance.sql（反応数の記録・取り込みの履歴・フォロワー数・下書きとバッチとAccountの列）
pnpm dev:fake
```

定期処理を1回動かす：

```bash
curl "http://localhost:8787/cdn-cgi/local/scheduled?cron=*/5+*+*+*+*"
```

経過時間の条件（24時間など）を満たすデータは、テスト用のシードで、投稿した日時を過去にずらした投稿済みの下書きを作って用意する（`pnpm --filter api seed:performance`。tasks.md T002）。

## 自動テスト

```bash
pnpm test                                   # すべて
pnpm --filter shared test                   # 判定・基準値・CSVの整形・プロンプトの節
pnpm --filter api test -- metrics           # 反応数の段階（時点・補い・確定・判定・失敗・回数の上限）
pnpm --filter api test -- performance       # API（画面・メモ・書き出し・grower機能・owner）
pnpm --filter web test -- performance       # 画面（タブ・アイコン・メモの保存・CSV）
```

自動テストで必ず確かめること：

| 確かめること | 根拠 |
|---|---|
| 境界値（倍率2.0・0.5、確定4件・5件、基準値0、遅れて確定）で判定と基準値がルールどおり | SC-002 |
| 外していない低調の新しい5件がプロンプトに入り、外した投稿・好調・普通・確定待ちが入らない。長さの調整で減らない | SC-003、FR-025〜FR-027 |
| 投稿ごとのCSVの行数が投稿済みの件数と、取り込みごとのCSVの行数が履歴の件数と一致する。日本語・改行・カンマ・引用符が崩れない | SC-005 |
| 確定の値の経過時間が167〜192時間に入る（補いで192時間を過ぎたら遅れて確定） | SC-008 |
| 時刻の処理で24時間・3日・7日の値が±1時間で取れる | SC-009、FR-002d |
| 1回の定期処理の外部への呼び出し（Neon・Threads）が50回を超えない（偽の`fetch`で数える） | research.md R3 |
| 投稿が見つからない → 計測できません、権限がない → Accountに印、上限 → その回を止める、認証 → 要再接続 | research.md R11 |
| grower機能を使えないAccountで403、他人のAccountで404 | FR-031・FR-032 |

## 手動の確認

### 1. 取り込みと確定待ち（US1）

1. 投稿済みの下書きを、投稿した日時が「今から1時間前」「24時間前」「72時間前」「168時間前」「10日前」の5件、シードで作る。
2. 定期処理を1回動かす（補いが動くよう、日本時間の3:00を過ぎた扱いにするか、KVの`metrics:catchup`を消す）。
3. **期待**：パフォーマンスの画面で、
   - 1時間前の投稿は「確定待ち」で「反応数は {M/D H:MM} ごろに取り込みます」
   - 24時間前・72時間前の投稿は「確定待ち」で暫定の値と「{M/D}ごろ値が確定して判定します」
   - 168時間前の投稿は確定（判定は5件たまるまで出ない）
   - 10日前の投稿は「投稿から10日後に取り込んだ値です」

### 2. 判定と基準値（US1）

1. 確定した投稿を5件以上（閲覧数 167・23・99・260・30・64 など）シードで作り、定期処理を動かす。
2. **期待**：基準値の欄に中央値が出る。各カードに右上がり（オレンジ）・右下がり（青）・横向き（グレー）の矢印と「×3.4」などが出る。アイコンにマウスを乗せると「伸びた（基準値の3.4倍）」と出る。タブの件数が合う。
3. 確定した投稿が3件だけのAccountでは、「確定した投稿が5件たまると判定を始めます（いま3件）」と出て、アイコンは出ない。

### 3. 改善フィードバックとプロンプト（US2）

1. 低調の投稿が6件あるAccountで、低調のタブを開き、1件にメモを書いて入力欄から離れる。別の1件の「プロンプトに入れる」を外す。
2. **期待**：保存ボタンなしで保存される。外した投稿には「外しています。以降のプロンプトには入りません」、繰り上がった投稿に「次のプロンプトに入ります」。
3. 投稿ストックでプロンプトを作り直す。
4. **期待**：却下の節の後ろに「■反応が低かった投稿」があり、外していない新しい5件が入り、メモを書いた投稿に「(傾向メモ: …)」が付く。プロンプトのカードの材料に「反応が低かった投稿 5件」。

### 4. CSV（US3）

1. 「CSVで書き出す」→「投稿ごと」と「取り込みごと」をそれぞれ保存する。
2. **期待**：Excel・Googleスプレッドシート・Numbersで開いて文字化けしない。本文の改行が1つのセルに入る。列は[contracts/csv.md](./contracts/csv.md)のとおり。投稿ごとの行数＝投稿済みの件数、取り込みごとの行数＝履歴の件数。

### 5. 計測できない・権限・要再接続

1. 偽のThreadsで、1件の投稿を「削除済み」に、別のAccountを「権限なし」にして定期処理を動かす。
2. **期待**：削除した投稿は「計測できません」で、判定・基準値・プロンプトから外れる。権限なしのAccountでは画面の上に「反応数を読む許可がありません…」と「再接続」が出る。

### 6. 本物のThreadsでの確認（1回だけ）

テスター招待したアカウントで、自動投稿した投稿について：
1. 24時間後の時刻の処理で反応数が入り、Threadsのアプリのインサイトの数とおおむね一致する。
2. テスト用の投稿を1件Threadsで削除し、次の取り込みで「計測できません」になることを確かめる。**このときのエラーの応答（コード・サブコード）を記録し、`ThreadsNotFoundError`の判定と合っているか確かめる**（research.md R1 の要確認）。
3. `views`の応答の形（`values`か`total_value`か）を記録する。

### 7. 費用と制限の確認（デプロイの後。その後は週に1回）

005の手順7に加えて、次を見る。
- Workersのログの`metrics: deferred`（出ていれば、同じ時刻に重なる投稿が多い。research.md R3）
- `metrics: run`の数と、Neonの計算時間・通信量に大きな変化がないこと

### 8. 表示の速さ（SC-007）

1. `pnpm --filter api seed:performance`で投稿済み500件のAccountを作る。
2. パフォーマンスの画面を開き、ブラウザの開発者ツールで最初の表示までの時間を測る。
3. **期待**：2秒以内。

### 9. 画面幅

PC（1280px）・タブレット（768px）・スマートフォン（390px）で、タブが横にはみ出さず（スマートフォンは横にスクロール）、反応数が3列×2行に並ぶ。ライト・ダークの両方で、矢印の色と向きで判定を見分けられる。
